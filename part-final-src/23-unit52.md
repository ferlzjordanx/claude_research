### 2. Prerequisite Knowledge

Units 47–48 (system and agent design), the curriculum's LLM/RAG/agent units, and Unit 53 in progress (you should have something real to talk about). Familiarity with at least one model provider's API (messages, tool use, structured output, streaming, token counting, prompt caching).

**What an FDE is.** A Forward Deployed Engineer embeds with customers to turn a platform's capabilities into working solutions: part software engineer, part solutions architect, part product discovery. Interviews test technical depth *and* the ability to navigate ambiguity, communicate trade-offs, and ship under real constraints (data access, security reviews, stakeholder politics).

### 3. Mental Model

```
Stakeholder ask (vague, outcome-oriented)
   ↓ discovery: who, what, why, current process, data, constraints, success metric
Testable requirements (inputs, outputs, accuracy targets, latency, cost, risk tier)
   ↓ design: deterministic core + probabilistic components with validation
Prototype on real (or representative) data
   ↓ evaluation: dataset, metrics, baseline (human or current process)
Evidence (numbers, traces, examples, failure analysis)
   ↓ decision: ship / iterate / don't use AI
Production: guardrails, observability, cost controls, human approval, rollback
```

**The evidence principle.** In AI interviews, claims without measurement are weak. "The agent works well" → weak. "On a 200-case eval set built from last quarter's tickets, task success rose from 71% to 86% after switching to hybrid retrieval; median cost is $0.04 per task; the remaining failures are mostly missing documents" → strong.

### 4. Comprehensive Theory

#### 4.1 LLM vs Augmented LLM vs Agent (and the rest of the taxonomy)

- **LLM:** next-token predictor exposed through an API; stateless between calls; knowledge frozen at training; can be wrong confidently.
- **Augmented LLM:** an LLM given retrieval, tools and memory — the building block of most applications.
- **RAG:** retrieval from a corpus injected into the prompt to ground answers in current, permissioned, citable sources.
- **Embeddings:** dense vectors representing meaning; used for semantic retrieval, clustering, dedup, classification features. Similarity ≠ relevance; domain vocabulary and exact identifiers often need lexical search (hybrid).
- **Tools:** functions the model can request; the application executes them. Tool design quality strongly influences agent quality.
- **Workflow:** code-defined orchestration of LLM calls and tools (chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer).
- **Agent:** model-driven loop selecting actions until a goal or limit; bounded by code.
- **MCP:** protocol to expose tools/resources/prompts to AI applications in a standard way (JSON-RPC; stdio and Streamable HTTP transports; OAuth-based authorization for HTTP). **[Version-dependent]** The 2026-07-28 revision made the core stateless, simplifying horizontal scaling of remote MCP servers.
- **Multi-agent system:** multiple agents with separate contexts/tools coordinated via an orchestrator or handoffs; justified by context isolation, permission separation or parallelism.

#### 4.2 RAG and Embeddings — Interview Depth

You must be able to explain each stage (ingestion, chunking, embedding, indexing, query transformation, retrieval, reranking, context construction, generation, citation, evaluation) and the knobs at each:

| Stage | Key decisions | Typical failure |
|---|---|---|
| Ingestion | Connectors, incremental sync, ACL capture, deletes | Stale or missing docs; leaked ACLs |
| Chunking | Structure-aware; size; overlap; parent-child | Answers split across chunks; tables broken |
| Embedding | Model choice, dimensionality, multilingual, versioning | Query/index model mismatch after upgrade |
| Indexing | HNSW params (`m`, `ef_construction`), filters | Low recall with restrictive filters |
| Query transform | Rewrite, decomposition, HyDE | Rewrites drift from user intent |
| Retrieval | Hybrid dense+BM25; k; filters | Exact IDs/acronyms missed by dense-only |
| Reranking | Cross-encoder top-50→top-8 | Latency/cost; reranker domain mismatch |
| Context | Ordering, dedup, budget, delimiting | "Lost in the middle"; injection via docs |
| Generation | Instructions, structured output, abstention | Unsupported claims; ignoring context |
| Citation | IDs, quotes, validation | Fabricated or misattributed citations |
| Evaluation | Retrieval vs generation metrics | One blended score hides cause |

#### 4.3 Tools, Workflows, Agents, MCP, Multi-Agent — When and Why

**Why agent?** Use an agent when:
- the sequence of steps can't be known in advance (investigations, research, troubleshooting),
- tool choice depends on intermediate results,
- the task benefits from iterative refinement against feedback (tests, validators),
- and you can bound it (tools, budget, approvals) and evaluate it.

**Why not agent?** Avoid when:
- the process is known and stable (use a workflow — cheaper, faster, testable),
- errors are costly and hard to detect (regulated decisions),
- latency budgets are tight (agents add round-trips),
- there's no way to evaluate success,
- a deterministic program or a single LLM call solves it.

#### 4.4 Guardrails, Evals, Observability, Security and Human Approval

**Guardrails** are layered controls around the model:
- *Input:* authentication, rate limits, size limits, PII detection/redaction, prompt-injection heuristics (as signals, not as security boundaries), topic routing.
- *Execution:* tool allow-lists per principal, argument validation, policy engine, approvals, budgets, sandboxing, egress allow-lists.
- *Output:* schema validation, citation validation, PII/secret scanning, toxicity/policy classifiers, safe rendering (escape HTML, block remote images/links in untrusted output), confidence/abstention rules.

**Evals** (offline and online), per Unit 48: component, step, trajectory, outcome, safety; calibrated LLM judges; human labels; regression gating; cost and latency as first-class metrics.

**Observability:** traces spanning model calls, tools, retrievals and services; tokens and cost; prompt/model/agent version attributes; sampled payload capture with access controls; dashboards by version.

**Security:** deterministic authZ, delegated credentials, OWASP LLM Top 10 mapping, supply-chain hygiene for models/MCP servers, data residency and retention, audit logs.

**Human approval:** specific, informed, argument-bound, role-authorized, expiring, audited; measure approval/rejection rates to detect rubber-stamping or overly conservative agents.

#### 4.5 Stakeholder Requirement Clarification

**Discovery question bank (use in interviews and on the job):**

| Dimension | Questions |
|---|---|
| Outcome | What decision or task improves? How is it measured today? What does success look like in 90 days? |
| Users | Who uses it? How often? What's their expertise? What do they do when it's wrong? |
| Current process | Walk me through the last time this was done. Where does time go? Which steps require judgment? |
| Data | Where does the information live? Who owns it? Access constraints? Quality? Freshness? Volume? |
| Authority | What's the source of truth? Which systems are authoritative for which facts? |
| Risk | What's the worst plausible error? Who is accountable? Regulatory constraints? Irreversible actions? |
| Constraints | Latency, cost per task, deployment environment (cloud, VPC, on-prem), data residency, model restrictions |
| Integration | Which systems must it read/write? Identity provider? Existing workflows/tools? |
| Evaluation | Do we have historical examples with known outcomes? Who can label? What accuracy is acceptable vs today's baseline? |
| Rollout | Pilot group? Shadow mode? Kill switch? Training? |

**From vague ask to testable requirement — example.**
- Ask: "Make our analysts faster with AI."
- After discovery: Analysts spend ~40% of time locating clauses across contracts in a document management system with folder-level ACLs.
- Requirement: "Given a natural-language question about a contract set the analyst can access, return relevant clauses with document/page citations. Acceptance: on a 150-question labeled set, recall@10 ≥ 0.9 for relevant clauses; answer faithfulness ≥ 0.95 (human-graded sample of 50); zero results from inaccessible documents in a 500-query permission test; p95 latency < 5 s; cost < $0.05/query. Pilot: 10 analysts, 2 weeks, measure time-to-answer vs baseline."

#### 4.6 Deterministic/Probabilistic Boundaries

**Rule of thumb:** Probabilistic components *propose, extract, rank, summarize and draft*; deterministic components *authorize, decide (when rules exist), compute, commit and audit*.

| Task component | Boundary |
|---|---|
| Who can access what | Deterministic |
| Money movement, account changes, permissions | Deterministic execution after approved proposal |
| Calculations (totals, dates, tax) | Deterministic (tools), never the model's arithmetic |
| Extracting fields from documents | Probabilistic + schema validation + confidence thresholds + human review for low confidence |
| Classifying intent | Probabilistic with measured accuracy; deterministic routing on the result |
| Drafting text | Probabilistic; human or rules review proportional to risk |
| Final regulated decisions | Deterministic rules or accountable humans |

### 5. Internal Mechanics — What Interviewers Expect You to Know Under the Hood

**Tool calling round trip.**
```
Request: system + messages + tool definitions (JSON Schema) → model
Response: stop_reason = tool_use; content = [text?, tool_use{id, name, input}]
App: validate input → authorize → execute → tool_result{tool_use_id, content, is_error?}
Request: previous messages + assistant tool_use + user tool_result → model
... until stop_reason = end_turn (or max_tokens / refusal / your limits)
```

**Structured output.** Providers offer JSON-schema-constrained output modes (constrained decoding or strict tool schemas). Still validate with Pydantic — schemas guarantee shape, not truth.

**Embedding search.** Query embedding → ANN index (HNSW graph traversal with `ef_search` candidates) → filtered candidates → distance ranking. Filtering after ANN can drop recall; pgvector ≥ 0.8 iterative scans mitigate.

**Tokens and cost.** Cost = input tokens × input price + output tokens × output price (+ cache write/read prices where prompt caching applies). Agent cost grows with turns because context is resent; prompt caching reduces repeated-prefix cost.

**Why models loop.** Ambiguous tool results, no explicit failure signals, no memory of attempted actions, overly broad goals, no stopping guidance — mitigated by tool design, loop detection and hard limits.

### 6. Implementation Examples

#### Example 1 — Minimal: "Why agent / why not agent" decision helper (for interviews and design reviews)

```python
from dataclasses import dataclass
from enum import StrEnum


class Recommendation(StrEnum):
    DETERMINISTIC = "deterministic code"
    SINGLE_CALL = "single LLM call (+ validation)"
    RAG = "RAG with citations"
    WORKFLOW = "LLM workflow"
    AGENT = "bounded agent"


@dataclass(frozen=True)
class TaskProfile:
    rules_fully_specifiable: bool
    unstructured_input: bool
    needs_private_knowledge: bool
    steps_known_in_advance: bool
    can_evaluate: bool
    irreversible_actions: bool


def recommend(p: TaskProfile) -> tuple[Recommendation, list[str]]:
    notes: list[str] = []
    if p.rules_fully_specifiable and not p.unstructured_input:
        return Recommendation.DETERMINISTIC, ["No model needed."]
    if not p.can_evaluate:
        notes.append("Build an evaluation set before choosing autonomy.")
    if p.irreversible_actions:
        notes.append("Irreversible actions: deterministic execution behind approval.")
    if p.steps_known_in_advance:
        rec = Recommendation.RAG if p.needs_private_knowledge else Recommendation.WORKFLOW
        return rec, notes
    if not p.can_evaluate:
        return Recommendation.WORKFLOW, notes + ["Unbounded autonomy without evals is not defensible."]
    return Recommendation.AGENT, notes + ["Bound turns, time, cost; least-privilege tools."]
```

This is deliberately simple — the point is to make your reasoning explicit and repeatable in interviews.

#### Example 2 — Realistic: RAG evaluation harness separating retrieval and generation

```python
# evals/rag_eval.py
import json
import statistics
from dataclasses import dataclass
from pathlib import Path

from pydantic import BaseModel


class Case(BaseModel):
    id: str
    question: str
    principal: dict
    gold_chunk_ids: list[str]          # empty → unanswerable case
    reference_answer: str | None = None


@dataclass
class CaseResult:
    id: str
    recall_at_k: float
    reciprocal_rank: float
    answered: bool
    should_abstain: bool
    citations_valid: bool
    faithfulness: float | None         # from calibrated judge or human label


def recall_at_k(retrieved: list[str], gold: list[str], k: int) -> float:
    if not gold:
        return 1.0
    return len(set(retrieved[:k]) & set(gold)) / len(gold)


def reciprocal_rank(retrieved: list[str], gold: list[str]) -> float:
    for rank, cid in enumerate(retrieved, start=1):
        if cid in gold:
            return 1.0 / rank
    return 0.0


async def run_case(case: Case, retriever, answerer, judge, k: int = 8) -> CaseResult:
    retrieved = await retriever.search_ids(case.question, case.principal, k=50)
    answer = await answerer.answer(case.question, case.principal)
    cited = {c.chunk_id for c in answer.citations}
    faith = None
    if not answer.insufficient_evidence:
        faith = await judge.faithfulness(answer=answer.answer, context_ids=list(cited))
    return CaseResult(
        id=case.id,
        recall_at_k=recall_at_k(retrieved, case.gold_chunk_ids, k),
        reciprocal_rank=reciprocal_rank(retrieved, case.gold_chunk_ids),
        answered=not answer.insufficient_evidence,
        should_abstain=not case.gold_chunk_ids,
        citations_valid=cited <= set(retrieved),
        faithfulness=faith,
    )


def summarize(results: list[CaseResult]) -> dict:
    answerable = [r for r in results if not r.should_abstain]
    unanswerable = [r for r in results if r.should_abstain]
    faith = [r.faithfulness for r in results if r.faithfulness is not None]
    return {
        "retrieval.recall@8": statistics.mean(r.recall_at_k for r in answerable),
        "retrieval.mrr": statistics.mean(r.reciprocal_rank for r in answerable),
        "generation.faithfulness_mean": statistics.mean(faith) if faith else None,
        "generation.citation_validity": statistics.mean(r.citations_valid for r in results),
        "abstention.correct_rate": (statistics.mean(not r.answered for r in unanswerable)
                                    if unanswerable else None),
        "abstention.false_abstain_rate": statistics.mean(not r.answered for r in answerable),
        "n": len(results),
    }
```

Interview talking point: this report lets you say *where* failures come from — "recall@8 is 0.93, so retrieval is mostly fine; faithfulness is 0.88 and the failures cluster in multi-document comparisons, so we're working on context construction and prompting."

### 7. Comparative Analysis

| Comparison | Key difference | Interview trap |
|---|---|---|
| LLM vs augmented LLM vs agent | Single call vs equipped call vs autonomous loop | Calling every chatbot an "agent" |
| RAG vs fine-tuning | Knowledge injection at runtime vs behavior change | Fine-tuning to teach facts that change weekly |
| RAG vs tool calling | Derived text vs live system-of-record data | RAG for account balances |
| Workflow vs agent | Fixed vs model-chosen path | Agent for fixed process |
| MCP vs direct function calling | Interop protocol vs in-app definitions | "MCP secures tools" |
| Guardrail classifiers vs deterministic controls | Probabilistic screening vs enforcement | Relying on an injection classifier as the security boundary |
| Observability vs evaluation | What happened vs was it good | Dashboards without quality metrics |
| Offline vs online evaluation | Controlled regression vs real-world behavior | Shipping on offline evals alone |
| Human approval vs human review | Gate before action vs after-the-fact sampling | Using review where an irreversible action needed approval |

### 8. Failure Modes and Debugging (Explain With Evidence)

Practice telling each as a **STAR+data** story (Situation, Task, Action, Result, plus the metrics and traces that proved it):

1. **Hallucinated policy answer.** Evidence: trace shows correct policy not retrieved (recall failure due to acronym); fix: hybrid search + synonym expansion; result: recall@8 0.78 → 0.94; faithfulness unchanged.
2. **Agent looped on flaky tool.** Evidence: 14 identical calls in trace; fix: loop detector + tool returns structured error with `retryable=false`; result: max-turn terminations 6% → 0.5%.
3. **Cost spike.** Evidence: tokens/run p95 tripled after a prompt change that injected full documents; fix: chunk-level context with budget; result: cost back to baseline, quality within 0.5 pt.
4. **Injection attempt in uploaded file.** Evidence: policy deny events on `send_email` correlated with one document; fix: remove tool from that agent, add test; result: zero denies, demonstrated containment to customer security team.
5. **Model upgrade regression.** Evidence: schema-compliance drop in eval gate; fix: adjust prompt + strict structured-output mode; result: compliance 99.6%.

### 12. Engineering Scenarios

**Scenario 1 (FDE, requirement clarification) — "We need an AI that approves vendor invoices."**
Expected reasoning: Clarify approval authority (delegation of authority matrix), current error rates, volume, systems (ERP, email), fraud risks. Reframe: AI extracts and three-way-matches, flags exceptions with explanations; deterministic rules auto-approve only exact matches under thresholds (if policy allows); humans approve exceptions. Acceptance: extraction accuracy ≥ 98% on key fields over 1,000 historical invoices; zero auto-approvals outside policy in a 3-month replay; time-to-approve reduced by X%.

**Scenario 2 — Customer insists on "fully autonomous" support agent.**
Present risk analysis and a staged autonomy plan with measured gates (draft-only → auto-send low-risk intents → expand), with kill switch and audit. Show eval evidence at each gate.

**Scenario 3 — On-prem, no external model APIs.**
Options: self-hosted open-weight models (vLLM/TGI), smaller models with RAG, quantization; evaluate quality drop; GPU sizing; update process; observability export constraints.

**Scenario 4 — Retrieval quality complaint in a multilingual corpus.**
Investigate per-language recall; multilingual embeddings; language-aware BM25; query translation; evaluate per language.

**Scenario 5 — Executive demo next week.**
Build a demo script around real user tasks with a fallback recording, show citations and a trace, include one "I don't know" case to demonstrate safe behavior, and prepare metrics slide.

### 13. Interview Preparation

#### The Six Core Questions

**Q1: Why use an agent here?**
Strong answer: Because the task's steps depend on intermediate findings — e.g. troubleshooting an integration requires checking logs, then configs, then recent deploys depending on what each reveals. A fixed workflow would either miss paths or explode in branches. We bound it with 8 turns, a 90-second deadline, read-only tools by default, approval for writes, and we measured: 84% resolution on 200 historical cases vs 61% for the best workflow variant, at $0.07/task.
Why asked: to see if you can justify autonomy with mechanism and evidence.
Weak answer: "Agents are the future"; no limits; no measurement.

**Q2: Why not use an agent?**
Strong: When the process is known (use a workflow), when errors are costly and hard to detect, when latency is tight, or when we can't evaluate. Example: invoice field extraction is a single structured-output call with validation; adding agency only adds cost and variance.
Trap: Treating "no agent" as a lack of ambition rather than good engineering.

**Q3: How do you authorize tools?**
Strong: Authentication produces a principal; tools are filtered per principal; each call passes through a gateway that validates arguments (schema), checks deterministic policy (RBAC/ABAC, tenant from auth context, limits), requires approval for high-risk actions bound to exact arguments, and executes with delegated, scoped, short-lived credentials; all calls audited and traced. The model never decides permissions; prompt injection can at most make the model *request* something the gateway will deny.
Trap: "The system prompt says only admins can delete."

**Q4: How do you evaluate RAG?**
Strong: Separately: retrieval (recall@k, MRR/nDCG against labeled relevant chunks; ACL-filter correctness) and generation (faithfulness, correctness vs reference, citation precision/recall, abstention on unanswerable questions). Dataset from real queries with unanswerable and adversarial cases; calibrated LLM judges plus human labels; CI regression gates; online feedback and sampled review. When an answer is wrong, I check whether the evidence was in the corpus, retrieved, kept in context, and then used.
Trap: One end-to-end "accuracy" score; no unanswerable cases.

**Q5: How do you prevent loops?**
Strong: Hard limits in the orchestrator (turns, time, tokens/cost, consecutive errors); loop detection on repeated tool+argument signatures and lack of new information; tools that return explicit, structured outcomes ("no results; not retryable"); stop with a partial result or escalation; eval cases for unanswerable tasks asserting bounded turns.
Trap: "Tell the model not to loop."

**Q6: How do you trace and safely deploy agents?**
Strong: OpenTelemetry traces spanning request → run → model calls (model, tokens, cost, latency) → tool calls (args validated, policy decision, latency) → retrievals, tagged with agent/prompt/model versions; GenAI semantic conventions where stable enough (they're still in Development). Deployment: version agents as units; offline eval gates (quality, safety zero-tolerance, cost/latency); shadow mode; canary with automatic rollback on alarms; feature flags; keep the previous version hot.
Trap: Logging prompts to stdout as "observability"; deploying prompt changes without evals.

#### Quick Questions
- **What's an embedding?** A vector representation where similar meanings are close; used for semantic retrieval; doesn't capture exact identifiers well.
- **What's MCP?** A protocol for AI apps to discover and call tools/resources from servers; standardizes integration, not authorization policy.
- **What's a guardrail?** A control around model inputs, actions or outputs — deterministic where security matters.
- **What's groundedness/faithfulness?** Whether the answer's claims are supported by the provided context.

#### Intermediate Questions
- **How do you choose chunk size?** Empirically: start structure-aware (sections), ~300–800 tokens, evaluate recall@k and answer quality on your dataset; tables and code need special handling.
- **How do you reduce cost without hurting quality?** Measure per-step tokens; route simpler steps to smaller models; prompt caching; context compaction; caching; evaluate each change.
- **What would you log, and what wouldn't you?** Log metadata (versions, tokens, latencies, tool names, policy decisions, IDs); capture payloads only in an access-controlled, retention-limited store; redact PII; honor customer data agreements.

#### Advanced Questions
- **A customer's security team asks how you prevent prompt injection.** We assume it can't be fully prevented at the model level; we contain it: least-privilege toolsets, no exfiltration-capable tools for agents reading untrusted content without approval, deterministic authZ, egress control, output handling, monitoring, and red-team suites — and we show the test results.
- **How would you evaluate an agent whose tasks have multiple valid solutions?** Outcome-based checks (end state correct — e.g. ticket fields updated properly in a sandbox), trajectory constraints (no forbidden tools, within budget), rubric-based judge scoring calibrated with humans, and pass@k / consistency across runs.
- **How do you handle non-determinism in evals?** Multiple runs per case, report mean and variance, fix seeds/temperature where available, compare distributions, set thresholds with margins.

### 14. Explain-It-at-Three-Levels

**RAG evaluation.** *30 s:* Evaluate retrieval and generation separately: did we fetch the right evidence (recall@k), and did the answer faithfully use it with correct citations — including abstaining when evidence is missing. *2 min:* Dataset construction, metrics, judges, gates, online feedback. *Deep:* nDCG vs recall, judge calibration (κ), position bias, unanswerable rates, per-segment analysis (language, document type), and linking metrics to business outcomes.

**Tool authorization.** *30 s:* The model can only request; a deterministic gateway validates, authorizes against the user's permissions, gates risky actions with approval, and executes with scoped credentials. *2 min / Deep:* Principal construction, policy engines (RBAC/ABAC/ReBAC), argument-bound approvals, token exchange and audience restriction, confused deputy, audit trails, MCP authorization specifics.

**Deterministic/probabilistic boundary.** *30 s:* Models propose, extract and draft; code authorizes, computes, decides by rule and commits. *Deep:* Confidence thresholds, human review routing, validation, measurement of each probabilistic component, and how to explain the boundary to auditors.

#### Knowledge Check Answers
1. Retrieved documents are outdated or wrong (faithful to bad evidence); conflicting sources and the model picked the wrong one; the question was ambiguous and answered a different interpretation.
2. A feature that's accurate but too slow or expensive fails the requirement; regressions in cost/latency must gate releases like quality.
3. Approval gates an action before it happens (required for irreversible/high-risk); review samples outputs after the fact for quality monitoring.
4. It's probabilistic and can be evaded; security must be enforced by deterministic controls limiting what any model output can cause.
5. When tools must be shared across multiple AI clients/hosts, vendors provide MCP servers, or you want standardized discovery/auth across an organization; less value for a single app's internal functions.
6. It measures answer rate, not correctness; rewards answering unanswerable questions; ignores faithfulness and citations.
7. No margin for noise (non-deterministic evals), no safety/cost/latency checks, no minimum sample size; one metric only.
8. Excessive agency and confused tool selection: tools should be filtered per principal and agent purpose.
9. Retrieval broke: embedding model mismatch between query and index, failed ACL ingestion (users now "can't see" documents), chunking change, index parameters/filters lowering recall, or reranker threshold miscalibrated for new score distribution.
10. Tokens per step (context growth, larger tool outputs), number of turns, model routing changes, prompt caching hit rate, retries.
11. Accuracy of what (definition), measured on which dataset (representative? includes unanswerable?), compared with what baseline (human accuracy today), cost of each error type (false positive vs negative), and what happens on uncertain cases.
12. Show the architecture of deterministic boundaries, run live injection attempts that get denied (with traces), show audit logs and permission tests, explain data flows/retention, and share red-team results.

### 16. Common Interview Traps

| Trap | Correct model |
|---|---|
| "RAG prevents hallucinations." | It reduces them when retrieval is good; measure faithfulness; require citations and abstention. |
| "An agent is simply an LLM with a prompt." | It's a bounded control loop with tools, state, policies, limits, observability and evals. |
| "We'll fine-tune it on our docs." | Use RAG for changing, permissioned knowledge; fine-tune for behavior/format. |
| "Our eval is the demo." | Demos are anecdotes; evals are datasets with metrics and baselines. |
| "The model will refuse unauthorized actions." | Authorization is deterministic code, not model behavior. |
| "Higher accuracy is always the goal." | Optimize for business outcome under cost, latency and risk constraints. |
| "Customers want autonomy." | Customers want outcomes with acceptable risk; propose staged autonomy with evidence. |

### 17. Cheat Sheet

- **Taxonomy:** LLM → augmented LLM → RAG / tools → workflow → agent → multi-agent; MCP = integration protocol.
- **Why agent:** unknown path + tool choice depends on findings + bounded + evaluable. **Why not:** known process, high error cost, tight latency, no evals.
- **Tool authZ:** principal → filtered tools → schema validation → policy → approval (args-bound) → scoped creds → audit.
- **RAG eval:** retrieval (recall@k, MRR, nDCG, ACL correctness) ≠ generation (faithfulness, correctness, citations, abstention).
- **Loops:** turns, time, tokens, errors, loop detector, explicit tool outcomes.
- **Deploy:** versioned agent units, eval gates, shadow, canary, flags, rollback.
- **Discovery:** outcome, users, process, data, authority, risk, constraints, integration, evaluation, rollout.
- **Boundary:** models propose/extract/draft; code authorizes/computes/decides/commits.
- **Evidence:** every claim → metric, trace, or example.
