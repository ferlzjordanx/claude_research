## Unit 42 — AI/FDE Interviews

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Distinguish** LLM, augmented LLM, RAG, tool calling, workflow, agent and multi-agent system precisely, and **justify** in an interview which one a use case needs.
2. **Answer** the five core questions with depth and evidence: *Why an agent instead of a workflow? When should an LLM not decide? How do you prevent unauthorized tools? How do you evaluate RAG? How do you trace multi-agent workflows?*
3. **Design** deterministic boundaries around probabilistic components: authorization, validation, loop control (max turns, deadlines, budgets), idempotency, durable state and checkpointing.
4. **Explain** a RAG pipeline stage by stage (ingestion, chunking, embedding, indexing, query transformation, retrieval, reranking, context construction, generation, citation, evaluation), and **diagnose** retrieval failure vs generation failure with separate metrics.
5. **Describe** safe deployment for AI features: model pinning, offline eval gates, shadow mode, canary with guard metrics, feature flags, kill switches, fallbacks and rollback.
6. **Conduct** an architecture defense of your capstone: present it in 10 minutes, then defend every component (what failure it addresses, what simpler alternative was considered).
7. **Answer** scenario questions with the structure *requirement clarification → design choice → implementation → evaluation → operational controls*, applying the FDE lens (stakeholders, ambiguity, authoritative data, demonstration and evidence).

### 2. Prerequisite Knowledge

- Units 33–37 (guardrails, structured output, approvals, evaluation, observability) and Unit 38 (system design). This unit assembles them into interview answers.
- Earlier curriculum units on LLM APIs, embeddings, pgvector, RAG, tool calling, MCP and agents.
- **MCP refresher** [Version-dependent]: the Model Context Protocol standardizes how clients (hosts/agents) discover and call **tools**, read **resources** and use **prompts** exposed by servers, over stdio or Streamable HTTP. The 2026-07-28 revision is stateless (no initialize handshake or session pinning). Spring AI 2.0 shipped against the 2025-11-25 revision with `@McpTool`/`@McpResource`/`@McpPrompt` annotations. MCP standardizes the *interface*. It doesn't make tools safe; your policy layer does.

### 3. Mental Model

AI/FDE interviews test whether you can **put a probabilistic component inside a deterministic system responsibly, and convince a skeptical stakeholder with evidence**.

```
                 ┌────────────── deterministic shell (you own it) ──────────────┐
 Stakeholder ──→ │ requirements → authN/Z → scope → workflow/agent → validation │ ──→ outcome
  ambiguity      │                       ▲          │                           │     + evidence
                 │          evals ───────┘          └── traces, audit, cost     │
                 └───────────────────────────────────────────────────────────────┘
                                 probabilistic core: model decisions
```

The **autonomy ladder**: use the lowest rung that solves the problem.

```
LLM                → one call, text in/out                       (summarize this)
Augmented LLM      → LLM + retrieval/tools/memory in one call    (answer with these docs)
RAG                → retrieve evidence, then generate with citations
Tool calling       → model proposes structured calls; code executes; one or few rounds
Workflow           → code defines the steps; LLM fills specific steps (classify, extract, draft)
Agent              → model chooses the next step in a bounded loop until a stop condition
Multi-agent system → several agents with roles/handoffs, orchestrated
```

Each rung up adds flexibility *and* cost, latency, failure modes and evaluation difficulty. Interviewers reward candidates who climb only when the problem demands it.

### 4. Comprehensive Theory

#### 4.1 The Taxonomy, Precisely

| Term | Who decides control flow? | Typical use | Key risk |
|---|---|---|---|
| **LLM** | n/a (single call) | Summarize, rewrite, classify | Hallucination, format drift |
| **Augmented LLM** | Code, with model using provided context/tools | Grounded answers, extraction with lookups | Context leakage, injection |
| **RAG** | Code (retrieve → generate) | Knowledge Q&A with citations | Retrieval misses, unfaithful generation |
| **Tool calling** | Model proposes; code executes | Lookups, actions | Unauthorized or malformed actions |
| **Workflow** | **Code** (predefined steps, possibly LLM-based routing at fixed points) | Ticket triage → draft → approval | Rigidity when cases vary |
| **Agent** | **Model**, within a bounded loop | Open-ended investigations, multi-step tasks with unknown paths | Loops, cost, unpredictability, agency risks |
| **Multi-agent** | Multiple models with an orchestrator or handoffs | Specialized roles, parallel research | Compounding errors, coordination cost, attribution difficulty |

**Agent definition checklist** (say these explicitly in interviews):

- **Goal**: what "done" means.
- **Instructions**: system prompt with role, constraints and output contract.
- **Available tools** and **tool schemas**: narrow, typed, documented (Unit 34).
- **State**: conversation, scratchpad, retrieved evidence, tool results, pending approvals; durable (checkpointed).
- **Decision loop**: model decision → validate → authorize → execute → observe → repeat.
- **Stopping condition**: ANSWER / ASK_CLARIFICATION / ESCALATE / PENDING_APPROVAL.
- **Maximum turns**, **timeout** (deadline), **token/cost budget**, **denial budget**.
- **Validation**: schema and semantic checks.
- **Error handling**: repair, retry (bounded), fallback, escalate.
- **Authorization boundary**: delegated user identity; policy before every tool (Unit 33).
- **Observability**: trace per run (Unit 37).
- **Evaluation strategy**: dataset, metrics and gates (Unit 36).

Never present `while (true) { askModel(); }` as an agent.

#### 4.2 Q1 — Why an Agent Instead of a Workflow?

**Strong answer structure:** start from the problem's *variability*.

- **Prefer a workflow** when the steps are known and stable, the order matters for compliance, the outcome must be predictable, latency and cost must be tight, or the process is auditable step by step. Most enterprise processes are like this: "classify ticket → fetch order → apply refund policy → draft reply → approve".
- **Prefer an agent** when the path depends on intermediate findings in ways you can't enumerate ("investigate why this customer was double-charged": might involve orders, payments, emails, logs in varying order), when the tool space is large and combinations matter, or when a human expert would explore rather than follow a checklist.
- **Hybrid** is common and often best: a workflow with an agentic step inside a bounded sandbox ("investigate" step with read-only tools, max 6 steps), or an agent whose high-risk actions route into a deterministic approval workflow.

**Evidence to cite:** eval results comparing a workflow and an agent on the same dataset (task success, cost, latency, variance). "On our 120-case suite, the workflow version solved 82% at $0.004/run with p95 2.1 s. The agent solved 91% at $0.019/run with p95 7.8 s. The gap was all in the 'investigation' slice, so we used the workflow with one agentic investigation step: 90% at $0.007."

**Trap:** "Agents are more advanced, so better."

#### 4.3 Q2 — When Should an LLM Not Decide?

**The LLM should not decide:**

1. **Authorization:** who may do what (identity, scopes, ownership, tenant). Always deterministic (Unit 33).
2. **Hard business rules and limits:** refund ceilings, eligibility, regulatory rules. Encode them as code or rules engines.
3. **Calculations requiring exactness:** money, tax, dosage, dates. Use code or tools, and let the model call the calculator, not be it.
4. **Irreversible high-impact actions without human approval** (Unit 35).
5. **Anything requiring a guaranteed, reproducible answer:** legal determinations, compliance attestations.
6. **When a simpler deterministic method works:** regex, lookup tables, SQL, a classifier with known accuracy.
7. **When you can't evaluate it:** if you can't measure whether the decision is right, you can't safely delegate it.

**The LLM may decide** (within bounds): which read-only tool to use next, how to phrase an answer, how to summarize evidence, which category a ticket likely belongs to (with confidence thresholds and human fallback), and which information is missing (ask a clarifying question).

**Trap:** "The model is very accurate now, so it can decide permissions."

#### 4.4 Q3 — How Do You Prevent Unauthorized Tools?

Layered answer (from Unit 33):

1. **Identity:** authenticate the user, and derive the authorization context server-side (JWT → scopes, tenant, limits). Never from the prompt or the model.
2. **Advertise only allowed tools** for this user, agent and context (the per-turn allowlist), with untrusted content reducing capabilities.
3. **Validate** every tool request (schema, typed args; Unit 34).
4. **Authorize** every concrete call in a central policy: tool exists, agent allowlist, user scope, tenant, ownership, argument bounds, budgets, context taint → ALLOW / DENY / REQUIRE_APPROVAL.
5. **Execute with delegated, least-privilege credentials** (per-tool credentials, token exchange), never a superuser service account.
6. **Approval** for high-risk actions; the exact payload is bound by hash.
7. **Audit and trace** every decision; alert on denial spikes.
8. **Structural enforcement:** only the executor can invoke tools (ArchUnit), and the framework's auto-execution is disabled for sensitive tools.
9. **MCP specifics:** allowlist servers and tools, pin versions, review tool descriptions (injection surface), sandbox servers, scope their credentials, and wrap MCP tools with the same policy.
10. **Test** with a "compromised model" suite that proves controls hold even when the model does what the attacker wants.

#### 4.5 Q4 — How Do You Evaluate RAG?

Teach and evaluate each stage separately:

| Stage | What can go wrong | How to evaluate |
|---|---|---|
| **Ingestion** | Missing/duplicated docs, stale versions, lost ACLs, broken parsing (tables, PDFs) | Ingestion reports (counts, failures), spot checks, ACL propagation tests |
| **Chunking** | Splits mid-table/section; chunks too big (diluted) or too small (no context) | Inspect chunks for golden docs; retrieval metrics per chunking config |
| **Embedding** | Model mismatch for domain/language; query/doc embedded with different models | Recall@k comparisons across embedding models; version pinning |
| **Indexing** | ANN recall loss (HNSW `ef_search` too low), filtered search returning too few results | Compare ANN vs exact search recall; check filtered-query hit counts (pgvector 0.8 iterative scans help) |
| **Query transformation** | Rewrites drift from intent; multi-query explodes cost | Retrieval metrics with/without transformation |
| **Retrieval** | Relevant doc not in top-k; wrong tenant/ACL filter | **Recall@k, precision@k, MRR, nDCG** on labelled queries |
| **Reranking** | Reranker demotes the right doc; latency | Metrics before vs after rerank |
| **Context construction** | Too much context (lost in the middle), truncation, missing doc IDs, injection via docs | Context recall/precision; token counts; spotlighting checks |
| **Generation** | Unfaithful claims, ignoring context, over-refusing | **Groundedness/faithfulness**, answer correctness (rubric), refusal appropriateness |
| **Citation** | Missing, fabricated, or not supporting the claim | Citations ⊆ retrieved; claim-citation support (judge) |
| **Evaluation (end-to-end)** | Metrics don't reflect user value | Task success per intent, online feedback, human review sample |

**Retrieval failure ≠ generation failure.** Report the 2×2 matrix (retrieval hit/miss × answer correct/incorrect) and fix the stage that failed.

**Trap:** "RAG prevents hallucinations." RAG reduces them when retrieval works and generation is faithful, and both must be measured.

#### 4.6 Q5 — How Do You Trace Multi-Agent Workflows?

From Unit 37:

- One trace per business operation. Orchestrator `invoke_agent` span is the parent of each sub-agent's `invoke_agent` span; each has `chat`, `execute_tool` and retrieval children.
- `gen_ai.agent.name` on agent spans; business IDs (`agent.run.id`, `ticket.id`) everywhere.
- Propagate context across process boundaries (HTTP `traceparent`, Kafka headers, MCP transports). Use **links** for async handoffs and human pauses.
- Record handoff payloads as IDs/hashes plus sizes, not content.
- Per-agent metrics: steps, tokens, cost, errors, stop reasons.
- Attribution: compare good vs bad traces to find the first agent whose output diverges. Per-agent eval cases.
- Note the GenAI conventions are in Development status: centralize attribute names.

#### 4.7 Loop Control, Idempotency and State

**Loop control.** `maxSteps` (for example 6–10), wall-clock deadline (for example 30 s interactive), token/cost budget per run and per user/tenant per day, denial budget (abort after N policy denials), repeated-call detection (same tool + same canonical args twice → stop or force a different action), and a progress check (no new information in 2 steps → summarize and stop). Every stop has a *reason*, recorded and metered.

**Idempotency.** Agent steps can be retried (crash, timeout, redelivery), so tool executions with side effects need idempotency keys derived from `(runId, stepIndex, toolCallId)` or the approval proposal ID (Unit 35). Read-only tools are naturally idempotent. External APIs get the key passed through.

**State.** Durable checkpoint after each step: conversation (or a summary plus references), tool results references, pending proposal, budget counters, and the agent definition version. Resume reconstructs the context. Memory across sessions (long-term) is a separate store with provenance and poisoning controls (OWASP ASI06). Never trust memory content as instructions.

#### 4.8 Safe Deployment of AI Features

```
Change (prompt/model/tool/retrieval)
 → offline eval gate (Unit 36): critical = 0, thresholds vs baseline
 → shadow mode: run new version on live traffic, don't show output; compare metrics (cost, latency, validity, judge scores)
 → canary: small % of users/tenants; guard metrics (GaveUp rate, denial rate, approval rejection, latency, cost, feedback)
 → progressive rollout with automatic rollback on guard breach
 → full rollout; new baseline accepted (reviewed)
Always: feature flag + kill switch per capability (e.g. disable write tools); pinned model versions; fallback model
         evaluated in advance; graceful degradation path (answer with KB only, or route to human)
```

**Model pinning.** Use dated model identifiers where the provider offers them, not floating aliases, so the model changes only when you choose (and re-run evals).

**Graceful degradation.** Provider outage → fallback model (pre-evaluated) → reduced capability (read-only answers) → deterministic fallback ("We've created a ticket; a human will respond"). Show these paths in traces.

#### 4.9 The FDE Lens

Forward Deployed Engineers sit with customers, turn ambiguous asks into working systems, and prove value. In interviews, apply these questions out loud:

- **What did the stakeholder actually request?** ("An AI agent for support" might mean "reduce handle time on refund tickets".)
- **What requirement is still ambiguous?** (Which tickets? What does success look like? Who approves refunds today?)
- **What must remain deterministic?** (Authorization, refund limits, compliance steps.)
- **What may safely be probabilistic?** (Drafting replies, summarizing history, suggesting categories.)
- **What data/source is authoritative?** (Order DB, not email claims; policy docs version X.)
- **What happens when a dependency fails?** (Provider outage, CRM timeout.)
- **How is access controlled?** (SSO groups → scopes; tenant isolation.)
- **How will we test success?** (Eval dataset from their tickets; thresholds agreed upfront.)
- **How will we demonstrate this to the customer?** (Demo script on their data, side-by-side with the current process.)
- **What evidence proves the feature works?** (Scorecard, pilot metrics, audit trail, cost report.)

#### 4.10 Architecture Defense Sessions

**Format.** 10-minute presentation of your capstone → 30–40 minutes of challenges. For every component, be ready with:

| Component | What failure it addresses | Simpler alternative considered | Why rejected (or when you'd switch) |
|---|---|---|---|
| Tool policy engine | Unauthorized/injected actions | Prompt rules only | Not enforceable; untestable |
| Typed decisions | Malformed/ambiguous outputs | Regex on prose | Fragile, injection via formatting |
| Approval service | Irreversible harm, compliance | No approval / approve everything | Unsafe / fatigue |
| Outbox + Kafka | Lost or phantom events | After-commit listener | Loses events on crash |
| pgvector | Retrieval with SQL filters + one DB | Dedicated vector DB | Extra infra; switch at ~10⁸ vectors or advanced needs |
| Redis | Rate limits, caching, budgets | In-memory per instance | Inconsistent across replicas |
| OpenTelemetry | Debugging, attribution, cost | Logs only | No causality, no attribution |
| Eval suite | Regressions on change | Manual testing | Not repeatable; misses slices |
| Agent loop (vs workflow) | Variable investigation paths | Fixed workflow | Show eval comparison; maybe hybrid |

### 5. Internal Mechanics — The Bounded Agent Loop, Step by Step

```
run(request, user):
  ctx ← AgentContext.from(authenticatedUser, ticket)                 // deterministic identity
  tools ← policy.availableTools(ctx)                                 // per-turn allowlist
  state ← checkpoint.loadOrNew(runId)
  while true:
     if state.steps ≥ MAX_STEPS        → stop(MAX_STEPS)
     if now ≥ deadline                  → stop(DEADLINE)
     if state.tokens ≥ TOKEN_BUDGET     → stop(TOKEN_BUDGET)
     if state.denials ≥ DENIAL_BUDGET   → stop(DENIAL_BUDGET)
     decision ← decisionLoop.decide(model, state.context, tools)      // validate + bounded repair
       GaveUp → stop(ESCALATED)
     switch decision.type:
       ANSWER            → outputGuard → stop(ANSWERED)
       ASK_CLARIFICATION → stop(ASK_CLARIFICATION)
       ESCALATE          → stop(ESCALATED)
       CALL_TOOL         → outcome ← executor.execute(runId, step, toolCall, ctx)   // policy, approval, idempotency
                             Executed       → state.add(untrusted observation)
                             Denied         → state.denials++; state.add(denial observation)
                             PendingApproval→ checkpoint; stop(PENDING_APPROVAL)
                             Failed         → state.add(failure observation)
     repeated(toolCall) twice → stop(LOOP_DETECTED)
     state.steps++ ; checkpoint.save(state)
```

Every branch terminates, and every stop is recorded with a reason, metered, and visible in the trace.

### 6. Implementation Examples

#### Example 1 — Minimal: Bounded agent loop (provider-neutral)

```java
package com.example.supportops.agent;

import com.example.supportops.decision.DecisionLoop;
import com.example.supportops.decision.DecisionType;
import com.example.supportops.policy.AgentContext;
import com.example.supportops.policy.ToolPolicy;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.*;

public final class BoundedAgent {

    public enum Stop { ANSWERED, ASK_CLARIFICATION, ESCALATED, PENDING_APPROVAL,
                       MAX_STEPS, DEADLINE, TOKEN_BUDGET, DENIAL_BUDGET, LOOP_DETECTED }

    public record Limits(int maxSteps, Duration deadline, long tokenBudget, int denialBudget) {
        public static Limits interactive() { return new Limits(6, Duration.ofSeconds(30), 20_000, 3); }
    }

    public record Result(Stop stop, String answer, List<String> citations, UUID pendingApproval, int steps) {}

    private final DecisionLoop decisions;
    private final GuardedToolExecutor executor;
    private final ToolPolicy policy;
    private final Clock clock;

    public BoundedAgent(DecisionLoop decisions, GuardedToolExecutor executor, ToolPolicy policy, Clock clock) {
        this.decisions = decisions; this.executor = executor; this.policy = policy; this.clock = clock;
    }

    public Result run(String runId, DecisionLoop.DecisionModel model, AgentState state, AgentContext ctx, Limits limits) {
        Instant deadline = clock.instant().plus(limits.deadline());
        Set<String> seenCalls = new HashSet<>();

        for (int step = state.steps(); ; step++) {
            if (step >= limits.maxSteps()) return state.stop(Stop.MAX_STEPS);
            if (clock.instant().isAfter(deadline)) return state.stop(Stop.DEADLINE);
            if (state.tokens() >= limits.tokenBudget()) return state.stop(Stop.TOKEN_BUDGET);
            if (state.denials() >= limits.denialBudget()) return state.stop(Stop.DENIAL_BUDGET);

            Set<String> tools = policy.availableTools(ctx.withTaint(state.hasUntrustedContent()));
            var outcome = decisions.decide(model, state.conversation(), tools, state.retrievedDocIds());

            if (outcome instanceof DecisionLoop.Outcome.GaveUp) return state.stop(Stop.ESCALATED);
            var valid = ((DecisionLoop.Outcome.Decided) outcome).valid();
            var d = valid.decision();

            switch (d.type()) {
                case ANSWER -> { return state.answer(d.answer(), d.citations()); }
                case ASK_CLARIFICATION -> { return state.clarify(d.clarificationQuestion()); }
                case ESCALATE -> { return state.stop(Stop.ESCALATED); }
                case CALL_TOOL -> {
                    var call = valid.toolCall();
                    String signature = call.toolName() + ":" + CanonicalArgs.hash(call.typedArgs());
                    if (!seenCalls.add(signature)) return state.stop(Stop.LOOP_DETECTED);

                    switch (executor.execute(runId, call.toolName(), call.typedArgs(), ctx.withCallsSoFar(step))) {
                        case GuardedToolExecutor.Outcome.Executed e -> state.observe(e.untrustedObservation());
                        case GuardedToolExecutor.Outcome.Denied den -> state.deny(den.messageForModel());
                        case GuardedToolExecutor.Outcome.PendingApproval p -> {
                            state.checkpoint();
                            return state.pending(p.approvalId());
                        }
                        case GuardedToolExecutor.Outcome.Failed f -> state.observe(f.messageForModel());
                    }
                }
            }
            state.checkpoint();
        }
    }
}
```

Every limit is explicit, every exit has a reason, and the loop has no `while (true)` without exits.

#### Example 2 — Realistic: RAG with tenant/ACL-filtered retrieval, context construction and citation validation

```java
package com.example.supportops.rag;

import org.springframework.ai.document.Document;
import org.springframework.ai.vectorstore.SearchRequest;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.filter.FilterExpressionBuilder;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Set;

@Service
public class KnowledgeRetriever {

    public record Evidence(String docId, String title, String text, double score) {}

    private final VectorStore vectorStore;       // pgvector-backed
    private final Reranker reranker;             // optional cross-encoder / LLM reranker port

    public KnowledgeRetriever(VectorStore vectorStore, Reranker reranker) {
        this.vectorStore = vectorStore;
        this.reranker = reranker;
    }

    public List<Evidence> retrieve(String query, String tenantId, Set<String> aclGroups) {
        var b = new FilterExpressionBuilder();
        // Authorization INSIDE the query: never retrieve-then-filter, never ask the model to filter.
        var filter = b.and(b.eq("tenantId", tenantId), b.in("aclGroup", aclGroups.toArray())).build();

        List<Document> candidates = vectorStore.similaritySearch(SearchRequest.builder()
            .query(query)
            .topK(20)                     // over-fetch for reranking
            .similarityThreshold(0.35)
            .filterExpression(filter)
            .build());

        return reranker.rerank(query, candidates, 5).stream()
            .map(d -> new Evidence(d.getId(), String.valueOf(d.getMetadata().get("title")),
                                   d.getText(), d.getScore() == null ? 0 : d.getScore()))
            .toList();
    }
}
```

[Version-dependent] The `VectorStore`/`SearchRequest`/`FilterExpressionBuilder` API shown follows Spring AI 1.x–2.0. Verify method names against your pinned version. With pgvector, the filter becomes a SQL `WHERE` on the metadata, so make sure it's selective and indexed (and consider pgvector 0.8's iterative index scans for filtered ANN queries).

```java
package com.example.supportops.rag;

import java.util.List;
import java.util.stream.Collectors;

final class ContextBuilder {

    private static final int MAX_CONTEXT_CHARS = 12_000;

    /** Stable doc IDs (D-<n>) let the model cite and let us verify citations deterministically. */
    static String build(List<KnowledgeRetriever.Evidence> evidence) {
        StringBuilder sb = new StringBuilder();
        for (var e : evidence) {
            String block = "<document id=\"" + e.docId() + "\" title=\"" + escape(e.title()) + "\">\n"
                         + escape(e.text()) + "\n</document>\n";
            if (sb.length() + block.length() > MAX_CONTEXT_CHARS) break;   // budget; most relevant first
            sb.append(block);
        }
        return sb.toString();
    }

    private static String escape(String s) {
        return s.replace("</document", "&lt;/document").replace("<document", "&lt;document");
    }
}
```

The answer is an `AgentDecision` (Unit 34) whose `citations` must be ⊆ retrieved IDs (checked by `DecisionValidator`). If retrieval returns nothing relevant, the prompt instructs the model to say it couldn't find the information (abstention), and the eval suite measures appropriate abstention.

#### Example 3 — Production-oriented: Scenario answer as code + operations (the "refund investigation" design)

A full scenario answer in interview shape:

**Scenario:** "A retailer wants an AI assistant that resolves 'where is my refund?' tickets."

1. **Requirement clarification (FDE).** Who uses it (reps, or customers directly)? What systems hold truth (orders DB, payments PSP, email)? Which actions are expected (answer only? re-issue refund?)? Success metric (handle time, first-contact resolution)? Constraints (PII, region, audit)? Volume (5k tickets/day)?
2. **Design choice.** A **workflow with one agentic step**: (a) deterministic intake (identify customer and order from the authenticated ticket), (b) agentic investigation with **read-only** tools (`get_order`, `get_refunds`, `get_psp_status`, `search_kb`), max 6 steps, (c) deterministic policy check for eligibility, (d) drafted reply (LLM) → rep review, (e) any re-issue goes through the approval workflow. This rejects a fully autonomous agent because refunds are irreversible and policy is deterministic.
3. **Implementation.** Spring Boot service, `BoundedAgent` for step (b), `ToolPolicy` with read-only allowlist for that step, typed decisions, RAG over policy docs with tenant filter, approval service for re-issues, outbox events.
4. **Evaluation.** 150 historical tickets labelled with the true refund status and correct reply elements. Metrics: correct status identification (task success), tool precision/recall, groundedness of the reply vs tool results, forbidden behavior (no write tools in investigation; no PII of other customers), latency p95 < 10 s, cost < $0.01/ticket. Gate: critical = 0, task success ≥ 90%.
5. **Operational controls.** Traces per ticket. Dashboards for stop reasons, denials and cost. Shadow mode for 1 week (agent drafts, reps work as usual; compare). Canary 10% of reps. Kill switch for the investigation step (fallback to the workflow without an agent). Pinned model. Weekly review of rep edits → new eval cases.

### 7. Comparative Analysis

| Comparison | Key difference | When to use | Interview trap |
|---|---|---|---|
| Workflow vs agent | Code decides steps vs model decides steps | Known paths vs open-ended investigation | "Agents are always better" |
| RAG vs tool calling | Retrieve unstructured knowledge vs query/act on systems of record | Policies/docs vs live data/actions | Using RAG for live order status |
| RAG vs fine-tuning | Inject knowledge at query time vs change model weights/behavior | Changing knowledge, citations, ACLs vs style/format/specialized behavior | "Fine-tune to teach facts" |
| Single vs multi-agent | One loop vs several roles | Default single; multi when roles/tools/contexts genuinely separate | Multi-agent for org-chart aesthetics |
| Spring AI vs direct provider SDK | Portable abstractions + Spring integration vs full provider features, fewer layers | Spring AI for multi-provider + Spring apps; SDK for cutting-edge features | Assuming abstraction covers every provider feature |
| MCP tool vs in-process tool | Standard protocol, separate process vs direct method | MCP for reuse across clients/teams; in-process for tight control and latency | "MCP makes tools secure" |
| Prompt rules vs policy code | Probabilistic vs deterministic | Behavior vs security | "We told the model not to" |
| Offline vs online eval | Curated vs live | Gate vs validate | Offline-only confidence |
| Observability vs evaluation | What happened vs was it good | Both | Conflating them |
| LLM-as-router vs classifier vs rules | Flexible vs measurable vs exact | Rules when exact; classifier when labelled data; LLM when variety is high | LLM for everything |

### 8. Failure Modes and Debugging (Scenario Drills)

**Drill 1 — "The agent sometimes refunds the wrong order."** → trace + audit → ownership check missing or model-derived → server-side ownership, compromised-model tests, eval case. (Unit 33)

**Drill 2 — "Answers cite policies that don't exist."** → fabricated citations → citation ⊆ retrieved validation, groundedness eval; check whether retrieval returned nothing and the model improvised → abstention instruction plus a retrieval fix. (Units 34, 36)

**Drill 3 — "Costs tripled this week."** → `agent.cost.usd` by agent/model → stop reasons show MAX_STEPS up → a new tool description confuses the model into loops → fix description, loop detection, budget alert, eval cost gate. (Units 36, 37)

**Drill 4 — "After the provider updated the model, JSON errors spiked."** → floating alias → pin model, schema-compliance gate, native structured output. (Units 34, 36)

**Drill 5 — "Multi-agent pipeline gives inconsistent answers."** → single trace across agents → the first divergent agent is the researcher with a nondeterministic retrieval (unstable top-k ties) → deterministic tie-breaking, per-agent evals. (Unit 37)

### 12. Engineering Scenarios

**Scenario 1 — Stakeholder-driven (FDE): "We want an agent that handles all customer emails automatically."**

**Scenario 2 — "When should the LLM not decide?" in a lending context.**
*Reasoning:* Credit decisions are regulated (explainability, fair lending), so the LLM must not decide approval. It can extract information from documents (with validation and human verification), summarize the file for an underwriter and draft explanations from the deterministic decision's reasons.

**Scenario 3 — Prompt injection via a shared document (security interview).**
*Reasoning:* Walk the indirect path, the lethal trifecta, capability restriction in tainted turns, policy and approval, output guard for exfiltration, and the compromised-model test. Then show evidence from Unit 33.

**Scenario 4 — "Our RAG answers are wrong 20% of the time."**
*Reasoning:* Ask for examples, then build a labelled set of 100 questions. Measure recall@k first. **Scenario 5 — Safe deployment under pressure.**
A sales demo is in 2 days, and the team wants to switch to a new model. *Reasoning:* Run the eval suite now (hours, not days). If critical failures or regressions appear, demo on the pinned model. ### 13. Interview Preparation

#### The Five Core Questions — Model Answers

**Q1: Why agent instead of workflow?**
*Strong answer:* "I start with the most deterministic option that solves the problem. If the steps are known, a workflow is cheaper, faster, more predictable and easier to audit. I use an agent when the path depends on what we discover, as in investigations across several systems, and even then I bound it: read-only tools, max steps, deadline, budget, and high-risk actions routed into deterministic approval. In my capstone I compared both on 120 cases: the hybrid got 90% at a third of the agent's cost, so that's what we shipped."
*Why asked:* Judgment and cost-awareness. *Weak answer:* "Agents are more flexible."

**Q2: When should an LLM not decide?**
*Strong answer:* "Authorization, hard business rules, exact calculations, irreversible actions without approval, regulated determinations, and anything we can't evaluate. The model can propose, classify with measured accuracy, summarize and draft; code and humans decide the rest."
*Weak answer:* "When it's not confident." Self-reported confidence isn't calibrated.

**Q3: How do you prevent unauthorized tools?**
*Strong answer:* The ten layers in 4.4, compressed: identity from auth, per-turn allowlist, validation, central policy (scope, tenant, ownership, bounds, taint), delegated least-privilege credentials, approvals, audit, structural enforcement, MCP hygiene, compromised-model tests.
*Weak answer:* "The system prompt lists allowed tools."

**Q4: How do you evaluate RAG?**
*Strong answer:* Stage-by-stage. A labelled dataset with relevant doc IDs and expected answers. Retrieval metrics (recall@k, MRR, nDCG) separate from generation metrics (faithfulness, correctness, citation validity). The 2×2 attribution matrix. Regression gates. Online feedback and sampled judging. Fix the failing stage.
*Weak answer:* "We ask users if answers are good" or "we use an LLM to rate answers 1–10".

**Q5: How do you trace multi-agent workflows?**
*Strong answer:* One trace per business operation with nested `invoke_agent` spans per agent and `chat`/`execute_tool`/retrieval children, context propagation across processes, links for async handoffs, business IDs, IDs/hashes instead of content, per-agent metrics, GenAI conventions centralized because they're still in Development, and attribution by comparing traces and per-agent evals.
*Weak answer:* "We log each agent's output."

#### Quick Questions

- What's the difference between RAG and tool calling? (Knowledge vs systems of record/actions.)
- What's MCP, and what doesn't it solve? (Standard tool/resource interface; doesn't solve authorization or injection.)
- What's a stopping condition? (A decision type or limit that ends the loop with a recorded reason.)
- What's groundedness? (Answer claims supported by provided context.)
- What's shadow mode? (Run the new version on live traffic without exposing output, then compare.)

#### Intermediate Questions

**Q: How do you make an agent step idempotent?**
*Strong answer:* Checkpoint after each step. Side-effecting tools take an idempotency key from `(runId, step, callId)` or the approval proposal. Downstream APIs dedupe. On resume, steps already recorded aren't re-executed.

**Q: How do you handle a provider outage?**
*Strong answer:* Timeouts, bounded retries with jitter, circuit breaker, a pre-evaluated fallback model, degraded modes (read-only, KB-only, human handoff), visible in traces and metrics, with alerting.

**Q: How do you control agent cost?**
*Strong answer:* Per-run token/cost budget, step limits, model routing (small models for classification/routing), caching (embeddings, retrieval, prompt caching where supported), context size control, per-tenant budgets in Redis, cost metrics and eval cost gates.

#### Advanced Questions

**Q: Defend pgvector vs a dedicated vector database for your capstone.**
*Strong answer:* One database for relational data, ACL metadata and vectors means SQL filters, transactions and simple ops. HNSW is adequate at our scale (≤ 10M chunks). pgvector 0.8's iterative scans address filtered-query recall. Switch when vector count/QPS or features (multi-vector, hybrid ranking at scale) exceed what Postgres handles comfortably, or when ops prefers isolation. Measure recall vs exact search before deciding.

**Q: Design memory for a long-running assistant safely.**
*Strong answer:* Separate short-term (run state) from long-term memory. Long-term entries have provenance (who/what wrote them), scope (user/tenant), TTL, and are reviewed or restricted to facts extracted by deterministic or validated processes. They're retrieved like documents (untrusted, spotlighted) and never treated as instructions. Poisoning tests in evals.

**Q: How would you roll out a new prompt version to 200 enterprise tenants?**
*Strong answer:* Offline gate, then per-tenant shadow for top tenants, a canary on a subset of tenants with guard metrics, progressive rollout, per-tenant override flags, an instant rollback path, and the version recorded in traces and audit.

### 14. Explain-It-at-Three-Levels

**Concept: Agent vs workflow**

- *30 seconds:* A workflow is code-defined steps with LLMs filling specific steps; an agent lets the model choose the next step in a bounded loop. I default to workflows, and use agents only where paths vary unpredictably, with strict bounds and deterministic controls around actions.
- *2 minutes:* The autonomy ladder, the selection criteria, the hybrid pattern, and evidence from an experiment.
- *Deep:* Agent definition elements (goal, tools, state, loop, stops, limits, validation, authz, observability, evals), failure modes of each, cost/latency math, evaluation differences (trajectory metrics), and operating models (shadow, canary, kill switches).

**Concept: RAG evaluation**

- *30 seconds:* Evaluate retrieval and generation separately. Use recall@k/MRR on labelled relevant documents for retrieval, and faithfulness/correctness/citation validity for generation, so you know which stage to fix.
- *2 minutes:* All stages, the 2×2 matrix, offline gates and online signals.
- *Deep:* Chunking and embedding experiments, ANN vs exact recall, filtered search, hybrid retrieval and reranking, context construction effects, judge validation, and turning production failures into cases.

**Concept: Safe deployment of AI features**

- *30 seconds:* Pin models, gate every change with offline evals, shadow then canary with guard metrics, keep feature flags and kill switches, and have evaluated fallbacks and graceful degradation.
- *2 minutes:* Pipeline stages and guard metrics.
- *Deep:* Statistics of canary analysis, per-tenant rollouts, rollback mechanics, versioning prompts/tools/schemas together, and audit of what version produced each action.

### 16. Common Interview Traps

- **"An agent is an LLM with a prompt."** An agent is a bounded loop with tools, state, validation, authorization, observability and evaluation.
- **"RAG prevents hallucinations."** It reduces them only when retrieval and faithful generation both work, and both are measured.
- **"The model only sees allowed tools, so it can't call others."** Re-authorize every call.
- **"MCP handles security."** It standardizes interfaces; policy is yours.
- **"We'll let the agent decide when to ask for approval."** Routing must be deterministic.
- **"We evaluate with a 1–10 LLM score."** Use stage-specific, validated metrics.
- **"Multi-agent is more powerful."** It's more complex. Prove the benefit.
- **"Use the latest model alias."** Pin versions and evaluate changes.

### 17. Cheat Sheet

- **Ladder:** LLM → augmented → RAG → tool calling → workflow → agent → multi-agent. Climb only when needed.
- **Agent spec:** goal, instructions, tools + schemas, state, loop, stop conditions, max turns, timeout, budgets, validation, error handling, authz boundary, observability, eval strategy.
- **Five answers:** workflow-first; LLM never decides authz/rules/exact math/irreversible/regulated; layered tool authorization; stage-wise RAG eval; one trace per operation with nested agent spans and links.
- **RAG stages:** ingestion, chunking, embedding, indexing, query transformation, retrieval, reranking, context construction, generation, citation, evaluation. Retrieval ≠ generation failure.
- **Loop control:** max steps, deadline, token/cost budget, denial budget, repeated-call detection, stop reasons metered.
- **Idempotency/state:** checkpoint per step; keys from run/step/call or proposal; resume without re-executing.
- **Deployment:** pin → eval gate → shadow → canary with guards → progressive → flags/kill switch → fallback → degrade.
- **FDE questions:** requested vs needed; ambiguity; deterministic vs probabilistic; authoritative data; dependency failure; access control; success tests; demo; evidence.
- **Scenario answer shape:** clarify → design → implement → evaluate → operate.
