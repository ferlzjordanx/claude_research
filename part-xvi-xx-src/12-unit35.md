## Unit 35 — Human-in-the-Loop

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Design** a deterministic risk-classification function that maps a proposed action (tool, arguments, context, requester) to a risk level and an approval requirement, and **justify** each rule.
2. **Compare** low-risk automatic execution with high-risk human review, and **evaluate** when to move an action between the two using approval and rejection data.
3. **Implement** an approval state machine (`PENDING → APPROVED/REJECTED/EXPIRED/CANCELLED → EXECUTING → EXECUTED/FAILED`) with legal transitions enforced in code and in the database.
4. **Implement** persistence for the proposed action, the reviewer decision and audit evidence in PostgreSQL with JPA, including optimistic locking, an append-only audit table and a payload hash that binds the approval to exactly what will execute.
5. **Implement** approval gates for sending email, modifying customer data, issuing refunds and deleting information, including four-eyes (reviewer ≠ requester) and role-based reviewer eligibility.
6. **Implement** safe execution after approval: re-validation at execution time, idempotency keys, a transactional outbox, and resumption of the paused agent run.
7. **Test** approval flows, including concurrent reviewers, expiry, tampered payloads, double execution and self-approval attempts.
8. **Explain** where humans belong in agent workflows, what an auditor needs to see, and how to prevent approval fatigue and rubber-stamping.

### 2. Prerequisite Knowledge

- **Units 33–34:** `ToolPolicy` returns `RequireApproval(risk, reason)`. `ValidatedToolCall` carries typed, validated arguments.
- **JPA/Hibernate:** entities, `@Version` optimistic locking (`OptimisticLockException` on concurrent update), transactions with `@Transactional` (proxy-based: self-invocation bypasses it; rollback by default only on unchecked exceptions).
- **PostgreSQL:** `jsonb`, `CHECK` constraints, unique and partial unique indexes, `REVOKE UPDATE, DELETE` for append-only tables, `now()` vs application clock.
- **Transactional outbox:** write the business change and an outbox row in one DB transaction; a relay publishes outbox rows to Kafka. This gives at-least-once delivery without a distributed transaction.
- **Idempotency keys:** a unique key per logical operation, so retries don't duplicate effects.

**Refresher: TOCTOU.** *Time-of-check to time-of-use*: a condition verified at one time may be false when you act. An approval granted at 10:00 for a refund of the "remaining balance" may be stale at 14:00 if another refund happened in between. Re-validate at execution time.

### 3. Mental Model

Human-in-the-loop is **a change-approval process, like a pull request for actions**:

```
Agent proposes action ──→ [Risk classifier] ──LOW──→ execute (audited)
                                │
                           HIGH/CRITICAL
                                ▼
                     (Proposal persisted: exact tool + args + hash + provenance)
                                ▼
            Reviewer sees: WHAT will happen, WHY (agent's justification),
                           WHERE it came from (evidence, untrusted inputs), RISK reasons
                                ▼
                   approve / reject / (edit = new proposal)
                                ▼
         [Execution] re-validate → idempotent execute → record result
                                ▼
                     Agent run resumes with the outcome
```

Like a pull request: the diff is exact (no "trust me"), the reviewer isn't the author, approval is bound to a specific commit (payload hash), merge happens once, and the history is permanent.

Two design questions drive everything: **which actions need a human** (risk classification) and **what makes the human's decision meaningful** (they see exact effects and provenance, and what they approve is exactly what executes).

### 4. Comprehensive Theory

#### 4.1 Where Humans Belong in Agent Workflows

**Definition.** Human-in-the-loop (HITL) means a human must take an explicit action before a step proceeds. Related terms: *human-on-the-loop* (human monitors and can intervene, but steps proceed automatically) and *human-out-of-the-loop* (fully automatic).

**Where humans add value:**

1. **Irreversible or high-impact actions:** money movement, external communication, deletion, permission changes.
2. **Ambiguous intent:** "clean up this customer's account" (which data? delete or archive?). Here the agent should *ask a clarifying question*, which is a different kind of human involvement.
3. **Policy exceptions:** goodwill refunds beyond policy, which need business judgment.
4. **Low-confidence or novel situations,** as determined by deterministic signals (first time this tool is used for this customer, untrusted content present, amount anomaly), not model self-reported confidence.

**Where humans add little:** high-volume, low-impact, reversible actions with stable approval rates. Gating these produces **approval fatigue**, where reviewers click "approve" without reading. That is worse than an honest automatic process, because it creates false assurance.

**Interview perspective.** Interviewers want a *risk-based* answer ("humans gate irreversible, high-impact or ambiguous actions; routing is deterministic; we tune with data"), not "humans approve everything" or "the model decides when to ask".

#### 4.2 Risk Classification

**Definition.** A deterministic function `classify(action, context) → RiskAssessment(level, reasons, approvalRequirement)`.

**Dimensions.**

| Dimension | Examples | Effect |
|---|---|---|
| Action type | read / draft / write / external send / financial / delete | Base level |
| Reversibility | draft (fully), address change (manual), refund (no), deletion (no) | Raises level |
| Magnitude | refund amount, number of records, recipients | Thresholds |
| Data sensitivity | PII, payment data, health data | Raises level, may require specific reviewer role |
| Context taint | untrusted content in context (Unit 33) | Forces approval for writes |
| Requester | role, tenure, own refund limit | Determines whether action is even allowed |
| Novelty/anomaly | first refund for this customer this year vs fifth this week | Raises level |
| Regulatory | GDPR erasure, financial controls (SOX) | Fixed requirement (for example two approvers) |

**SupportOps classification.**

| Action | Condition | Level | Requirement |
|---|---|---|---|
| `search_kb`, `get_order` | always | LOW | auto |
| `get_customer` | masked projection | LOW | auto |
| `get_customer` | full PII projection | MEDIUM | auto + audit + reason code |
| `draft_email` | always | LOW | auto |
| `send_email` | templated, to address on file, no untrusted content | MEDIUM | approval (v1); candidate for auto in v2 |
| `send_email` | free text or untrusted content in context | HIGH | approval |
| `update_customer` | marketing flag only | MEDIUM | approval (v1) |
| `update_customer` | address/phone/email | HIGH | approval |
| `issue_refund` | ≤ $50 | MEDIUM | approval (v1) |
| `issue_refund` | $50–$500 | HIGH | approval by team lead |
| `issue_refund` | > $500 | CRITICAL | two approvals (lead + finance) |
| `delete_customer_data` | always | CRITICAL | approval by privacy officer; verified erasure request on file |

**Design considerations.**

- **Start strict, relax with evidence.** v1 gates more than it strictly needs to. After N weeks, examine approval data per category: approval rate, edit rate, rejection reasons, and time to decision. Move a category to auto only when the data supports it and the risk owner signs off.
- **Rules are code.** They are versioned, unit-tested and recorded on every proposal (`policyVersion`), so you can later explain why an action was or wasn't gated.
- **Never let the model choose the risk level.** The model may *recommend* escalation (an `ESCALATE` decision), but the classifier is authoritative and can only make things stricter based on the model's input, never looser.

**Trade-offs.** More gating means more safety and more cost: reviewer time, latency to the customer, and fatigue. Less gating means faster service with more exposure. Quantify both: expected loss per auto-executed action (incident rate × impact) vs reviewer cost per approval.

#### 4.3 Approval Gates and the Approval State Machine

**Definition.** An *approval gate* is a point where the workflow stops until a recorded human decision exists. The *approval state* is the lifecycle of one proposed action.

```
               ┌──────────── cancel (requester / system) ────────────┐
               │                                                      ▼
 [PENDING] ──approve──→ [APPROVED] ──claim──→ [EXECUTING] ──ok──→ [EXECUTED]
    │  │                    │                      │
    │  └──reject──→ [REJECTED]                     └──error──→ [FAILED] ──(manual retry → new proposal)
    │                       │
    └──ttl──→ [EXPIRED] ←───┘ (approved but not executed within window)
```

For CRITICAL actions with two required approvals, `PENDING` stays until the approval count reaches the requirement (with distinct reviewers and the required roles), or any reviewer rejects.

**Rules.**

1. **Legal transitions only.** Enforced in the domain object *and* by a DB `CHECK`/conditional update (`UPDATE … WHERE status = 'PENDING'`).
2. **Terminal states are terminal.** `REJECTED`, `EXPIRED`, `CANCELLED`, `EXECUTED` never change. `FAILED` doesn't retry by itself; a retry creates a new proposal that may need fresh approval.
3. **Four-eyes:** reviewer ≠ requester. For two-approval actions, approvers must be distinct.
4. **Eligibility:** reviewer must hold the required role (`SCOPE_approvals:refund_high`), and should not be the subject (a rep shouldn't approve a refund to their own customer account).
5. **Expiry:** pending proposals expire (for example 24 h), and approved-but-unexecuted ones expire too (for example 1 h). Stale approvals are dangerous because the world changes.
6. **Edits are new proposals.** If a reviewer changes the amount, that's a new proposal (authored by the reviewer, possibly needing another reviewer). Otherwise "approve with edits" becomes self-approval.

#### 4.4 Binding the Approval to Exactly What Executes

**Problem.** A reviewer approves "refund $49 on order 8812". If the stored payload can be changed between approval and execution (a bug, a malicious insider, a race), the approval is meaningless.

**Solution: payload hash.**

- At proposal time, serialize the canonical action `{tool, args, tenantId, subjectId, policyVersion}` with a deterministic serializer (sorted keys, normalized numbers) and compute `SHA-256` → `payloadHash`.
- The review UI displays the payload and the hash prefix. The decision row stores the `payloadHash` the reviewer saw.
- At execution, recompute the hash from the stored payload. It must equal both the proposal hash and the decision hash, or execution aborts.

For higher assurance, sign the decision (HMAC with a key the application holds, or an asymmetric signature from a dedicated approval service). Then even someone with DB write access can't forge an approval without the key.

#### 4.5 Persisting Proposed Action, Reviewer Decision and Audit Evidence

**What auditors ask:** *Who* requested *what*, *why*, *based on which evidence*, *who approved it*, *when*, *what exactly executed*, and *what the result was*. Can you prove the record wasn't altered?

**Schema (PostgreSQL).**

```sql
-- V3__approvals.sql
CREATE TABLE action_proposal (
    id                 uuid PRIMARY KEY,
    tenant_id          text        NOT NULL,
    agent_run_id       text        NOT NULL,
    requested_by       text        NOT NULL,          -- end user (sub) on whose behalf the agent acted
    agent_id           text        NOT NULL,
    tool_name          text        NOT NULL,
    payload            jsonb       NOT NULL,          -- canonical typed args
    payload_hash       char(64)    NOT NULL,
    risk_level         text        NOT NULL CHECK (risk_level IN ('LOW','MEDIUM','HIGH','CRITICAL')),
    risk_reasons       jsonb       NOT NULL,
    required_approvals smallint    NOT NULL CHECK (required_approvals BETWEEN 1 AND 3),
    required_role      text        NOT NULL,
    justification      text        NOT NULL,          -- model's stated reason (display only)
    evidence           jsonb       NOT NULL,          -- doc ids, tool results refs, untrusted sources
    policy_version     text        NOT NULL,
    status             text        NOT NULL CHECK (status IN
                         ('PENDING','APPROVED','REJECTED','EXPIRED','CANCELLED','EXECUTING','EXECUTED','FAILED')),
    idempotency_key    text        NOT NULL UNIQUE,
    expires_at         timestamptz NOT NULL,
    created_at         timestamptz NOT NULL DEFAULT now(),
    updated_at         timestamptz NOT NULL DEFAULT now(),
    version            bigint      NOT NULL DEFAULT 0
);
CREATE INDEX action_proposal_queue ON action_proposal (tenant_id, required_role, created_at)
    WHERE status = 'PENDING';

CREATE TABLE approval_decision (
    id             uuid PRIMARY KEY,
    proposal_id    uuid        NOT NULL REFERENCES action_proposal(id),
    reviewer_id    text        NOT NULL,
    decision       text        NOT NULL CHECK (decision IN ('APPROVE','REJECT')),
    reason         text,
    payload_hash   char(64)    NOT NULL,              -- the hash the reviewer saw
    decided_at     timestamptz NOT NULL DEFAULT now(),
    UNIQUE (proposal_id, reviewer_id)                 -- one vote per reviewer
);

CREATE TABLE audit_event (
    id           bigserial PRIMARY KEY,
    tenant_id    text        NOT NULL,
    proposal_id  uuid,
    agent_run_id text,
    actor        text        NOT NULL,                -- user, reviewer, or 'system'
    event_type   text        NOT NULL,                -- PROPOSED, APPROVED, REJECTED, EXECUTED, ...
    details      jsonb       NOT NULL,
    occurred_at  timestamptz NOT NULL DEFAULT now(),
    prev_hash    char(64),
    hash         char(64)    NOT NULL                 -- sha256(prev_hash || canonical(row))
);
-- Append-only: the application role may insert and select, never update or delete.
REVOKE UPDATE, DELETE ON audit_event FROM supportops_app;

CREATE TABLE action_execution (
    idempotency_key text PRIMARY KEY,
    proposal_id     uuid        NOT NULL REFERENCES action_proposal(id),
    result          jsonb,
    executed_at     timestamptz NOT NULL DEFAULT now()
);
```

**Design notes.**

- `evidence` records **provenance**: which KB documents, which ticket emails (flagged as untrusted), and which prior tool results led to the proposal. The reviewer sees it, and so does an auditor later.
- `justification` is the model's text. It's shown to the reviewer *labelled as model-generated*, and nothing depends on it.
- The **hash chain** on `audit_event` makes tampering detectable: altering a row breaks every later hash. Combined with `REVOKE UPDATE, DELETE` and shipping events to WORM storage (for example S3 Object Lock) or a SIEM, this is strong tamper evidence. Note that `REVOKE` must target the actual application role, and the table owner can still modify rows, so run migrations with a separate owner role.
- Retention: audit evidence may contain PII. Store references (IDs) rather than full content where possible, and apply retention rules consistent with the erasure process. GDPR erasure versus audit retention is a real tension, so resolve it with your privacy officer (often: keep the audit fact, pseudonymize the subject).

#### 4.6 Executing After Approval

**Steps.**

1. **Claim:** `UPDATE action_proposal SET status='EXECUTING', version=version+1 WHERE id=? AND status='APPROVED' AND expires_at > now()`. If 0 rows are updated, someone else claimed it or it expired. This conditional update is the concurrency guard.
2. **Verify binding:** recompute the payload hash and compare it to the proposal and decision hashes.
3. **Re-validate:** run the Unit 33 policy *again* with **current** state: the refundable balance, whether the customer still exists, whether the requester's limit changed, and whether the requester's account is still active. Approval doesn't override policy. It adds a requirement on top of it.
4. **Execute idempotently:** call the downstream API with `Idempotency-Key: <proposal.idempotency_key>`. Record in `action_execution` (primary key on the same key). If the downstream supports idempotency keys (payment APIs typically do), a retry after a timeout returns the original result instead of refunding twice.
5. **Record result:** `EXECUTED` or `FAILED` plus an audit event, in one transaction with an **outbox** row (`ApprovalExecuted` event) for notifications and to resume the agent run.

**Synchronous vs asynchronous execution.** Approval often happens minutes or hours later, in a different HTTP request. Execute either (a) synchronously in the reviewer's approve request (simple, but the reviewer waits and failures show in their UI) or (b) asynchronously via the outbox/Kafka to an executor worker (resilient, retryable, the standard production choice). Either way the claim step guarantees at-most-once *claim*, and the idempotency key guarantees at-most-once *effect* downstream.

**Resuming the agent.** The agent run was **checkpointed** when it hit the gate: conversation state, pending decision and proposal ID stored against `agent_run_id`. When the `ApprovalExecuted`/`ApprovalRejected` event arrives, the run resumes. The model receives an observation ("refund executed: ref R-123" / "refund rejected by reviewer: reason") and continues, bounded as always. Never keep a thread blocked waiting for a human.

#### 4.7 Auditability

**Definition.** The ability to reconstruct, after the fact and with integrity guarantees, what happened and why.

**Auditable means:**

- **Complete:** every proposal, decision, execution and failure produces an event. There is no path to execution that skips the event. This is enforced structurally: the executor is the only code path, the outbox and audit write share the same transaction, and an ArchUnit test checks it.
- **Attributable:** each event names the human actor, the agent identity and the run/trace ID, so you can jump from audit to trace (Unit 37).
- **Tamper-evident:** append-only with a hash chain, exported off-box.
- **Explainable:** risk reasons and policy version are stored, so "why did this need approval?" and "why didn't that?" can both be answered.
- **Queryable:** reviewers' decisions per category drive the risk-tuning loop.

#### 4.8 Reviewer Experience: Making Approvals Meaningful

Approval only works if the human can make an informed decision quickly.

- **Show the exact effect,** rendered for humans: "Refund **$49.00** to Visa •••• 4242 for order **8812** (order total $249.00; previously refunded $0.00)". Don't show the agent's prose summary as the main content.
- **Show diffs** for updates: old address → new address.
- **Show provenance:** "This proposal was influenced by: customer email (external, untrusted), KB article D-12". Highlight untrusted sources.
- **Show risk reasons:** "Amount above $50 ceiling; untrusted content present".
- **Make rejection easy and structured:** reason codes ("wrong amount", "not entitled", "suspicious") feed the eval dataset (Unit 36).
- **Sample for quality:** periodically insert known-bad "canary" proposals in training environments, or audit a sample of approvals, to detect rubber-stamping. Track time-to-decision: a median of 2 seconds for a $400 refund is a warning sign.

### 5. Internal Mechanics

#### 5.1 Concurrency: two reviewers click "approve" at once

```
T1: SELECT ... version=3, status=PENDING          T2: SELECT ... version=3, status=PENDING
T1: INSERT approval_decision (reviewer A)         T2: INSERT approval_decision (reviewer B)
T1: UPDATE proposal SET status='APPROVED',        T2: UPDATE proposal SET status='APPROVED',
       version=4 WHERE id=? AND version=3                version=4 WHERE id=? AND version=3
T1: COMMIT  (1 row)                                T2: 0 rows → OptimisticLockException → ROLLBACK
```

With JPA `@Version`, Hibernate adds `AND version=?` to the `UPDATE` and throws `OptimisticLockException` when 0 rows are affected. T2's transaction rolls back, including its decision insert. The UI shows "already decided". For two-approval actions, T2 should *retry* its read (the count changed), not fail permanently. Handle this explicitly with a bounded retry in the service layer, using the Spring Framework 7 core `@Retryable` (from `org.springframework.resilience.annotation`, enabled with `@EnableResilientMethods`) or a simple loop. [Version-dependent]

#### 5.2 `@Transactional` boundaries in the approval service

`ApprovalService.decide(...)` must be one transaction: decision insert, proposal state change, audit event and outbox row all commit together or not at all. Because `@Transactional` works through a proxy, `decide()` must be called from another bean (the controller), not via `this.decide()` from inside the service. The outbox relay runs in its own transaction after commit. Use the transactional outbox, not `@TransactionalEventListener(AFTER_COMMIT)` alone: an in-memory event is lost if the process dies between commit and publish.

#### 5.3 Canonical serialization for the payload hash

Use a dedicated Jackson mapper with `SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS` and `MapperFeature.SORT_PROPERTIES_ALPHABETICALLY` enabled. Write `BigDecimal` values as plain strings with a fixed scale (`amount.setScale(2).toPlainString()`), and write no insignificant whitespace. Hash the UTF-8 bytes with `MessageDigest.getInstance("SHA-256")` and encode with `HexFormat.of().formatHex(...)`. Test that two equal payloads built in different field orders hash identically.

### 6. Implementation Examples

#### Example 1 — Minimal: Risk classifier as a pure function

```java
package com.example.supportops.approval;

import com.example.supportops.policy.RiskLevel;
import com.example.supportops.tools.args.*;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public final class RiskClassifier {

    public static final String POLICY_VERSION = "risk-2026.10.1";

    public record Assessment(RiskLevel level, List<String> reasons,
                             int requiredApprovals, String requiredRole) {
        public boolean autoExecute() { return requiredApprovals == 0; }
    }

    private static final BigDecimal LEAD_THRESHOLD = new BigDecimal("50.00");
    private static final BigDecimal FINANCE_THRESHOLD = new BigDecimal("500.00");

    public Assessment classify(String tool, Object args, boolean untrustedContent) {
        List<String> reasons = new ArrayList<>();
        if (untrustedContent) reasons.add("untrusted content in context");

        return switch (args) {
            case IssueRefundArgs r when r.amount().compareTo(FINANCE_THRESHOLD) > 0 -> {
                reasons.add("refund > " + FINANCE_THRESHOLD);
                yield new Assessment(RiskLevel.CRITICAL, reasons, 2, "approvals:refund_critical");
            }
            case IssueRefundArgs r when r.amount().compareTo(LEAD_THRESHOLD) > 0 -> {
                reasons.add("refund > " + LEAD_THRESHOLD);
                yield new Assessment(RiskLevel.HIGH, reasons, 1, "approvals:refund_high");
            }
            case IssueRefundArgs r -> {
                reasons.add("all refunds reviewed (v1)");
                yield new Assessment(RiskLevel.MEDIUM, reasons, 1, "approvals:refund");
            }
            case SendEmailArgs e -> {
                reasons.add("outbound customer communication");
                yield new Assessment(untrustedContent ? RiskLevel.HIGH : RiskLevel.MEDIUM,
                                     reasons, 1, "approvals:email");
            }
            case UpdateCustomerArgs u -> {
                reasons.add("customer data modification");
                boolean contactChange = u.shippingAddress() != null || u.phone() != null;
                yield new Assessment(contactChange ? RiskLevel.HIGH : RiskLevel.MEDIUM,
                                     reasons, 1, "approvals:customer_data");
            }
            case DeleteCustomerDataArgs d -> {
                reasons.add("irreversible deletion of personal data");
                yield new Assessment(RiskLevel.CRITICAL, reasons, 1, "approvals:privacy");
            }
            default -> untrustedContent
                ? new Assessment(RiskLevel.MEDIUM, reasons, 0, "none")   // read-only tools stay auto
                : new Assessment(RiskLevel.LOW, List.of(), 0, "none");
        };
    }
}
```

Guarded `case … when …` patterns (Java 21+) express thresholds readably. The order matters: the most specific case comes first. Because the class is pure, you can unit-test every threshold boundary ($50.00 → MEDIUM, $50.01 → HIGH).

#### Example 2 — Realistic: Proposal entity with state machine and payload hash

```java
package com.example.supportops.approval;

import com.example.supportops.policy.RiskLevel;
import jakarta.persistence.*;
import org.hibernate.annotations.JdbcTypeCode;
import org.hibernate.type.SqlTypes;

import java.time.Instant;
import java.util.EnumSet;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.UUID;

@Entity
@Table(name = "action_proposal")
public class ActionProposal {

    public enum Status { PENDING, APPROVED, REJECTED, EXPIRED, CANCELLED, EXECUTING, EXECUTED, FAILED }

    private static final Map<Status, Set<Status>> ALLOWED = Map.of(
        Status.PENDING,   EnumSet.of(Status.APPROVED, Status.REJECTED, Status.EXPIRED, Status.CANCELLED),
        Status.APPROVED,  EnumSet.of(Status.EXECUTING, Status.EXPIRED, Status.CANCELLED),
        Status.EXECUTING, EnumSet.of(Status.EXECUTED, Status.FAILED));

    @Id private UUID id;
    @Column(nullable = false) private String tenantId;
    @Column(nullable = false) private String agentRunId;
    @Column(nullable = false) private String requestedBy;
    @Column(nullable = false) private String agentId;
    @Column(nullable = false) private String toolName;
    @JdbcTypeCode(SqlTypes.JSON) @Column(nullable = false) private String payload;
    @Column(nullable = false, length = 64) private String payloadHash;
    @Enumerated(EnumType.STRING) @Column(nullable = false) private RiskLevel riskLevel;
    @JdbcTypeCode(SqlTypes.JSON) @Column(nullable = false) private List<String> riskReasons;
    @Column(nullable = false) private short requiredApprovals;
    @Column(nullable = false) private String requiredRole;
    @Column(nullable = false) private String justification;
    @JdbcTypeCode(SqlTypes.JSON) @Column(nullable = false) private Map<String, Object> evidence;
    @Column(nullable = false) private String policyVersion;
    @Enumerated(EnumType.STRING) @Column(nullable = false) private Status status;
    @Column(nullable = false, unique = true) private String idempotencyKey;
    @Column(nullable = false) private Instant expiresAt;
    @Column(nullable = false) private Instant createdAt;
    @Column(nullable = false) private Instant updatedAt;
    @Version private long version;

    protected ActionProposal() {}  // JPA

    public static ActionProposal create(String tenantId, String agentRunId, String requestedBy, String agentId,
                                        String toolName, String canonicalPayload, String payloadHash,
                                        RiskClassifier.Assessment risk, String justification,
                                        Map<String, Object> evidence, Instant now, java.time.Duration ttl) {
        var p = new ActionProposal();
        p.id = UUID.randomUUID();
        p.tenantId = tenantId;
        p.agentRunId = agentRunId;
        p.requestedBy = requestedBy;
        p.agentId = agentId;
        p.toolName = toolName;
        p.payload = canonicalPayload;
        p.payloadHash = payloadHash;
        p.riskLevel = risk.level();
        p.riskReasons = List.copyOf(risk.reasons());
        p.requiredApprovals = (short) risk.requiredApprovals();
        p.requiredRole = risk.requiredRole();
        p.justification = justification;
        p.evidence = Map.copyOf(evidence);
        p.policyVersion = RiskClassifier.POLICY_VERSION;
        p.status = Status.PENDING;
        p.idempotencyKey = "proposal:" + p.id;
        p.createdAt = now;
        p.updatedAt = now;
        p.expiresAt = now.plus(ttl);
        return p;
    }

    public void transitionTo(Status next, Instant now) {
        if (!ALLOWED.getOrDefault(status, Set.of()).contains(next)) {
            throw new IllegalStateTransitionException(id, status, next);
        }
        this.status = next;
        this.updatedAt = now;
    }

    public boolean isExpired(Instant now) { return now.isAfter(expiresAt); }

    // getters omitted for brevity: id(), tenantId(), requestedBy(), toolName(), payload(), payloadHash(),
    // requiredApprovals(), requiredRole(), status(), idempotencyKey(), agentRunId(), riskLevel() ...
    public UUID id() { return id; }
    public String tenantId() { return tenantId; }
    public String requestedBy() { return requestedBy; }
    public String toolName() { return toolName; }
    public String payload() { return payload; }
    public String payloadHash() { return payloadHash; }
    public int requiredApprovals() { return requiredApprovals; }
    public String requiredRole() { return requiredRole; }
    public Status status() { return status; }
    public String idempotencyKey() { return idempotencyKey; }
    public String agentRunId() { return agentRunId; }
}
```

```java
import tools.jackson.databind.json.JsonMapper;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;
import java.util.Map;

public final class CanonicalPayload {

    private static final JsonMapper CANONICAL = JsonMapper.builder()
        .enable(SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS)
        .enable(MapperFeature.SORT_PROPERTIES_ALPHABETICALLY)
        .build();

    public record Canonical(String json, String sha256) {}

    public static Canonical of(String tenantId, String subjectId, String tool, Object typedArgs, String policyVersion) {
        Map<String, Object> envelope = Map.of(
            "tenantId", tenantId, "subjectId", subjectId, "tool", tool,
            "args", typedArgs, "policyVersion", policyVersion);
        String json = CANONICAL.writeValueAsString(envelope);
        return new Canonical(json, sha256(json));
    }

    public static String sha256(String s) {
        try {
            byte[] d = MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(d);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);   // SHA-256 is mandatory in every JDK
        }
    }
}
```

*Money precision note:* `IssueRefundArgs.amount` is validated with `@Digits(fraction = 2)`. Normalize it to scale 2 before hashing (for example in the args' compact constructor: `amount = amount.setScale(2, RoundingMode.UNNECESSARY)`), so `49` and `49.00` don't hash differently.

```java
package com.example.supportops.approval;

import com.example.supportops.audit.AuditLog;
import com.example.supportops.outbox.Outbox;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.Clock;
import java.time.Instant;
import java.util.UUID;

@Service
public class ApprovalService {

    public record DecisionCommand(UUID proposalId, String reviewerId, java.util.Set<String> reviewerAuthorities,
                                  boolean approve, String reason, String payloadHashSeen) {}

    public sealed interface DecisionResult {
        record Recorded(ActionProposal.Status status, int approvalsSoFar) implements DecisionResult {}
        record Rejected(String code) implements DecisionResult {}   // command refused (not a REJECT vote)
    }

    private final ActionProposalRepository proposals;
    private final ApprovalDecisionRepository decisions;
    private final AuditLog audit;
    private final Outbox outbox;
    private final Clock clock;

    public ApprovalService(ActionProposalRepository proposals, ApprovalDecisionRepository decisions,
                           AuditLog audit, Outbox outbox, Clock clock) {
        this.proposals = proposals;
        this.decisions = decisions;
        this.audit = audit;
        this.outbox = outbox;
        this.clock = clock;
    }

    @Transactional
    public DecisionResult decide(DecisionCommand cmd) {
        Instant now = clock.instant();
        ActionProposal p = proposals.findById(cmd.proposalId()).orElse(null);
        if (p == null) return new DecisionResult.Rejected("NOT_FOUND");
        if (p.status() != ActionProposal.Status.PENDING) return new DecisionResult.Rejected("NOT_PENDING");
        if (p.isExpired(now)) {
            p.transitionTo(ActionProposal.Status.EXPIRED, now);
            audit.record(p, "system", "EXPIRED", java.util.Map.of());
            return new DecisionResult.Rejected("EXPIRED");
        }
        if (p.requestedBy().equals(cmd.reviewerId())) {
            audit.record(p, cmd.reviewerId(), "SELF_APPROVAL_BLOCKED", java.util.Map.of());
            return new DecisionResult.Rejected("SELF_APPROVAL");
        }
        if (!cmd.reviewerAuthorities().contains("SCOPE_" + p.requiredRole())) {
            return new DecisionResult.Rejected("NOT_ELIGIBLE");
        }
        if (!p.payloadHash().equals(cmd.payloadHashSeen())) {
            // Reviewer looked at a different version of the payload than what's stored.
            audit.record(p, cmd.reviewerId(), "HASH_MISMATCH", java.util.Map.of("seen", cmd.payloadHashSeen()));
            return new DecisionResult.Rejected("STALE_VIEW");
        }
        if (decisions.existsByProposalIdAndReviewerId(p.id(), cmd.reviewerId())) {
            return new DecisionResult.Rejected("ALREADY_VOTED");
        }

        decisions.save(ApprovalDecision.of(p.id(), cmd.reviewerId(), cmd.approve(), cmd.reason(),
                                           cmd.payloadHashSeen(), now));
        audit.record(p, cmd.reviewerId(), cmd.approve() ? "APPROVE_VOTE" : "REJECT_VOTE",
                     java.util.Map.of("reason", cmd.reason() == null ? "" : cmd.reason()));

        if (!cmd.approve()) {
            p.transitionTo(ActionProposal.Status.REJECTED, now);
            outbox.publish("approval.decided", p.agentRunId(), new ApprovalDecided(p.id(), "REJECTED", cmd.reason()));
            return new DecisionResult.Recorded(p.status(), 0);
        }

        int approvals = decisions.countByProposalIdAndDecision(p.id(), "APPROVE");
        if (approvals >= p.requiredApprovals()) {
            p.transitionTo(ActionProposal.Status.APPROVED, now);   // @Version guards concurrent final votes
            outbox.publish("approval.decided", p.agentRunId(), new ApprovalDecided(p.id(), "APPROVED", null));
        }
        return new DecisionResult.Recorded(p.status(), approvals);
    }

    public record ApprovalDecided(UUID proposalId, String outcome, String reason) {}
}
```

```java
                           @Size(max = 1000) String reason,
                           @NotBlank @Pattern(regexp = "[0-9a-f]{64}") String payloadHash) {}

    private final ApprovalService service;

    @PostMapping("/{id}/decision")

                             JwtAuthenticationToken auth) {
        var authorities = auth.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority).collect(Collectors.toUnmodifiableSet());
        var result = service.decide(new ApprovalService.DecisionCommand(
            id, auth.getName(), authorities, body.approve(), body.reason(), body.payloadHash()));
        return switch (result) {
            case ApprovalService.DecisionResult.Recorded r -> ResponseEntity.ok(r);
            case ApprovalService.DecisionResult.Rejected r when r.code().equals("NOT_FOUND") ->
                ResponseEntity.notFound().build();
            case ApprovalService.DecisionResult.Rejected r when r.code().equals("NOT_ELIGIBLE")
                                                             || r.code().equals("SELF_APPROVAL") ->
                ResponseEntity.status(403).body(r);
            case ApprovalService.DecisionResult.Rejected r -> ResponseEntity.status(409).body(r);
        };
    }
}
```

```java
package com.example.supportops.approval;

import com.example.supportops.audit.AuditLog;
import com.example.supportops.outbox.Outbox;
import com.example.supportops.policy.AgentContextFactory;
import com.example.supportops.policy.PolicyDecision;
import com.example.supportops.policy.ToolPolicy;
import com.example.supportops.tools.ToolRegistry;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionTemplate;
import tools.jackson.databind.json.JsonMapper;

import java.time.Clock;
import java.util.Map;
import java.util.UUID;

@Service
public class ApprovedActionExecutor {

    private final ActionProposalRepository proposals;
    private final ApprovalDecisionRepository decisions;
    private final ToolRegistry registry;
    private final ToolPolicy policy;
    private final AgentContextFactory contexts;
    private final AuditLog audit;
    private final Outbox outbox;
    private final TransactionTemplate tx;
    private final JsonMapper json;
    private final Clock clock;

    public ApprovedActionExecutor(ActionProposalRepository proposals, ApprovalDecisionRepository decisions,
                                  ToolRegistry registry, ToolPolicy policy, AgentContextFactory contexts,
                                  AuditLog audit, Outbox outbox, TransactionTemplate tx,
                                  JsonMapper json, Clock clock) {
        this.proposals = proposals; this.decisions = decisions; this.registry = registry;
        this.policy = policy; this.contexts = contexts; this.audit = audit; this.outbox = outbox;
        this.tx = tx; this.json = json; this.clock = clock;
    }

    /** Called by the Kafka worker for approval.decided(APPROVED). Safe to call more than once. */
    public void execute(UUID proposalId) {
        // 1. Claim in its own short transaction: conditional update guarantees a single winner.
        Boolean claimed = tx.execute(s -> proposals.claimForExecution(proposalId, clock.instant()) == 1);
        if (!Boolean.TRUE.equals(claimed)) return;   // already claimed/executed/expired: idempotent no-op

        ActionProposal p = proposals.findById(proposalId).orElseThrow();
        var def = registry.require(p.toolName());

        // 2. Verify binding between what was approved and what we're about to run.
        String recomputed = CanonicalPayload.sha256(p.payload());
        boolean allVotesMatch = decisions.findApprovals(proposalId).stream()
            .allMatch(d -> d.payloadHash().equals(recomputed));
        if (!recomputed.equals(p.payloadHash()) || !allVotesMatch) {
            finish(p, false, Map.of("error", "PAYLOAD_HASH_MISMATCH"));
            return;
        }

        // 3. Re-validate with CURRENT state and the requester's CURRENT permissions (TOCTOU).
        Object typedArgs = json.treeToValue(json.readTree(p.payload()).get("args"), def.argsType());
        var ctx = contexts.forRequesterNow(p.tenantId(), p.requestedBy(), p.agentRunId());
        var decision = policy.authorize(p.toolName(), typedArgs, ctx.withApprovalSatisfied());
        if (decision instanceof PolicyDecision.Deny d) {
            finish(p, false, Map.of("error", "POLICY_DENIED_AT_EXECUTION", "code", d.code()));
            return;
        }

        // 4. Execute with the proposal's idempotency key; downstream dedupes retries.
        try {
            String result = def.invokeIdempotent(typedArgs, ctx, p.idempotencyKey());
            finish(p, true, Map.of("result", result));
        } catch (RuntimeException e) {
            finish(p, false, Map.of("error", e.getClass().getSimpleName()));
        }
    }

    private void finish(ActionProposal p, boolean ok, Map<String, Object> details) {
        tx.executeWithoutResult(s -> {
            ActionProposal fresh = proposals.findById(p.id()).orElseThrow();
            fresh.transitionTo(ok ? ActionProposal.Status.EXECUTED : ActionProposal.Status.FAILED, clock.instant());
            audit.record(fresh, "system", ok ? "EXECUTED" : "EXECUTION_FAILED", details);
            outbox.publish("approval.executed", fresh.agentRunId(),
                           Map.of("proposalId", fresh.id(), "ok", ok, "details", details));
        });
    }
}
```

```java
package com.example.supportops.approval;

import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.time.Instant;
import java.util.UUID;

public interface ActionProposalRepository extends JpaRepository<ActionProposal, UUID> {

    @Modifying
    @Query(value = """
        UPDATE action_proposal
           SET status = 'EXECUTING', version = version + 1, updated_at = :now
         WHERE id = :id AND status = 'APPROVED' AND expires_at > :now
        """, nativeQuery = true)
    int claimForExecution(@Param("id") UUID id, @Param("now") Instant now);
}
```

**Why `claimForExecution` is a native conditional update** rather than load-modify-save: it's a single atomic statement, so exactly one worker wins even across many pods, without holding a row lock across the downstream call. The Kafka consumer may redeliver `approval.decided`. The second delivery finds 0 rows and returns. If the process crashes *after* the downstream call but *before* `finish`, the proposal stays `EXECUTING`. A sweeper job finds stale `EXECUTING` rows, then queries the downstream API **by idempotency key** to learn the true outcome before marking `EXECUTED` or `FAILED`. Never blindly re-execute.

### 7. Comparative Analysis

| Comparison | Key difference | When to use | Trap |
|---|---|---|---|
| Human-in-the-loop vs human-on-the-loop | Blocks until decision vs monitors and can intervene | In-loop for irreversible/high-impact; on-loop for reversible, high-volume | Gating everything → fatigue |
| Deterministic risk rules vs model-chosen escalation | Code decides vs model decides | Rules authoritative; model may only escalate further | "The agent asks for approval when unsure" |
| Synchronous vs async execution after approval | In reviewer's request vs worker via outbox | Async for resilience; sync for simple internal tools | Blocking threads waiting for humans |
| Optimistic vs pessimistic locking for decisions | `@Version` conflict detection vs `SELECT … FOR UPDATE` | Optimistic (low contention, short tx) | Holding row locks during downstream calls |
| Approve-with-edits vs new proposal | Mutates approved payload vs re-proposes | New proposal (keeps four-eyes intact) | Reviewer edits become self-approved actions |
| Audit table vs application logs | Structured, append-only, tamper-evident vs mutable text | Audit for compliance; logs for debugging | "It's in the logs" isn't auditability |
| `@TransactionalEventListener` vs outbox | In-memory after-commit vs durable row | Outbox for anything that must not be lost | Lost events on crash between commit and publish |

### 8. Failure Modes and Debugging

**Failure 1 — Double refund.**

- SYMPTOM: Customer refunded twice; two payment-API calls.
- LIKELY CAUSE: Two workers processed redelivered `approval.decided` events, and execution loaded the entity, checked `status == APPROVED` in Java and then saved, which is a race. Or the downstream call didn't send the idempotency key.
- INVESTIGATE: Trace both executions (same `proposalId`, different trace IDs); audit events; payment API logs by idempotency key.
- FIX: Conditional-update claim; idempotency key on the downstream call; `action_execution` PK.
- PREVENT: Concurrency IT (above); consumer redelivery test.

**Failure 2 — Approval rubber-stamping.**

- SYMPTOM: 99.9% approval rate; median decision time 1.8 s; an injected refund was approved.
- CAUSE: Fatigue (too many low-risk items gated) and a UI that showed the agent's prose summary instead of exact effects and provenance.
- FIX: Relax low-risk categories based on data; redesign the review card; add canary audits; enforce a minimum review view for HIGH (for example, the details must be expanded before the approve button activates).

**Failure 3 — Stale approval executed.**

- SYMPTOM: Approved address change executed after the customer had already updated it themselves; old data overwrote new.
- CAUSE: No expiry on approved actions; no re-validation (optimistic check of the record's version at proposal time).
- FIX: Store the target record's version in the payload; execution fails if it changed. Short TTL for approved-not-executed.

**Failure 4 — Stuck `EXECUTING`.**

- SYMPTOM: Proposals stuck in `EXECUTING` for hours after a pod crash.
- INVESTIGATE: `SELECT id, updated_at FROM action_proposal WHERE status='EXECUTING' AND updated_at < now() - interval '10 minutes'`.
- FIX: Sweeper reconciles via the downstream idempotency-key lookup.
- PREVENT: Alert on stuck count > 0.

**Failure 5 — Agent run never resumes.**

- SYMPTOM: Rep sees "pending approval" forever although the refund executed.
- CAUSE: The resume event was published with `@TransactionalEventListener` and lost on restart, or the consumer failed on deserialization and the message went to a DLT unnoticed.
- FIX: Outbox; DLT monitoring; idempotent resume keyed by `(runId, proposalId)`.

### 12. Engineering Scenarios

**Scenario 1 — "We need approvals, but the reviewers are the same reps" (FDE).**
A 6-person support team wants refund approvals, but everyone is both requester and reviewer. *Questions:* What does the customer's finance policy require? Is four-eyes mandatory or just desired? *Expected reasoning:* Clarify with the risk owner. Options: peer review (anyone except the requester), with team leads for HIGH; or a time-boxed auto-approve for MEDIUM with post-hoc sampling. Demonstrate with audit reports. Document that the system enforces requester ≠ reviewer regardless.

**Scenario 2 — Latency complaints.**
Customers wait hours for small refunds. *Investigate:* the time-to-decision distribution by category and time of day, and approval/edit rates. *Options:* auto-execute ≤ $20 for customers with no prior refunds this quarter, reviewer staffing, SLA-based escalation. *Reasoning:* Use data, a pilot and monitoring. Keep a kill switch. The risk owner signs off.

**Scenario 3 — GDPR erasure via agent.**
Product wants "delete my data" requests handled by the agent. *Reasoning:* Erasure must be verified (identity of the data subject), is irreversible, and has legal deadlines. The agent can *prepare* the request (find records, draft the plan). A privacy officer approves. Execution is a deterministic, tested erasure job, not a set of ad-hoc tool calls, and the audit keeps a pseudonymized record of the erasure.

**Scenario 4 — Approvals in Slack.**
Stakeholders want one-click approve buttons in Slack. *Trade-offs:* convenience vs weaker reviewer context, Slack identity mapping, and replay of interactive payloads. *Reasoning:* The Slack message links to the review UI (where hash binding, full context and eligibility checks live). If buttons are required, verify the Slack request signature, map the Slack user to your identity provider, and still go through `ApprovalService.decide` with the payload hash.

### 13. Interview Preparation

#### Quick Questions

**Q: Where do humans belong in an agent workflow?**
*Strong answer:* At irreversible or high-impact actions, ambiguous intent (clarification), and policy exceptions, routed by deterministic risk rules and tuned with approval data. Not on every step, because fatigue destroys the value.

**Q: What's approval state?**
*Strong answer:* The lifecycle of a proposed action (pending → approved/rejected/expired/cancelled → executing → executed/failed) with only legal transitions, persisted and audited.

**Q: Why bind an approval to a payload hash?**
*Strong answer:* So that what executes is exactly what the reviewer saw. Any change invalidates the approval.

#### Intermediate Questions

**Q: How do you ensure an approved refund executes exactly once?**
*Strong answer:* Atomic conditional claim (`UPDATE … WHERE status='APPROVED'`), an idempotency key passed to the payment API, an execution table keyed by that key, and a sweeper that reconciles stuck executions by querying the downstream system by key rather than re-executing.
*Trap:* "We use `@Transactional`." A DB transaction doesn't cover the external API.

**Q: What does an auditor need, and how do you store it?**
*Strong answer:* Who requested (user + agent), what (canonical payload), why (risk reasons, justification labelled as model output), based on what (evidence/provenance), who approved and when, what executed, and the result. Store it in an append-only, hash-chained audit table with the trace ID, exported to WORM storage or a SIEM.

**Q: The reviewer wants to change the amount before approving. How?**
*Strong answer:* The edit creates a new proposal authored by the reviewer, which then needs someone else's approval (or is within the reviewer's own authority by policy). Never mutate an approved payload.

#### Advanced Questions

**Q: Design human approval for an agent that can send emails, change customer data, refund and delete data.**
*Strong answer:* Cover the classifier table, proposal schema, state machine, four-eyes and eligibility, payload hash, review UX (exact effect, diff, provenance, risk reasons), async execution via outbox with claim, re-validation and idempotency, pause/resume of the agent, audit chain, metrics and the tuning loop, and erasure as a special deterministic job.

**Q: How do you decide to move a category from human review to auto-execution?**
*Strong answer:* With data over a meaningful window: approval rate, edit rate, rejection reasons, incident history, and expected loss vs review cost. Pilot with a cap and monitoring, keep a kill switch, and get the risk owner's sign-off. Keep sampling-based post-hoc review.

**Q: Your approval rate is 99.9% with a 2-second median decision time. Good or bad?**
*Strong answer:* Probably bad: it suggests rubber-stamping. Either the category doesn't need gating (move to auto with sampling) or reviewers aren't getting useful information. Check with canary audits and UX changes.

#### Coding Questions

1. Implement the state-transition table and a parameterized test covering all 64 from→to pairs.
2. Implement `CanonicalPayload.of` and a test proving key-order independence and amount-scale normalization.
3. Write the SQL for a reviewer queue: pending proposals for the reviewer's roles and tenant, excluding ones they requested or already voted on, ordered by risk then age.

#### Scenario Questions

**Q: A customer's compliance team asks you to prove no refund over $500 ever executed without two approvals. What do you show them?**
*Strong answer:* A query over `action_proposal` joined with `approval_decision` for executed refunds > $500, grouped by distinct approvers. Add the audit-chain verification result, the code enforcing the rule (policy + tests), and evidence that no other execution path exists (ArchUnit test, payments API key scope restricted to the executor service).

### 14. Explain-It-at-Three-Levels

**Concept: Approval gates**

- *30 seconds:* Deterministic rules decide which agent actions need a human: irreversible, high-impact or tainted ones. The exact action is saved, a different eligible person approves exactly that payload, and a worker executes it once, idempotently, after re-checking policy. Everything is audited.
- *2 minutes:* Add the risk dimensions, the state machine, four-eyes, hash binding, async execution with claim and idempotency, pause/resume and fatigue management.
- *Deep:* Go through the schema and indexes, optimistic locking vs conditional updates, outbox vs after-commit listeners, sweeper reconciliation, the hash-chained audit and its limits (table owner, export to WORM), the GDPR vs retention tension, and the data-driven tuning loop.

**Concept: Auditability**

- *30 seconds:* Every proposal, decision and execution is an append-only, tamper-evident event linked to the people, the agent run and the trace, so we can prove what happened and why.
- *2 minutes:* What auditors ask, provenance and policy versions, the hash chain, and export.
- *Deep:* Structural completeness (single execution path plus ArchUnit), clock and ordering issues, chain concurrency, retention vs erasure, and joining audit to traces for incident investigations.

### 15. Knowledge Check

1. Why is gating every action with human approval often *less* safe than a risk-based approach?
2. Why must the model never choose the risk level?
3. Why are edits by a reviewer treated as a new proposal?
4. What problem does re-validation at execution time solve?
5. What's the difference between the claim step and the idempotency key?
6. *Code reading:* In `ApprovalService.decide`, why is the vote count computed after saving the decision, and what protects against two concurrent "final" votes?
7. *Code reading:* Why does `ApprovedActionExecutor.execute` return silently when the claim fails?
8. *Code reading:* What would break if `CanonicalPayload` didn't sort properties?
9. *Debugging:* Proposals stuck in `EXECUTING`. What happened, and how do you recover safely?
10. *Debugging:* Two refunds for one proposal. List the checks you'd make.
11. *Design:* Sync or async execution after approval for refunds? Why?
12. *Design:* How would you handle approvals for an agent used by a 3-person team?

#### Knowledge Check Answers

1. Fatigue leads to rubber-stamping and false assurance. Reviewer attention is a finite resource, so spend it on high-risk actions.
2. Model output is manipulable (injection) and uncalibrated. Risk must come from deterministic rules. The model may only request escalation.
3. Otherwise the reviewer becomes the author of an action they also approved, which breaks four-eyes.
4. TOCTOU: state and permissions may have changed between approval and execution (balance, record version, requester's role).
5. The claim guarantees only one worker *starts* execution in your system. The idempotency key guarantees the *external effect* happens once even if the call is retried or the outcome is unknown.
6. The count must include the current vote. `@Version` on the proposal makes the concurrent transition to `APPROVED` conflict, so one transaction rolls back and retries or reports a conflict.
7. Because a failed claim means it was already claimed, executed or expired. Returning silently makes the worker idempotent under message redelivery.
8. Equal payloads could serialize differently, so hashes wouldn't match, causing false mismatches (or forcing you to weaken the check).
9. A crash between the downstream call and the result recording. Use a sweeper that queries the downstream system by idempotency key to determine the real outcome, then records it. Never blindly re-execute.
10. Was the claim a conditional update? Was the idempotency key sent and honored downstream? Are there two proposals (duplicate proposal creation) rather than two executions? Check traces and audit for both executions, and consumer redelivery logs.
11. Async via outbox for resilience, retries and decoupling from the reviewer's request. Sync can be acceptable for internal low-volume tools if idempotency and claim are still used.
12. Peer review with requester ≠ reviewer enforced; leads for HIGH; consider sampling-based post-hoc review for MEDIUM; confirm with the risk owner what the policy requires.

### 16. Common Interview Traps

- **"The agent asks for approval when it's unsure."** Routing must be deterministic.
- **"Humans approve everything, so it's safe."** Fatigue makes approval meaningless.
- **"`@Transactional` makes the refund exactly-once."** External effects need idempotency keys.
- **"We log approvals."** Logs aren't audit evidence. Use append-only, attributable, tamper-evident records.
- **"Approve with edits."** Edits are a new proposal.
- **"Approval means we can skip policy checks."** Approval adds a requirement; it doesn't remove policy. Re-validate at execution.
- **"Wait for approval in the request thread."** Never block on humans; checkpoint and resume.

### 17. Cheat Sheet

- **Risk dimensions:** action type, reversibility, magnitude, data sensitivity, taint, requester, novelty, regulation.
- **States:** PENDING → APPROVED | REJECTED | EXPIRED | CANCELLED; APPROVED → EXECUTING | EXPIRED | CANCELLED; EXECUTING → EXECUTED | FAILED.
- **Rules:** four-eyes; eligibility by role; payload hash bound to vote; edits = new proposal; expiry for pending and approved.
- **Execution:** conditional claim → verify hash → re-validate policy → idempotent call (key) → record + audit + outbox (one tx) → resume agent.
- **Persistence:** `action_proposal` (`@Version`, jsonb payload, hash, risk reasons, evidence, policy version), `approval_decision` (unique per reviewer), `audit_event` (append-only, hash chain, REVOKE), `action_execution` (PK = idempotency key), `outbox`.
- **Spring:** `@Transactional` proxy rules; `TransactionTemplate` for programmatic boundaries; `@Version` → `OptimisticLockException`/`ObjectOptimisticLockingFailureException` → 409; inject `Clock`.
- **Metrics:** approval rate, edit rate, time-to-decision p50/p95, expiries, failures, stuck executions.
