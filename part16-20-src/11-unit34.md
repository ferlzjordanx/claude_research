## Unit 34 — Structured Agent Output

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** why arbitrary prose is unsafe as input to software decisions and identify the failure classes (ambiguity, injection, partial output, silent misinterpretation).
2. **Design** typed agent decisions — `AgentDecision`, `ToolRequest`, `FinalAnswer`, `Clarification`, `Escalation` — as Java records with explicit discriminators and invariants.
3. **Compare** three ways of obtaining structured output: prompt-described format with post-parsing, provider-native structured output (constrained decoding against a JSON Schema) and native tool calling.
4. **Generate and constrain** JSON Schemas for Java records, and explain the schema subset limitations of provider "strict" modes.
5. **Configure** Jackson 3 for strict deserialization of model output (unknown properties, scalar coercion, trailing tokens, duplicate keys, enum handling, numeric precision, input size limits).
6. **Implement** Bean Validation for decisions, including cascaded validation and a custom class-level constraint for cross-field invariants.
7. **Implement** a two-stage validation pipeline: envelope validation (decision shape) then tool-specific argument validation, followed by business rules.
8. **Classify** malformed-output failures (syntax, schema, constraint, semantic, refusal, truncation, empty) and **implement** controlled retry with bounded attempts, corrective feedback and fail-closed fallback.
9. **Use** Spring AI 2.0 structured-output features (`.entity(...)`, `validateSchema()`, provider-native structured output) and explain what each does and does not guarantee.
10. **Test** structured-output handling with parameterized malformed outputs and measure schema compliance as an evaluation metric.

### 2. Prerequisite Knowledge

- **Unit 33**: the model is untrusted; every software-facing decision passes deterministic checks before execution.
- **Records and sealed types (Java 16/17+)**: records are transparent, shallowly immutable data carriers with a canonical constructor; sealed interfaces restrict implementations so `switch` can be exhaustive.
- **Jackson basics**: `ObjectMapper`/`JsonMapper`, `readValue`, `JsonNode`, annotations (`@JsonProperty`, `@JsonTypeInfo`, `@JsonSubTypes`). In Spring Boot 4 the auto-configured mapper is Jackson 3's immutable `JsonMapper` in package `tools.jackson.databind`; annotations remain in `com.fasterxml.jackson.annotation` ([Spring blog](https://spring.io/blog/2025/10/07/introducing-jackson-3-support-in-spring/)).
- **Bean Validation**: built-in constraints, `@Valid` cascading, `Validator`, `ConstraintValidator`.
- **JSON Schema basics**: `type`, `properties`, `required`, `enum`, `additionalProperties`, `pattern`, `minimum`/`maximum`, `anyOf`/`oneOf`.

**Refresher — record components and annotations.** An annotation on a record component (`record A(@NotBlank String x)`) is propagated to the generated field, accessor and canonical-constructor parameter where the annotation's `@Target` allows it. Jakarta constraints target fields, methods and parameters, so `Validator.validate(record)` sees them.

### 3. Mental Model

Structured output turns the model from a *writer* into a *form-filler*. Your code defines the form (schema); the model fills it in; your code checks the form like a bank teller checks a cheque — format, signature, amount, account — before anything happens.

```
model text/JSON
   ↓  (1) syntax        — is it parseable JSON, exactly one value, within size limits?
JsonNode
   ↓  (2) shape         — does it match the decision schema (types, required, enums, no extras)?
AgentDecision record
   ↓  (3) constraints   — Bean Validation: lengths, patterns, ranges, cross-field invariants
valid AgentDecision
   ↓  (4) semantics     — tool exists in run profile? args parse into the tool's own record? references valid?
validated ToolRequest / FinalAnswer
   ↓  (5) policy        — Unit 33 gateway: authorization, ownership, limits, approval (Unit 35)
EXECUTION
```

Failures at (1)–(4) are *model output quality* problems and may be retried with feedback. Failures at (5) are *policy* outcomes and must **not** be "retried until it passes" — a denial is an answer, not a parsing error.

Two principles:

1. **Make illegal states unrepresentable, then verify anyway.** Types, enums and sealed hierarchies narrow what the model can express; validation catches what types cannot.
2. **Retries are bounded and classified.** You retry *formatting* problems a small number of times with specific feedback; you never retry *policy* failures, and after the budget is spent you fail closed to a safe outcome (escalate to a human, return an apology, do nothing).

### 4. Comprehensive Theory

#### 4.1 Why Arbitrary Prose Is Unsafe for Machine Decisions

**Definition.** A *machine decision* is any model output that software acts on: which tool to call, with which arguments; whether to escalate; a classification label that routes a ticket; an amount; a yes/no.

**Why prose fails.**

| Problem | Prose example | Consequence |
|---|---|---|
| Ambiguity | "I think a refund of about 40 would be fair, maybe 45." | Which number? Regex picks the first. |
| Hidden negation | "Do **not** issue the refund for A-1001." | Keyword search for "issue refund" + order id triggers it. |
| Injection pass-through | Prose copies an injected phrase "ACTION: delete_customer_data" | Naive parser executes it. |
| Format drift | Model update changes "Action: X" to "**Action**: X" | Parser silently stops matching; behavior changes without errors. |
| Partial output | Response truncated at max tokens | Half a decision parsed as a whole one. |
| Locale/units | "1.000,50 €" vs "1,000.50" | Wrong amount. |

**The fix** is a contract: a schema the model must fill, a parser that rejects anything else, and validators that enforce invariants. Prose is still fine for *human-facing* text — inside a typed field (`finalAnswer.text`) that software treats as opaque display content.

**Interview perspective.** The interviewer wants to hear that structured output is about **determinism at the software boundary**: the downstream code needs a closed set of well-typed possibilities, and anything outside that set is an error, not a best-effort guess.

#### 4.2 Typed Decisions: Designing `AgentDecision` and `ToolRequest`

**Definition.** A *typed decision* is a closed set of next steps the agent may take, each with its own required fields.

**Typical decision kinds.**

- `TOOL_CALL` — invoke a tool with arguments (→ `ToolRequest`).
- `FINAL_ANSWER` — respond to the user (text, cited source ids, confidence).
- `ASK_CLARIFICATION` — the request is ambiguous (question to ask).
- `ESCALATE` — hand to a human (reason category, summary).

**Two encodings.**

*Flat record with discriminator* (works with every provider's strict mode; simplest JSON Schema):

```java
public record AgentDecision(
        DecisionType type,
        String rationale,          // short, for audit; never executed
        ToolRequest toolRequest,   // required iff type == TOOL_CALL
        FinalAnswer finalAnswer,   // required iff type == FINAL_ANSWER
        String clarificationQuestion,
        Escalation escalation) { }
```

Invariants ("exactly the branch matching `type` is non-null") are enforced with a class-level constraint.

*Sealed hierarchy with polymorphic JSON* (best Java ergonomics; exhaustive `switch`):

```java
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({
        @JsonSubTypes.Type(value = Decision.CallTool.class, name = "TOOL_CALL"),
        @JsonSubTypes.Type(value = Decision.Answer.class, name = "FINAL_ANSWER"),
        @JsonSubTypes.Type(value = Decision.Clarify.class, name = "ASK_CLARIFICATION"),
        @JsonSubTypes.Type(value = Decision.Escalate.class, name = "ESCALATE")})
public sealed interface Decision {
    record CallTool(@Valid @NotNull ToolRequest toolRequest) implements Decision { }
    record Answer(@Valid @NotNull FinalAnswer finalAnswer) implements Decision { }
    record Clarify(@NotBlank @Size(max = 300) String question) implements Decision { }
    record Escalate(@NotNull EscalationReason reason, @Size(max = 500) String summary) implements Decision { }
}
```

The polymorphic schema becomes `anyOf`/`oneOf` of four object schemas. Some providers' strict modes restrict root-level unions or `oneOf`; check your provider. A pragmatic pattern: use the flat record as the **wire format** for the model, and map it to the sealed hierarchy internally after validation.

**`ToolRequest` design — envelope plus typed arguments.** Different tools have different argument types. A single schema with every tool's arguments is large and brittle. The common pattern is:

```java
public record ToolRequest(
        @NotBlank @Pattern(regexp = "^[a-z_]{3,40}$") String toolName,
        @NotNull JsonNode arguments) { }
```

Stage 1 validates the envelope; stage 2 (the gateway) looks up the tool and deserializes `arguments` into that tool's own record (`RefundTool.Args`) with strict settings and Bean Validation. When the provider supports it, you can instead generate a discriminated union over tool names so constrained decoding enforces argument shapes too — native tool calling effectively does this per tool.

**Design considerations.**

- Keep decisions *small*. Every field is a chance for error and an injection surface. Do not ask the model for fields you can compute (customer id, tenant, timestamps, approval status).
- Use **enums** for anything that drives branching (decision type, refund reason, escalation category).
- Use **ids, not copies**: `citedSourceIds` must refer to retrieved chunk ids; your code resolves them.
- Put a `rationale` field *for audit and debugging only*; never parse it for behavior. Note it may contain sensitive data and is model-authored.
- Version the schema (`schemaVersion` constant in prompts and stored decisions) so you can evolve it.

#### 4.3 JSON Schema and Structured-Output Mechanisms

**Definition.** JSON Schema (current draft 2020-12) is a vocabulary for describing JSON structure. LLM providers accept a JSON Schema and either (a) include it in the prompt as guidance or (b) enforce it during decoding.

**Three mechanisms.**

1. **Prompt-described format + post-parse.** The schema (or an example) is placed in the prompt; the model usually complies; your parser validates. Works with any model. Failure rate depends on the model and schema complexity. Spring AI's default `.entity(Class)` path appends format instructions derived from a `BeanOutputConverter` (which generates a JSON Schema from the class) and parses the response ([Spring AI structured output docs](https://docs.spring.io/spring-ai/reference/api/structured-output-converter.html)).
2. **Provider-native structured output / constrained decoding.** The provider compiles the schema into a grammar and masks tokens during sampling so only schema-conformant output can be produced. Syntax and shape errors effectively disappear (except for truncation and refusals). Supported by OpenAI (Structured Outputs), Anthropic (structured outputs), Gemini (`responseSchema`), Mistral and others. Spring AI 2.0 enables it per call (`spec.useProviderStructuredOutput()`) or globally (`AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT`) **[Version-dependent]** ([Spring AI blog](https://spring.io/blog/2026/06/23/spring-ai-self-correcting-structured-output/)).
3. **Native tool calling.** Each tool declares a JSON Schema for its input; the model emits tool-use blocks. Arguments conform to the schema when the provider's strict tool mode is on.

**What constrained decoding guarantees and what it doesn't.**

| Guaranteed (when strict) | Not guaranteed |
|---|---|
| Valid JSON | Semantic correctness ("amount" is plausible) |
| Required fields present, types correct | Values satisfy Bean Validation rules not expressible in the provider's schema subset |
| Enum values from the list | That the chosen tool is appropriate or authorized |
| No extra properties (with `additionalProperties: false`) | Completeness if output is truncated (max tokens) |
| | That the model didn't refuse (refusal fields/messages) |

Hence: **constrained decoding reduces retries; it does not replace validation.**

**Schema subset limitations (typical strict modes).** All properties required (optionality expressed as `"type": ["string","null"]`); `additionalProperties: false` required; limited support for `pattern`, `format`, `minLength`, numeric bounds, `oneOf`, recursive schemas; limits on nesting depth and number of properties. Constraints that the provider drops must be re-checked in Java — another reason Bean Validation stays mandatory.

**Generating schemas from Java.** Spring AI uses the victools `jsonschema-generator` under the hood; it reads Jackson annotations and can map some Jakarta constraints. You can also hand-write the schema and test that it stays in sync with the record (a schema snapshot test).

Example schema for the flat decision (abbreviated):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "required": ["type", "rationale", "toolRequest", "finalAnswer", "clarificationQuestion", "escalation"],
  "properties": {
    "type": { "type": "string", "enum": ["TOOL_CALL", "FINAL_ANSWER", "ASK_CLARIFICATION", "ESCALATE"] },
    "rationale": { "type": "string", "maxLength": 300 },
    "toolRequest": {
      "type": ["object", "null"],
      "additionalProperties": false,
      "required": ["toolName", "arguments"],
      "properties": {
        "toolName": { "type": "string", "enum": ["get_order", "search_policies", "issue_refund", "send_email"] },
        "arguments": { "type": "object" }
      }
    },
    "finalAnswer": {
      "type": ["object", "null"],
      "additionalProperties": false,
      "required": ["text", "citedSourceIds"],
      "properties": {
        "text": { "type": "string", "maxLength": 4000 },
        "citedSourceIds": { "type": "array", "items": { "type": "string" }, "maxItems": 10 }
      }
    },
    "clarificationQuestion": { "type": ["string", "null"], "maxLength": 300 },
    "escalation": { "type": ["object", "null"] }
  }
}
```

Note the `toolName` enum is generated *per run* from the effective tool set (Unit 33) — the schema itself narrows what the model can request.

#### 4.4 Jackson Deserialization of Model Output

**How Jackson builds a record.** `JsonMapper.readValue(text, AgentDecision.class)` creates a `JsonParser` (streaming tokenizer), finds or builds a `ValueDeserializer` for the type (cached per type), and for records uses the canonical constructor as a properties-based creator: it buffers properties by name, converts each value with the component type's deserializer, and invokes the constructor. Polymorphic types read the type id property first (or buffer until found) and dispatch to the subtype deserializer.

**Settings that matter for model output (Jackson 3).**

| Concern | Setting | Recommended for decisions | Default in Jackson 3 |
|---|---|---|---|
| Extra/hallucinated fields | `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES` | **Enable** | Disabled (changed from 2.x) |
| `"amount": "45"` → number | `MapperFeature.ALLOW_COERCION_OF_SCALARS` / coercion configs | **Disable** coercion from strings | Allowed |
| `null` for primitive (`int`) | `DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES` | Enable (or avoid primitives) | Enabled (changed from 2.x) |
| JSON followed by prose | `DeserializationFeature.FAIL_ON_TRAILING_TOKENS` | Enable | Enabled (changed from 2.x) |
| Duplicate keys `{"amount":1,"amount":999}` | `StreamReadFeature.STRICT_DUPLICATE_DETECTION` | **Enable** | Disabled |
| Unknown enum value | `READ_UNKNOWN_ENUM_VALUES_AS_NULL` / `..._USING_DEFAULT_VALUE` | Keep failing (default) | Fails |
| Money precision | `USE_BIG_DECIMAL_FOR_FLOATS` + `BigDecimal` fields | Use `BigDecimal` | Double for untyped |
| Oversized input | `StreamReadConstraints` (max string length, nesting depth, number length, document length) | Tighten for decisions | Generous limits |

If your Jackson 3.x minor no longer exposes `ALLOW_COERCION_OF_SCALARS`, configure the same behavior with coercion configs: `builder.withCoercionConfig(LogicalType.Integer, c -> c.setCoercion(CoercionInputShape.String, CoercionAction.Fail))` (and likewise for `Float`, `Boolean`). Defaults per the Jackson 3.0 release notes and JSTEP-2 ([Jackson 3.0 GA](https://cowtowncoder.medium.com/jackson-3-0-0-ga-released-1f669cda529a)) **[Version-dependent]**. Never rely on defaults for security-relevant parsing; configure explicitly so a library upgrade cannot silently change behavior.

**Duplicate keys** deserve attention: with detection off, the *last* value wins. A schema validator might check the first, your code use the last — a classic parser-differential attack.

**Separate mappers.** Do not mutate the application-wide `JsonMapper` (REST APIs may need lenient settings for backward compatibility). Create a dedicated `decisionMapper` bean via `JsonMapper.builder()` or `springMapper.rebuild()`.

#### 4.5 Bean Validation for Decisions

**Why after Jackson?** Jackson checks *shape*; Bean Validation checks *values and invariants*: string length, patterns, ranges, collection sizes, cross-field consistency.

**Mechanics.** `Validator.validate(obj)` walks the bean metadata (cached per class), evaluates constraints on fields/getters (for records: component fields and accessors), recursively validates properties annotated `@Valid`, and returns a `Set<ConstraintViolation>` with property paths (`toolRequest.toolName`) and messages. Groups (`groups = Strict.class`) let you apply different sets in different contexts. Class-level constraints receive the whole object — ideal for "exactly one branch is set".

**Custom class-level constraint.**

```java
package com.acme.support.decision;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = ConsistentDecisionValidator.class)
public @interface ConsistentDecision {
    String message() default "decision payload does not match decision type";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

```java
package com.acme.support.decision;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

import java.util.stream.Stream;

public class ConsistentDecisionValidator implements ConstraintValidator<ConsistentDecision, AgentDecision> {

    @Override
    public boolean isValid(AgentDecision d, ConstraintValidatorContext ctx) {
        if (d == null || d.type() == null) {
            return true; // @NotNull on type reports this case
        }
        long branchesSet = Stream.of(d.toolRequest(), d.finalAnswer(), d.clarificationQuestion(), d.escalation())
                .filter(v -> v != null).count();
        boolean expectedBranchSet = switch (d.type()) {
            case TOOL_CALL -> d.toolRequest() != null;
            case FINAL_ANSWER -> d.finalAnswer() != null;
            case ASK_CLARIFICATION -> d.clarificationQuestion() != null && !d.clarificationQuestion().isBlank();
            case ESCALATE -> d.escalation() != null;
        };
        if (expectedBranchSet && branchesSet == 1) {
            return true;
        }
        ctx.disableDefaultConstraintViolation();
        ctx.buildConstraintViolationWithTemplate(
                        "for type " + d.type() + " exactly the matching field must be set and all others null")
                .addConstraintViolation();
        return false;
    }
}
```

**Validator configuration.** In Spring Boot, inject the auto-configured `jakarta.validation.Validator` (a `LocalValidatorFactoryBean`) rather than building a factory per call — building a `ValidatorFactory` is expensive. Enable Hibernate Validator's *fail-fast* mode only if you want the first violation; for corrective retries you want *all* violations so the model can fix them in one pass.

#### 4.6 Two-Stage Validation and Semantic Checks

After the envelope is valid:

1. **Tool name in run profile** (the per-run enum already narrows it, but check again).
2. **Arguments** → tool's own record with the strict mapper → Bean Validation.
3. **References** → `citedSourceIds` ⊆ ids of chunks actually retrieved in this run; `orderId` patterns; ids in the trusted case context.
4. **Consistency with the request** → e.g., a "summarize" request whose decision is `send_email` is suspicious (Unit 33 taint / intent checks).
5. **Business policy** → the gateway (Unit 33) — *not retried*.

The gateway from Unit 33 already performs steps 1–2 for tools; this unit adds the envelope stage, references and the retry logic around steps that are model-quality problems.

#### 4.7 Malformed Output Handling

**Failure taxonomy.**

| Class | Detection | Retry? | Typical feedback to model |
|---|---|---|---|
| `EMPTY` | blank content | Yes (once) | "Respond with a JSON object matching the schema." |
| `TRUNCATED` | finish reason = length / max tokens; or EOF inside JSON | Yes, with higher limit or shorter answer instruction | "Your answer was cut off. Keep `finalAnswer.text` under 1200 characters." |
| `SYNTAX` | `StreamReadException` | Yes | Parser message (line/column) |
| `SHAPE` | unknown property, wrong type, unknown enum, missing creator property | Yes | Property path + expected type/enum values |
| `CONSTRAINT` | Bean Validation violations | Yes | All violations as `path: message` |
| `SEMANTIC` | unknown tool, citation to unretrieved source, ids not in context | Yes (bounded) | "Source id X was not provided; cite only from [list]." |
| `REFUSAL` | provider refusal field / refusal content | No (usually) | — map to safe response or escalate |
| `POLICY_DENIED` | gateway denial | **Never** as a parse retry | Feed denial as a tool observation; model may choose another path |
| `PROVIDER_ERROR` | 429/5xx/timeouts | Retry with backoff at the HTTP layer, separate budget | — |

**Extraction heuristics.** Some models wrap JSON in Markdown fences. A *narrow* extraction — strip a single leading ```` ```json ```` fence and trailing fence — is acceptable. Searching for "the first `{` to the last `}`" in arbitrary prose is risky: it can pick JSON that came from quoted untrusted content. Prefer native structured output so extraction isn't needed.

**Never repair silently.** "Fixing" JSON with lenient parsers (single quotes, trailing commas, comments) or LLM-based "repair" can change meaning. If you repair, re-validate fully and record that repair happened (metric), and never repair fields that drive money or deletion.

#### 4.8 Controlled Retry and Failure

**Definition.** A controlled retry re-asks the model for a corrected decision, with the specific errors, under a strict attempt budget, then fails closed.

**Design.**

- **Budget:** 1–2 corrective retries (3 attempts total) is typical; Spring AI's `StructuredOutputValidationAdvisor` defaults to 3 attempts.
- **Feedback:** include the precise errors and the original schema; do *not* include the full previous invalid output if it may contain injected content you don't want to amplify — a short excerpt or just the errors suffices.
- **Temperature:** use low temperature for decisions; optionally lower further on retry.
- **Escalation of model:** optionally retry once on a stronger model (router).
- **Accounting:** count tokens and latency across attempts; expose `agent.decision.attempts` and `agent.decision.failures{class}` metrics. Spring AI's validation advisor reports cumulative usage across retries.
- **Fail closed:** after the budget, return a safe outcome — escalate to a human with context, or respond "I couldn't complete that; a support agent will follow up". Never "best guess" execute.
- **Idempotency:** retries happen *before* side effects. If decision generation and tool execution are coupled, ensure the tool layer is idempotent (Unit 33 idempotency keys) so a retried run cannot double-execute.
- **Separate budgets:** transport retries (HTTP 429/5xx) are handled by the client with exponential backoff and jitter; output-correction retries are a different budget. Don't multiply them (3 × 3 = 9 calls) unintentionally.

**Interview perspective.** "How do you handle malformed LLM output?" is answered by the taxonomy, the bounded corrective retry, the fail-closed path and the metrics — not by "we retry until it works".

### 5. Internal Mechanics

#### 5.1 Constrained decoding

At each step the model produces logits over the vocabulary. With constrained decoding, the provider maintains a state machine (compiled from the JSON Schema into a grammar) representing what may legally come next — e.g., after `{"type": "` only tokens that continue one of the enum strings. Tokens that would violate the grammar get their probability set to zero before sampling. Consequences: (1) output is always grammar-valid unless generation stops early (max tokens) or the model emits a refusal; (2) forcing structure can slightly change answer quality for complex schemas, which is why field order matters (put `rationale` *before* `type` if you want the model to "think" before choosing — but keep rationale short); (3) first-request latency may include schema compilation (providers cache compiled grammars).

#### 5.2 Spring AI `.entity(...)` pipeline (2.0) **[Version-dependent]**

```
chatClient.prompt().user(...).call().entity(AgentDecision.class, spec -> spec.validateSchema())
  → BeanOutputConverter<AgentDecision>: generate JSON Schema from the class (victools generator + Jackson annotations)
  → default path: append format instructions + schema to the prompt
    (or provider-native: set response format/schema on the request when useProviderStructuredOutput())
  → advisor chain executes the model call (ToolCallingAdvisor etc.)
  → StructuredOutputValidationAdvisor (when validateSchema()): validate response JSON against schema (draft 2020-12);
       on failure append the validation error to the prompt and re-call, up to N attempts (default 3)
  → converter strips markdown fences if present, deserializes with Jackson into AgentDecision
  → returns AgentDecision (or throws on final failure)
```

It validates against the **JSON Schema**, not against your Bean Validation annotations or business rules. You still run `Validator.validate(decision)` and semantic checks afterwards, and your own retry wrapper decides whether to retry those.

#### 5.3 The agent loop with typed decisions

```
user goal
 → assemble prompt (instructions + per-run schema with toolName enum + history + wrapped data)
 → model call (structured output)
 → parse → validate envelope → semantic checks       ← corrective retry loop (≤ 2) on failure
 → switch (decision.type)
     TOOL_CALL         → gateway (args → authZ → policy → approval?) → observation → next turn
     FINAL_ANSWER      → citation check → output guard → return
     ASK_CLARIFICATION → return question to user (run paused)
     ESCALATE          → create handoff ticket → return
 → stop when FINAL_ANSWER/ASK/ESCALATE, or maxTurns/deadline/budget reached (→ ESCALATE)
```

### 6. Implementation Examples

#### Example 1 — Minimal: strict parse + Bean Validation for one record

```java
package com.acme.support.example;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;
import tools.jackson.core.JacksonException;
import tools.jackson.core.StreamReadFeature;
import tools.jackson.databind.DeserializationFeature;
import tools.jackson.databind.MapperFeature;
import tools.jackson.databind.json.JsonMapper;

import java.util.Set;

public class TicketClassifier {

    public enum Category { SHIPPING, REFUND, ACCOUNT, OTHER }

    public record Classification(@NotNull Category category, @NotNull @Size(max = 200) String summary) { }

    private static final JsonMapper STRICT = JsonMapper.builder()
            .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
            .enable(DeserializationFeature.FAIL_ON_TRAILING_TOKENS)
            .enable(StreamReadFeature.STRICT_DUPLICATE_DETECTION)
            .disable(MapperFeature.ALLOW_COERCION_OF_SCALARS)
            .build();

    private static final Validator VALIDATOR = Validation.buildDefaultValidatorFactory().getValidator();

    public static Classification parse(String modelOutput) {
        Classification c;
        try {
            c = STRICT.readValue(modelOutput, Classification.class);
        } catch (JacksonException e) {
            throw new IllegalArgumentException("Malformed classification: " + e.getOriginalMessage(), e);
        }
        Set<ConstraintViolation<Classification>> violations = VALIDATOR.validate(c);
        if (!violations.isEmpty()) {
            throw new IllegalArgumentException("Invalid classification: " + violations);
        }
        return c;
    }
}
```

Try it with: `{"category":"REFUND","summary":"late"}` (ok), `{"category":"refund","summary":"x"}` (unknown enum constant: case-sensitive by default), `{"category":"REFUND","summary":"x","priority":"HIGH"}` (unknown property), `{"category":"REFUND","summary":"x"} Sure!` (trailing tokens), `{"category":"REFUND","category":"OTHER","summary":"x"}` (duplicate).

```java
package com.acme.support.decision;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validator;
import org.springframework.stereotype.Component;
import tools.jackson.core.JacksonException;
import tools.jackson.core.StreamReadConstraints;
import tools.jackson.core.StreamReadFeature;
import tools.jackson.core.exc.StreamReadException;
import tools.jackson.core.json.JsonFactory;
import tools.jackson.databind.DeserializationFeature;
import tools.jackson.databind.MapperFeature;
import tools.jackson.databind.json.JsonMapper;

import java.util.ArrayList;
import java.util.List;
import java.util.Set;

import static com.acme.support.decision.ParseResult.FailureClass.*;

@Component
public class DecisionParser {

    private final JsonMapper mapper;
    private final Validator validator;

    public DecisionParser(Validator validator) {
        this.validator = validator;
        JsonFactory factory = JsonFactory.builder()
                .streamReadConstraints(StreamReadConstraints.builder()
                        .maxStringLength(20_000)
                        .maxNestingDepth(20)
                        .maxDocumentLength(64_000)
                        .build())
                .enable(StreamReadFeature.STRICT_DUPLICATE_DETECTION)
                .build();
        this.mapper = JsonMapper.builder(factory)
                .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
                .enable(DeserializationFeature.FAIL_ON_TRAILING_TOKENS)
                .enable(DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES)
                .disable(MapperFeature.ALLOW_COERCION_OF_SCALARS)
                .build();
    }

    public ParseResult parse(String raw, boolean truncated, DecisionContext ctx) {
        if (truncated) {
            return new ParseResult.Invalid(TRUNCATED, List.of("Output was cut off before completion."));
        }
        if (raw == null || raw.isBlank()) {
            return new ParseResult.Invalid(EMPTY, List.of("Empty response."));
        }
        String json = stripSingleCodeFence(raw.strip());
        AgentDecision decision;
        try {
            decision = mapper.readValue(json, AgentDecision.class);
        } catch (StreamReadException e) {
            return new ParseResult.Invalid(SYNTAX, List.of("Invalid JSON: " + e.getOriginalMessage()));
        } catch (JacksonException e) {
            return new ParseResult.Invalid(SHAPE, List.of(describe(e)));
        }
        Set<ConstraintViolation<AgentDecision>> violations = validator.validate(decision);
        if (!violations.isEmpty()) {
            return new ParseResult.Invalid(CONSTRAINT, violations.stream()
                    .map(v -> v.getPropertyPath() + ": " + v.getMessage()).sorted().toList());
        }
        List<String> semanticErrors = semanticCheck(decision, ctx);
        if (!semanticErrors.isEmpty()) {
            return new ParseResult.Invalid(SEMANTIC, semanticErrors);
        }
        return new ParseResult.Valid(decision);
    }

    private static List<String> semanticCheck(AgentDecision d, DecisionContext ctx) {
        List<String> errors = new ArrayList<>();
        if (d.toolRequest() != null && !ctx.effectiveTools().contains(d.toolRequest().toolName())) {
            errors.add("toolRequest.toolName: '" + d.toolRequest().toolName()
                    + "' is not available; choose one of " + ctx.effectiveTools());
        }
        if (d.finalAnswer() != null) {
            for (String id : d.finalAnswer().citedSourceIds()) {
                if (!ctx.retrievedSourceIds().contains(id)) {
                    errors.add("finalAnswer.citedSourceIds: '" + id + "' was not retrieved; cite only " + ctx.retrievedSourceIds());
                }
            }
        }
        return errors;
    }

    private static String stripSingleCodeFence(String s) {
        if (s.startsWith("```")) {
            int firstNewline = s.indexOf('\n');
            int lastFence = s.lastIndexOf("```");
            if (firstNewline > 0 && lastFence > firstNewline) {
                return s.substring(firstNewline + 1, lastFence).strip();
            }
        }
        return s;
    }

    private static String describe(JacksonException e) {
        // getOriginalMessage() omits the source excerpt, which may contain untrusted text.
        String path = e.getPath() == null ? "" : e.getPathReference();
        return (path.isEmpty() ? "" : path + ": ") + e.getOriginalMessage();
    }
}

#### Example 3 — Production-oriented: `StructuredDecisionService` with controlled retry, fail-closed fallback, metrics and tests

**Architecture.** An `LlmClient` interface hides the provider and returns raw text plus metadata (finish reason, token usage). `StructuredDecisionService` calls it, parses with `DecisionParser`, and on retryable failures appends a corrective message and tries again, up to `maxAttempts`. It records metrics and returns a `DecisionOutcome`: either a valid decision or a fail-closed escalation.

```java
package com.acme.support.decision;

import com.acme.support.llm.LlmClient;
import com.acme.support.llm.LlmClient.LlmRequest;
import com.acme.support.llm.LlmClient.LlmResponse;
import com.acme.support.llm.LlmClient.Message;
import io.micrometer.core.instrument.MeterRegistry;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.EnumSet;
import java.util.List;
import java.util.Set;

import static com.acme.support.decision.ParseResult.FailureClass;

@Service
public class StructuredDecisionService {

    private static final Logger log = LoggerFactory.getLogger(StructuredDecisionService.class);
    private static final Set<FailureClass> RETRYABLE =
            EnumSet.of(FailureClass.EMPTY, FailureClass.TRUNCATED, FailureClass.SYNTAX,
                    FailureClass.SHAPE, FailureClass.CONSTRAINT, FailureClass.SEMANTIC);

    private final LlmClient llm;
    private final DecisionParser parser;
    private final DecisionSchemaFactory schemas;
    private final MeterRegistry meters;
    private final int maxAttempts;

    public StructuredDecisionService(LlmClient llm, DecisionParser parser, DecisionSchemaFactory schemas,
                                     MeterRegistry meters) {
        this(llm, parser, schemas, meters, 3);
    }

    StructuredDecisionService(LlmClient llm, DecisionParser parser, DecisionSchemaFactory schemas,
                              MeterRegistry meters, int maxAttempts) {
        this.llm = llm;
        this.parser = parser;
        this.schemas = schemas;
        this.meters = meters;
        this.maxAttempts = maxAttempts;
    }

    public DecisionOutcome decide(List<Message> conversation, DecisionContext ctx) {
        String schema = schemas.forTools(ctx.effectiveTools());          // toolName enum narrowed per run
        List<Message> messages = new ArrayList<>(conversation);
        int maxTokens = 1_500;
        ParseResult.Invalid lastFailure = null;
        int totalIn = 0, totalOut = 0;

        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            LlmResponse response = llm.complete(new LlmRequest(List.copyOf(messages), schema, 0.0, maxTokens));
            totalIn += response.inputTokens();
            totalOut += response.outputTokens();

            if (response.finishReason() == LlmClient.FinishReason.REFUSAL) {
                record(attempt, "REFUSAL");
                return DecisionOutcome.failClosed("model_refusal", totalIn, totalOut);
            }
            ParseResult result = parser.parse(response.text(),
                    response.finishReason() == LlmClient.FinishReason.LENGTH, ctx);

            switch (result) {
                case ParseResult.Valid v -> {
                    record(attempt, "VALID");
                    return DecisionOutcome.valid(v.decision(), attempt, totalIn, totalOut);
                }
                case ParseResult.Invalid invalid -> {
                    lastFailure = invalid;
                    record(attempt, invalid.failureClass().name());
                    log.info("decision.invalid attempt={} class={} errors={}", attempt, invalid.failureClass(),
                            invalid.errors().size());
                    if (!RETRYABLE.contains(invalid.failureClass())) {
                        return DecisionOutcome.failClosed("non_retryable_" + invalid.failureClass(), totalIn, totalOut);
                    }
                    if (invalid.failureClass() == FailureClass.TRUNCATED) {
                        maxTokens = Math.min(maxTokens * 2, 4_000);
                    }
                    // Do NOT echo the full invalid output back; send only precise, bounded error descriptions.
                    messages.add(new Message(Message.Role.USER, correctiveFeedback(invalid)));
                }
            }
        }
        return DecisionOutcome.failClosed("max_attempts_" + lastFailure.failureClass(), totalIn, totalOut);
    }

    private static String correctiveFeedback(ParseResult.Invalid invalid) {
        List<String> errors = invalid.errors().stream().limit(10)
                .map(e -> e.length() > 300 ? e.substring(0, 300) : e).toList();
        return """
                Your previous response could not be accepted (%s).
                Fix exactly these problems and respond again with ONLY a JSON object matching the schema:
                - %s
                """.formatted(invalid.failureClass(), String.join("\n- ", errors));
    }

    private void record(int attempt, String outcome) {
        meters.counter("agent.decision.attempts", "attempt", String.valueOf(attempt), "outcome", outcome).increment();
    }
}

package com.acme.support.decision;

public sealed interface DecisionOutcome {

    record Valid(AgentDecision decision, int attempts, int inputTokens, int outputTokens) implements DecisionOutcome { }

    /** Safe default: the orchestrator escalates to a human and tells the user someone will follow up. */
    record FailClosed(String reason, int inputTokens, int outputTokens) implements DecisionOutcome { }

    static DecisionOutcome valid(AgentDecision d, int attempts, int in, int out) { return new Valid(d, attempts, in, out); }
    static DecisionOutcome failClosed(String reason, int in, int out) { return new FailClosed(reason, in, out); }
}
```

`DecisionSchemaFactory.forTools(Set<String>)` loads the base schema (generated from `AgentDecision` at build time or startup and snapshot-tested) and replaces the `toolName` enum with the effective tools.

**Why these choices.** Temperature 0 for decisions; truncation doubles the token limit once; feedback contains bounded error messages only; refusals fail closed without retry; tokens are summed across attempts so cost dashboards are honest.

### 7. Comparative Analysis

| Comparison | Key difference | When to use | Trade-offs | Interview trap |
|---|---|---|---|---|
| Prose + regex vs structured output | Implicit, fragile format vs explicit contract | Structured for anything software acts on; prose only for display | Structured needs schema design and validation code | "We parse the model's answer with regex" |
| Prompt-described schema vs provider-native structured output | Model asked to comply vs decoding constrained to schema | Native when available; prompt-described for portability/local models | Native: provider schema-subset limits, possible compile latency; prompt: more retries | "Native structured output means no validation needed" |
| Structured output vs native tool calling | One decision object vs provider tool-use blocks | Tool calling for standard loops and framework support; structured decision when you want explicit decision kinds (clarify/escalate) and a uniform schema | Tool calling: framework-managed loop, parallel calls; decision object: full control, easier to audit | Treating them as unrelated: both are structured output with schemas |
| Flat record vs sealed polymorphic hierarchy | Discriminator + nullable branches vs subtypes | Flat for wire format/strict modes; sealed internally for exhaustive handling | Flat needs class-level constraint; sealed may hit provider union limits | Using `Object`/`Map<String,Object>` for decisions |
| JSON Schema validation vs Bean Validation | Structural contract vs Java-side value/invariant rules | Both: schema for model/provider; Bean Validation for richer rules | Duplication — keep in sync with snapshot tests | Choosing one and skipping the other |
| Corrective retry vs repair | Ask model to fix vs fix programmatically | Retry for most failures; minimal deterministic repair (fence stripping) only | Retries cost tokens/latency; repair can change meaning | Lenient parsing that silently accepts garbage |
| Retry vs fail closed | Try again vs safe default | Retry formatting errors (bounded); fail closed on refusal, policy denial, exhausted budget | Fail closed hurts UX; must be rare and measured | "Retry until valid" |

### 8. Failure Modes and Debugging

**F1 — Silent field drop after framework upgrade.**
SYMPTOM: After upgrading to Spring Boot 4, refunds carry no `reason`; no errors logged.
↓ CAUSE: The model began emitting `refundReason` instead of `reason`; Jackson 3 ignores unknown properties by default, so the field was dropped and `reason` became null — and the record had no `@NotNull`.
↓ INVESTIGATE: Log decision parse warnings; replay recorded model outputs through the parser; diff Jackson config before/after.
↓ FIX: Dedicated strict mapper; `@NotNull` on required fields; schema with `additionalProperties: false`.
↓ PREVENT: Parser tests with unknown fields; snapshot test of the generated schema; explicit feature configuration.

**F2 — Retry storm and cost spike.**
SYMPTOM: Token spend triples; latency p95 jumps; traces show 9 model calls per turn.
↓ CAUSE: Output-correction retries (3) nested inside HTTP retries (3) on timeouts; plus a semantic error that the model cannot fix (it cites a document that was never retrieved because retrieval failed).
↓ INVESTIGATE: Trace span counts per turn; attempts metric by failure class; check retrieval spans.
↓ FIX: Separate budgets; don't retry SEMANTIC errors caused by upstream failures (fix retrieval or fail closed); cap total model calls per turn.
↓ PREVENT: Alerts on `agent.decision.attempts{attempt="3"}` rate; per-run call cap.

**F3 — Truncated decision executed.**
SYMPTOM: Email sent with half a body.
↓ CAUSE: Lenient parser auto-closed JSON; finish reason not checked.
↓ FIX: Check finish reason; never auto-close; treat LENGTH as TRUNCATED.
↓ PREVENT: Test with truncated fixtures.

**F4 — Duplicate key parser differential.**
SYMPTOM: Audit shows approved refund amount 20, payments shows 2000.
↓ CAUSE: Approval UI parsed the proposal with a JSON library that takes the first duplicate key; executor used last-wins Jackson.
↓ FIX: Strict duplicate detection everywhere; store and display the *canonicalized* parsed record, not the raw JSON.
↓ PREVENT: Fuzz tests with duplicate keys; one canonical serialization for persisted proposals (Unit 35).

**F5 — Schema/record drift.**
SYMPTOM: Provider rejects requests with "invalid schema" after a record change; or schema allows values the record rejects, causing constant CONSTRAINT retries.
↓ FIX: Generate the schema from the record at build time; snapshot test; contract test against the provider in CI (nightly).

**F6 — Model "fixes" errors by changing intent.**
SYMPTOM: On retry after a validation error on `amount`, the model switches to a different tool.
↓ CAUSE: Feedback too vague; model reinterprets.
↓ FIX: Specific feedback ("amount must be ≤ 2 decimal places; keep the same toolName"); semantic consistency check between attempts for high-risk tools (if the tool changes on retry, fail closed).

### 10. Independent Implementation Project

**Goal.** Build the **Decision Contract Module** for the support agent: typed decisions, strict parsing, validation, controlled retry and an exhaustive orchestrator, with evidence that *no model-generated software-facing decision executes without validation*.

**Functional requirements.**

**Testing requirements.** ≥ 25 malformed fixtures across all failure classes; retry and fail-closed tests; orchestrator scenario tests with scripted LLM; property-based or fuzz test (optional: jqwik) generating random JSON mutations to prove the parser never throws unexpected exceptions; schema snapshot test.

**Definition of Done.**
- [ ] No code path executes a tool from anything other than a `ParseResult.Valid` decision passed through the gateway.
- [ ] Every failure class is tested and has a metric.
- [ ] Retries are bounded; fail-closed path tested; tokens summed across attempts.
- [ ] Global Spring `JsonMapper` unchanged; decision mapper explicitly configured.
- [ ] Schema compliance rate reported on the recorded corpus.

**Optional extensions.** Discriminated union over tools for per-tool argument schemas; stronger-model fallback on second retry; jqwik fuzzing; compare compliance across two providers.

### 11. Testing Strategy

- **Unit tests:** parser per failure class; constraint validator; schema factory.
- **Parameterized tests:** fixture corpus loaded from `src/test/resources/fixtures` with expected class in the filename.
- **Snapshot tests:** generated schema vs committed file; fail with a diff on change.
- **Scripted-model tests:** deterministic `LlmClient` returning sequences to test retry, fail closed and orchestration.
- **Contract tests (nightly):** real provider with native structured output on a small prompt set; assert schema accepted and compliance ≥ threshold.
- **Fuzz/property tests:** mutate valid decisions (delete fields, change types, add fields, duplicate keys, inject unicode) and assert the parser returns `Invalid` rather than throwing.
- **Evaluation metric:** *schema compliance rate* = valid-on-first-attempt / total; *eventual compliance* = valid within budget / total; *fail-closed rate* — tracked in Unit 36 baselines.

### 12. Engineering Scenarios

**Scenario 1 — Provider without native structured output.** Your customer mandates a self-hosted open-weights model behind their firewall; it supports neither strict JSON mode nor reliable tool calling.
*Expected reasoning.* Use prompt-described schema with a simplified flat decision; reduce the number of fields; few-shot examples; strict parsing and corrective retry; measure compliance on recorded traffic; consider a grammar-constrained serving stack (e.g., vLLM/llama.cpp grammar or JSON-schema guided decoding) if available; keep every downstream validation identical so switching models doesn't change safety.

**Scenario 2 — FDE: "Just give us the JSON, we'll handle it."** A customer's integration team wants the agent's raw JSON decision sent to their workflow engine to execute.
*Questions.* What's the risk? What must be clarified?
*Expected reasoning.* The customer's engine becomes the executor of untrusted model output; validation and authorization must exist there or before it. Clarify: which actions, which identities, who owns validation, what schema/versioning contract, error semantics, idempotency. Offer to publish a versioned JSON Schema plus a validation library, and only emit decisions after your gateway validated and authorized them; include decision id and idempotency key.

**Scenario 3 — Compliance dropped after prompt change.** A prompt edit improved answer tone but schema compliance fell from 99% to 94%.
*Expected reasoning.* Run the eval suite (Unit 36) comparing baseline and candidate; inspect failing classes; perhaps the new instructions conflict with format rules; consider moving formatting to native structured output; block the release if compliance is a gated metric.

**Scenario 4 — Retry policy for refunds.** Should a refund decision that failed validation twice be retried on a stronger model or escalated?
*Expected reasoning.* For high-risk tools, consistency matters more than completion: fail closed to a human with the context. For low-risk reads, a stronger-model retry is fine. Make retry policy a function of risk level.

### 13. Interview Preparation

#### Quick Questions

**Q: Why is arbitrary prose unsafe for machine decisions?**
*Strong answer:* It's ambiguous, format-unstable across model versions, vulnerable to negation and injection, and can be truncated; parsing it means guessing. Software needs a closed, typed set of possibilities with validation, so anything else is an explicit error.
*Trap:* "Regex works fine in testing."

**Q: Does provider-native structured output remove the need for validation?**
*Strong answer:* No. It guarantees syntactic/schema conformance (when strict), not semantic correctness, business rules, authorization, completeness under truncation or absence of refusal. Bean Validation, semantic checks and the gateway remain.

**Q: What Jackson settings do you change for parsing model output?**
*Strong answer:* Fail on unknown properties (off by default in Jackson 3), disable scalar coercion, keep trailing-token and null-for-primitives failures on, enable duplicate detection, tighten read constraints, use `BigDecimal` for money, and use a dedicated mapper rather than the global one.

**Q: How many retries?**
*Strong answer:* Typically one or two corrective retries, classified by failure type, with a separate budget from transport retries, then fail closed. Never retry policy denials.

#### Intermediate Questions

**Q: Design `AgentDecision` and `ToolRequest`.**
*Strong answer:* Discriminated decision with `TOOL_CALL`, `FINAL_ANSWER`, `ASK_CLARIFICATION`, `ESCALATE`; flat wire record with a class-level constraint enforcing one branch, mapped to an internal sealed hierarchy; `ToolRequest(toolName, arguments as JsonNode)` with the tool name constrained by a per-run enum and arguments validated in stage two against the tool's own record. No identity, approval or tenant fields — those come from the server.
*Why asked:* Tests typed-API design for untrusted producers.

**Q: Walk through your validation pipeline.**
*Strong answer:* Finish-reason check → syntax (strict parser, limits) → shape (records, enums, no unknowns) → Bean Validation incl. cross-field → semantic (tool in profile, citations retrieved, ids in context) → gateway (authZ, policy, approval). Stages 1–4 may be retried with feedback; stage 5 is final.

**Q: What feedback do you send in a corrective retry?**
*Strong answer:* Specific, bounded error descriptions with property paths and allowed values, plus the instruction to return only the schema; not the full prior output (which might include untrusted content) and no internal policy details.

#### Advanced Questions

**Q: How does constrained decoding work and what are its costs?**
*Strong answer:* The schema is compiled into a grammar; at each token step, tokens that would violate the grammar are masked. Costs: schema subset restrictions, possible first-call compilation latency, potential quality impact for complex nested schemas or field orderings, and it doesn't prevent truncation or refusal.

**Q: What's a parser differential and how could it bite an approval system?**
*Strong answer:* Two components parse the same bytes differently (duplicate keys, number precision, Unicode normalization). A reviewer approves what the UI showed while the executor runs what it parsed. Fix: parse once strictly, persist the canonical typed record and its hash, display and execute from that.

**Q: Structured decision object or native tool calling for your agent loop?**
*Strong answer:* Native tool calling integrates with frameworks, supports parallel calls and is well-trained in models. A structured decision object makes non-tool outcomes (clarify, escalate) first-class and gives one auditable schema. Many systems combine: tool calling for tools, plus "virtual tools" like `escalate_to_human` and `ask_clarification`. Either way the same validation and gateway apply.

#### Coding Questions

1. Implement `ConsistentDecisionValidator` and tests.
2. Implement `stripSingleCodeFence` safely and explain why "first `{` to last `}`" is unsafe.
3. Given a `JsonNode` schema, write `forTools(Set<String>)` that replaces the `toolName` enum.
4. Write a scripted `LlmClient` and a test proving fail-closed after three invalid outputs.

#### Scenario Questions

**Q: After a model upgrade, 3% of refund decisions fail validation and escalate, overwhelming the human queue. What do you do?**
*Strong answer:* Quantify by failure class; replay recorded outputs; compare baseline vs new model on the eval suite; if the new model systematically uses a different but correct format, decide whether to adapt the schema (versioned) or roll back the model; meanwhile pin the previous model for the refund flow via the router; add the new failure patterns to the regression corpus.

### 14. Explain-It-at-Three-Levels

**Structured output for agent decisions**
- *30 seconds:* The model fills a typed form (JSON Schema → Java record); strict parsing and validation reject anything else before execution, with bounded corrective retries and a fail-closed fallback.
- *2 minutes:* Define a closed set of decision types; generate a schema and, when possible, use provider-native constrained decoding; parse with a strict Jackson mapper into records; run Bean Validation including cross-field invariants; do semantic checks against run context; hand tool requests to the authorization gateway. Retries are classified and bounded; policy denials are not retried.
- *Deep:* Discuss decoding-time constraint vs response-time validation, provider schema subsets, Jackson 3 default changes and parser differentials, container-element constraints, schema snapshotting, the token cost of retries, failure metrics, the relationship to native tool calling, and how this feeds evaluation (schema-compliance metric) and observability (decision spans with attempt counts).

**Controlled retry**
- *30 seconds:* Retry only formatting/validation failures, at most once or twice, with specific error feedback; then fail closed.
- *2 minutes:* Taxonomy (empty, truncated, syntax, shape, constraint, semantic, refusal, policy), separate transport and correction budgets, temperature and model choice, token accounting, risk-dependent policies.
- *Deep:* Interaction with idempotency, cascading-cost risks, consistency checks across attempts for high-risk tools, and metrics/alerting.

### 15. Knowledge Check

**Conceptual**
1. What does constrained decoding guarantee, and name three things it does not?
2. Why should policy denials not trigger corrective retries?
3. Why should `ToolRequest` not contain `customerId` or `approved` fields?
4. Why prefer a dedicated decision `JsonMapper` over changing the global one?
5. What is the difference between "schema compliance on first attempt" and "eventual compliance", and why track both?

**Code reading**
6. What's wrong with `record RefundArgs(String orderId, double amount) {}` for model output?
7. With Jackson 3 defaults, what happens to `{"orderId":"A-1","amount":5,"currency":"EUR"}` deserialized into `RefundArgs(String orderId, BigDecimal amount)`? Why might that be dangerous?
8. What does `List<@Pattern(regexp="^doc-.*") String> ids` validate that `@Pattern` on the list would not?

**Debugging**
9. Decisions intermittently fail with `TRUNCATED` only for long policy answers. Two fixes?
10. An approval UI shows amount 20 but the executor refunded 2000. What class of bug is likely and how do you prevent it?

**Design**
11. Flat discriminated record or sealed polymorphic JSON for the model wire format? Justify.
12. Design a retry policy that differs for `get_order` vs `issue_refund`.

### Knowledge Check Answers

1. Valid JSON conforming to the (supported subset of the) schema. Not guaranteed: semantic correctness/business rules, completeness under truncation, absence of refusal, constraints dropped by the provider's subset, authorization.
2. A denial is a correct, deterministic outcome; retrying invites the model to search for wording or arguments that slip through (probing) and wastes tokens. Feed it back as an observation instead.
3. Identity and approval state must come from the server (principal, approval workflow). If the model can supply them, injection or hallucination can impersonate users or self-approve.
4. REST and messaging may rely on lenient defaults for compatibility; changing global settings risks regressions elsewhere, and decisions need stricter, explicit, version-pinned behavior.
5. First-attempt compliance measures model/prompt quality and cost; eventual compliance measures user-visible success after retries. A drop in first-attempt with stable eventual compliance means rising cost/latency — a regression you'd miss otherwise.
6. `double` for money (precision), no validation constraints, primitive accepts coercion/defaults; use `BigDecimal` with `@DecimalMin/@Digits`, `@NotBlank @Pattern` on the id.
7. `currency` is silently ignored (unknown properties are ignored by default in Jackson 3); the system may refund in the wrong currency assumption. Enable `FAIL_ON_UNKNOWN_PROPERTIES` or model `currency` explicitly.
8. It validates each element; `@Pattern` isn't applicable to `List` at all.
9. Raise `maxOutputTokens` for answers (or on retry), and instruct/limit answer length (schema `maxLength`, summarization); also consider streaming to the UI with structured final metadata.
10. A parser differential (e.g., duplicate keys) or display/execution from different representations. Parse once strictly, persist the canonical typed proposal with a hash, display and execute from the same record.
11. Flat discriminated record: maximally compatible with strict modes (no root unions) and easy to schema-constrain; map to sealed internally for exhaustive handling. Sealed polymorphic JSON is fine when the provider supports `anyOf` well and you want the schema to encode branch requirements.
12. `get_order`: up to 2 corrective retries, optional stronger-model retry, low risk. `issue_refund`: at most 1 corrective retry; if the tool or key arguments change between attempts, fail closed; after any failure escalate to a human with context.

### 16. Common Interview Traps

| Trap | Correct mental model |
|---|---|
| "JSON mode = validated." | JSON mode/structured output ensures shape, not meaning or permission. |
| "We can always repair the JSON." | Repairs can change meaning; repair minimally, re-validate, never for high-risk fields. |
| "Retry until it parses." | Bounded, classified retries; fail closed. |
| "Bean Validation is for REST DTOs." | It's the natural place for value/invariant checks on model decisions too. |
| "The schema is the record, so they can't drift." | Generated schemas, provider subsets and manual edits drift; snapshot-test. |
| "Unknown fields are harmless." | Silent drops hide model misunderstandings and enable parser differentials. |
| "Tool calling and structured output are different things." | Tool calling *is* structured output with a schema per tool; same validation rules apply. |

### 17. Cheat Sheet

- **Pipeline:** finish reason → syntax → shape → Bean Validation → semantic → gateway (no retry) → execute.
- **Decision kinds:** TOOL_CALL · FINAL_ANSWER · ASK_CLARIFICATION · ESCALATE.
- **Records:** `AgentDecision(type, rationale, toolRequest, finalAnswer, clarificationQuestion, escalation)` + `@ConsistentDecision`; `ToolRequest(toolName, JsonNode arguments)`.
- **Jackson 3 strict:** `enable(FAIL_ON_UNKNOWN_PROPERTIES)`, `disable(MapperFeature.ALLOW_COERCION_OF_SCALARS)`, `FAIL_ON_TRAILING_TOKENS` (default on), `FAIL_ON_NULL_FOR_PRIMITIVES` (default on), `StreamReadFeature.STRICT_DUPLICATE_DETECTION`, `StreamReadConstraints`, `BigDecimal` for money. Exceptions: `JacksonException` (unchecked), `StreamReadException` (syntax).
- **Bean Validation:** `@Valid` cascade; container-element constraints `List<@Pattern String>`; class-level constraints; inject Spring's `Validator`.
- **Spring AI 2.0:** `.call().entity(T.class, spec -> spec.useProviderStructuredOutput().validateSchema())`; `StructuredOutputValidationAdvisor` (JSON Schema 2020-12, default 3 attempts) **[Version-dependent]**.
- **Retry:** 1–2 corrective; separate from HTTP retries; feedback = bounded errors; fail closed → escalate.
- **Metrics:** first-attempt compliance, eventual compliance, attempts histogram, failures by class, fail-closed rate, tokens per decision.
