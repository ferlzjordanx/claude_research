## Unit 36 — Single-Agent Application with FastAPI

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Design** an agent runtime as an application service: API layer, agent service, runner, tools, persistence, and the dependencies wired through FastAPI `Depends` and lifespan.
2. **Distinguish** request-scoped from durable agent state, and **choose** synchronous request/response, streaming within a request, or asynchronous runs (202 + event stream) based on workflow lifetime.
3. **Implement** streaming of agent events over Server-Sent Events: typed events, sequence IDs, heartbeats, resumable streams (`Last-Event-ID`) and safe event content.
4. **Implement** async tool execution with bounded concurrency (per tool, per provider, per tenant) and correct use of threads for blocking clients.
5. **Implement** API cancellation (client disconnect) and agent cancellation (explicit cancel endpoint, cooperative cancellation at step boundaries, shielding of side effects), and **explain** how they differ.
6. **Implement** Customer Support tools (customer, orders, shipment, knowledge, ticket) behind the Unit 34 registry.
7. **Persist** workflow state (runs, steps, events) so runs survive disconnects and can be inspected, and **test** streaming, cancellation and concurrency.

### 2. Prerequisite Knowledge

- Unit 35: `BoundedAgent`, `AgentState`, stop reasons, scripted LLM tests.
- Unit 34: tool registry, `ToolContext`, approvals.
- FastAPI: dependencies with `yield` (setup/teardown), lifespan, `StreamingResponse`, background tasks, exception handlers.
- AnyIO/asyncio: task groups, `CancelScope`, cancellation semantics, `asyncio.Queue`, `asyncio.Event`.
- SQLAlchemy 2.0 async sessions; Redis pub/sub (or PostgreSQL `LISTEN/NOTIFY`).

**Refresher: FastAPI dependency lifetimes.** A dependency with `yield` runs setup before the endpoint and teardown after the response is sent. For `StreamingResponse`, recent FastAPI versions run teardown after streaming ends. [Version-dependent] Check the release notes for exactly when `yield` dependencies' exit code runs relative to streaming. In practice, don't rely on a request-scoped DB session staying open during a long stream. Open your own sessions inside the streaming generator or the background worker.

### 3. Mental Model

The key question is **request lifetime vs workflow lifetime**:

```
Request lifetime:  ── HTTP request ── (seconds; tied to one connection; ends on disconnect/timeout)
Workflow lifetime: ── agent run ────────────────── (seconds to hours; may pause for approval; survives restarts)
```

If the workflow can outlive the request (long tool calls, approvals, retries), **decouple them**: start the run, return a run ID, execute in a worker, and let clients subscribe to events (and reconnect).

```
Client ──POST /agent/runs──▶ API: authN/Z → create run row (pending) → enqueue → 202 {run_id, events_url}
Client ──GET /agent/runs/{id}/events (SSE)──▶ API: replay stored events after Last-Event-ID → live tail
Worker ⇢ consumes run → BoundedAgent.run(...) with event sink → writes events + state to Postgres
                                                  → publishes notifications (Redis / NOTIFY)
Client ──POST /agent/runs/{id}/cancel──▶ API: set cancel_requested → worker checks at step boundaries
```

For short, interactive runs (a few seconds, read-only tools), a simpler **in-request streaming** design works: the endpoint runs the agent and streams its events directly. You still persist the run for audit.

### 4. Comprehensive Theory

#### 4.1 Agent Runtime as an Application Service

**Layers.**

| Layer | Responsibility | Must not |
|---|---|---|
| API (routers) | AuthN/Z, request validation, HTTP semantics, streaming transport | Contain agent logic |
| Agent service | Create runs, build `ToolContext` from identity, choose agent config, start/cancel/resume, map results | Talk HTTP |
| Runner (Unit 35) | The bounded loop | Know about HTTP or DB transactions |
| Tools (Unit 34) | Authorized domain operations | Trust model-supplied identity |
| Persistence | Runs, steps, events, proposals | Store secrets or unbounded content |
| Infrastructure | LLM client, DB pools, Redis, queues, telemetry | Leak into domain code |

**Dependency injection.** Long-lived resources (LLM client, DB engine, Redis, HTTP clients, tool registry) are created in **lifespan** and exposed via dependencies, so tests override them (`app.dependency_overrides`). The runner receives its collaborators explicitly (constructor injection), so it's testable without FastAPI.

#### 4.2 Request-Scoped vs Durable Agent State

| | Request-scoped | Durable |
|---|---|---|
| Where | Python objects for the duration of a call | Database rows (runs, steps, events, checkpoints) |
| Survives disconnect | No | Yes |
| Survives process restart | No | Yes (resumable, Unit 37) |
| Supports approvals/pauses | No (or only within request) | Yes |
| Cost | Minimal | Writes per step, schema, cleanup |
| Use | Short read-only Q&A | Investigations, approvals, long tools, audit requirements |

Even request-scoped runs should **persist an audit record** (run ID, user, tools called, stop reason, cost). Without it, you can't debug or bill.

#### 4.3 Streaming Agent Events

**Why stream.** Agent runs take seconds to minutes. Users need progress ("Looking up order 8812…", "Checking shipment…") and partial answers. Operators need visibility.

**Event design.** Typed, versioned, small, safe:

| Event | Payload (examples) | Notes |
|---|---|---|
| `run_started` | run_id, agent, limits | |
| `step_started` | step | |
| `tool_call` | step, tool, safe argument summary | Don't stream raw args if they contain PII; summarize |
| `tool_result` | step, tool, ok/error, short summary | Never stream full raw observations to end users |
| `answer_delta` | text chunk | If you stream the final answer tokens |
| `awaiting_approval` | proposal_ids | |
| `final` | kind, text, citations | |
| `error` | code, message (safe) | |
| `heartbeat` | — | Every ~15 s to keep proxies from closing idle connections |

**SSE mechanics.** `id:` (monotonic sequence per run), `event:` (type), `data:` (JSON), blank line. Clients reconnect automatically and send `Last-Event-ID`, and the server replays events after that ID from storage, then tails live events. Set `Cache-Control: no-cache`, disable proxy buffering, and keep heartbeats below load-balancer idle timeouts (AWS ALB default 60 s).

**SSE vs WebSockets.** SSE is server→client only, plain HTTP, auto-reconnect, simple through proxies, and fits agent progress. WebSockets are bidirectional, which you'd use when the client must send mid-run input frequently. Most agent UIs use SSE plus regular POSTs for cancel/approve/answer.

#### 4.4 Async Tool Execution and Concurrency

**Concurrency layers to bound:**

1. **Runs per process/worker:** a semaphore or worker concurrency setting.
2. **Runs per tenant/user:** fairness (Redis counters). Reject or queue beyond limits.
3. **Model calls per provider:** token-bucket limits shared across workers (Unit 29).
4. **Tool calls per downstream:** per-tool semaphores protect fragile APIs. Use breakers.
5. **Blocking clients:** offload to threads with a bounded `CapacityLimiter` (`anyio.to_thread.run_sync(..., limiter=...)`). The default AnyIO thread limiter (40 tokens) is shared with FastAPI's sync endpoints and dependencies.

**Parallel read-only tools within a step** (when the model requests several) use a task group, with each call bounded by its own timeout and the step's remaining deadline.

**Event loop hygiene.** No blocking I/O (sync DB drivers, `requests`, boto3 without threads) in async code. Use async clients, or threads with limits. CPU-heavy work (reranking, parsing) goes to threads or processes.

#### 4.5 API Cancellation vs Agent Cancellation

**API cancellation (client disconnect).** The HTTP connection closes, and Starlette cancels the streaming response task. What should happen to the run?

- **In-request mode:** usually cancel the run too (no one is listening). Make sure cancellation stops the LLM stream and doesn't interrupt a side effect halfway.
- **Async-run mode:** the run **continues**. The client can reconnect to events. Disconnect is not cancellation.

**Agent cancellation (explicit intent).** `POST /agent/runs/{id}/cancel` by an authorized user sets `cancel_requested` in the DB (and notifies the worker). The runner checks a **cancellation token at step boundaries** (before each model call and tool call) and stops with `CANCELLED`. In-flight model calls can be cancelled immediately (closing the HTTP request stops generation). In-flight **side effects** should be **shielded** so they complete and are recorded (or rely on idempotency plus reconciliation).

**Python cancellation semantics.** `asyncio.CancelledError` is raised at the next `await`. Never swallow it without re-raising. Use `finally` for cleanup. AnyIO's `CancelScope(shield=True)` protects critical sections, and `asyncio.shield()` serves a similar purpose. Cancellation inside a shielded section is deferred until the section completes.

#### 4.6 Customer Support Tools

The five tools (built on Unit 34's patterns):

| Tool | Args | Effect | Authorization |
|---|---|---|---|
| `get_customer` | — (customer from ticket context) or `customer_id` validated against context | read | `customers:read`, tenant, conversation scope |
| `list_orders` / `get_order` | `order_id` | read | `orders:read`, ownership |
| `get_shipment_status` | `tracking_number` (from order) | read (external API) | `orders:read` |
| `search_knowledge_base` | `query` | read | `kb:read`, ACL groups |
| `create_ticket_note` / `update_ticket` | `ticket_id` (context), `note`, `status` | write (internal, low risk) | `tickets:write`, ticket assigned to user/team; idempotent |

Ticket writes are low-risk, internal and reversible, so they may auto-execute with idempotency and audit. Refunds and outbound emails stay approval-gated.

#### 4.7 Agent API Design

```
POST   /api/agent/runs                     {ticket_id, message, mode: "sync"|"async"} → 200 (sync) | 202 {run_id}
GET    /api/agent/runs/{run_id}            → run summary {status, stop_reason, final, cost, steps}
GET    /api/agent/runs/{run_id}/events     → SSE stream (replay + live), supports Last-Event-ID
POST   /api/agent/runs/{run_id}/cancel     → 202 (idempotent)
POST   /api/agent/runs/{run_id}/messages   {text} → continue a run waiting for user input (Unit 37)
```

Rules: run IDs are unguessable (UUIDv4/v7), every endpoint checks that the caller may access that run (tenant + owner/team), `POST /runs` accepts an `Idempotency-Key`, rate limits apply per user/tenant, and responses never include raw tool outputs or prompts.

### 5. Internal Mechanics

#### 5.1 In-request streaming run

```
POST /api/agent/stream
→ Depends(current_user) → ToolContext(identity, ticket) → create agent_run row (status=running)
→ StreamingResponse(event_generator)
   event_generator:
     queue = asyncio.Queue(maxsize=100); sink = QueueSink(queue) (+ DB persistence)
     task = create_task(runner.run(..., events=sink, cancel_token=token))
     while True: event = await queue.get() (with heartbeat timeout) → yield SSE bytes; break on final
   client disconnect → Starlette cancels generator → finally: token.cancel(); await task (bounded); record CANCELLED
```

The queue's `maxsize` provides **backpressure**: if a slow client can't keep up, the runner's event emission waits (or you drop non-essential events like heartbeats or deltas).

#### 5.2 Async run with worker and resumable events

```
POST /runs → INSERT agent_run(pending) + outbox/queue message (same transaction) → 202
worker: claim run (UPDATE … SET status='running' WHERE id=? AND status='pending') → runner.run(..., sink=DbEventSink)
  DbEventSink.emit(event): INSERT agent_event(run_id, seq, type, payload) → NOTIFY / Redis PUBLISH run:{id}
GET /runs/{id}/events (Last-Event-ID: 7):
  SELECT events WHERE run_id=? AND seq > 7 ORDER BY seq → yield
  SUBSCRIBE run:{id} → for each notification: SELECT new events after last seq → yield (no gaps, no duplicates)
  stop after final event; heartbeat every 15 s
```

Reading events from the database after notifications (instead of trusting pub/sub payloads) guarantees ordering and no gaps. Pub/sub is just a wake-up signal.

#### Example 2 — Realistic: In-request SSE streaming with an event sink, cancellation on disconnect and persistence

```python
# app/agent/events.py
from collections.abc import Awaitable, Callable
from dataclasses import dataclass, field
from typing import Any, Protocol


@dataclass
class AgentEvent:
    type: str
    data: dict[str, Any]
    seq: int = 0


class EventSink(Protocol):
    async def emit(self, event: AgentEvent) -> None: ...


@dataclass
class CancelToken:
    _cancelled: bool = False
    reason: str = ""

    def cancel(self, reason: str = "requested") -> None:
        self._cancelled, self.reason = True, reason

    @property
    def cancelled(self) -> bool:
        return self._cancelled


@dataclass
class FanoutSink:
    """Assigns sequence numbers and forwards to several sinks (queue for streaming, DB for durability)."""
    sinks: list[EventSink]
    _seq: int = 0

    async def emit(self, event: AgentEvent) -> None:
        self._seq += 1
        event.seq = self._seq
        for sink in self.sinks:
            await sink.emit(event)
```

```python
# app/api/agent_stream.py
import asyncio
import contextlib
import json
from typing import Annotated

from fastapi import APIRouter, Depends, HTTPException, Request
from fastapi.responses import StreamingResponse

from app.agent.events import AgentEvent, CancelToken, FanoutSink
from app.agent.runner import BoundedAgent
from app.api.agent_sync import RunRequest
from app.core.deps import get_agent, get_run_store
from app.core.security import User, require_scope
from app.persistence.runs import RunStore
from app.services.context import build_tool_context

router = APIRouter(prefix="/api/agent", tags=["agent"])
HEARTBEAT_S = 15


class QueueSink:
    def __init__(self, queue: asyncio.Queue[AgentEvent]) -> None:
        self.queue = queue

    async def emit(self, event: AgentEvent) -> None:
        await self.queue.put(event)                       # bounded queue → backpressure on slow clients


def sse(event: AgentEvent) -> bytes:
    return f"id: {event.seq}\nevent: {event.type}\ndata: {json.dumps(event.data, default=str)}\n\n".encode()


@router.post("/stream")
async def stream_run(req: RunRequest, request: Request,
                     user: Annotated[User, Depends(require_scope("agent:use"))],
                     agent: Annotated[BoundedAgent, Depends(get_agent)],
                     store: Annotated[RunStore, Depends(get_run_store)]) -> StreamingResponse:
    ctx = await build_tool_context(user, req.ticket_id)
    if ctx is None:
        raise HTTPException(404, "Ticket not found")
    run_id = await store.create_run(ctx, mode="stream")            # durable audit record

    async def events():
        queue: asyncio.Queue[AgentEvent] = asyncio.Queue(maxsize=100)
        sink = FanoutSink([QueueSink(queue), store.sink(run_id)])
        cancel = CancelToken()
        task = asyncio.create_task(agent.run("Resolve the support agent's question about this ticket.",
                                             req.message, ctx, events=sink, cancel=cancel))
        try:
            yield sse(AgentEvent("run_started", {"run_id": run_id}, 0))
            while True:
                try:
                    event = await asyncio.wait_for(queue.get(), timeout=HEARTBEAT_S)
                except TimeoutError:
                    if task.done() and queue.empty():
                        break
                    yield b": heartbeat\n\n"                         # SSE comment keeps proxies alive
                    continue
                yield sse(event)
                if event.type == "final":
                    break
        finally:
            # Runs on normal end AND on client disconnect (generator cancelled by Starlette).
            if not task.done():
                cancel.cancel("client_disconnected")                 # cooperative stop at next step boundary
                with contextlib.suppress(Exception):
                    await asyncio.wait_for(asyncio.shield(task), timeout=10)
            state = task.result() if task.done() and not task.cancelled() and task.exception() is None else None
            await store.finish_run(run_id, state)

    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

**Key decisions.**

- The agent runs in its own task, and the generator only relays events, so event production and the HTTP write are decoupled by a bounded queue.
- On disconnect, the `finally` block asks the agent to stop cooperatively and waits briefly (shielded, so cleanup itself isn't cancelled), then records the final state. A tool in progress (for example a ticket note write) completes rather than being torn mid-write.
- The audit record is created before streaming starts and finalized in `finally`, so every run is accounted for.
- Heartbeats as SSE comments (`: heartbeat`) keep connections alive without polluting the event stream.

```python
# app/api/agent_runs.py
import asyncio
import json
from typing import Annotated
from uuid import UUID

from fastapi import APIRouter, Depends, Header, HTTPException, Request, Response
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

from app.api.agent_sync import RunRequest
from app.core.deps import get_run_store, get_notifier
from app.core.security import User, require_scope
from app.persistence.runs import RunStore
from app.services.context import build_tool_context

router = APIRouter(prefix="/api/agent/runs", tags=["agent-runs"])


class Accepted(BaseModel):
    run_id: str
    events_url: str


@router.post("", status_code=202, response_model=Accepted)
async def create_run(req: RunRequest,
                     user: Annotated[User, Depends(require_scope("agent:use"))],
                     store: Annotated[RunStore, Depends(get_run_store)],
                     idempotency_key: Annotated[str | None, Header(alias="Idempotency-Key")] = None) -> Accepted:
    ctx = await build_tool_context(user, req.ticket_id)
    if ctx is None:
        raise HTTPException(404, "Ticket not found")
    if not await store.tenant_has_capacity(ctx.tenant_id, max_running=20):
        raise HTTPException(429, "Too many concurrent runs", headers={"Retry-After": "10"})
    run_id = await store.create_pending_run(ctx, req.message, idempotency_key)   # insert + enqueue (outbox)
    return Accepted(run_id=run_id, events_url=f"/api/agent/runs/{run_id}/events")


@router.post("/{run_id}/cancel", status_code=202)
async def cancel_run(run_id: UUID, user: Annotated[User, Depends(require_scope("agent:use"))],
                     store: Annotated[RunStore, Depends(get_run_store)],
                     notifier=Depends(get_notifier)) -> Response:
    if not await store.user_can_access(run_id, user):
        raise HTTPException(404, "Run not found")
    await store.request_cancel(run_id)                    # idempotent flag
    await notifier.publish(f"run:{run_id}:control", "cancel")
    return Response(status_code=202)


@router.get("/{run_id}/events")
async def run_events(run_id: UUID, request: Request,
                     user: Annotated[User, Depends(require_scope("agent:use"))],
                     store: Annotated[RunStore, Depends(get_run_store)],
                     notifier=Depends(get_notifier),
                     last_event_id: Annotated[int | None, Header(alias="Last-Event-ID")] = None) -> StreamingResponse:
    if not await store.user_can_access(run_id, user):
        raise HTTPException(404, "Run not found")

    async def stream():
        last = last_event_id or 0
        async with notifier.subscribe(f"run:{run_id}:events") as wakeups:
            while True:
                for ev in await store.events_after(run_id, last, limit=200):     # replay / catch up from DB
                    last = ev.seq
                    yield f"id: {ev.seq}\nevent: {ev.type}\ndata: {json.dumps(ev.payload, default=str)}\n\n"
                    if ev.type == "final":
                        return
                if await request.is_disconnected():
                    return
                try:
                    await asyncio.wait_for(wakeups.next(), timeout=15)           # wake on new events
                except TimeoutError:
                    yield ": heartbeat\n\n"

    return StreamingResponse(stream(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})
```

**Worker with concurrency limits and cooperative cancellation.**

```python
# worker/agent_worker.py
import asyncio
import logging
import signal

import anyio

from app.agent.events import CancelToken, FanoutSink
from app.agent.runner import BoundedAgent

log = logging.getLogger("agent.worker")


class AgentWorker:
    def __init__(self, store, agent: BoundedAgent, notifier, max_concurrent_runs: int = 8) -> None:
        self._store, self._agent, self._notifier = store, agent, notifier
        self._slots = asyncio.Semaphore(max_concurrent_runs)
        self._stopping = asyncio.Event()

    async def serve(self) -> None:
        loop = asyncio.get_running_loop()
        loop.add_signal_handler(signal.SIGTERM, self._stopping.set)
        async with anyio.create_task_group() as tg:
            while not self._stopping.is_set():
                await self._slots.acquire()
                run = await self._store.claim_next_pending()          # UPDATE … WHERE status='pending' … SKIP LOCKED
                if run is None:
                    self._slots.release()
                    await asyncio.sleep(0.5)
                    continue
                tg.start_soon(self._execute, run)
        log.info("worker drained")                                   # task group waits for in-flight runs

    async def _execute(self, run) -> None:
        cancel = CancelToken()
        try:
            async with anyio.create_task_group() as tg:
                tg.start_soon(self._watch_cancel, run.id, cancel)
                sink = FanoutSink([self._store.sink(run.id, notifier=self._notifier)])
                state = await self._agent.run(run.goal, run.message, run.ctx, events=sink, cancel=cancel)
                tg.cancel_scope.cancel()                             # stop the watcher
            with anyio.CancelScope(shield=True):                     # always record the outcome
                await self._store.finish_run(run.id, state)
        except Exception:
            log.exception("run_failed run=%s", run.id)
            with anyio.CancelScope(shield=True):
                await self._store.fail_run(run.id)
        finally:
            self._slots.release()

    async def _watch_cancel(self, run_id, cancel: CancelToken) -> None:
        async with self._notifier.subscribe(f"run:{run_id}:control") as messages:
            while not cancel.cancelled:
                if await self._store.cancel_requested(run_id):       # DB is source of truth
                    cancel.cancel("user_requested")
                    return
                with anyio.move_on_after(5):
                    await messages.next()
```

```python
            owns = await s.scalar(text(
                "SELECT 1 FROM ticket WHERE tenant_id = :t AND id = :id AND assigned_team = ANY(:teams)"),
                {"t": ctx.tenant_id, "id": ctx.ticket_id, "teams": list(ctx.groups)})
            if not owns:
                raise ToolDenied("ticket not accessible")
            await s.execute(text(
                "INSERT INTO ticket_note (ticket_id, tenant_id, author, body, source, idempotency_key) "
                "VALUES (:id, :t, :u, :b, 'agent', :k) ON CONFLICT (idempotency_key) DO NOTHING"),
                {"id": ctx.ticket_id, "t": ctx.tenant_id, "u": ctx.user_id, "b": args.note, "k": key})
        return ToolResult("Internal note added to the ticket.")

    return ToolSpec("add_ticket_note", "Add an internal (not customer-visible) note to the current ticket.",
                    TicketNoteArgs, add_note, Effect.WRITE, required_scope="tickets:write", timeout_s=2.0)
```

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| Sync endpoint vs in-request streaming vs async run | Single response vs progressive in one connection vs decoupled lifetime | Sync for < ~5 s read-only; stream for interactive; async for long/approval/durable | Long agent in a sync request behind a 60 s LB timeout |
| Request-scoped vs durable state | Memory vs DB | Durable when runs outlive requests or need audit/resume | No audit record for short runs |
| SSE vs WebSockets | One-way, HTTP, auto-reconnect vs bidirectional | SSE for agent progress | WebSockets for simple progress (more infra) |
| Disconnect vs cancel | Transport ended vs user intent | Async mode: disconnect ≠ cancel | Cancelling long runs on flaky mobile connections |
| Hard cancel vs cooperative cancel | Interrupt immediately vs stop at safe points | Cooperative for side effects; immediate for model streams | Tearing a write mid-way |
| FastAPI BackgroundTasks vs worker queue | After-response in-process vs durable external | Workers for agent runs | BackgroundTasks lost on restart, unbounded |
| Pub/sub payloads vs DB events + wake-ups | Lossy vs durable ordered | DB events as truth | Gaps when subscriber reconnects |
| Per-process vs per-tenant limits | Local vs fair across fleet | Both | One tenant monopolizing workers |

### 8. Failure Modes and Debugging

**Failure 1 — Streams cut at ~60 s.**

- CAUSE: load balancer idle timeout, no heartbeats, proxy buffering.
- FIX: heartbeats < idle timeout, `X-Accel-Buffering: no`, increase the idle timeout where appropriate, async mode with reconnect.

**Failure 2 — Duplicate or missing events after reconnect.**

- CAUSE: events kept only in memory or pub/sub; no sequence IDs; `Last-Event-ID` ignored.
- FIX: persist events with `(run_id, seq)`, replay after the last ID, use pub/sub only as a wake-up.

**Failure 3 — Client disconnect leaves orphan runs consuming tokens.**

- CAUSE: the agent task isn't cancelled in in-request mode, or the runner doesn't check the cancel token.
- FIX: the `finally` in the generator cancels cooperatively, the runner checks the token each step, and LLM streams are closed on cancellation.

**Failure 4 — Cancellation corrupts state.**

- SYMPTOM: run marked cancelled but a ticket note was written twice or a proposal half-created.
- FIX: cooperative cancellation at boundaries, shielded writes, idempotency keys, outcome recorded in a shielded scope.

**Failure 5 — Event loop stalls under load.**

- CAUSE: sync clients (boto3/requests) in tools, CPU-heavy reranking on the loop, the thread limiter exhausted by sync dependencies.
- INVESTIGATE: asyncio debug mode, `py-spy dump --pid`, thread-pool saturation metrics.
- FIX: async clients, dedicated limiters, separate worker processes for CPU work.

**Failure 6 — DB session closed during streaming.**

- CAUSE: a request-scoped `yield` dependency's teardown ran before or while the stream used the session.
- FIX: open sessions inside the generator or worker. Don't rely on request-scoped sessions for long streams.

**Failure 7 — Noisy neighbor.**

- SYMPTOM: one tenant's bulk runs starve others.
- FIX: per-tenant concurrency caps, a fair queue (per-tenant queues or weighted selection), 429 with `Retry-After`.

### 12. Engineering Scenarios

**Scenario 1 — "The agent should keep working if I close my laptop" (FDE).** *Clarify:* do they need results later (notifications), or only while watching? Are approvals involved? *Reasoning:* Async runs with durable state and events, notification on completion (email/Slack via the notification system), reconnectable UI. In-request streaming is insufficient.

**Scenario 2 — Long tool calls.** A carrier API sometimes takes 40 s. *Reasoning:* Use async mode, a per-tool timeout with a user-visible "still checking…" event, a breaker, and a fallback to "check later" with a follow-up run.

**Scenario 3 — Cost of idle streams.** 5,000 concurrent SSE connections. *Reasoning:* SSE connections are cheap in async servers but not free (memory, file descriptors, LB limits). Use event-driven wake-ups (no polling), heartbeats, connection limits per user, and horizontal scaling. Consider moving fan-out to a dedicated gateway.

**Scenario 4 — Approvals with streaming.** *Reasoning:* The stream emits `awaiting_approval` and ends with a `final` event of kind `pending_approval`. The approval UI uses a separate endpoint, and the run resumes as a new run segment (Units 37–38) with its own events on the same run ID.

### 13. Interview Preparation

#### Quick Questions

**Q: Request lifetime vs workflow lifetime?**
*Strong answer:* An HTTP request lasts seconds and dies with the connection. An agent workflow can last minutes or hours, pause for approval and survive restarts. When the workflow can outlive the request, decouple them with durable runs and an event stream.

**Q: SSE or WebSockets for agent progress?**
*Strong answer:* SSE: one-way, HTTP-friendly, auto-reconnect with `Last-Event-ID`. WebSockets only if you need frequent bidirectional messages.

**Q: Disconnect vs cancel?**
*Strong answer:* Disconnect is a transport event, and cancel is user intent. In async mode, a disconnect shouldn't cancel the run.

#### Intermediate Questions

**Q: How do you stream agent events safely?**
*Strong answer:* Typed small events with sequence IDs, user-facing summaries instead of raw tool payloads, heartbeats, persisted events for replay, access checks on the run, and no prompts or PII.

**Q: How do you implement cancellation in an async agent?**
*Strong answer:* A cancel endpoint sets a durable flag and notifies the worker. The runner checks a token before each model call and tool call. In-flight model streams are cancelled, side effects are shielded and idempotent, and the outcome is recorded in a shielded scope.

**Q: How do you bound concurrency for agent runs?**
*Strong answer:* Worker concurrency, per-tenant caps (429 or queue), provider token buckets, per-tool semaphores, and thread limiters for blocking clients. Measure queue depth and loop lag.

#### Advanced Questions

**Q: Design the events endpoint so reconnects never lose or duplicate events.**
*Strong answer:* Persist events with `(run_id, seq)`. The endpoint replays from the DB after `Last-Event-ID`, then waits on a pub/sub wake-up and re-queries the DB after the last seq. Pub/sub is a signal only. Stop after `final`. Heartbeats keep the connection alive.

**Q: What can go wrong with FastAPI `yield` dependencies and streaming responses?**
*Strong answer:* The dependency teardown timing relative to the stream has changed across versions, so a request-scoped session may close while the stream still needs it, or stay open too long. Use dedicated sessions inside the generator or worker.

#### Coding Questions

1. Write an SSE generator with heartbeats and cleanup on cancellation.
2. Write a worker loop with a semaphore and shielded result recording.
3. Write the SQL to claim the next pending run safely across workers (`FOR UPDATE SKIP LOCKED`).

#### Scenario Questions

**Q: An agent run was cancelled by the user, but a refund proposal was still created. Is that a bug?**
*Strong answer:* It depends on timing. If the proposal tool was already in flight, completing it (shielded) is correct, and the run should report it and the proposal can be rejected. If it started after the cancel was recorded, the cooperative check was missing. Either way, the proposal still needs human approval, so no money moved.

### 14. Explain-It-at-Three-Levels

**Concept: Agent runtime in FastAPI**

- *30 seconds:* The API authenticates, builds the tool context from identity and starts a run. Short runs stream events within the request. Long runs are durable jobs executed by workers, with events stored and streamed over SSE that clients can reconnect to and cancel.
- *2 minutes:* Layers, modes, event design, concurrency limits, disconnect vs cancel.
- *Deep:* Generator lifecycle and cancellation in Starlette, backpressure queues, shielded scopes, durable event replay, worker claiming, fairness and observability.

**Concept: Cancellation**

- *30 seconds:* Disconnect isn't cancel. Explicit cancel sets a flag that the agent checks at safe points, model calls stop immediately, side effects finish safely and idempotently, and the outcome is always recorded.
- *2 minutes:* asyncio `CancelledError` semantics, `finally`, shield, and cooperative tokens.
- *Deep:* Race conditions between cancel and tool start, unknown outcomes, and testing with deterministic clocks and fakes.

2. Why include sequence IDs in SSE events?
3. Why are user-facing summaries used instead of raw tool results in events?
4. What's the purpose of the bounded `asyncio.Queue` in in-request streaming?

10. *Debugging:* After reconnect, users see some events twice. Cause?

#### Knowledge Check Answers

1. When it may exceed request timeouts, pause for approval, require durability across restarts, or continue after the client disconnects.
2. For ordering, deduplication and resumption with `Last-Event-ID`.
3. Raw results may contain PII, internal fields or injection text, and they're large. Summaries are safe and meaningful to users.
4. Backpressure: if the client is slow, event production waits instead of growing memory without bound.
5. Pub/sub is lossy (messages are missed when not subscribed). The DB holds ordered, durable events, so re-query after each wake-up.
6. Starlette cancels the generator, and `finally` sets the cancel token, waits (shielded, bounded) for the agent to stop at the next safe point, and records the run's outcome.
7. So recording the outcome can't be interrupted by cancellation, and every run reaches a terminal state.
8. The work isn't done yet. 202 Accepted signals asynchronous processing, and the response points to the events URL.
9. A load-balancer or proxy idle timeout without heartbeats, or proxy buffering.
10. Events replayed from memory or pub/sub without sequence tracking, or the server ignoring `Last-Event-ID`.
11. No. Disconnect isn't intent. Provide an explicit cancel and possibly a timeout for abandoned runs.
12. At run creation (API) using an atomic counter or a DB query of running runs per tenant, and again at worker claim time.

### 16. Common Interview Traps

- **"Just make the endpoint async and the agent can run long."** Request timeouts and disconnects still apply.
- **"BackgroundTasks are fine for agents."** Not durable, not bounded, and lost on restart.
- **"Disconnect means cancel."** Not for durable runs.
- **"Stream the tool outputs to the UI."** That leaks PII and injection text. Summarize.
- **"Pub/sub is enough for event delivery."** It's lossy without a durable log.
- **"Cancel kills everything immediately."** Side effects need safe points and idempotency.
- **"The request session can be used inside the stream."** Lifetimes differ. Open sessions where you use them.
