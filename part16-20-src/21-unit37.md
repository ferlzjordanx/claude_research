### 2. Prerequisite Knowledge

- **Units 33–36**: the components you'll trace (gateway, decision parser, approval service, eval graders).
- **Spring Boot Actuator and Micrometer basics**: `MeterRegistry`, counters, timers, distribution summaries, tags; why tag cardinality matters for time-series databases.
- **Logging with SLF4J/Logback** and MDC.
- **Kafka basics**: records, headers, producers/consumers.
- **HTTP headers** and the idea of request correlation ids.

**Refresher — three signals.** *Traces* show the path and timing of one request across components. *Metrics* are aggregated numbers over time (rates, percentiles) — cheap to store and alert on, but they lose per-request detail. *Logs* are timestamped events with arbitrary detail. Correlating them (trace id in logs; exemplars linking metrics to traces) is what makes debugging fast.

### 3. Mental Model

A trace is the **flight recorder** of one business operation. Each component writes a labeled, timed segment (span) into the same recording, nested under whatever called it. When something goes wrong you replay the recording and see exactly where the plane started to drift.

```
TRACE 7f3a…  "POST /api/agent/messages"  (conversation c-91, run r-552, user staff-17, tenant t1)
└─ invoke_agent SupportAgent                         4.8 s   turns=3  tokens=6.1k  cost=$0.021  outcome=PROPOSE_ACTION
   ├─ guard.input                                    3 ms    verdict=ALLOW
   ├─ retrieval policies                             180 ms  results=5  top_score=0.82  index=v4
   │   └─ embeddings text-embedding-x                 60 ms   input_tokens=14
   ├─ chat model-x (turn 1)                          1.3 s   in=2.1k out=95  finish=stop  decision=TOOL_CALL attempts=1
   ├─ execute_tool get_order                         45 ms   outcome=Success
   │   └─ GET orders-service /orders/A-1001          38 ms   http 200
   ├─ chat model-x (turn 2)                          1.6 s   in=2.6k out=120 decision=TOOL_CALL attempts=2 ← retry
   ├─ execute_tool issue_refund                      30 ms   outcome=PendingApproval  risk=APPROVAL_SINGLE
   │   └─ approval.propose                           22 ms   proposal=p-77
   ├─ chat model-x (turn 3)                          1.2 s   decision=FINAL_ANSWER
   └─ guard.output                                   2 ms    redactions=0 links_removed=0
   event: eval.online faithfulness=1.0 citations_valid=true  (async, sampled)
```

Two lenses:

- **Observability** (this unit): *what happened, where, how long, how much, which component failed?*
- **Evaluation** (Unit 36): *was the behavior correct, grounded, safe, efficient?* Online eval results are attached to traces so you can filter "traces with faithfulness < 1" and debug them.

### 4. Comprehensive Theory

#### 4.1 AI Observability vs AI Evaluation

| | Observability | Evaluation |
|---|---|---|
| Question | What happened? | Was it good? |
| Unit of analysis | Request/trace, component | Case/dataset, behavior |
| Signals | Spans, metrics, logs | Scores, pass/fail, rates vs baseline |
| Typical findings | "Tool X timed out", "retriever returned 0 docs", "3 decision retries", "$0.30 for this run" | "Faithfulness fell to 0.91", "refund amount accuracy regressed" |
| Time | Real time, always on | Pre-release offline, plus sampled online |
| Users | On-call engineers, SRE, cost owners | AI engineers, product, risk owners |

They reinforce each other: traces supply trajectories for evaluation; online eval scores annotate traces; eval failures are debugged by reading traces. Neither replaces the other — a perfectly traced agent can still be wrong, and a well-evaluated agent can still fail in production for operational reasons.

#### 4.2 OpenTelemetry Core Concepts

**Trace and span.** A *trace* is a tree (more precisely, a DAG with links) of *spans* sharing a 16-byte trace id. Each span has an 8-byte span id, parent span id, name, kind (`SERVER`, `CLIENT`, `PRODUCER`, `CONSUMER`, `INTERNAL`), start/end time, attributes (key/values), events (timestamped annotations, e.g., exceptions), links (references to other spans/traces) and status (`UNSET`, `OK`, `ERROR`).

**Context and propagation.** The *current context* (active span + baggage) lives in a thread-local-like `Context`. Crossing process boundaries requires *propagation*: the W3C Trace Context header `traceparent: 00-<trace-id>-<parent-span-id>-<flags>` (and `tracestate`) is injected into outgoing HTTP headers/Kafka record headers and extracted on the receiving side. *Baggage* carries user-defined key/values across services (e.g., `tenant=t1`) — useful but propagated to every downstream service, so never put secrets or PII in it.

**Metrics.** Instruments: counters, up-down counters, histograms, gauges. Metrics are aggregated with *attributes* (dimensions); each unique attribute combination is a time series, so attributes must be **low cardinality** (model, tool, outcome — not user id or conversation id).

**Logs.** Logs carry `trace_id`/`span_id` so you can jump from a log line to its trace. In Spring Boot, Micrometer Tracing puts trace/span ids into the MDC and Boot's default log pattern includes them when tracing is on.

**Resource.** Attributes describing the emitting entity: `service.name`, `service.version`, `deployment.environment.name`, host/container info.

**Exporters and the Collector.** Applications export via OTLP (gRPC/HTTP) to an OpenTelemetry Collector, which receives, processes (batching, redaction, tail sampling, attribute transforms) and exports to backends (Jaeger, Grafana Tempo, Prometheus/Mimir, Loki, vendor APMs, LLM-observability tools like Langfuse/Phoenix that accept OTLP).

**Sampling.** *Head sampling* decides at trace start (e.g., 10%) — cheap but blind to whether the request will fail. *Tail sampling* (in the Collector) decides after seeing the whole trace — keep all errors, slow traces, high-cost runs and policy denials, plus a percentage of the rest. Agents produce long, expensive, rare-failure traces: tail sampling is usually worth it.

#### 4.3 Tracing an Agent Workflow as One Business Operation

**Principle.** The unit of observability is the *business operation* (answer this support request), not the individual LLM call. Every component participating in that operation contributes spans to the same trace, so you can answer "why did this request fail/cost $0.40/take 14 s?" from one view.

**Span model for the support agent.**

| Span | Kind | Key attributes |
|---|---|---|
| `POST /api/agent/messages` | SERVER | http.*, user/tenant as *span* attributes (not metric tags), conversation id |
| `invoke_agent SupportAgent` | INTERNAL | `gen_ai.operation.name=invoke_agent`, `gen_ai.agent.name`, `gen_ai.conversation.id`, run id, turns, total tokens, cost, outcome, stop reason |
| `guard.input` / `guard.output` | INTERNAL | verdict, signals (names only), redaction counts |
| `retrieval {source}` | INTERNAL/CLIENT | query hash, top-k, result count, top score, index version, filter summary |
| `embeddings {model}` | CLIENT | `gen_ai.operation.name=embeddings`, model, input tokens |
| `chat {model}` | CLIENT | `gen_ai.operation.name=chat`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, temperature, max tokens; plus decision type, parse attempts, failure classes |
| `execute_tool {tool}` | INTERNAL | `gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, gateway outcome (Success/Denied/Invalid/PendingApproval/Failed), denial code, risk tier |
| downstream HTTP/DB | CLIENT | auto-instrumented |
| `approval.propose` / `approval.decide` / `approval.execute` | INTERNAL | proposal id, tier, decision, approvals count |
| Kafka produce/consume | PRODUCER/CONSUMER | messaging.* |

**Long waits and async hops.** An approval may take hours. Don't keep a span open for hours (spans should cover active work; many backends drop very long traces). Instead:

- End the request trace when the run pauses (outcome `AWAITING_APPROVAL`).
- The reviewer's approval request starts its own trace (`POST /api/approvals/{id}/approve`).
- The resumed agent run starts a new trace with a **span link** to the original `invoke_agent` span (store the original trace/span ids on the proposal) and carries the same business correlation attributes (`gen_ai.conversation.id`, run id, proposal id).
- Search by run id or conversation id to see the whole story across traces.

For short async hops (Kafka between services within seconds), normal propagation through headers keeps one trace.

#### 4.4 OpenTelemetry GenAI Semantic Conventions

**What they are.** A shared vocabulary for GenAI telemetry so tools and backends can interpret spans and metrics consistently. They define span names/operations (`chat`, `text_completion`, `embeddings`, `create_agent`, `invoke_agent`, `execute_tool`), attributes (`gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, `gen_ai.request.temperature`, `gen_ai.request.max_tokens`, `gen_ai.conversation.id`, `gen_ai.agent.name`, `gen_ai.agent.id`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.type`, `error.type`) and metrics (`gen_ai.client.operation.duration`, `gen_ai.client.token.usage` histograms, with server-side metrics for model servers). Opt-in content attributes/events capture input/output messages, system instructions and tool definitions ([OpenTelemetry GenAI semconv](https://opentelemetry.io/docs/specs/semconv/gen-ai/)).

**Stability.** **[Experimental]** As of 2026 the GenAI conventions remain in *Development* status: names have changed (e.g., `gen_ai.system` was replaced by `gen_ai.provider.name`; token attributes moved from `prompt_tokens/completion_tokens` naming to `input_tokens/output_tokens`) and agent/tool attributes are the most likely to change further. Instrumentations that implement them may gate the newest names behind `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`. Practical guidance: centralize attribute names in one constants class so you can migrate; record your semconv version as a resource attribute; check the live spec before building dashboards.

**Content capture.** Prompts, completions and tool arguments are **not captured by default** in the conventions and in well-behaved instrumentations, because they may contain PII and secrets. Treat enabling content capture as a data-processing decision (where stored, who can read, retention), typically limited to non-production or to redacted, sampled production traffic.

#### 4.5 Instrumenting Spring Boot 4

**Three building blocks.**

1. **Micrometer Observation API** — Spring's instrumentation abstraction. One `Observation` produces a timer metric (with low-cardinality key values as tags) *and* a span (with low- and high-cardinality key values as attributes) through registered handlers. Spring MVC, RestClient, JDBC (via datasource-micrometer), Spring Kafka, Spring Data repositories and Spring AI emit observations.
2. **Micrometer Tracing with the OpenTelemetry bridge** — turns observations into OTel spans and handles propagation.
3. **Export** — OTLP to a Collector.

**Option A — Spring Boot's OpenTelemetry starter** **[Current, Version-dependent]**. Spring Boot 4 adds `spring-boot-starter-opentelemetry`, which brings the OpenTelemetry API, the Micrometer→OTel tracing bridge and OTLP export for metrics (and logs). Configure under `management.opentelemetry.*`/`management.otlp.*` properties ([Spring blog](https://spring.io/blog/2025/11/18/opentelemetry-with-spring-boot/); [Boot 4 tracing reference](https://docs.spring.io/spring-boot/4.0/reference/actuator/tracing.html)). Check the reference for exact property names in your Boot minor version — they were reorganized in 4.0.

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

```yaml
spring:
  application:
    name: support-agent
management:
  tracing:
    sampling:
      probability: 1.0            # head sampling in the app; do tail sampling in the Collector
  opentelemetry:
    resource-attributes:
      deployment.environment.name: ${ENV:local}
      service.version: ${APP_VERSION:dev}
    tracing:
      export:
        otlp:
          endpoint: http://otel-collector:4318/v1/traces
  otlp:
    metrics:
      export:
        url: http://otel-collector:4318/v1/metrics
        step: 30s
```

**Option B — OpenTelemetry Java agent.** Attach `-javaagent:opentelemetry-javaagent.jar` with `OTEL_*` environment variables. Bytecode instrumentation covers hundreds of libraries without code changes; the Spring team notes the agent remains a strong default where you can use it, and the starter suits cases where you can't (e.g., native images, restricted environments). Mixing the agent with Micrometer tracing requires care to avoid duplicate spans — pick one primary approach.

**Spring AI observations.** Spring AI instruments `ChatClient`, advisors, `ChatModel`, `EmbeddingModel`, `VectorStore` and tool calling through Micrometer observations aligned with GenAI conventions (e.g., `gen_ai.client.operation` timers and token-usage metrics; spans named like `chat {model}`). Prompt/completion content logging is **disabled by default** and enabled via `spring.ai.*.observations.*` properties — names have changed across versions, so check your version's observability page **[Version-dependent]**.

**Spring Kafka.** Enable observation so `traceparent` is propagated through record headers:

```yaml
spring:
  kafka:
    template:
      observation-enabled: true
    listener:
      observation-enabled: true
```

**Virtual threads and executors.** Context lives in thread-locals; when you hand work to another thread (executors, `CompletableFuture`, virtual-thread executors), wrap with `ContextSnapshot`/`ContextExecutorService` (Micrometer Context Propagation) or `Context.taskWrapping(executor)` (OTel) so spans stay connected. Reactor-based streaming needs `Hooks.enableAutomaticContextPropagation()`.

#### 4.6 What to Track: Model, Tool, Latency, Tokens, Errors, Retries, Loops, Cost, Eval Result

| Signal | Span attribute (per request) | Metric (aggregated, low-cardinality tags) |
|---|---|---|
| Model | `gen_ai.request.model`, `gen_ai.response.model`, provider | tag `model` on all GenAI metrics |
| Tool | `gen_ai.tool.name`, call id, outcome, denial code | `agent.tool.calls{tool,outcome}`, `agent.tool.duration{tool}` |
| Latency | span durations (critical path visible) | `gen_ai.client.operation.duration{model,operation}`, `agent.run.duration{outcome}` — use histograms for p95/p99 |
| Tokens | input/output (and cached) tokens per call; totals on `invoke_agent` | `gen_ai.client.token.usage{model,token.type}` |
| Errors | span status ERROR, `error.type`, exception event | `agent.errors{component,error.type}` |
| Retries | `agent.decision.attempts`, HTTP retry count, failure classes | `agent.decision.attempts{outcome}` |
| Loops | turns, tool calls, repeated identical `(tool,argsHash)` count, stop reason (`max_turns`, `budget`, `deadline`, `final`) | `agent.run.turns` histogram, `agent.run.stopped{reason}` |
| Cost | computed `agent.cost.usd` on model spans and the run | `agent.cost.usd{model,agent}` counter |
| Guardrails | verdicts, denials, redactions, approvals | `agent.guard.verdicts{guard,verdict}`, `agent.approvals{tier,decision}` |
| Eval result | online eval scores as span event/attributes on the run (or separate linked eval span) | `agent.eval.score{metric}` histogram, `agent.eval.failures{metric}` |

**Cardinality rule.** Never use user ids, conversation ids, order ids, prompts or free text as metric tags. Put them (carefully) on spans or logs.

#### 4.7 Span Attribution: Finding the Responsible Component

When a request fails, the *symptom span* (where the error surfaced) often differs from the *cause span*. A systematic approach:

1. **Find the root outcome.** On `invoke_agent`: outcome (`FAIL_CLOSED`, `ESCALATE`, error), stop reason.
2. **Walk children in time order** and find the *first* anomaly: an ERROR span, an unusual attribute (retrieval `results=0`, `finish_reasons=length`, `attempts=3`, tool `Denied`), or an outlier duration.
3. **Classify by component**: input guard, retrieval/index, model provider, decision parsing, tool gateway policy, downstream service, approval, output guard.
4. **Separate deterministic from probabilistic causes**: a `Denied` tool outcome is a policy decision (deterministic, possibly correct); repeated invalid decisions are model-behavior issues; timeouts are infrastructure.
5. **Check critical path** for latency: which spans are on the longest sequential path? Parallelizable work done sequentially shows up here.
6. **Confirm with metrics**: is this an isolated trace or part of a spike (e.g., provider latency across all requests)?

Error status conventions: set ERROR on the span where the failure *occurred* and propagate an outcome attribute upward rather than marking every ancestor ERROR — otherwise every span is red and attribution gets harder. Policy denials and fail-closed outcomes are not errors in the span-status sense (the system worked); record them as attributes/events so they're searchable without polluting error rates.

#### 4.8 Safe Logging and Telemetry

Telemetry pipelines are data pipelines: they copy data into more systems, retained longer and accessed by more people than the primary database.

**Rules.**

1. **Content capture off by default** in production; if enabled, sample and redact, store in a restricted backend, short retention.
2. **Redact at the source and again at the Collector** (defense in depth): patterns for emails, phone numbers, card numbers, API keys, JWTs.
3. **Hash or tokenize identifiers** when you only need joinability (`user.hash`), keeping raw ids out of broadly accessible backends.
4. **No secrets** in attributes, baggage, logs or exception messages; exception messages from tools often contain request payloads.
5. **Structured logs** with explicit fields rather than `log.info("Request: {}", request)` (which calls `toString()` — records print all components!).
6. **Access control and retention** on observability backends; audit access to content-bearing traces.
7. **Tenant isolation** in multi-tenant observability (separate datasets or attribute-based access).
8. **Don't use telemetry as audit** (Unit 35): sampling and retention make it unsuitable.

#### 4.9 Cross-Agent and Cross-Service Correlation

- **Synchronous agent-to-agent calls** (HTTP, gRPC, A2A): propagate W3C trace context; the callee's `invoke_agent` span is a child of the caller's tool span — one trace shows the whole delegation tree.
- **MCP**: HTTP transports propagate context through headers when instrumented; there is ongoing standardization of trace context in MCP message metadata (`_meta`) **[Experimental]**. If your MCP client/server stack doesn't propagate, add it explicitly.
- **Async via Kafka**: headers propagate context; consumer spans link or parent accordingly.
- **Fan-out/fan-in** (supervisor with parallel sub-agents): child spans under the supervisor; parallel spans visible as overlapping bars; fan-in aggregation span.
- **Long-running / human-paused**: new traces linked by span links and shared correlation attributes.
- **Business correlation ids**: conversation id, run id, proposal id, order id (as span attributes, not metric tags) — let you search across traces and join with audit records.

### 5. Internal Mechanics

#### 5.1 From `Observation` to OTLP

```
Observation.createNotStarted("agent.tool", registry).lowCardinalityKeyValue(...).highCardinalityKeyValue(...)
  .start()
     → ObservationHandlers notified (onStart):
         DefaultMeterObservationHandler → starts Timer.Sample / LongTaskTimer
         PropagatingSenderTracingObservationHandler / DefaultTracingObservationHandler → tracer.nextSpan(parent = current)
  .openScope()  → puts span into current context (thread-local); MDC gets traceId/spanId
  … work … (nested observations become child spans)
  .error(e)     → span records exception event, status ERROR; timer tagged error
  .stop()       → Timer recorded with low-cardinality tags; span ended with low+high cardinality attributes
     → OTel SDK SpanProcessor (BatchSpanProcessor) queues span
     → OtlpHttpSpanExporter batches → POST /v1/traces → Collector
```

Low-cardinality key values become both metric tags and span attributes; high-cardinality key values become span attributes only. That split is the mechanism that protects your metrics backend.

#### 5.2 Propagation through Kafka

```
Producer thread: current span = execute_tool issue_refund
  KafkaTemplate.send(record) [observation enabled]
     → PRODUCER span "approvals.events send"
     → TextMapPropagator.inject(context, record.headers())  → header traceparent=00-<trace>-<producer-span>-01
Consumer thread (other service):
  listener container [observation enabled]
     → extract(record.headers()) → parent context
     → CONSUMER span "approvals.events receive" (child of producer span)
     → listener method runs inside that context; its spans nest under it
```

#### 5.3 Tail sampling in the Collector

The Collector buffers spans by trace id for a decision window (e.g., 10–30 s), then evaluates policies (status code ERROR, latency > threshold, attribute `agent.outcome` in {FAIL_CLOSED, ESCALATE}, `agent.cost.usd > 0.10`, probabilistic 10%). Requirements: all spans of a trace must reach the *same* Collector instance (use a load-balancing exporter tier keyed by trace id), and the window must exceed your normal trace duration.

### 6. Implementation Examples

#### Example 1 — Minimal: an `Observation` around a tool call

```java
package com.acme.support.observability;

import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;

import java.util.function.Supplier;

public final class ToolObservations {

    public static <T> T observeTool(ObservationRegistry registry, String toolName, String callId, Supplier<T> work) {
        return Observation.createNotStarted("agent.tool", registry)
                .contextualName("execute_tool " + toolName)                 // span name per GenAI conventions
                .lowCardinalityKeyValue("gen_ai.operation.name", "execute_tool")
                .lowCardinalityKeyValue("gen_ai.tool.name", toolName)       // safe as a metric tag: bounded set
                .highCardinalityKeyValue("gen_ai.tool.call.id", callId)     // span only
                .observe(work);
    }

    private ToolObservations() { }
}
```

This single call produces a timer metric `agent.tool` tagged by tool and a span `execute_tool get_order` nested under whatever is current.

**Agent run observation** wrapping the orchestrator:

```java
package com.acme.support.agent;

import com.acme.support.observability.GenAiAttributes;
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Component;

@Component
public class ObservedAgentRunner {

    private final AgentOrchestrator orchestrator;
    private final ObservationRegistry registry;

    public ObservedAgentRunner(AgentOrchestrator orchestrator, ObservationRegistry registry) {
        this.orchestrator = orchestrator;
        this.registry = registry;
    }

    public AgentRunResult run(AgentRunRequest request) {
        Observation obs = Observation.createNotStarted("agent.run", registry)
                .contextualName("invoke_agent SupportAgent")
                .lowCardinalityKeyValue(GenAiAttributes.OPERATION, "invoke_agent")
                .lowCardinalityKeyValue(GenAiAttributes.AGENT_NAME, "SupportAgent")
                .lowCardinalityKeyValue("acme.agent.profile", request.profileName())
                .highCardinalityKeyValue(GenAiAttributes.CONVERSATION_ID, request.conversationId())
                .highCardinalityKeyValue(GenAiAttributes.RUN_ID, request.runId());
        obs.start();
        try (Observation.Scope scope = obs.openScope()) {
            AgentRunResult result = orchestrator.run(request);
            obs.lowCardinalityKeyValue(GenAiAttributes.OUTCOME, result.outcome().name());          // bounded enum
            obs.lowCardinalityKeyValue(GenAiAttributes.STOP_REASON, result.stopReason().name());   // bounded enum
            obs.highCardinalityKeyValue(GenAiAttributes.TURNS, String.valueOf(result.turns()));
            obs.highCardinalityKeyValue(GenAiAttributes.INPUT_TOKENS, String.valueOf(result.inputTokens()));
            obs.highCardinalityKeyValue(GenAiAttributes.OUTPUT_TOKENS, String.valueOf(result.outputTokens()));
            obs.highCardinalityKeyValue(GenAiAttributes.COST_USD, result.costUsd().toPlainString());
            return result;
        } catch (RuntimeException e) {
            obs.lowCardinalityKeyValue(GenAiAttributes.ERROR_TYPE, e.getClass().getSimpleName());
            obs.error(e);
            throw e;
        } finally {
            obs.stop();
        }
    }
}
```

**Usage and cost metrics.**

```java
package com.acme.support.observability;

import io.micrometer.core.instrument.Counter;
import io.micrometer.core.instrument.DistributionSummary;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.stereotype.Component;

import java.math.BigDecimal;
import java.math.MathContext;
import java.util.Map;

@Component
public class UsageMetrics {

    @ConfigurationProperties("acme.pricing")
    public record PricingProperties(Map<String, ModelPrice> models) {
        public record ModelPrice(BigDecimal inputPerMillion, BigDecimal outputPerMillion) { }
    }

    private static final BigDecimal MILLION = BigDecimal.valueOf(1_000_000);

    private final MeterRegistry meters;
    private final PricingProperties pricing;

    public UsageMetrics(MeterRegistry meters, PricingProperties pricing) {
        this.meters = meters;
        this.pricing = pricing;
    }

    public BigDecimal record(String model, int inputTokens, int outputTokens) {
        DistributionSummary.builder("gen_ai.client.token.usage").baseUnit("tokens")
                .tag("gen_ai.request.model", model).tag("gen_ai.token.type", "input")
                .publishPercentileHistogram().register(meters).record(inputTokens);
        DistributionSummary.builder("gen_ai.client.token.usage").baseUnit("tokens")
                .tag("gen_ai.request.model", model).tag("gen_ai.token.type", "output")
                .publishPercentileHistogram().register(meters).record(outputTokens);

        PricingProperties.ModelPrice price = pricing.models().get(model);
        if (price == null) {
            meters.counter("acme.pricing.unknown_model", "model", model).increment();
            return BigDecimal.ZERO;
        }
        BigDecimal cost = price.inputPerMillion().multiply(BigDecimal.valueOf(inputTokens))
                .add(price.outputPerMillion().multiply(BigDecimal.valueOf(outputTokens)))
                .divide(MILLION, MathContext.DECIMAL64);
        Counter.builder("acme.agent.cost").baseUnit("usd").tag("model", model).register(meters)
                .increment(cost.doubleValue());
        return cost;
    }
}
```

**Redaction before export (application side).** An `ObservationFilter` runs before handlers and can rewrite key values:

```java
package com.acme.support.observability;

import io.micrometer.common.KeyValue;
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationFilter;
import org.springframework.stereotype.Component;

import java.util.regex.Pattern;

@Component
public class RedactingObservationFilter implements ObservationFilter {

    private static final Pattern EMAIL = Pattern.compile("[\\w.+-]+@[\\w-]+\\.[\\w.]+");
    private static final Pattern CARD = Pattern.compile("\\b(?:\\d[ -]?){13,19}\\b");

    @Override
    public Observation.Context map(Observation.Context context) {
        for (KeyValue kv : context.getHighCardinalityKeyValues()) {
            String redacted = CARD.matcher(EMAIL.matcher(kv.getValue()).replaceAll("[email]")).replaceAll("[card]");
            if (!redacted.equals(kv.getValue())) {
                context.addHighCardinalityKeyValue(KeyValue.of(kv.getKey(), redacted));
            }
        }
        return context;
    }
}
```

Register with `ObservationRegistryCustomizer<ObservationRegistry>` (`registry.observationConfig().observationFilter(filter)`) if not picked up automatically. This is a *second* line — primary rule: don't put content in attributes.

### 7. Comparative Analysis

| Comparison | Key difference | Use when | Trade-offs | Interview trap |
|---|---|---|---|---|
| Observability vs evaluation | What happened vs was it good | Both, linked by trace ids | Different consumers/retention | "We have traces, so quality is covered" |
| OTel Java agent vs Boot OTel starter vs manual | Bytecode auto-instrumentation vs Spring-native Micrometer bridge vs hand-written spans | Agent for broad coverage with no code; starter for Spring-native config/native images; manual for business spans | Agent: startup overhead, duplicate-span risk with Micrometer; starter: Spring-instrumented libs only | Thinking auto-instrumentation produces agent-level business spans |
| Micrometer Observation vs OTel API | Spring abstraction producing metrics+spans vs direct tracing API | Observation in Spring code; OTel API for links/advanced features | Observation hides some OTel features; OTel API doesn't make metrics automatically | Using both naïvely → duplicate spans |
| Head vs tail sampling | Decide at start vs after completion | Tail for agents (rare, expensive failures) | Tail needs Collector memory and trace-id-aware routing | 1% head sampling and wondering why failures are missing |
| Span attributes vs metric tags | Per-request detail vs aggregated dimensions | High-cardinality ids on spans; bounded enums as tags | Tags multiply time series | Putting user id on metrics |
| Logs vs traces vs audit | Debug events vs request flow vs business record | Each for its purpose | Audit requires integrity and retention | Using logs as audit |
| Parent-child vs span links | Same trace vs references across traces | Links for long waits, batches, fan-in from many triggers | Links are less visible in some UIs | Keeping a span open for hours |
| LLM-specific platforms (Langfuse, Phoenix, LangSmith) vs general APM | AI-centric views (prompts, evals) vs infra-centric | Both via OTLP; AI platform for prompt/eval workflows | Content storage/privacy; cost | Choosing one and losing either infra or AI context |

### 8. Failure Modes and Debugging

**O1 — Broken traces (orphan spans).**
SYMPTOM: Tool and model spans appear as separate root traces.
↓ CAUSE: Work moved to another thread (virtual-thread executor, `CompletableFuture`) without context propagation; or Kafka observation disabled.
↓ INVESTIGATE: Compare trace ids in logs across threads; check executor wrapping; check Kafka headers for `traceparent`.
↓ FIX: `ContextExecutorService.wrap(executor)` / `Context.taskWrapping`; enable `observation-enabled` for Kafka; Reactor automatic context propagation.
↓ PREVENT: Integration test asserting a single trace id for a full scripted run.

**O2 — Metrics backend explodes.**
SYMPTOM: Prometheus memory spikes; queries slow; cardinality alerts.
↓ CAUSE: `conversation.id` or `user.id` added as a low-cardinality key value (metric tag); or free-text error messages as tags.
↓ FIX: Move to high-cardinality key values; use bounded `error.type`.
↓ PREVENT: Code review checklist; meter filter that denies unknown tag keys (`MeterFilter.denyUnless`) or caps tag values.

**O3 — PII in traces.**
SYMPTOM: Customer emails visible in Tempo.
↓ CAUSE: Content capture enabled via property in production profile; tool exception messages containing payloads recorded as exception events.
↓ FIX: Disable capture; sanitize exception messages in tools; Collector redaction; purge affected data per policy.
↓ PREVENT: Staging scan for PII patterns in exported spans as a CI/nightly check.

**O4 — Duplicate spans.**
SYMPTOM: Two `chat` spans per model call, double-counted tokens.
↓ CAUSE: OTel Java agent instrumentation plus Spring AI/Micrometer observation, or custom wrapper plus built-in observation.
↓ FIX: Choose one instrumentation path per library; disable specific agent instrumentations (`OTEL_INSTRUMENTATION_<NAME>_ENABLED=false`) or remove the wrapper.
↓ PREVENT: Test that counts `chat` spans per scripted model call.

**O5 — Missing failures due to sampling.**
SYMPTOM: Users report failures, but no traces found.
↓ CAUSE: 5% head sampling.
↓ FIX: Tail sampling keeping errors/bad outcomes; or always-sample for flagged routes; ensure trace-id-aware Collector routing.

**O6 — Cost dashboard disagrees with invoice.**
SYMPTOM: Dashboard shows $8k/month; provider invoice $11k.
↓ CAUSE: Retries and judge/eval calls not instrumented; cached-token pricing differences; embeddings not counted; price table outdated.
↓ FIX: Instrument every provider call path (including evals with a separate tag); update price config; reconcile monthly.

### 13. Interview Preparation

#### Quick Questions

**Q: AI observability vs AI evaluation?**
*Strong answer:* Observability tells you what happened in a request — components, timing, tokens, errors, cost. Evaluation tells you whether the behavior was good against criteria. You need both, linked by trace ids: evals use traces as trajectories and traces carry eval scores.

**Q: What should be on an LLM call span?**
*Strong answer:* Operation, provider, requested/response model, input/output tokens, finish reasons, key parameters, latency, error type; plus app attributes like decision type and parse attempts. No prompt content by default.

**Q: Why not put conversation id on metrics?**
*Strong answer:* Each unique tag value creates a time series; unbounded ids explode cardinality and cost. Put ids on spans and logs.

#### Intermediate Questions

**Q: How do you trace a multi-agent workflow?**
*Strong answer:* One business trace: root request span, supervisor `invoke_agent`, child `invoke_agent` spans for sub-agents (W3C context propagated across HTTP/A2A/MCP), `chat` and `execute_tool` spans under each; Kafka hops propagated via headers; long waits split into linked traces sharing run/conversation ids. GenAI conventions for names/attributes, with a central constants class due to Development status.
*Trap:* Separate traces per agent with no correlation.

**Q: How do you identify the responsible component in a failed agent request?**
*Strong answer:* Start at the root outcome; walk spans chronologically to the first anomaly (error status, zero results, truncation, retries, denial); classify the component; distinguish deterministic policy outcomes from model behavior from infrastructure; confirm with metrics whether it's systemic.

**Q: What is safe logging for AI systems?**
*Strong answer:* Content off by default; structured logs with hashes/ids instead of payloads; redaction at source and Collector; sanitize exception messages; no secrets in baggage; access control and retention; separate audit.

#### Advanced Questions

**Q: Head vs tail sampling for agents?**
*Strong answer:* Agent failures are rare and expensive to miss; head sampling drops them blindly. Tail sampling in a Collector tier keeps errors, slow, costly and bad-outcome traces plus a baseline percentage; requires trace-id-aware load balancing and enough buffer for the decision window.

**Q: How does Micrometer Observation become an OTel span, and how do you avoid cardinality issues?**
*Strong answer:* Observation handlers create a timer (low-cardinality key values as tags) and a span via the tracing bridge (both key-value sets as attributes); scope puts the span in context; stop ends both and the OTel SDK exports via OTLP. Using high-cardinality key values for ids keeps them off metrics.

**Q: How do you keep a trace coherent across a human approval that takes a day?**
*Strong answer:* Don't keep spans open; end the first trace at pause; store the origin span context on the proposal; resume in a new trace with a span link and shared run/conversation ids; dashboards and search join by those ids.

#### Coding Questions

1. Write an Observation-based wrapper for model calls that records tokens and finish reason without double-counting with Spring AI's built-in observation.
2. Write a `TestObservationRegistry` test asserting cardinality split.
3. Write a `MeterFilter` that rejects any tag key not on an allow-list.

#### Scenario Questions

**Q: Users report wrong refund amounts, but traces look healthy (no errors). What now?**
*Strong answer:* Healthy traces mean no infra failures — this is a quality issue: use evals. Filter traces with `issue_refund` proposals; compare proposed amounts to policy (online deterministic grader); find the pattern (e.g., model uses order total including shipping); add eval cases; fix the prompt/tool (compute refundable amount in the tool rather than letting the model calculate).

### 14. Explain-It-at-Three-Levels

**Agent observability**
- *30 seconds:* Each user request is one trace with spans for the agent run, every model call, retrieval, tool call, guardrail and approval, carrying model, tokens, latency, errors, retries and cost; metrics aggregate them with low-cardinality tags; logs carry trace ids; content capture is off by default.
- *2 minutes:* Add: GenAI semantic conventions (Development status), Micrometer Observation + OTel bridge in Spring Boot 4 or the Java agent, Kafka propagation, links for long waits, tail sampling and redaction in the Collector, cost/loop metrics, and attribution by first anomaly.
- *Deep:* Explain observation→span→OTLP internals, context propagation across threads and Kafka, cardinality mechanics, tail-sampling architecture, duplicate-instrumentation pitfalls, privacy engineering of telemetry, and how online eval results annotate traces to close the loop with Unit 36.

**Span attribution**
- *30 seconds:* Walk the trace from the root outcome to the first anomaly; that component is usually responsible, not the one that surfaced the error.
- *2 minutes:* Classify anomalies (error status, empty retrieval, truncation, retries, denial, latency outliers); deterministic vs probabilistic vs infra; confirm with metrics.
- *Deep:* Error-status conventions, critical path analysis, cross-trace correlation, systematic fault-injection drills.

### Knowledge Check Answers

1. It records what happened, not whether it met quality criteria; a fast, error-free trace can contain a wrong, ungrounded or unsafe answer. Evaluation applies criteria.
2. Low-cardinality key values become metric tags and span attributes; high-cardinality ones become only span attributes — protecting metrics backends from unbounded series.
3. Spans should represent active work; very long traces are dropped or mis-rendered by backends; links preserve causality across separate traces.
4. Attribute names may change; centralize them, record the semconv version, use opt-in flags where instrumentations offer them, and review on upgrades.
5. The system behaved correctly; marking it ERROR inflates error rates and hides real failures. Record it as an attribute/event.
6. It becomes a metric tag → cardinality explosion. Use high-cardinality key value.
7. The common pool thread lacks the current context; wrap the executor with context propagation or capture/restore context.
8. Keeps all error traces plus 10% of the rest (policies are OR'ed: a trace is sampled if any policy says sample).
9. Duplicate instrumentation (Java agent + Micrometer/Spring AI, or wrapper + built-in observation).
10. Head sampling dropped them (or export failures). Use tail sampling keeping errors/bad outcomes; check exporter health metrics.
11. See 4.3 table: SERVER request span → `invoke_agent` (agent name, conversation, run id, outcome, stop reason, turns, tokens, cost) → guard, retrieval/embeddings, `chat {model}` (provider, models, tokens, finish reasons, decision type, attempts), `execute_tool {tool}` (call id, outcome, denial code, risk tier) → approval spans; Kafka producer/consumer; resume as linked trace.
12. At the source (don't record content; sanitize exceptions; ObservationFilter) and at the Collector (attribute delete/hash/regex transforms), because code paths and third-party instrumentations can leak, and defense in depth protects downstream vendors.

### 16. Common Interview Traps

| Trap | Correct mental model |
|---|---|
| "We log prompts and responses for observability." | Content capture is a privacy decision; default off; redacted and restricted if enabled. |
| "Each LLM call is traced, so we have agent observability." | You need the *business operation* trace including tools, retrieval, guards and approvals. |
| "Auto-instrumentation covers agents." | It covers libraries; agent decisions, outcomes and costs need business spans. |
| "Tracing tells us quality." | That's evaluation. |
| "More tags = better dashboards." | Unbounded tags break metrics systems. |
| "GenAI semconv is stable, hard-code the names." | It's in Development; centralize and review. |
| "Sample 1% to save money." | Rare failures disappear; use tail sampling. |

### 17. Cheat Sheet

- **Spans:** `invoke_agent {agent}` · `chat {model}` · `embeddings {model}` · `execute_tool {tool}` · retrieval · guards · approvals · Kafka send/receive.
- **GenAI attrs:** `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`, `gen_ai.agent.name`, `gen_ai.conversation.id`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `error.type` **[Development]**.
- **GenAI metrics:** `gen_ai.client.operation.duration`, `gen_ai.client.token.usage`.
- **Spring Boot 4:** `spring-boot-starter-opentelemetry`, `management.tracing.sampling.probability`, `management.opentelemetry.*` / `management.otlp.*` export properties **[Version-dependent]**; Kafka `spring.kafka.template.observation-enabled`, `spring.kafka.listener.observation-enabled`.
- **Observation API:** `Observation.createNotStarted(name, registry).contextualName(..).lowCardinalityKeyValue(..).highCardinalityKeyValue(..).observe(..)`; `start/openScope/error/stop`; `ObservationFilter`; `TestObservationRegistry`.
- **Track:** model · tool · latency (histograms) · tokens · errors · retries · loops (turns, repeated calls, stop reason) · cost · guard verdicts · approvals · eval scores.
- **Rules:** ids on spans not metrics; content off; redact twice; links for long waits; tail sampling; one instrumentation path per library; propagate context across threads.
- **Attribution:** root outcome → first anomaly → component → deterministic/probabilistic/infra → confirm with metrics.
