## Unit 39 — Multi-Agent Systems

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** the main multi-agent patterns (supervisor/router, handoff, specialists, orchestrator-workers, evaluator-optimizer) and **decide** when a multi-agent design is justified over a single agent or a workflow.
2. **Design** shared vs isolated state between agents and **define** agent-to-agent contracts as typed, versioned messages.
3. **Implement** a supervisor that routes to specialist agents (research, customer, order) with routing limits, delegation budgets and loop prevention.
4. **Enforce** authorization across agents: each specialist has its own tools and scopes, and delegation never widens privileges.
5. **Handle** failure propagation, partial results and cost multiplication across agents.
6. **Instrument** multi-agent runs with a shared trace (parent/child spans, per-agent tokens and cost) and **evaluate** the system against a single-agent baseline.

### 3. Mental Model

A multi-agent system is **an organization chart for model calls**. It's useful when the work genuinely splits into roles with different tools, context or permissions, and costly when it doesn't.

```
                       ┌────────────── run budget: tokens, cost, deadline, delegations ≤ D ──────────────┐
user request ─▶ Supervisor (router + synthesizer; no domain tools)
                   │ Delegate(to="order", task, inputs)        typed contract, child budget slice
                   ├──────────────▶ Order specialist   (tools: get_order, get_shipment_status; scopes: orders:read)
                   ├──────────────▶ Customer specialist(tools: get_customer, ticket notes;      scopes: customers:read, tickets:write)
                   └──────────────▶ Research specialist(tools: kb_search;                       scopes: kb:read)
                   ◀── SpecialistResult(status, findings, citations, cost) ─┘
                   → synthesize final answer (or escalate) → validate → stop
```

**Default stance:** start with one well-tooled agent. Move to multiple agents when you can name the reason: context isolation (each specialist sees only what it needs), permission isolation, parallelism on independent subtasks, or separate ownership/evaluation of capabilities.

### 4. Comprehensive Theory

#### 4.1 Patterns

| Pattern | How it works | Good for | Costs/risks |
|---|---|---|---|
| **Router** | One classification step picks a specialist (or workflow); no return | Clear intent categories | Misroutes; no recovery |
| **Supervisor** | A coordinator delegates subtasks, receives results, decides next delegation or final answer | Multi-part requests | Extra LLM calls; supervisor loops |
| **Handoff** | The active agent transfers control (and conversation) to another agent | Conversational transfers (billing → shipping) | Ping-pong; context loss |
| **Orchestrator-workers** | Planner splits work into parallel subtasks, then merges | Independent research subtasks | Cost multiplication; merge quality |
| **Evaluator-optimizer** | One agent generates, another critiques against criteria, bounded rounds | Drafting with clear quality criteria | Endless refinement; same-model bias |
| **Hierarchical** | Supervisors of supervisors | Rarely justified | Latency, cost, debuggability |

**Routing decision as code where possible.** A deterministic router (rules, a classifier) is cheaper and testable. Use a model router when intents are fuzzy, and still constrain its output to an enum.

#### 4.2 Shared vs Isolated State

| | Shared state (blackboard) | Isolated state + messages |
|---|---|---|
| How | All agents read and write a common state object | Each agent has private state; communicates via typed messages |
| Pros | Simple; everyone sees everything | Context isolation, permission isolation, clear contracts, smaller prompts |
| Cons | Context bloat, injection spreads across agents, unclear ownership, write conflicts | More plumbing; information must be passed explicitly |
| Use | Small, trusted, tightly coupled agents | Default for production |

**Rule:** the supervisor sees specialists' **results** (summaries, findings, citations), not their raw tool outputs. Raw observations stay inside the specialist that fetched them. This limits context growth and the spread of injected text.

#### 4.3 Agent-to-Agent Contracts

Treat delegation like an internal API:

```python
class Delegate(BaseModel):
    type: Literal["delegate"]
    to: Literal["order", "customer", "research"]
    task: str = Field(max_length=500)                 # natural-language subtask
    inputs: dict[str, str] = Field(default_factory=dict)   # e.g. {"order_id": "8812"} — validated per specialist

class SpecialistResult(BaseModel):
    status: Literal["ok", "partial", "failed", "denied", "needs_approval"]
    findings: list[str] = Field(max_length=10)
    citations: list[str] = Field(default_factory=list)
    proposal_ids: list[str] = Field(default_factory=list)
    error: str | None = None
    usage: Usage
```

Each specialist defines its **input schema** (what `inputs` keys it accepts, validated) and **output schema** (`SpecialistResult`). Version these contracts. Contract tests check that the supervisor's delegation outputs validate against each specialist's input schema.

**Identity in delegation.** Specialists run with a `ToolContext` derived from the **original user**, narrowed to the specialist's scopes (`ctx.narrow(scopes=specialist.scopes)`). Delegation can only narrow, never widen. The model can't pass identity or tenant in `inputs`.

#### 4.4 Loop Prevention and Routing Limits

Multi-agent loops are the classic failure: supervisor → order → supervisor → order, or handoff ping-pong.

Controls:

1. **Max delegations per run** (e.g. 4), **max delegations per specialist** (e.g. 2).
2. **Delegation signatures** `(to, normalized task, inputs)`. A repeated delegation is refused, and the supervisor gets an observation "already asked; result: …".
3. **No specialist-to-specialist delegation** unless explicitly designed (keep the graph a star, not a mesh).
4. **Handoff counters** in handoff designs, with a cap and a fallback to a human.
5. **Depth limit** (hierarchy depth ≤ 1 or 2).
6. **Global run budget** shared across agents: each delegation receives a **budget slice** (tokens, time) from the remaining run budget.

#### 4.5 Failure Propagation

| Specialist status | Supervisor behavior |
|---|---|
| `ok` | Use findings |
| `partial` | Use what's there; mention gaps; maybe one more targeted delegation |
| `failed` (transient) | One retry if budget allows; otherwise answer with what's known or escalate |
| `denied` | Don't retry or reroute to bypass. Tell the user what can't be done |
| `needs_approval` | Stop the run with `awaiting_approval` (proposals bubble up) |

**Never let a supervisor "work around" a denial** by delegating the same task to another specialist with broader tools. That is a privilege escalation path, and the specialist tool sets should make it impossible anyway.

**Timeouts.** A child's deadline is the minimum of its own limit and the parent's remaining time minus a synthesis reserve. Cancellation propagates from parent to children (task groups).

#### 4.6 Cost Multiplication

Every agent adds a system prompt, tool definitions and its own reasoning loop. A supervisor with three specialists commonly uses **2–5×** the tokens of a single agent on the same task. Mitigations: cheaper models for specialists or routing, short specialist prompts, results instead of transcripts, parallel independent delegations (saves latency, not tokens), caching of stable prompt prefixes, and hard run budgets.

**Measure before adopting.** Compare against the single-agent baseline on the same eval set: success, safety violations, tokens, cost, p50/p95 latency, number of steps. Adopt the multi-agent design only if it wins on something that matters (often: fewer permission risks, better accuracy on multi-part questions).

#### 4.7 Observability

- One **trace per run**, with spans: `agent.run (supervisor)` → `agent.delegate (to=order)` → `agent.run (order)` → `llm.call`, `tool.call`.
- Attributes: agent name, contract version, delegation index, status, tokens, cost, stop reason. [Version-dependent] Align names with the OpenTelemetry GenAI semantic conventions (e.g. `gen_ai.agent.name`, `gen_ai.operation.name = invoke_agent`), which are still in Development status.
- Metrics: delegations per run, per-agent cost, misroute rate (from evals), loops prevented, denial counts.
- Events to the UI: "Checking order details…", "Searching policy…", not internal agent chatter.

### 5. Internal Mechanics

#### 5.1 Supervisor loop with delegation

```
run(request, ctx):
  budget = RunBudget(tokens=60k, cost=$0.20, deadline=60s, delegations=4)
  loop (bounded by budget.steps):
    decision = supervisor_llm(request, results_so_far)  → Delegate | DelegateParallel | FinalAnswer | Escalate
    Delegate:
      check limits (total, per specialist, signature) → refuse with observation if violated
      child_ctx = ctx.narrow(specialist.scopes); child_budget = budget.slice(...)
      validate inputs against specialist.input_schema
      result = await specialist.run(task, inputs, child_ctx, child_budget)   (child span)
      budget.charge(result.usage); results_so_far.append(summary(result))
      if result.status == needs_approval → stop(awaiting_approval)
    FinalAnswer: validate citations ⊆ union(results.citations) → stop(finished)
```

#### 5.2 Parallel delegations

Independent subtasks (`order` and `research`) run concurrently in a task group. Each has its own budget slice. If one fails, the other's result is still used (`partial`). The parent deadline cancels both.

### 6. Implementation Examples

#### Example 1 — Minimal: Deterministic router to specialists

```python
# app/multi/router.py
import re
from typing import Literal

Route = Literal["order", "customer", "research", "general"]

ORDER_RE = re.compile(r"\b(order|tracking|shipment|deliver|package)\b", re.I)
ACCOUNT_RE = re.compile(r"\b(account|email|address|profile|contact)\b", re.I)
POLICY_RE = re.compile(r"\b(policy|return|refund window|warranty|terms)\b", re.I)


def route(message: str) -> Route:
    """Cheap, testable first-pass router. Ambiguous messages go to the general agent."""
    hits = [name for name, rx in (("order", ORDER_RE), ("customer", ACCOUNT_RE), ("research", POLICY_RE))
            if rx.search(message)]
    return hits[0] if len(hits) == 1 else "general"   # type: ignore[return-value]
```

A router like this handles the easy majority. Multi-intent or ambiguous messages go to a single general agent (or a supervisor), which keeps the multi-agent path for cases that need it.

#### Example 2 — Realistic: Specialists with narrowed contexts and typed results

```python
# app/multi/specialists.py
from dataclasses import dataclass
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field

from app.agent.runner import BoundedAgent
from app.agent.state import Limits
from app.tools.registry import ToolContext


class Usage(BaseModel):
    input_tokens: int = 0
    output_tokens: int = 0
    cost_usd: float = 0.0


class SpecialistResult(BaseModel):
    model_config = ConfigDict(extra="forbid")
    contract_version: Literal["1"] = "1"
    status: Literal["ok", "partial", "failed", "denied", "needs_approval"]
    findings: list[str] = Field(default_factory=list, max_length=10)
    citations: list[str] = Field(default_factory=list)
    proposal_ids: list[str] = Field(default_factory=list)
    error: str | None = None
    usage: Usage = Field(default_factory=Usage)


class OrderInputs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^\d{1,12}$")


class ResearchInputs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    topic: str = Field(min_length=3, max_length=200)


class CustomerInputs(BaseModel):
    model_config = ConfigDict(extra="forbid")


STATUS_BY_STOP = {"finished": "ok", "needs_input": "partial", "escalated": "partial",
                  "awaiting_approval": "needs_approval"}


@dataclass(frozen=True)
class Specialist:
    name: str
    description: str                    # shown to the supervisor
    scopes: frozenset[str]              # the maximum this specialist may use
    input_model: type[BaseModel]
    agent: BoundedAgent                 # its own registry (only its tools) and prompt

    async def run(self, task: str, raw_inputs: dict, ctx: ToolContext, limits: Limits) -> SpecialistResult:
        try:
            inputs = self.input_model.model_validate(raw_inputs)
        except ValueError as e:
            return SpecialistResult(status="failed", error=f"invalid inputs: {e.errors()[0]['msg']}")
        child_ctx = ctx.narrow(scopes=self.scopes)          # intersection: never wider than the user
        state = await self.agent.run(goal=task, user_message=inputs.model_dump_json(),
                                     ctx=child_ctx, limits=limits)
        status = STATUS_BY_STOP.get(str(state.stop_reason), "failed")
        if state.denied_tools:
            status = "denied"
        return SpecialistResult(
            status=status,
            findings=state.findings_summary(max_items=10),     # summaries, not raw observations
            citations=state.final.citations if state.final else [],
            proposal_ids=state.final.proposal_ids if state.final else [],
            error=None if status == "ok" else str(state.stop_reason),
            usage=Usage(input_tokens=state.input_tokens, output_tokens=state.output_tokens,
                        cost_usd=float(state.cost_usd)))
```

```python
# app/tools/registry.py (addition)
def narrow(self, scopes: frozenset[str]) -> "ToolContext":
    return dataclasses.replace(self, scopes=frozenset(self.scopes) & scopes)
```

(`BoundedAgent.run` gains an optional `limits` argument that overrides the agent's configured limits for this run. `denied_tools` and `findings_summary` are small additions to `AgentState`: a list of tools refused by authorization and a bounded list of observation summaries.)

#### Example 3 — Production-oriented: Supervisor with routing limits, parallel delegation, budgets, shared trace and baseline comparison

```python
# app/multi/supervisor.py
import time
from dataclasses import dataclass, field
from typing import Annotated, Literal, Union

import anyio
from opentelemetry import trace
from pydantic import BaseModel, ConfigDict, Field, TypeAdapter

from app.agent.state import Limits, action_signature
from app.multi.specialists import Specialist, SpecialistResult

tracer = trace.get_tracer("supportdesk.multi")


class Delegate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    type: Literal["delegate"]
    to: Literal["order", "customer", "research"]
    task: str = Field(max_length=500)
    inputs: dict[str, str] = Field(default_factory=dict)


class DelegateParallel(BaseModel):
    model_config = ConfigDict(extra="forbid")
    type: Literal["delegate_parallel"]
    calls: list[Delegate] = Field(min_length=2, max_length=3)


class Final(BaseModel):
    model_config = ConfigDict(extra="forbid")
    type: Literal["final_answer"]
    text: str
    citations: list[str] = Field(default_factory=list)


class Escalate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    type: Literal["escalate"]
    reason: str


SupervisorDecision = Annotated[Union[Delegate, DelegateParallel, Final, Escalate], Field(discriminator="type")]
DECISION = TypeAdapter(SupervisorDecision)


@dataclass
class RunBudget:
    max_tokens: int = 60_000
    max_cost_usd: float = 0.20
    deadline_s: float = 60.0
    max_delegations: int = 4
    max_per_specialist: int = 2
    synthesis_reserve_s: float = 8.0
    started: float = field(default_factory=time.monotonic)
    tokens: int = 0
    cost: float = 0.0
    delegations: int = 0
    per_specialist: dict[str, int] = field(default_factory=dict)
    signatures: set[str] = field(default_factory=set)

    def remaining_s(self) -> float:
        return self.deadline_s - (time.monotonic() - self.started)

    def admit(self, d: Delegate) -> str | None:
        """Return a refusal reason, or None if the delegation may proceed. Records it if admitted."""
        sig = action_signature(d.to, {"task": d.task.strip().lower(), **d.inputs})
        if sig in self.signatures:
            return "duplicate delegation; reuse the earlier result"
        if self.delegations >= self.max_delegations:
            return "delegation limit reached"
        if self.per_specialist.get(d.to, 0) >= self.max_per_specialist:
            return f"limit for {d.to} reached"
        if self.remaining_s() < self.synthesis_reserve_s + 5:
            return "not enough time left"
        if self.tokens >= self.max_tokens or self.cost >= self.max_cost_usd:
            return "budget exhausted"
        self.signatures.add(sig)
        self.delegations += 1
        self.per_specialist[d.to] = self.per_specialist.get(d.to, 0) + 1
        return None

    def child_limits(self, share: float = 0.4) -> Limits:
        return Limits(max_turns=5,
                      deadline_s=max(5.0, (self.remaining_s() - self.synthesis_reserve_s) * share),
                      max_tokens=int((self.max_tokens - self.tokens) * share))

    def charge(self, r: SpecialistResult) -> None:
        self.tokens += r.usage.input_tokens + r.usage.output_tokens
        self.cost += r.usage.cost_usd


@dataclass
class SupervisorOutcome:
    kind: Literal["answer", "escalation", "pending_approval", "stopped"]
    text: str
    citations: list[str]
    proposal_ids: list[str]
    budget: RunBudget


class Supervisor:
    def __init__(self, llm, specialists: dict[str, Specialist], prompt, max_rounds: int = 5) -> None:
        self._llm, self._specs, self._prompt, self._max_rounds = llm, specialists, prompt, max_rounds

    async def run(self, request: str, ctx, budget: RunBudget | None = None) -> SupervisorOutcome:
        budget = budget or RunBudget()
        results: list[tuple[Delegate, SpecialistResult]] = []
        notes: list[str] = []
        with tracer.start_as_current_span("agent.run", attributes={"gen_ai.agent.name": "supervisor"}) as span:
            for round_ in range(self._max_rounds):
                if budget.remaining_s() <= 0:
                    break
                out = await self._llm.structured(self._prompt.build(request, results, notes), DECISION,
                                                 timeout_s=min(20.0, budget.remaining_s()))
                budget.tokens += out.usage.input_tokens + out.usage.output_tokens
                budget.cost += out.usage.cost_usd
                if out.error is not None:
                    notes.append("Previous decision was invalid; respond with one valid decision.")
                    continue
                d = out.value
                if isinstance(d, Final):
                    allowed = {c for _, r in results for c in r.citations}
                    if not set(d.citations) <= allowed:                     # citations must come from specialists
                        notes.append("Cited sources not returned by any specialist; cite only returned sources.")
                        continue
                    return self._done("answer", d.text, d.citations, results, budget, span)
                if isinstance(d, Escalate):
                    return self._done("escalation", d.reason, [], results, budget, span)

                calls = d.calls if isinstance(d, DelegateParallel) else [d]
                admitted = []
                for c in calls:
                    refusal = budget.admit(c)
                    if refusal:
                        notes.append(f"Delegation to {c.to} refused: {refusal}.")
                    else:
                        admitted.append(c)
                new = await self._delegate_all(admitted, ctx, budget)
                results.extend(new)
                if any(r.status == "needs_approval" for _, r in new):
                    ids = [p for _, r in new for p in r.proposal_ids]
                    return self._done("pending_approval", "A refund proposal is waiting for approval.", [],
                                      results, budget, span, proposal_ids=ids)
            return self._done("stopped", "I couldn't complete this within limits; escalating to a human.",
                              [], results, budget, span)

    async def _delegate_all(self, calls: list[Delegate], ctx, budget: RunBudget):
        out: list[tuple[Delegate, SpecialistResult]] = []
        share = 1.0 / max(1, len(calls)) * 0.8

        async def one(c: Delegate) -> None:
            spec = self._specs[c.to]
            with tracer.start_as_current_span("agent.delegate", attributes={
                    "gen_ai.agent.name": spec.name, "supportdesk.delegation_index": budget.delegations}) as s:
                with anyio.move_on_after(budget.child_limits(share).deadline_s) as scope:
                    r = await spec.run(c.task, c.inputs, ctx, budget.child_limits(share))
                if scope.cancelled_caught:
                    r = SpecialistResult(status="failed", error="timeout")
                s.set_attribute("supportdesk.status", r.status)
                s.set_attribute("gen_ai.usage.input_tokens", r.usage.input_tokens)
                s.set_attribute("gen_ai.usage.output_tokens", r.usage.output_tokens)
                budget.charge(r)
                out.append((c, r))

        async with anyio.create_task_group() as tg:
            for c in calls:
                tg.start_soon(one, c)
        return out

    def _done(self, kind, text, citations, results, budget, span, proposal_ids=None) -> SupervisorOutcome:
        span.set_attribute("supportdesk.delegations", budget.delegations)
        span.set_attribute("supportdesk.cost_usd", budget.cost)
        span.set_attribute("supportdesk.outcome", kind)
        return SupervisorOutcome(kind, text, citations, proposal_ids or [], budget)
```

**Design notes.**

- The supervisor has **no domain tools**. It can only delegate, answer or escalate. Its final citations must be a subset of what specialists returned.
- Delegation refusals become **notes** for the next supervisor decision, so the model learns it can't loop.
- Parallel delegations share the remaining time. One timing out yields `failed` for that child without cancelling the others.
- Denials are reported to the supervisor as `denied`, and since specialists' scopes are fixed and narrowed from the user's, re-delegating can't bypass them.

**Baseline comparison harness.**

```python
# tests/eval/compare_single_vs_multi.py
import statistics


async def compare(cases, single_agent, supervisor, judge) -> dict:
    rows = []
    for case in cases:
        s = await single_agent.run_case(case)
        m = await supervisor.run_case(case)
        rows.append({"id": case.id,
                     "single_ok": judge(case, s.answer), "multi_ok": judge(case, m.answer),
                     "single_cost": s.cost_usd, "multi_cost": m.cost_usd,
                     "single_ms": s.latency_ms, "multi_ms": m.latency_ms,
                     "single_violations": s.policy_violations, "multi_violations": m.policy_violations})
    def rate(key): return sum(r[key] for r in rows) / len(rows)
    return {
        "success": {"single": rate("single_ok"), "multi": rate("multi_ok")},
        "cost_per_case": {"single": statistics.mean(r["single_cost"] for r in rows),
                          "multi": statistics.mean(r["multi_cost"] for r in rows)},
        "p95_latency_ms": {"single": sorted(r["single_ms"] for r in rows)[int(0.95 * len(rows)) - 1],
                           "multi": sorted(r["multi_ms"] for r in rows)[int(0.95 * len(rows)) - 1]},
        "violations": {"single": sum(r["single_violations"] for r in rows),
                       "multi": sum(r["multi_violations"] for r in rows)},
        "rows": rows,
    }
```

Segment results by case type (single-intent vs multi-intent). Multi-agent designs often only help on the multi-intent slice.

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| Single agent vs multi-agent | One loop, all tools vs roles with isolated tools/context | Multi when isolation/parallelism/ownership justify cost | Multi-agent by default "because it's more advanced" |
| Router vs supervisor | One-shot choice vs iterative coordination | Router for clear intents; supervisor for multi-part | Supervisor for single-intent traffic |
| Supervisor vs handoff | Central control vs transfer of control | Handoff for conversational transfer | Ping-pong without counters |
| Shared vs isolated state | Blackboard vs messages | Isolated by default | Raw tool outputs shared everywhere |
| Model router vs rule router | Flexible vs cheap, testable | Rules first, model for the rest | Unconstrained router output |
| Parallel vs sequential delegation | Latency vs dependency order | Parallel for independent subtasks | Parallelizing dependent steps |
| Same model vs mixed models | Simplicity vs cost | Cheaper models for routing/specialists | Quality drop unmeasured |

### 8. Failure Modes and Debugging

**Failure 1 — Delegation loop.**

- SYMPTOM: supervisor asks the order specialist the same thing repeatedly.
- FIX: signatures, per-specialist caps, refusal notes, max rounds.

**Failure 2 — Privilege escalation via delegation.**

- SYMPTOM: a denied action succeeds through another specialist.
- CAUSE: overlapping tools with different scopes, contexts not narrowed, identity passed in `inputs`.
- FIX: tools assigned to exactly one specialist where possible, `narrow()` by intersection, identity only from the original context.

**Failure 3 — Context and cost explosion.**

- SYMPTOM: supervisor prompts grow to tens of thousands of tokens.
- CAUSE: specialists return transcripts or raw tool output.
- FIX: `SpecialistResult` with bounded findings, budget slices, metrics per agent.

**Failure 4 — Misrouting.**

- SYMPTOM: policy questions answered by the order specialist without KB evidence.
- FIX: routing eval set with labeled intents, rule router for clear cases, supervisor instructions with specialist descriptions, citation checks in the final answer.

**Failure 5 — Hidden partial failure.**

- SYMPTOM: confident answer although the research specialist timed out.
- FIX: status propagated, supervisor prompt requires mentioning gaps, a deterministic check that answers about policy carry KB citations.

**Failure 6 — Untraceable runs.**

- FIX: one trace with child spans per delegation, run ID in all logs, per-agent token attributes.

from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

pytestmark = pytest.mark.anyio

def spans(monkeypatch):
    exporter = InMemorySpanExporter()
    provider = TracerProvider()
    provider.add_span_processor(SimpleSpanProcessor(exporter))
    monkeypatch.setattr("app.multi.supervisor.tracer", provider.get_tracer("test"))
    return exporter


async def test_delegations_are_child_spans_of_the_run(spans, supervisor_with_scripts, ctx):

    run = next(s for s in finished if s.name == "agent.run")
    delegates = [s for s in finished if s.name == "agent.delegate"]

### 12. Engineering Scenarios

**Scenario 1 — "We want an AI team of agents" (FDE).** A client executive saw a demo of many cooperating agents. *Clarify:* what tasks fail today with a single agent, and what are the cost and latency budgets? *Reasoning:* Run the baseline first. Propose multi-agent only for proven gaps (e.g. multi-intent tickets or permission isolation between billing and logistics teams). Show the comparison table. Present cost multiplication honestly.

**Scenario 2 — Permission isolation as the real reason.** Billing data must never be visible to the logistics assistant. *Reasoning:* separate specialists with disjoint tools and scopes, isolated state, and a supervisor that only sees summaries. This is a legitimate multi-agent driver even without accuracy gains.

**Scenario 3 — Latency budget of 8 s.** *Reasoning:* sequential supervisor rounds won't fit. Use a rule router plus one specialist, parallel delegations, cheaper routing models, and streaming progress.

**Scenario 4 — Different teams own different agents.** *Reasoning:* contracts become team boundaries: versioned schemas, contract tests in CI, per-agent eval suites and SLOs, and MCP or internal APIs if specialists run as separate services (Unit 40).

### 13. Interview Preparation

#### Quick Questions

**Q: When is a multi-agent system justified?**
*Strong answer:* When roles need isolated context or permissions, independent subtasks benefit from parallelism, or separate ownership matters, and an eval shows it beats a single agent at acceptable cost.

**Q: Supervisor vs router?**
*Strong answer:* A router makes one choice and hands off. A supervisor iterates: delegates, reads results, delegates again or synthesizes.

**Q: How do you prevent agent loops?**
*Strong answer:* Delegation caps, per-agent caps, signatures for duplicate requests, depth limits, a global budget and max rounds, with refusals fed back as observations.

#### Intermediate Questions

**Q: How do you handle authorization across agents?**
*Strong answer:* Every agent runs with the original user's identity narrowed to its scopes by intersection. Delegation never widens permissions, identity never comes from model inputs, and denials propagate instead of being rerouted.

**Q: Shared or isolated state?**
*Strong answer:* Isolated by default with typed results. Shared blackboards spread context, cost and injected content and blur ownership.

**Q: How do you control cost?**
*Strong answer:* A run budget sliced to children, summaries instead of transcripts, cheaper models where quality allows, prompt caching, rule routing for easy cases, and per-agent cost metrics.

#### Advanced Questions

**Q: Design agent-to-agent contracts.**
*Strong answer:* Typed delegation requests with validated per-specialist inputs, typed results with status, findings, citations, proposals, usage and contract version. Contract tests in CI, versioned evolution like an API.

**Q: How do failures propagate?**
*Strong answer:* Status-based handling: partial results used with stated gaps, transient failures retried once within budget, denials reported not bypassed, approvals bubbled up to pause the run, and child timeouts derived from the parent deadline with a synthesis reserve.

#### Coding Questions

1. Implement `RunBudget.admit` with tests.
2. Implement `ToolContext.narrow` and a property test.
3. Implement parallel delegation with per-child timeouts using AnyIO.

#### Scenario Questions

**Q: Your multi-agent system gives a worse answer than the single agent on simple questions. Why, and what do you do?**
*Strong answer:* Extra hops lose context and add misrouting, and summaries drop details. Route simple intents directly (rule router or single agent), keep the supervisor for multi-intent cases, and verify with the segmented eval.

### 14. Explain-It-at-Three-Levels

**Concept: Multi-agent systems**

- *30 seconds:* A supervisor delegates subtasks to specialists that each have their own tools and permissions, then combines their results. It's useful for isolation and multi-part tasks, but costs more, so we bound it and prove it beats one agent.
- *2 minutes:* Patterns, state isolation, contracts, limits, failure handling, tracing, baseline comparison.
- *Deep:* Budget slicing, privilege narrowing, contract versioning, parallel cancellation, and evaluation by segment.

**Concept: Cost multiplication**

- *30 seconds:* Each agent adds prompts, tools and reasoning steps, so multi-agent runs typically cost several times more. Measure against a single-agent baseline before adopting.
- *2 minutes:* Sources of tokens, mitigations, routing easy cases away from the supervisor.
- *Deep:* Per-agent cost attribution, caching, model mixing and quality trade-offs.

#### Knowledge Check Answers

1. Context isolation, permission isolation, parallelizable independent subtasks, separate team ownership/evaluation.
2. Context bloat and cost, the spread of injected text across agents, and exposure of data the supervisor doesn't need.
3. The child context's scopes are the intersection of the user's scopes and the specialist's scopes, so never wider than either.
4. So the model knows why the delegation didn't happen and changes course, instead of the loop silently repeating.
5. Report the limitation to the user (or escalate), never retry via another specialist to bypass it.
6. To make sure the answer is grounded in evidence actually retrieved during the run, not invented sources.
7. A share of the remaining time minus the synthesis reserve, with a minimum of 5 s.
8. That child returns `failed` (timeout). The others continue and their results are used.
9. Routing (is research invoked for every request?), the per-agent token metrics, the size of the research results, the prompt size, whether results are cached, and the eval segmentation.
10. Not necessarily. If the customer specialist was denied only because it doesn't hold the refund tool, the order specialist proposing an approval-gated refund is the designed path. It's a bug if the *user* lacked the refund scope: narrowing by intersection should then deny it in every specialist.
11. Generally no. Keep a star topology. Mesh delegation creates loops and unclear accountability.
12. Each specialist exposes a typed API or an MCP server (Unit 40), receives a delegated identity token (not model-supplied identity), propagates the trace context, and enforces its own authorization.

### 16. Common Interview Traps

- **"More agents = better results."** Often worse and always more expensive without evidence.
- **"Agents can share one big state."** That spreads context, cost and injection.
- **"The supervisor can pass the user ID to specialists."** Identity comes from the authenticated context, not model output.
- **"If one agent is denied, try another."** Privilege escalation.
- **"We'll trace each agent separately."** You need one trace per run with child spans.
- **"Handoffs don't need limits."** Ping-pong is the classic failure.

### 17. Cheat Sheet

- **Patterns:** router · supervisor · handoff · orchestrator-workers · evaluator-optimizer.
- **Default:** single agent; multi-agent only with a named reason + eval evidence.
- **Contracts:** `Delegate(to, task, inputs)` → validated per specialist → `SpecialistResult(status, findings, citations, proposal_ids, usage, contract_version)`.
- **Limits:** delegations total/per specialist, signatures, max rounds, depth, budget slices, synthesis reserve.
- **Security:** `ctx.narrow(scopes)` by intersection; identity from original context; denials propagate.
- **Failures:** ok · partial · failed · denied · needs_approval → explicit supervisor behavior.
- **Observability:** one trace, child spans per delegation, per-agent tokens/cost, outcome attributes.
