## Unit 27 — AWS for Python/FastAPI Engineers

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** IAM (principals, policies, roles, trust policies, policy evaluation) and **write** least-privilege policies for a FastAPI task, a worker and a CI deployer.
2. **Design** a VPC for a web service: public/private subnets across availability zones, route tables, NAT, security groups, VPC endpoints, and **explain** what each protects.
3. **Compare** EC2, ECS on Fargate, Lambda (+ API Gateway), and Bedrock AgentCore runtime for different Python workloads, using cost, latency, concurrency, duration limits and operations as criteria.
4. **Deploy** a representative FastAPI stack on ECS Fargate behind an ALB, with images from ECR, RDS PostgreSQL (pgvector), ElastiCache, S3, SQS or MSK, CloudWatch logs/metrics, and secrets from Secrets Manager / Parameter Store.
5. **Manage** RDS connections correctly: pool sizing math, RDS Proxy, Lambda connection storms, failover behavior, IAM database authentication.
6. **Implement** stateless deployment and autoscaling (target tracking on CPU/requests, queue-depth scaling for workers) and graceful shutdown on ECS.
7. **Call** Amazon Bedrock from Python (Converse / ConverseStream with boto3) with IAM-scoped access, and **explain** when Bedrock fits vs a direct provider API.
8. **Debug** common AWS failures: tasks failing to start, `AccessDenied`, timeouts to RDS, NAT/egress issues, secrets not injected, Lambda cold starts and connection exhaustion.

### 2. Prerequisite Knowledge

- Units 25–26: container image, health checks, CI with OIDC.
- Networking: CIDR blocks, private vs public IPs, DNS, TCP ports.
- PostgreSQL connection model: one backend process per connection, so connections are expensive. `max_connections` is finite and scales with instance memory.
- boto3 basics: clients vs resources, credential chain (env → shared config → container/instance role), pagination, retries (`botocore.config.Config(retries={"mode": "adaptive"})`).

**Refresher: the AWS credential chain inside a container.** On ECS, the task's **task role** credentials come from the container credentials endpoint (`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`), and boto3 picks them up automatically. You never put access keys in images or environment variables.

### 3. Mental Model

AWS is **a set of managed building blocks connected by networks and authorized by IAM**. Every request is two questions: *can the packet get there?* (VPC routing, security groups, NACLs, endpoints) and *is the caller allowed?* (IAM policies, resource policies, key policies).

```
Internet ─▶ Route 53 ─▶ ALB (public subnets, SG: 443 from 0.0.0.0/0, WAF)
                          │
                          ▼  SG: 8000 from ALB SG only
            ECS Fargate tasks: api ×N, worker ×M (private subnets, task role, exec role)
              │        │          │             │                 │
              ▼        ▼          ▼             ▼                 ▼
         RDS Proxy  ElastiCache  SQS / MSK    S3 (VPC gateway   Bedrock / external LLM
           │        (Redis/Valkey)            endpoint)         (interface endpoint or NAT)
           ▼
         RDS PostgreSQL Multi-AZ (private subnets, SG: 5432 from Proxy SG only)
Secrets Manager / Parameter Store ─▶ injected into tasks at start (exec role) or fetched at runtime (task role)
CloudWatch Logs / Metrics / Alarms ◀─ awslogs/FireLens + OTel collector (ADOT)
```

Rule of thumb: **the network decides reachability, IAM decides permission, and you need both**. A security group allowing port 5432 doesn't let a task read a secret, and an IAM policy allowing `bedrock:InvokeModel` doesn't help if the task has no route to Bedrock.

### 4. Comprehensive Theory

#### 4.1 IAM

**Concepts.**

- **Principals:** users (avoid for workloads), roles (assumed by services/people via STS), AWS services.
- **Identity-based policies** attached to roles; **resource-based policies** on resources (S3 bucket policies, KMS key policies, SQS queue policies); **trust policies** say *who may assume a role*; **permission boundaries** and **SCPs** cap the maximum.
- **Evaluation:** explicit `Deny` wins → otherwise need an `Allow` from applicable policies (and within boundaries/SCPs) → default deny.
- **Conditions:** `aws:SourceVpce`, `aws:PrincipalTag`, `s3:prefix`, `aws:SecureTransport`, etc.

**ECS has two roles. Don't confuse them.**

| Role | Used by | Typical permissions |
|---|---|---|
| **Task execution role** | ECS agent, to start the task | Pull from ECR, write logs, fetch secrets referenced in the task definition |
| **Task role** | Your application code at runtime | S3 bucket prefix, SQS queue, Bedrock model invocation, specific secrets |

**Least privilege example (task role for the API).**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "KbBucketRead",
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::supportdesk-kb-prod/tenants/*" },
    { "Sid": "IngestQueueSend",
      "Effect": "Allow",
      "Action": ["sqs:SendMessage"],
      "Resource": "arn:aws:sqs:eu-west-1:123456789012:supportdesk-ingest" },
    { "Sid": "BedrockInvoke",
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:eu-west-1::foundation-model/amazon.titan-embed-text-v2:0",
        "arn:aws:bedrock:eu-west-1:123456789012:inference-profile/eu.anthropic.*"
      ] }
  ]
}
```

(`Converse`/`ConverseStream` calls are authorized by `bedrock:InvokeModel` / `bedrock:InvokeModelWithResponseStream`. Cross-region inference profiles need permission on both the profile and the underlying models. [Version-dependent] Check current Bedrock IAM docs for the exact resource ARNs your models need.)

**Common mistakes.** `"Action": "s3:*", "Resource": "*"`. Using the execution role as the task role. Long-lived access keys on laptops and in CI (use SSO and OIDC). Forgetting KMS key policies when buckets or secrets use customer-managed keys.

**Interview perspective.** Interviewers check that you scope by action, resource and condition, separate roles by workload, and know where credentials come from.

#### 4.2 VPC Concepts

- **VPC:** your private network (for example `10.0.0.0/16`) in a region.
- **Subnets:** per AZ. **Public** subnets have a route to an Internet Gateway (for ALBs and NAT gateways). **Private** subnets have no direct inbound internet; outbound goes via a **NAT gateway** (or not at all).
- **Security groups (SGs):** stateful, allow-only, attachable per ENI, and can reference other SGs ("allow 5432 from the API SG"). **NACLs:** stateless subnet-level filters, rarely needed.
- **VPC endpoints:** **gateway endpoints** for S3/DynamoDB (free, route-table based). **Interface endpoints** (PrivateLink ENIs, hourly + data cost) for ECR, CloudWatch Logs, Secrets Manager, SQS, STS and Bedrock Runtime. Endpoints keep traffic private and reduce NAT data-processing costs.
- **Multi-AZ:** spread subnets, tasks and databases across ≥ 2 AZs to survive an AZ failure.

**NAT costs.** NAT gateways charge per hour and per GB processed. Image pulls and S3/ECR traffic through NAT can be a surprising bill. Use endpoints for heavy AWS-service traffic.

#### 4.3 Compute: EC2, ECS/Fargate, Lambda, API Gateway

| Option | Model | Strengths | Limits / costs | Good for |
|---|---|---|---|---|
| **EC2** | VMs you manage | Full control, GPUs, cheapest at steady high utilization (Savings Plans/Spot) | Patching, scaling, AMIs | Custom runtimes, GPU inference, legacy |
| **ECS on Fargate** | Serverless containers; tasks with vCPU/memory | No servers; long-running; any duration; WebSockets/SSE; per-task IAM | Pay per vCPU-second even when idle at min capacity; cold start of new tasks ~tens of seconds | FastAPI APIs, workers, agent runtimes |
| **ECS on EC2** | Containers on your instances | Bin-packing, GPUs, cheaper at scale | Manage capacity providers | Large fleets, GPUs |
| **Lambda** | Functions per event; scales per request | Scale to zero; per-ms billing; event integrations (SQS, S3, EventBridge) | 15-minute max; cold starts (SnapStart for Python mitigates); concurrency and connection storms; payload limits; response streaming has caveats | Spiky/low-volume APIs, event handlers, glue |
| **API Gateway** | Managed HTTP/REST/WebSocket front door | Auth (JWT/Cognito/IAM), throttling, usage plans | Integration timeout limits (raised for REST APIs, check current limits); cost per request | Lambda front end, public APIs with quotas |
| **Bedrock AgentCore Runtime** | Managed runtime for agent code | Session isolation, identity, memory/gateway services for agents | Newer service; check regions/quotas [Version-dependent] | Hosting agents without building infra |

**FastAPI on Lambda.** Use an ASGI adapter (Mangum, or AWS Lambda Web Adapter running Uvicorn). This works well for simple APIs. It's weaker for long-lived streaming (SSE), WebSockets, heavy startup (large dependencies), and anything holding many DB connections.

**Decision heuristics.**

- Steady traffic, streaming responses, long agent runs, or WebSockets → **ECS Fargate**.
- Event-driven glue, spiky low-volume endpoints, cron-like jobs < 15 min → **Lambda**.
- GPU or very high steady load → **EC2/ECS on EC2** (or managed inference such as Bedrock/SageMaker).

#### 4.4 Data Services: RDS, S3, ElastiCache, Messaging

**RDS PostgreSQL.** Managed backups, Multi-AZ failover (the standby promotes in roughly 1–2 minutes and the DNS endpoint flips), read replicas, Performance Insights, parameter groups. **Aurora PostgreSQL** has shared distributed storage, faster failover and up to 15 replicas. Both support the `vector` extension (pgvector). Check the supported pgvector version per engine version. [Version-dependent]

**RDS connection management.**

```
total connections = Σ over services (tasks × processes_per_task × (pool_size + max_overflow))
example: 20 API tasks × 1 process × (5 + 5) = 200, + 6 workers × (5 + 5) = 60 → 260 connections
```

Compare against `max_connections` (which depends on instance memory) minus a reserve for admin/maintenance. Scaling out API tasks multiplies connections, which is the classic outage during traffic spikes.

**Mitigations:**

- **Small per-process pools**, sized by Little's Law: concurrent DB work per process, not concurrent requests.
- **RDS Proxy**: pools and multiplexes connections, absorbs connection storms (essential for Lambda), and preserves connections during failover, which shortens application-visible failover. Watch for **pinning**: session state (`SET`, prepared statements in some drivers, temp tables, advisory locks) pins a client to a backend and reduces multiplexing.
- `pool_pre_ping=True` and `pool_recycle` to drop dead connections after failover. Retry idempotent operations on connection errors.
- **IAM database authentication** (short-lived tokens) or Secrets Manager with rotation for passwords.
- For Lambda: create the engine/pool **outside the handler** (reused across warm invocations), use `NullPool` or pool size 1 behind RDS Proxy, and cap reserved concurrency.

**S3.** Object storage for documents, exports and eval artifacts. Block Public Access on, default encryption (SSE-S3 or SSE-KMS), bucket policies requiring TLS, lifecycle rules, and presigned URLs for client uploads/downloads (short expiry, scoped key) so large files don't pass through your API.

**ElastiCache (Redis OSS / Valkey).** Caching, rate limits, short-lived state. Cluster mode for scale-out. TLS in transit + AUTH/RBAC. ElastiCache Serverless for spiky loads. It isn't durable storage: design for cache loss.

**Messaging.**

| Service | Model | Ordering | Use |
|---|---|---|---|
| **SQS Standard** | Queue, at-least-once, nearly unlimited throughput | Best-effort | Background jobs, ingestion tasks |
| **SQS FIFO** | Exactly-once processing within dedupe window, ordered per message group | Per group | Per-customer ordered work |
| **SNS** | Pub/sub fan-out | — | Fan-out to queues/Lambdas/emails |
| **EventBridge** | Event bus with routing rules, schedules | — | Integrations, cron, SaaS events |
| **Amazon MSK** (Kafka) / MSK Serverless | Partitioned log | Per partition | Event streaming, replay, many consumers |
| **Kinesis Data Streams** | Partitioned stream | Per shard | AWS-native streaming |

For SupportDesk, SQS is the simplest choice for ingestion and agent-run jobs. MSK fits if the organization already standardizes on Kafka or needs replay across many consumer groups. In either case: at-least-once delivery, idempotent consumers (Unit 25 worker), DLQs (SQS redrive policy), visibility timeouts longer than processing time, and scaling on queue depth.

#### 4.5 CloudWatch, Secrets Manager, Parameter Store

**CloudWatch.** Logs (log groups per service, retention set explicitly, Logs Insights queries), metrics (ECS/ALB/RDS built-ins plus custom via EMF or OTel), alarms (on SLOs: ALB 5xx rate, target response time p95, RDS CPU/connections/free storage, SQS age of oldest message), dashboards. For traces, use AWS Distro for OpenTelemetry (ADOT) → X-Ray/CloudWatch Application Signals, or export to a third-party backend.

**Structured JSON logs** with request/trace IDs make Logs Insights effective:

```
fields @timestamp, level, msg, trace_id, route, status, latency_ms
| filter service = "api" and status >= 500
| stats count() by route
| sort count() desc
```

**Secrets Manager vs Parameter Store.**

| | Secrets Manager | SSM Parameter Store |
|---|---|---|
| Purpose | Secrets with **rotation** (DB passwords, API keys) | Config + secrets (SecureString) |
| Rotation | Built-in (Lambda rotation, RDS-managed) | No built-in rotation |
| Cost | Per secret per month + API calls | Standard tier free; advanced tier paid |
| Use | DB creds, provider API keys | Feature flags, non-secret config, simple SecureStrings |

**Injection patterns on ECS.**

1. **Task definition `secrets`**: ECS fetches values at task start (execution role) and injects them as env vars. Simple, but rotated values only take effect on new tasks.
2. **Fetch at runtime** with the task role (boto3 + a cache with TTL). Supports rotation without redeploy, at the cost of more code and handling fetch failures.

Never log secrets. Mask them in Pydantic with `SecretStr`.

#### 4.6 ECR and Container Deployment

**ECR.** Private registry per account/region. Enable **image scanning** (basic or Inspector enhanced), **tag immutability** (prevent overwriting `:sha` tags), lifecycle policies (expire untagged images, keep last N), and cross-account pull for multi-account setups. Push via CI with OIDC (Unit 26).

**ECS task definition essentials.** Image by digest, CPU/memory, port mappings, `healthCheck`, `logConfiguration` (awslogs or FireLens), `secrets`, environment, `stopTimeout`, `readonlyRootFilesystem`, task role and execution role, `runtimePlatform` (ARM64/Graviton is usually cheaper if all dependencies have ARM wheels).

**Service:** desired count, deployment configuration (circuit breaker), load balancer target group (health check path `/health/ready`, deregistration delay matching your drain time), autoscaling (target tracking on `ECSServiceAverageCPUUtilization` or `ALBRequestCountPerTarget`; workers on SQS `ApproximateNumberOfMessagesVisible` per task or age of oldest message).

**Stateless deployment.** No local files that matter (write to S3), no in-memory sessions (use JWT or Redis), no sticky sessions requirement, idempotent startup, configuration from environment. Any task can be killed at any time, and Fargate Spot will do exactly that with a 2-minute warning.

#### 4.7 Bedrock for AI Workloads

**What it is.** A managed service to call foundation models (Anthropic Claude, Amazon Nova/Titan, Meta Llama, Mistral, Cohere, and others) through AWS APIs, with IAM auth, VPC endpoints, CloudWatch metrics, regional data processing, Guardrails, Knowledge Bases (managed RAG), Agents, and AgentCore (agent runtime, memory, identity, gateway, code interpreter).

**APIs.**

- **Converse / ConverseStream** (`bedrock-runtime`): one message format across models, with tool use and system prompts. AWS recommends it over `InvokeModel` where supported.
- **InvokeModel**: model-native request bodies. Use it for features not exposed via Converse.
- For Claude specifically, Anthropic's SDK also offers a Bedrock client (`AnthropicBedrockMantle`) that speaks the Messages API against Bedrock. [Version-dependent]

**When Bedrock vs direct provider API.**

| Factor | Bedrock | Direct provider API |
|---|---|---|
| Auth/networking | IAM roles, VPC endpoints, no API keys to manage | API keys in Secrets Manager; egress through NAT/proxy |
| Data governance | AWS region, AWS agreements, CloudTrail | Provider's terms and regions |
| Feature lag | Some features arrive later or differ | Newest features first |
| Quotas | AWS service quotas per region/model (tokens/min) | Provider rate limits |
| Multi-model | Many providers behind one API | One provider per SDK |

Many enterprises (common in FDE work) mandate Bedrock for governance. Design your LLM client (Unit 29) so Bedrock is just another adapter.

### 5. Internal Mechanics

#### 5.1 What happens when an ECS Fargate task starts

```
Service scheduler decides to place a task (deployment/scale-out/replacement)
→ Fargate provisions an isolated micro-VM with an ENI in your private subnet (awsvpc mode)
→ ECS agent uses the EXECUTION role: pull image from ECR (via NAT or ECR interface + S3 gateway endpoints),
   fetch secrets from Secrets Manager/SSM, create log stream
→ container starts with env + injected secrets; TASK role credentials served via container credentials endpoint
→ container health check passes → service registers task IP in ALB target group
→ ALB health checks pass (healthy threshold) → traffic flows
On stop: deregister from target group (deregistration delay drains connections) → SIGTERM → stopTimeout → SIGKILL
```

Most "task stuck in PENDING/STOPPED" issues are failures in the second arrow: image pull (no route to ECR/S3) or secrets fetch (execution role lacks permission, KMS key policy, or no route to Secrets Manager).

#### 5.2 What happens on an RDS Multi-AZ failover

```
Primary failure detected → standby promoted → DNS CNAME of the endpoint updated (short TTL)
→ existing connections are dropped → clients see errors on in-flight queries
→ pools must discard dead connections (pre_ping) and reconnect (new DNS resolution)
→ with RDS Proxy: proxy holds client connections, reconnects to new primary; clients see shorter blips
```

#### 5.3 What happens on a Bedrock Converse call

```
boto3 signs request (SigV4) with task-role credentials → bedrock-runtime endpoint
(public or VPC interface endpoint) → IAM authorization on model/profile ARN
→ quota check (tokens/requests per minute) → ThrottlingException if exceeded
→ model inference → response with output message, stopReason, usage {inputTokens, outputTokens}, metrics.latencyMs
```

### 6. Implementation Examples

#### Example 1 — Minimal: Settings with secrets from AWS and a boto3 client with sane retries

```python
# app/core/aws.py
import json
import time
from functools import lru_cache
from threading import Lock

import boto3
from botocore.config import Config

BOTO_CONFIG = Config(
    retries={"mode": "adaptive", "max_attempts": 5},   # adaptive = standard + client-side rate limiting
    connect_timeout=2,
    read_timeout=10,
)


@lru_cache
def secrets_client():
    return boto3.client("secretsmanager", config=BOTO_CONFIG)


class SecretCache:
    """Runtime secret fetch with TTL, so rotated secrets are picked up without redeploy."""

    def __init__(self, ttl_seconds: int = 300) -> None:
        self._ttl = ttl_seconds
        self._values: dict[str, tuple[float, dict[str, str]]] = {}
        self._lock = Lock()

    def get(self, secret_id: str) -> dict[str, str]:
        now = time.monotonic()
        with self._lock:
            cached = self._values.get(secret_id)
            if cached and now - cached[0] < self._ttl:
                return cached[1]
        resp = secrets_client().get_secret_value(SecretId=secret_id)
        value = json.loads(resp["SecretString"])
        with self._lock:
            self._values[secret_id] = (now, value)
        return value


secret_cache = SecretCache()
```

boto3 is synchronous. Calling it from `async def` endpoints blocks the event loop. Either call it in a thread (`await anyio.to_thread.run_sync(...)` / `asyncio.to_thread`), use `aioboto3`, or call it at startup only. Secrets are typically fetched in lifespan or cached, so the cost is negligible.

#### Example 3 — Production-oriented: Bedrock Converse client, SQS worker, and the ECS vs Lambda comparison

**Bedrock Converse with streaming, timeouts and usage logging.**

```python
# app/llm/bedrock_adapter.py
import logging
import time
from collections.abc import Iterator
from dataclasses import dataclass

import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

log = logging.getLogger("llm.bedrock")

_RETRYABLE = {"ThrottlingException", "ServiceUnavailableException", "ModelNotReadyException",
              "InternalServerException"}


@dataclass(frozen=True)
class Usage:
    input_tokens: int
    output_tokens: int
    latency_ms: int


class BedrockChat:
    def __init__(self, model_id: str, region: str) -> None:
        self._model_id = model_id
        self._client = boto3.client(
            "bedrock-runtime",
            region_name=region,
            config=Config(retries={"mode": "adaptive", "max_attempts": 4},
                          connect_timeout=3, read_timeout=60),
        )

    def complete(self, system: str, user: str, max_tokens: int = 1024) -> tuple[str, Usage]:
        started = time.monotonic()
        try:
            resp = self._client.converse(
                modelId=self._model_id,                     # model ID or inference profile ARN
                system=[{"text": system}],
                messages=[{"role": "user", "content": [{"text": user}]}],
                inferenceConfig={"maxTokens": max_tokens},
            )
        except ClientError as e:
            code = e.response["Error"]["Code"]
            log.warning("bedrock_error code=%s retryable=%s", code, code in _RETRYABLE)
            raise
        text = "".join(b.get("text", "") for b in resp["output"]["message"]["content"])
        usage = Usage(resp["usage"]["inputTokens"], resp["usage"]["outputTokens"],
                      int((time.monotonic() - started) * 1000))
        log.info("bedrock_call model=%s stop=%s in=%d out=%d ms=%d", self._model_id,
                 resp["stopReason"], usage.input_tokens, usage.output_tokens, usage.latency_ms)
        return text, usage

    def stream(self, system: str, user: str, max_tokens: int = 1024) -> Iterator[str]:
        resp = self._client.converse_stream(
            modelId=self._model_id,
            system=[{"text": system}],
            messages=[{"role": "user", "content": [{"text": user}]}],
            inferenceConfig={"maxTokens": max_tokens},
        )
        for event in resp["stream"]:
            if "contentBlockDelta" in event:
                yield event["contentBlockDelta"]["delta"].get("text", "")
            elif "metadata" in event:
                u = event["metadata"]["usage"]
                log.info("bedrock_stream_usage in=%d out=%d", u["inputTokens"], u["outputTokens"])
```

Notes. Logs contain sizes, model and usage, never the prompt or response text (Unit 29 covers safe logging). `inferenceConfig` also accepts `temperature`/`topP` for models that support them. Some newer models reject sampling parameters, so keep them optional per model in configuration. boto3 is synchronous: call `complete` via `anyio.to_thread.run_sync` from async endpoints, or use an async AWS client.

import signal
import threading

def process(message: dict) -> None:
    body = json.loads(message["Body"])
    # Idempotency: unique (document_id, version) in Postgres; second delivery is a no-op.
    ingest_document(body["document_id"], body["version"])


def main() -> None:
    while not stop.is_set():
        resp = sqs.receive_message(QueueUrl=QUEUE_URL, MaxNumberOfMessages=10,
                                   WaitTimeSeconds=20,             # long polling: fewer empty receives
                                   VisibilityTimeout=300)          # > max processing time
        for msg in resp.get("Messages", []):
            try:
                process(msg)
                sqs.delete_message(QueueUrl=QUEUE_URL, ReceiptHandle=msg["ReceiptHandle"])
            except Exception:
                log.exception("processing failed; message will reappear after visibility timeout")
                # After maxReceiveCount (redrive policy) SQS moves it to the DLQ.
    log.info("worker stopping")


def ingest_document(document_id: str, version: int) -> None: ...

    logging.basicConfig(level=logging.INFO)
    main()

| Workload | Recommendation | Reasoning |
|---|---|---|
| Public API with SSE streaming of agent progress | ECS Fargate | Long-lived connections, steady traffic, connection pooling |
| Document ingestion (minutes per large PDF, bursts) | ECS Fargate worker scaled on SQS depth (or Lambda if < 15 min and light) | Duration and memory; heavy parsing libraries |
| S3 upload → enqueue ingestion message | Lambda | Tiny event glue, scale to zero |
| Nightly eval run (30–90 min) | ECS scheduled task (EventBridge Scheduler) | Exceeds Lambda's 15-minute limit |
| Low-traffic internal admin API | Lambda + API Gateway (or Function URL) | Scale to zero; low cost; RDS Proxy for DB |
| Agent runs with tool calls lasting minutes | ECS worker or Bedrock AgentCore Runtime | Duration, state, streaming, concurrency control |

### 7. Comparative Analysis

| Comparison | Key difference | Use when | Trap |
|---|---|---|---|
| Task role vs execution role | App runtime permissions vs ECS agent startup permissions | Separate, least privilege each | Giving the app the execution role's powers (or vice versa) |
| Security group vs NACL | Stateful, per-ENI, allow-only vs stateless, subnet-level | SGs almost always | Opening 0.0.0.0/0 to the DB "temporarily" |
| NAT vs VPC endpoints | General egress vs private path to AWS services | Endpoints for ECR/S3/Logs/Secrets/Bedrock | Surprise NAT data charges |
| ECS Fargate vs Lambda | Long-running containers vs per-event functions | See table above | FastAPI on Lambda with SSE and big pools |
| RDS vs Aurora | Instance storage vs distributed storage, faster failover | Aurora for scale/HA; RDS for simplicity/cost | Assuming Multi-AZ = read scaling (it isn't) |
| RDS Proxy vs app pooling only | Central multiplexed pool vs per-process pools | Proxy for Lambda, many tasks, failover smoothing | Pinning from session state defeats multiplexing |
| Secrets Manager vs Parameter Store | Rotation vs config + simple secrets | Secrets Manager for credentials | Secrets in plain env vars in task definitions |
| SQS vs MSK | Managed queue vs Kafka log | SQS for jobs; MSK for streaming/replay | Using Kafka for a simple job queue |
| Bedrock vs direct API | AWS IAM/governance vs newest features | Enterprise governance → Bedrock | Assuming feature parity |

### 8. Failure Modes and Debugging

**Failure 1 — Task stops with `CannotPullContainerError`.**

- CAUSE: no route to ECR/S3 from private subnets (no NAT, missing endpoints), execution role lacks ECR permissions, wrong digest.
- INVESTIGATE: `aws ecs describe-tasks --cluster c --tasks t --query 'tasks[].stoppedReason'`; check route tables and endpoints (ECR API + ECR DKR interface endpoints **and** S3 gateway endpoint, since layers come from S3).
- FIX/PREVENT: add endpoints or NAT; IaC tests for the network.

**Failure 2 — `ResourceInitializationError: unable to pull secrets`.**

- CAUSE: execution role lacks `secretsmanager:GetSecretValue` on that ARN, KMS key policy denies decrypt, or no route to Secrets Manager.
- FIX: grant on exact ARNs, add `kms:Decrypt` with key policy, interface endpoint.

**Failure 3 — `AccessDenied` from the app (S3/Bedrock).**

- INVESTIGATE: the error message shows the principal ARN. Check whether it's the task role. Use IAM Policy Simulator and CloudTrail event `errorCode=AccessDenied`. Check resource policies and SCPs.
- FIX: least-privilege grant on the precise resource. Don't widen to `*`.

**Failure 4 — `remaining connection slots are reserved` during a spike.**

- CAUSE: autoscaling multiplied tasks × pool size beyond `max_connections`; Lambda concurrency burst without a proxy.
- INVESTIGATE: RDS `DatabaseConnections` metric vs task count; `pg_stat_activity` grouped by `application_name`.
- FIX: RDS Proxy, smaller pools, cap max tasks, reserved concurrency for Lambda.
- PREVENT: connection budget documented; alarm at 80% of `max_connections`.

**Failure 5 — Timeouts to an external LLM API from private subnets.**

- CAUSE: no NAT/egress path, egress firewall blocks the domain, DNS resolution through a restricted resolver.
- INVESTIGATE: run a debug task in the same subnet with `curl -v`; check VPC Flow Logs.
- FIX: NAT or egress proxy with allowlist; or use Bedrock via interface endpoint.

**Failure 6 — Bedrock `ThrottlingException` under load.**

- CAUSE: tokens-per-minute or requests-per-minute quota for that model/region.
- FIX: adaptive retries with jitter, client-side token budgeting (Unit 29), request a quota increase, cross-region inference profiles, fallback model.

**Failure 7 — 502s during deployments.**

- CAUSE: tasks stopped before draining (deregistration delay > stopTimeout), app not handling `SIGTERM`, readiness not failing during shutdown.
- FIX: align timings; graceful shutdown (Unit 25).

### 13. Interview Preparation

#### Quick Questions

**Q: Task role vs execution role?**
*Strong answer:* Execution role: what ECS needs to start the task (pull image, write logs, fetch injected secrets). Task role: what the application code can do at runtime.

**Q: How do you keep a FastAPI service stateless on ECS?**
*Strong answer:* No local persistent files (S3), no in-memory sessions (JWT/Redis), config from env/secrets, idempotent startup, any task killable at any time.

**Q: Secrets Manager or Parameter Store?**
*Strong answer:* Secrets Manager for credentials needing rotation and audit; Parameter Store for configuration and simple secure strings.

#### Intermediate Questions

**Q: How do you manage RDS connections for a horizontally scaled FastAPI service?**
*Strong answer:* Budget connections: tasks × processes × (pool + overflow) ≤ `max_connections` minus a reserve. Small pools sized from DB time per request, RDS Proxy for multiplexing and failover smoothing (watch pinning), pre-ping and recycle, a max task count tied to the budget, alarms on connection count, and retries for idempotent operations on failover.
*Trap:* "Just increase `max_connections`." Each connection costs memory and CPU on the database.

**Q: ECS Fargate or Lambda for a FastAPI agent API?**
*Strong answer:* Fargate for streaming, long runs, steady load and pooled connections. Lambda for spiky, short, event-driven pieces. Support the choice with duration, concurrency and cost numbers.

**Q: How would you let the API call Bedrock with least privilege?**
*Strong answer:* Task role allowing `bedrock:InvokeModel*` only on the specific model/inference-profile ARNs, an interface VPC endpoint (optionally with an endpoint policy), no API keys, and CloudTrail for audit.

#### Advanced Questions

**Q: Walk me through what happens when an ECS task starts in a private subnet, and where it can fail.**
*Strong answer:* Section 5.1 with failure points: ECR/S3 reachability, execution role/KMS for secrets, container health, ALB health, and SG rules.

**Q: Design multi-AZ resilience for SupportDesk.**
*Strong answer:* ALB across AZs, ≥ 2 tasks spread across AZs (Fargate spreads across subnets), RDS Multi-AZ + Proxy, ElastiCache with replicas and automatic failover, SQS (regional by design), and S3 (regional). Test failover, set alarms, and document RTO/RPO.

#### Coding Questions

1. Write a boto3 Converse call with adaptive retries and usage logging.
2. Write an SQS long-polling worker with graceful shutdown and DLQ semantics.
3. Write a least-privilege IAM policy for reading one S3 prefix and sending to one SQS queue.

#### Scenario Questions

**Q: A customer's security team asks how your service accesses their data and models. What do you show?**
*Strong answer:* The IAM matrix (roles, permissions, resources), network diagram (private subnets, endpoints, no egress), secrets handling (no static keys, rotation), CloudTrail/CloudWatch evidence, and data-flow description (what goes to Bedrock, retention). Offer a walkthrough in their account.

### 14. Explain-It-at-Three-Levels

**Concept: IAM least privilege for workloads**

- *30 seconds:* Each workload gets its own role with only the actions and resources it needs, credentials come from STS automatically, and there are no static keys.
- *2 minutes:* Execution vs task role, resource-scoped statements, conditions, OIDC for CI, and policy evaluation (explicit deny wins).

#### Knowledge Check Answers

1. SGs control network reachability (which packets can reach which ENIs and ports). IAM controls which authenticated principals may call which AWS APIs on which resources.
2. Private connectivity to AWS services without internet egress, lower data-processing cost for heavy traffic (ECR/S3), and endpoint policies for extra control.
3. Streaming/SSE and long durations, steady traffic economics, and pooled DB connections (also WebSockets, no 15-minute limit, simpler local parity).
4. More tasks means more pools, so total connections can exceed `max_connections`. New connections and query load arrive at once.
5. When a client session uses state that can't be shared (session variables, certain prepared statements, temp tables, advisory locks), the proxy binds it to one backend connection, which reduces multiplexing.
6. It's derived from the DB connection budget: 12 tasks × 10 connections plus workers stays under the proxy/DB limits.
7. So a message isn't redelivered to another worker while the first is still processing it. It must exceed maximum processing time.
8. The ALB should route only to tasks that can serve (dependencies reachable, not draining). The container health check should restart only stuck processes and must not depend on the DB.
9. Execution role lacks `GetSecretValue` on the ARN; the KMS key policy denies decrypt; no network path to Secrets Manager (no NAT/endpoint). Also possible: wrong ARN or JSON key.
10. No route to the Bedrock endpoint from private subnets (missing NAT or interface endpoint), or the task role lacks permission (that would usually be AccessDenied rather than a timeout).
11. SQS with a DLQ for simple, at-least-once background jobs (managed, scales, cheap). Use MSK if you need replay/multiple consumers or already standardize on Kafka.
12. When governance requires AWS-native auth, networking, data residency and audit, or you want multiple model providers behind one AWS API, and Bedrock's feature set meets your needs.

### 16. Common Interview Traps

- **"Put access keys in environment variables."** Use roles and STS.
- **"Multi-AZ RDS gives read scaling."** It's for HA. Read replicas scale reads.
- **"Lambda is always cheaper."** Not at steady load, and connection/duration limits matter.
- **"Security groups replace IAM."** Network and identity are separate controls.
- **"Increase `max_connections` to fix connection errors."** Fix pooling and budgets first.
- **"Bedrock and the direct API are the same."** Features, quotas and request shapes differ.
- **"Secrets in task definition env are rotated automatically."** Injected secrets refresh only on new tasks.

### 17. Cheat Sheet

- **IAM:** explicit deny > allow > implicit deny; execution role (ECR, logs, injected secrets) vs task role (app); OIDC for CI; scope by action + resource + condition.
- **VPC:** ALB in public, tasks/DB in private, SG-to-SG rules, S3 gateway + interface endpoints (ECR api/dkr, logs, secretsmanager, sts, sqs, bedrock-runtime), NAT for the rest.
- **Compute:** Fargate (APIs, workers, streaming, long jobs); Lambda (events, spiky, < 15 min); EC2/GPU (custom/heavy); AgentCore Runtime (managed agents).
- **RDS:** budget connections; small pools; RDS Proxy; pre_ping/recycle; Multi-AZ failover ~1–2 min; IAM auth or rotated secrets.
- **Messaging:** SQS (+DLQ, visibility timeout, long polling); SNS fan-out; EventBridge routing/schedules; MSK for Kafka.
- **Secrets:** Secrets Manager (rotation) vs Parameter Store (config); injected at start vs runtime fetch with TTL.
- **ECR/ECS:** immutable tags, scan on push, lifecycle policies; deploy by digest; circuit breaker; ALB readiness; deregistration delay < stopTimeout.
- **Bedrock:** `bedrock-runtime` `converse` / `converse_stream`; IAM on model/profile ARNs; quotas → ThrottlingException → adaptive retry/fallback.
- **CLI:** `aws ecs describe-services/describe-tasks`, `aws logs tail /ecs/api --follow`, `aws ecs execute-command`, `aws iam simulate-principal-policy`, `aws sts get-caller-identity`.
