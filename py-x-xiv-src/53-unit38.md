## Unit 38 — LangGraph and Durable Agent Workflows

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Model** an agent workflow as a LangGraph graph: typed state, nodes, edges, conditional routing, reducers, and `Command` for combined update-and-route.
2. **Combine** deterministic nodes (validation, authorization checks, policy, persistence) with probabilistic nodes (model decisions, drafting) and **explain** why the boundary matters.
3. **Implement** durable checkpoints with `AsyncPostgresSaver`, thread IDs, state history and resumption after failure.
4. **Implement** human-in-the-loop with `interrupt()` and `Command(resume=...)`, and **design** nodes so side effects never repeat on resume.
5. **Implement** error routes, retry policies and bounded cycles (per-cycle counters plus `recursion_limit`).
6. **Reimplement** the Unit 35 manual agent as a graph with an approval node, and **compare** the two implementations.
7. **Test** every node as a pure function and every edge (router) exhaustively, plus end-to-end graph runs with checkpoints and interrupts.

### 3. Mental Model

A LangGraph workflow is **a state machine whose transitions are code, some of whose states call a model**:

```
START → load_context (det) → decide (LLM) → route_decision (det router)
                                 ▲              ├─ call_tool → authorize (det) ─┬─ read  → execute_tool (det, retry) ─┐
                                 │              │                               └─ needs approval → propose (det, idempotent)
                                 │              │                                       → approval (interrupt) ─┬─ approved → execute_approved (det, idempotent)
                                 │              │                                                               └─ rejected → record_rejection
                                 └──────────────┴──── observe (det: append observation, update budgets) ◀────────┘
                                                ├─ final_answer → validate_answer (det) → finalize → END
                                                ├─ ask_user / escalate → finalize → END
                                                └─ limits hit → stop (det) → finalize → END
```

The model chooses among options; **the graph defines which options exist**. Every arrow is a router you can unit-test.

### 4. Comprehensive Theory

#### 4.1 Nodes, Edges, Routing and State

**State** is a `TypedDict` (or Pydantic model / dataclass). Each key may have a **reducer** (`Annotated[list[Obs], operator.add]`) that defines how node updates merge. Keys without reducers are overwritten.

**Nodes** are functions `(state) -> partial update` (sync or async). Keep them small, with a single responsibility.

**Edges.** `add_edge(a, b)` is unconditional. `add_conditional_edges(a, router, path_map)` calls `router(state) -> str` and follows the matching edge. Alternatively a node can return `Command(update={...}, goto="next")` to update and route in one step, which suits nodes whose routing depends on what they just computed.

**Supersteps.** Nodes scheduled in the same step run concurrently, and their updates merge via reducers, then a checkpoint is saved. Parallel branches writing the same non-reducer key cause an `InvalidUpdateError`.

**Design rules for state.**

- Small and serializable: IDs and summaries, not raw documents or tool payloads.
- No secrets or authorization data. Pass identity through `config["configurable"]` or a runtime context (re-derived per run), not graph state.
- Explicit counters for bounds (`steps`, `errors`, `repairs`) and an explicit `stop_reason`.

#### 4.2 Deterministic and Probabilistic Nodes

| Node type | Examples | Properties |
|---|---|---|
| Probabilistic | `decide` (next action), `draft_reply`, `summarize` | Can be wrong; outputs validated; bounded retries/repairs; cost and latency |
| Deterministic | `authorize`, `validate_answer`, `check_limits`, `propose_refund`, `execute_tool`, `finalize` | Testable as pure functions; enforce policy; perform side effects |

**The boundary rule.** Probabilistic nodes produce **proposals** (decisions, drafts). Deterministic nodes **decide what is allowed** and **perform effects**. The model never sits on the path between a request and an effect without a deterministic check in between.

#### 4.3 Checkpoints, Threads and Durable Execution

- A **thread** (`config["configurable"]["thread_id"]`) is one workflow instance. In SupportDesk, one thread per agent run (or per ticket conversation, if you want continuity).
- The checkpointer saves state after each superstep. `graph.aget_state(config)` returns the latest snapshot (`values`, `next`, `tasks`, interrupts). `aget_state_history(config)` iterates past snapshots for debugging and time travel.
- **Durability modes.** [Version-dependent] Recent LangGraph versions let you choose when checkpoints are persisted (e.g. `durability="sync" | "async" | "exit"` on invoke/stream). Use synchronous persistence for workflows with side effects and approvals, so a crash can't lose a step that already happened.
- **Resume after failure.** Re-invoking with the same `thread_id` and input `None` continues from the last checkpoint. Nodes that completed in a superstep where another node failed keep their **pending writes**, so they don't re-run.

#### 4.4 Interrupts and Resumption

```python
def approval(state):
    decision = interrupt({"proposal_id": state["proposal_id"], "summary": state["proposal_summary"]})
    return {"approval": decision}
```

1. First execution: `interrupt()` raises internally, the graph saves a checkpoint and returns. The caller sees the interrupt payload (in `result["__interrupt__"]` for `invoke`, or via `aget_state().interrupts`/tasks, depending on version).
2. Later: `await graph.ainvoke(Command(resume={"approved": True, "approver": "u-9"}), config)`.
3. The `approval` node **re-runs from the start**, and this time `interrupt()` returns the resume value.

**Consequences.**

- Anything before `interrupt()` in the same node runs twice. Keep interrupt nodes free of side effects.
- Multiple `interrupt()` calls in one node are matched by order, so keep their order deterministic.
- **The resume value is input, not truth.** Validate it in a deterministic node: is the approver authorized (checked against your identity system, not the payload), is the proposal still pending, has it expired?
- Prefer `interrupt()` in a dedicated node over `interrupt_before=[...]` at compile time when you need a payload and typed resume values. `interrupt_before` is handy for debugging breakpoints.

#### 4.5 Error Routes, Retries and Bounded Cycles

- **Retry policy per node** for transient errors (e.g. `RetryPolicy(max_attempts=3, initial_interval=0.5, retry_on=TransientError)`). Use it only on idempotent nodes.
- **Error routes:** catch domain errors inside the node and write them to state (`last_error`), then route to `observe` (the model sees "tool failed: timeout") or to `stop` when error counters exceed limits. Don't let expected errors bubble out as exceptions.
- **Bounded cycles:** a `steps` counter checked by the router (graceful stop with a reason), and `recursion_limit` in config as a hard backstop (raises `GraphRecursionError`). Set the recursion limit higher than your expected supersteps so the graceful check fires first.
- **Loop detection:** keep action signatures in state (Unit 35) and route to `stop` on repeats.

#### 4.6 Testing Graphs

- **Nodes:** call node functions directly with a state dict. Assert the returned partial update.
- **Routers:** exhaustive tables or Hypothesis over state shapes. Every branch reached and every output a valid node name.
- **Graph runs:** compile with `InMemorySaver`, fake model (scripted decisions), fake tools. Assert the node path (via `astream(stream_mode="updates")`), final state, and interrupts.
- **Durability:** Testcontainers PostgreSQL + `AsyncPostgresSaver`. Interrupt, create a fresh graph instance (simulating a restart), resume, and assert effects happen exactly once.
- **Graph structure snapshot:** `graph.get_graph().draw_mermaid()` committed and compared in tests, so structural changes are reviewed.

### 5. Internal Mechanics

#### 5.1 Execution of an approval cycle

```
invoke(input, thread T)
  superstep 1: load_context → checkpoint c1
  superstep 2: decide → checkpoint c2   (decision = CallTool issue_refund)
  superstep 3: authorize → requires approval → checkpoint c3
  superstep 4: propose (INSERT proposal ON CONFLICT DO NOTHING; key = run:step) → checkpoint c4
  superstep 5: approval → interrupt(payload) → checkpoint c5 (pending interrupt) → return to caller
... hours later, possibly another process ...
invoke(Command(resume={...}), thread T)
  load c5 → re-run approval node → interrupt() returns resume value → checkpoint c6
  superstep 7: verify_approval (det: approver authority, proposal pending, not expired) → route
  superstep 8: execute_approved (idempotent refund call with proposal key) → checkpoint c8
  superstep 9: observe → decide → ... → finalize → END
```

#### 5.2 Mapping Unit 35 concepts to graph elements

| Unit 35 (manual) | Unit 38 (graph) |
|---|---|
| `while` loop | `decide → … → observe → decide` cycle |
| `AgentDecision` validation | `decide` node with structured output + repair counter |
| `if isinstance(d, CallTool)` | `route_decision` router |
| `registry.dispatch` authorization | `authorize` node + router |
| Approval proposal | `propose` → `approval` (interrupt) → `verify_approval` → `execute_approved` |
| `Limits` checks | `check_limits` router + `recursion_limit` |
| Loop detection | signature list in state + router |
| Your checkpoints (Unit 37) | LangGraph checkpointer |
| Event sink | `astream(stream_mode=["updates", "custom"])` + `get_stream_writer()` |

### 6. Implementation Examples

#### Example 1 — Minimal: A bounded cycle with conditional routing

```python
# app/graphs/minimal_cycle.py
import operator
from typing import Annotated, Literal, TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    question: str
    attempts: int
    notes: Annotated[list[str], operator.add]
    answer: str | None


def think(state: State) -> dict:
    # Stand-in for a model call; deterministic for the example.
    n = state["attempts"] + 1
    answer = "42" if n >= 2 else None
    return {"attempts": n, "notes": [f"attempt {n}"], "answer": answer}


def route(state: State) -> Literal["think", "done"]:
    if state["answer"] is not None:
        return "done"
    if state["attempts"] >= 3:          # bounded cycle: graceful stop
        return "done"
    return "think"


def done(state: State) -> dict:
    return {"answer": state["answer"] or "Could not determine an answer."}


builder = StateGraph(State)
builder.add_node("think", think)
builder.add_node("done", done)
builder.add_edge(START, "think")
builder.add_conditional_edges("think", route, {"think": "think", "done": "done"})
builder.add_edge("done", END)
graph = builder.compile(checkpointer=InMemorySaver())

# result = graph.invoke({"question": "?", "attempts": 0, "notes": [], "answer": None},
#                       {"configurable": {"thread_id": "t1"}, "recursion_limit": 20})
```

#### Example 2 — Realistic: Approval node with interrupt, verification and idempotent execution

```python
# app/graphs/approval.py
from typing import Literal, TypedDict

from langgraph.types import Command, interrupt
from pydantic import BaseModel, ConfigDict


class ApprovalDecision(BaseModel):
    model_config = ConfigDict(extra="forbid")
    approved: bool
    reason: str = ""


class ApprovalState(TypedDict, total=False):
    run_id: str
    proposal_id: str | None
    proposal_summary: str
    approval_raw: dict | None
    approval: ApprovalDecision | None
    last_error: str | None


def make_nodes(proposals, refunds, approvers):
    async def propose(state: ApprovalState, config) -> dict:
        ctx = config["configurable"]["tool_context"]                    # injected per run, not stored in state
        proposal = await proposals.create_or_get(                       # idempotent: key = run_id:propose
            key=f"{state['run_id']}:propose", ctx=ctx, summary=state["proposal_summary"])
        return {"proposal_id": proposal.id}

    def approval(state: ApprovalState) -> dict:
        # No side effects here: this node re-runs from the top on resume.
        raw = interrupt({"type": "refund_approval", "proposal_id": state["proposal_id"],
                         "summary": state["proposal_summary"]})
        return {"approval_raw": raw}

    async def verify_approval(state: ApprovalState, config) -> Command[Literal["execute_approved", "observe"]]:
        approver_id = config["configurable"]["approver_id"]             # from the authenticated resume request
        try:
            decision = ApprovalDecision.model_validate(state["approval_raw"] or {})
        except ValueError:
            return Command(update={"last_error": "invalid approval payload"}, goto="observe")
        proposal = await proposals.get(state["proposal_id"])
        if not await approvers.may_approve(approver_id, proposal):      # authority checked in code
            return Command(update={"last_error": "approver not authorized"}, goto="observe")
        if proposal.is_expired() or proposal.status != "pending":
            return Command(update={"last_error": f"proposal {proposal.status}"}, goto="observe")
        if not decision.approved:
            await proposals.reject(proposal.id, approver_id, decision.reason)
            return Command(update={"approval": decision}, goto="observe")
        await proposals.approve(proposal.id, approver_id)
        return Command(update={"approval": decision}, goto="execute_approved")

    async def execute_approved(state: ApprovalState) -> dict:
        result = await refunds.execute_proposal(state["proposal_id"])   # idempotent: proposal ID is the key
        return {"last_error": None if result.ok else result.error}

    return propose, approval, verify_approval, execute_approved
```

**Key decisions.**

- `propose` and `execute_approved` are separate nodes with idempotency keys. `approval` only interrupts.
- The approver's identity comes from the authenticated HTTP request that resumes the graph (placed into `configurable`), not from the resume payload.
- `verify_approval` uses `Command` to update and route in one step, and every branch is explicit.

**Resuming from FastAPI.**

#### Example 3 — Production-oriented: The Unit 35 agent as a durable graph

```python
# app/graphs/support_agent.py
import operator
from typing import Annotated, Literal, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, RetryPolicy

from app.agent.decisions import AgentDecision
from app.agent.state import StopReason, action_signature
from app.graphs.approval import ApprovalDecision, make_nodes
from app.llm.errors import TransientLLMError
from app.tools.errors import ToolDenied, ToolError, TransientToolError


class Observation(TypedDict):
    step: int
    tool: str
    ok: bool
    summary: str


class AgentGraphState(TypedDict, total=False):
    run_id: str
    goal: str
    user_message: str
    decision: dict | None                       # serialized AgentDecision
    observations: Annotated[list[Observation], operator.add]
    signatures: Annotated[list[str], operator.add]
    steps: int
    errors: int
    repairs: int
    input_tokens: int
    output_tokens: int
    proposal_id: str | None
    proposal_summary: str
    approval_raw: dict | None
    approval: ApprovalDecision | None
    last_error: str | None
    stop_reason: str | None
    final: dict | None


MAX_STEPS, MAX_ERRORS, MAX_REPAIRS = 8, 3, 2


def build_support_graph(llm, registry, proposals, refunds, approvers, prompt_builder):
    propose, approval, verify_approval, execute_approved = make_nodes(proposals, refunds, approvers)

    # ---------- probabilistic ----------
    async def decide(state: AgentGraphState) -> dict:
        messages = prompt_builder.build(state)                           # bounded context (Unit 37)
        out = await llm.structured(messages, AgentDecision)              # validated union or error
        if out.error is not None:
            return {"decision": None, "repairs": state.get("repairs", 0) + 1,
                    "last_error": "invalid decision"}
        return {"decision": out.value.model_dump(mode="json"), "repairs": 0, "last_error": None,
                "input_tokens": state.get("input_tokens", 0) + out.usage.input_tokens,
                "output_tokens": state.get("output_tokens", 0) + out.usage.output_tokens}

    # ---------- deterministic ----------
    def route_decision(state: AgentGraphState) -> Literal["decide", "authorize", "validate_answer",
                                                          "finalize", "stop"]:
        if state.get("steps", 0) >= MAX_STEPS:
            return "stop"
        if state.get("decision") is None:
            return "decide" if state.get("repairs", 0) <= MAX_REPAIRS else "stop"
        kind = state["decision"]["type"]
        if kind == "call_tool":
            sig = action_signature(state["decision"]["tool"], state["decision"]["arguments"])
            return "stop" if sig in state.get("signatures", []) else "authorize"
        if kind == "final_answer":
            return "validate_answer"
        return "finalize"                                                # ask_user / escalate

    async def authorize(state: AgentGraphState, config) -> Command[Literal["execute_tool", "propose", "observe"]]:
        ctx = config["configurable"]["tool_context"]
        d = state["decision"]
        verdict = registry.authorize(d["tool"], d["arguments"], ctx)     # scopes, schema, policy
        sig = action_signature(d["tool"], d["arguments"])
        if verdict.denied:
            return Command(update={"last_error": f"denied: {verdict.reason}", "signatures": [sig]}, goto="observe")
        if verdict.requires_approval:
            return Command(update={"proposal_summary": verdict.summary, "signatures": [sig]}, goto="propose")
        return Command(update={"signatures": [sig]}, goto="execute_tool")

    async def execute_tool(state: AgentGraphState, config) -> dict:
        ctx = config["configurable"]["tool_context"]
        d, step = state["decision"], state.get("steps", 0)
        try:
            result = await registry.dispatch(d["tool"], d["arguments"], ctx,
                                             idempotency_key=f"{state['run_id']}:{step}")
            obs = Observation(step=step, tool=d["tool"], ok=not result.is_error, summary=result.summary)
            return {"observations": [obs], "last_error": None}
        except TransientToolError:
            raise                                                        # handled by RetryPolicy
        except (ToolDenied, ToolError) as e:
            return {"observations": [Observation(step=step, tool=d["tool"], ok=False, summary=str(e))],
                    "last_error": str(e)}

    def observe(state: AgentGraphState) -> dict:
        errors = state.get("errors", 0) + (1 if state.get("last_error") else 0)
        update: dict = {"steps": state.get("steps", 0) + 1, "errors": errors, "decision": None}
        if state.get("last_error") and not any(o["summary"] == state["last_error"]
                                               for o in state.get("observations", [])[-1:]):
            update["observations"] = [Observation(step=state.get("steps", 0), tool="system", ok=False,
                                                  summary=state["last_error"])]
        return update

    def route_after_observe(state: AgentGraphState) -> Literal["decide", "stop"]:
        return "stop" if state.get("errors", 0) >= MAX_ERRORS else "decide"

    def validate_answer(state: AgentGraphState) -> Command[Literal["finalize", "observe"]]:
        ans = state["decision"]
        problems = registry.validate_citations(ans.get("citations", []), state.get("observations", []))
        if problems:
            return Command(update={"last_error": f"answer rejected: {problems}"}, goto="observe")
        return Command(update={"final": ans, "stop_reason": StopReason.FINISHED.value}, goto="finalize")

    def stop(state: AgentGraphState) -> dict:
        if state.get("steps", 0) >= MAX_STEPS:
            reason = StopReason.MAX_TURNS
        elif state.get("errors", 0) >= MAX_ERRORS:
            reason = StopReason.TOO_MANY_ERRORS
        elif state.get("repairs", 0) > MAX_REPAIRS:
            reason = StopReason.INVALID_OUTPUT
        else:
            reason = StopReason.LOOP_DETECTED
        return {"stop_reason": reason.value,
                "final": {"type": "escalate", "reason": f"Agent stopped: {reason.value}"}}

    def finalize(state: AgentGraphState) -> dict:
        if state.get("final") is None and state.get("decision") is not None:
            return {"final": state["decision"], "stop_reason": state["decision"]["type"]}
        return {}

    b = StateGraph(AgentGraphState)
    b.add_node("decide", decide, retry_policy=RetryPolicy(max_attempts=3, retry_on=TransientLLMError))
    b.add_node("authorize", authorize)
    b.add_node("execute_tool", execute_tool,
               retry_policy=RetryPolicy(max_attempts=3, retry_on=TransientToolError))
    b.add_node("propose", propose)
    b.add_node("approval", approval)
    b.add_node("verify_approval", verify_approval)
    b.add_node("execute_approved", execute_approved)
    b.add_node("observe", observe)
    b.add_node("validate_answer", validate_answer)
    b.add_node("stop", stop)
    b.add_node("finalize", finalize)

    b.add_edge(START, "decide")
    b.add_conditional_edges("decide", route_decision)
    b.add_edge("execute_tool", "observe")
    b.add_edge("propose", "approval")
    b.add_edge("approval", "verify_approval")
    b.add_edge("execute_approved", "observe")
    b.add_conditional_edges("observe", route_after_observe)
    b.add_edge("stop", "finalize")
    b.add_edge("finalize", END)
    return b
```

**Wiring with the Postgres checkpointer.**

```python
# app/graphs/runtime.py
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from psycopg_pool import AsyncConnectionPool


async def compile_support_graph(pool: AsyncConnectionPool, deps):
    saver = AsyncPostgresSaver(pool)
    await saver.setup()                     # once at deploy/startup (creates checkpoint tables)
    return build_support_graph(**deps).compile(checkpointer=saver)


def run_config(run, tool_context, approver_id=None) -> dict:
    return {"configurable": {"thread_id": str(run.id), "tool_context": tool_context,
                             "approver_id": approver_id},
            "recursion_limit": 60}           # hard backstop above MAX_STEPS × nodes per cycle
```

[Version-dependent] The pool needs `autocommit=True` and `row_factory=dict_row` connection kwargs for the Postgres saver. Check the `langgraph-checkpoint-postgres` README for your version. Passing non-serializable objects in `configurable` is fine because config isn't checkpointed, but anything in **state** must serialize.

**Streaming progress.** `async for mode, chunk in graph.astream(inp, config, stream_mode=["updates", "custom"])` gives per-node updates. Map them to the Unit 36 event types (`step_started`, `tool_result` summaries, `awaiting_approval` when the run pauses on an interrupt). Inside nodes, `get_stream_writer()` emits custom progress events.

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| Manual loop (Unit 35) vs graph | Implicit control flow in code vs explicit nodes/edges | Graph when durability, HITL, inspection matter; manual for small, simple agents | Graph that's just one big `agent` node |
| Router function vs `Command(goto=)` | Separate routing vs update+route in a node | `Command` when the route depends on node computation | Mixing both on one node confusingly |
| `interrupt()` vs `interrupt_before` | Dynamic, payload + resume value vs static breakpoint | `interrupt()` for approvals | Side effects before `interrupt()` |
| RetryPolicy vs error route | Automatic re-run vs model-visible failure | Retry transient + idempotent; route domain errors | Retrying non-idempotent writes |
| Graceful step limit vs `recursion_limit` | Reasoned stop vs exception | Both, with recursion limit as backstop | Only the backstop → `GraphRecursionError` to users |
| LangGraph checkpoints vs own tables (Unit 37) | Framework vs custom | LangGraph for speed; own for full control/compliance | Assuming checkpoints = exactly-once effects |
| State vs config | Checkpointed vs per-invocation | Identity, clients, context in config | Secrets in checkpointed state |

### 8. Failure Modes and Debugging

**Failure 1 — Duplicate side effect after approval.**

- CAUSE: the write was in the `approval` node before `interrupt()`, or `execute_approved` isn't idempotent and was retried.
- FIX: isolate effects, idempotency keys, no retry on non-idempotent nodes.

**Failure 2 — `GraphRecursionError` in production.**

- CAUSE: the graceful step limit is missing or counted wrongly (e.g. not incremented on the error path).
- FIX: increment counters in a node every path passes through (`observe`), test cycles with a scripted model that never finishes.

**Failure 3 — `InvalidUpdateError` on parallel branches.**

- CAUSE: two nodes in one superstep write the same key without a reducer.
- FIX: reducers for shared keys, or separate keys.

**Failure 4 — Resume fails after deploy.**

- CAUSE: renamed nodes or changed state keys. Checkpoints reference old node names in pending tasks.
- FIX: treat node names and state keys as a persisted schema, keep old names as aliases until in-flight threads drain, test resume of fixture checkpoints.

**Failure 5 — Approver spoofing.**

- SYMPTOM: anyone with the run URL can approve.
- FIX: authenticate the resume endpoint, check authority in `verify_approval` against identity data, ignore approver fields in payloads.

**Failure 6 — State bloat.**

- SYMPTOM: checkpoint rows of megabytes, slow resumes.
- FIX: summaries and references in state, raw data in your own tables, checkpoint retention.

**Debugging tools.** `aget_state` to see `next` nodes and pending interrupts, `aget_state_history` to walk steps, the Mermaid graph to review structure, and tracing (LangSmith or OpenTelemetry via your own callbacks) for per-node latency and tokens.

### 11. Testing Strategy

- **Node tests:** call functions with dict states. For async nodes with config, pass `{"configurable": {...}}`.
- **Router tests:** tables + Hypothesis. Assert outputs are in the declared `Literal` set.
- **Graph path tests:** `astream(stream_mode="updates")` collects the sequence of node names. Assert expected paths for scripted scenarios (happy path, denial, approval rejected, loop).
- **Interrupt tests:** run until interrupt, check `aget_state(config)` for the pending interrupt payload, resume with `Command(resume=...)`.
- **Durability tests:** Postgres saver, new graph instance per phase.
- **Structure test:** compare `draw_mermaid()` output to a committed file.

```python
# tests/graphs/test_interrupt_resume.py
import pytest
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

pytestmark = pytest.mark.anyio


async def node_path(graph, inp, config):
    path = []
    async for chunk in graph.astream(inp, config, stream_mode="updates"):
        path.extend(chunk.keys())
    return path


async def test_refund_requires_approval_and_executes_once(graph_builder, scripted_refund_then_final, fakes):
    graph = graph_builder(llm=scripted_refund_then_final).compile(checkpointer=InMemorySaver())
    config = fakes.config(thread_id="r1", approver_id="lead-1")

    first = await node_path(graph, fakes.initial_state("r1"), config)
    assert first[-1] == "__interrupt__" or "approval" in first
    assert fakes.refunds.executed == []                               # nothing executed before approval

    second = await node_path(graph, Command(resume={"approved": True}), config)
    assert "execute_approved" in second
    assert fakes.refunds.executed == [fakes.proposals.last_id]        # exactly once

    state = await graph.aget_state(config)
    assert state.values["stop_reason"] == "finished"
```

### 12. Engineering Scenarios

**Scenario 1 — "Can we see why the agent did that?" (FDE).** The client's compliance team wants an explanation for each refund. *Reasoning:* the graph gives a node-by-node history (`aget_state_history`) and your events give summaries. Produce an "audit view" per run: decision, authorization verdict, proposal, approver, execution result, timestamps. Don't expose raw prompts, but keep them retrievable for authorized investigators per retention policy.

**Scenario 2 — Approvals in Slack.** *Reasoning:* the Slack action calls your authenticated approval endpoint (mapping the Slack user to an internal identity with approval authority). The graph resumes via the same path. Never trust Slack payload fields for authority without verification of the request signature and the user mapping.

**Scenario 3 — Graph or not?** A team wants LangGraph for a 3-step deterministic pipeline (classify → retrieve → answer). *Reasoning:* no cycles, no pauses, no need for durability. A plain function is simpler. Use a graph when you need cycles, interrupts, durable resume or parallel branches.

**Scenario 4 — Upgrading LangGraph.** *Reasoning:* pin versions, read release notes, run the restart/resume fixture tests against checkpoints written by the old version, and drain or migrate in-flight threads if serialization changed.

### 13. Interview Preparation

#### Quick Questions

**Q: What happens to a node that calls `interrupt()` when resumed?**
*Strong answer:* It re-runs from the beginning, and `interrupt()` returns the resume value. Code before it runs again, so keep it free of side effects.

**Q: Router function or `Command`?**
*Strong answer:* A router for routing based on state, `Command` when a node computes something and decides the next node in one step. Both should be explicit and tested.

**Q: How do you bound cycles?**
*Strong answer:* Counters in state checked by routers for a graceful stop with a reason, plus `recursion_limit` as a hard backstop.

#### Intermediate Questions

**Q: Where do identity and authorization live in a LangGraph agent?**
*Strong answer:* Re-derived per invocation and passed via config/runtime context. Authorization is enforced in deterministic nodes. Never stored in checkpointed state or taken from model output or resume payloads.

**Q: How do you test a graph?**
*Strong answer:* Nodes as functions, routers exhaustively, path tests with a scripted model and `stream_mode="updates"`, interrupt/resume tests, restart tests against Postgres, and a structure snapshot.

**Q: Does checkpointing give exactly-once tool execution?**
*Strong answer:* No. A node can run, perform an effect and crash before its checkpoint, and retries re-run nodes. Exactly-once effects come from idempotency keys and reconciliation.

#### Advanced Questions

**Q: Compare your manual agent and the graph version.**
*Strong answer:* Same decisions and tools. The graph makes transitions explicit and testable, adds durable checkpoints, interrupts and inspection for free, but adds a framework dependency, serialization constraints and schema coupling to node names. I'd use the graph when runs pause or must survive restarts, and keep the manual loop for short, read-only agents.

**Q: How do you evolve a graph with in-flight threads?**
*Strong answer:* Treat node names and state keys as a schema: additive changes, aliases for renamed nodes until threads drain, fixture tests of old checkpoints, and version tags in thread metadata to route old threads to a compatible graph version if needed.

#### Coding Questions

1. Write an approval subgraph with `interrupt()` and a verification node.
2. Write a router with exhaustive tests.
3. Write a test that resumes after re-compiling the graph with a Postgres saver.

#### Scenario Questions

**Q: An approved refund was executed twice. Walk through the investigation.**
*Strong answer:* Check state history for which node ran twice, check whether the effect lived in the interrupt node or a retried node, check the refund call's idempotency key and the downstream's dedup behavior, then fix by isolating and keying the effect and add a restart test.

### 14. Explain-It-at-Three-Levels

**Concept: Durable agent graph**

- *30 seconds:* The agent is a graph: the model decides in one node, and deterministic nodes authorize, execute, propose and verify. State is checkpointed in Postgres after every step, so runs pause for approval and resume anywhere, and every transition is testable.
- *2 minutes:* Nodes, routers, `Command`, reducers, interrupts, retry policies and bounds.

**Concept: Human-in-the-loop**

- *30 seconds:* A node interrupts with a payload, the run waits durably, an authenticated approver resumes it, and a deterministic node verifies authority before any effect.

- *Deep:* Spoofing defenses, audit views, multi-approver policies and timeouts.

#### Knowledge Check Answers

1. A function that merges updates for a key (e.g. list append). Needed when several nodes or parallel branches write the same key.
2. `approval` re-runs on resume, so it must have no side effects. Proposal creation and execution must each happen once, with their own idempotency keys.
3. From the authenticated resume request, placed into `configurable` by the API, never from the payload.
4. Config isn't checkpointed: it holds per-invocation, re-derived identity and non-serializable objects. State is persisted and must stay free of authorization data.
5. The graceful limit routes to `stop` with a reason and a user-facing result. `recursion_limit` raises an exception as a last-resort backstop.
6. It records the signature and routes to `propose` with a summary, via `Command`.
7. So the node's `RetryPolicy` handles transient failures automatically, while domain errors are turned into observations.
8. So the next `decide` must produce a fresh decision, and a stale decision can't be re-routed.
9. Two nodes in one superstep wrote the same key without a reducer.
10. Node names or state keys changed, or serialization changed, so checkpoints reference names or shapes the new graph doesn't have.
11. Linear pipelines without cycles, pauses or durability needs. A function is simpler.
12. A second interrupt node (or a loop over required approvers) after the first verification, with the policy deciding the number of approvers in code, distinct approver identities enforced, and expiry for each.

### 16. Common Interview Traps

- **"Put the whole agent in one node."** That loses every benefit of the graph.
- **"Interrupt is a pause; code before it runs once."** It re-runs.
- **"Checkpointing makes tools exactly-once."** It doesn't.
- **"Retry every node."** Not non-idempotent ones.
- **"Store the user and permissions in state."** Re-derive per invocation.
- **"Rename nodes freely."** In-flight checkpoints depend on names.
- **"Use LangGraph for everything."** Linear flows don't need it.

### 17. Cheat Sheet

- **Build:** `StateGraph(State)` · `add_node(name, fn, retry_policy=RetryPolicy(...))` · `add_edge` · `add_conditional_edges(src, router)` · `compile(checkpointer=...)`.
- **Route:** router returns a `Literal[...]` node name, or a node returns `Command(update=..., goto=...)`.
- **Run:** `config={"configurable": {"thread_id": ..., ...}, "recursion_limit": N}` · `ainvoke` / `astream(stream_mode="updates"|"values"|"custom")`.
- **HITL:** `interrupt(payload)` in a side-effect-free node → `ainvoke(Command(resume=value), config)` → verify in a deterministic node.
- **Persist:** `AsyncPostgresSaver(pool)`, `await saver.setup()` · `aget_state` · `aget_state_history`.
- **Bounds:** counters + graceful `stop` node + `recursion_limit` backstop + loop signatures.
- **Effects:** separate nodes, idempotency keys, retry only idempotent nodes.
