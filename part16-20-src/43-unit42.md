### 2. Prerequisite Knowledge

**Refresher — the taxonomy (used precisely in interviews).**

| Term | What it is | Who controls the flow? |
|---|---|---|
| **LLM call** | One prompt → one completion | Your code (single step) |
| **Augmented LLM** | LLM + retrieval, tools and/or memory available in a call | Model may choose tools within the call; your code executes |
| **RAG** | Retrieve relevant documents, put them in context, generate grounded answer | Your code (retrieval pipeline) + model (generation) |
| **Tool calling** | Model emits structured requests to call functions; your code executes them and returns results | Model proposes; code disposes |
| **Workflow** | Predefined sequence/graph of steps, some of which use LLMs (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer) | **Your code** defines the paths |
| **Agent** | LLM decides the next step dynamically in a loop (tools, observations) until a goal or stop condition | **The model** chooses the path within bounds |
| **Multi-agent system** | Several agents (often specialized) coordinate via a supervisor, handoffs or shared state | Models coordinate within an orchestration you define |

This taxonomy follows widely cited practitioner guidance (e.g., Anthropic's "Building effective agents"): start with the simplest thing — often a single augmented LLM call or a workflow — and add agency only when it demonstrably improves outcomes.

### 3. Mental Model

AI/FDE interviews test **judgment under ambiguity**: can you turn a fuzzy business request into a safe, evaluable, operable system, and can you explain why each part exists?

```
Stakeholder request ("we want an AI agent that handles refunds")
   ↓ CLARIFY      goal, users, volumes, risks, authoritative data, success metrics, constraints
   ↓ DECIDE       LLM vs RAG vs workflow vs agent; where determinism is required; where humans are required
   ↓ IMPLEMENT    components, contracts, boundaries (authZ, gateway, schemas, approvals, state)
   ↓ EVALUATE     datasets, metrics, baselines, gates (offline) + online signals
   ↓ OPERATE      tracing, cost, rollout (shadow/canary), kill switches, incident response
```

Every answer you give should visibly move through these five stages. Interviewers listen for: (1) you didn't jump to "use an agent"; (2) security and money decisions stay deterministic; (3) you can prove quality with evals; (4) you can run it in production.

### 4. Comprehensive Theory

#### 4.1 Agent vs Workflow

**Definition.** A *workflow* executes a path your code defines (possibly branching on LLM outputs such as a classification). An *agent* lets the model choose actions iteratively until done.

**Why the distinction matters.** Workflows are predictable, testable, cheaper and easier to authorize; agents handle open-ended tasks where the steps can't be enumerated in advance, at the cost of variance, latency, cost and harder evaluation.

**Decision criteria.**

| Question | Points to workflow | Points to agent |
|---|---|---|
| Are the steps known in advance? | Yes | No — depends on what's discovered |
| How many distinct paths? | Few, enumerable | Many, combinatorial |
| Cost of a wrong step? | High (money, compliance) | Low/reversible, or bounded by controls |
| Latency budget | Tight | Tolerant |
| Need for auditability/predictability | High | Moderate |
| Tools needed | Few, in fixed order | Many, chosen situationally |
| Evaluation | Per-step deterministic checks | Trajectory and outcome evals |

**Common workflow patterns (with LLM steps).** Prompt chaining (draft → check → refine); routing (classify → specialized handler); parallelization (sectioning or voting); orchestrator-workers (an LLM splits a task into subtasks dynamically — a step toward agency); evaluator-optimizer (generate → critique → improve loop with a bound).

**Hybrid is the norm.** A deterministic workflow with an agentic step inside a bounded box: e.g., refund handling is a workflow (authenticate → load order → compute eligibility → approval if needed → execute → notify), and only the *investigation* of an unusual complaint ("customer says the parcel was damaged and the photos are attached") is agentic.

**Example — refund flow as workflow, with the model only where it adds value.**

```java
package com.acme.support.refunds;

import java.math.BigDecimal;

/** Deterministic workflow: the model classifies and drafts text; code decides eligibility and amount. */
public final class RefundWorkflow {

    private final ComplaintClassifier classifier;     // LLM → typed enum (Unit 34)
    private final OrderService orders;                // authoritative order data
    private final RefundPolicy policy;                // deterministic rules (versioned config)
    private final ApprovalService approvals;          // Unit 35
    private final MessageDrafter drafter;             // LLM drafts the customer message from structured facts

    public RefundWorkflow(ComplaintClassifier classifier, OrderService orders, RefundPolicy policy,
                          ApprovalService approvals, MessageDrafter drafter) {
        this.classifier = classifier; this.orders = orders; this.policy = policy;
        this.approvals = approvals; this.drafter = drafter;
    }

    public RefundOutcome handle(Principal principal, String orderId, String complaintText) {
        Order order = orders.getForPrincipal(principal, orderId);                  // authZ + ownership
        ComplaintCategory category = classifier.classify(complaintText);           // probabilistic, typed, validated
        Eligibility eligibility = policy.evaluate(order, category);                // deterministic
        if (!eligibility.eligible()) {
            return RefundOutcome.declined(eligibility.reason(), drafter.declineMessage(order, eligibility));
        }
        BigDecimal amount = eligibility.maxAmount();                               // computed, not generated
        if (policy.requiresApproval(amount, category)) {
            String proposalId = approvals.propose(principal, "issue_refund", order.id(), amount, category);
            return RefundOutcome.pendingApproval(proposalId, drafter.pendingMessage(order));
        }
        String refundId = orders.refund(order, amount, "refund:" + order.id() + ":" + category);  // idempotency key
        return RefundOutcome.refunded(refundId, drafter.confirmationMessage(order, amount));
    }
}
```

The model's two jobs — classifying messy text and writing a friendly message — are where language understanding adds value. Eligibility, amount, authorization and execution are code.

#### 4.2 When Should an LLM Not Decide?

**Rule.** The model should not be the decision-maker when the decision is (a) **security-relevant** (who may access what), (b) **computable from authoritative data with explicit rules** (eligibility, prices, taxes, limits), (c) **high-impact and irreversible** without human review, (d) **regulated** and requiring explainable, consistent rationale, or (e) **cheaper and more reliable in code** (deterministic lookups, arithmetic, date math).

**Where the LLM may decide.** Interpreting unstructured input (classification, extraction into typed fields), choosing among safe, authorized options (which read-only tool to call next), generating language (summaries, drafts), ranking/reranking, and proposing actions that deterministic controls or humans then accept or reject.

**Pattern: "LLM proposes, code disposes."** Even when the model chooses, its choice passes through schemas, policies and approvals. The question is never "can the model do X?" but "what happens when the model gets X wrong, and is that acceptable?"

#### 4.3 Deterministic Boundaries, Authorization and Tool Safety

**The security spine (repeat it in every relevant answer).**

```
authentication (OIDC/JWT)
   ↓
authorization (roles/scopes, tenant, object ownership)          ← code
   ↓
validated scope (effective tools = profile ∩ user permissions; retrieval filters)
   ↓
retrieval/tool execution through a gateway                        ← code
   (allow-list → schema/Bean Validation → scope → object authZ → policy → approval → scoped creds → audit)
   ↓
LLM (sees only what this user may see; proposes only what this user may do)
```

Not: `LLM → "should this user be allowed?"`.

**How to prevent unauthorized tools (the canonical answer).**
1. Authenticate the user; build a server-side principal.
2. Compute effective tools; expose only those to the model (fewer tools also improves accuracy).
3. Re-check at execution in a single gateway: tool in allow-list; arguments strictly parsed and validated; scope; object-level ownership loaded from the authoritative source; business policy; approval for high risk; idempotency key; timeout; audit.
4. Identity and approval state come from server context (`ToolContext`), never from model arguments.
5. Downstream calls use delegated, scoped credentials; the model never sees secrets.
6. MCP/external tools are proxied through the same gateway; tool descriptions treated as untrusted.
7. Test with scripted unauthorized calls for every tool × role; adversarial evals with injected content.

#### 4.4 RAG Evaluation and Retrieval Failure

**How to evaluate RAG (canonical answer).** Separate stages:
- *Retrieval:* labeled queries with relevant chunk ids → recall@k, precision@k, MRR, nDCG; context precision/recall; filter correctness (ACL/tenant) as a hard check.
- *Generation:* faithfulness (claims supported by context), citation accuracy (cited ⊆ retrieved; cited supports claim), answer correctness vs reference/rubric, abstention on unanswerable questions.
- *End-to-end:* task success, latency, cost; plus online signals (escalations, thumbs, re-asks).
- *Gate:* baseline comparison before changing chunking, embeddings, index parameters, reranker, prompts or models.

**Debugging a retrieval failure.**

| Symptom | Investigate | Typical causes | Fixes |
|---|---|---|---|
| Relevant doc never retrieved | Is the doc indexed (status, version)? Does lexical search find it? | Ingestion failure, wrong ACL/tenant metadata, stale index | Fix pipeline; reindex; ingestion monitoring |
| Retrieved but ranked low | Scores of relevant vs top results | Query/document vocabulary mismatch, poor chunking, embedding model domain gap | Hybrid search (BM25 + vector), query rewriting, reranker, better chunk boundaries/metadata |
| Right doc, wrong chunk | Chunk content | Chunk too small/large, tables split, headers lost | Structure-aware chunking, parent-document retrieval, overlap |
| Works for some tenants only | Filter clauses | ACL filter bug, metadata missing | Tests for filters; pre-filtering; HNSW filtering behavior (pgvector iterative scans) |
| Degraded after embedding change | Index versions | Mixed embedding models in one index | Version embeddings; reindex fully; dual-read migration |
| Generation ignores good context | Context order/length | Lost-in-the-middle, truncation, conflicting docs | Context construction (order, dedupe, budget), instructions, citations required |

**Key phrase:** *retrieval failure ≠ generation failure* — measure them separately so you fix the right component.

#### 4.5 Loop Control

Never `while (true) askModel()`. Every agent loop has:

- **Goal and stop conditions:** final answer, clarification needed, escalation, or failure.
- **Max turns** (e.g., 6–10) and **max tool calls**.
- **Deadline** (wall-clock) and per-call timeouts.
- **Token/cost budget** per run, user and tenant.
- **Repeated-call detection** (same tool + args twice → change strategy; thrice → stop).
- **No-progress detection** (no new information over N turns → escalate).
- **Error budget** (consecutive tool failures → escalate).
- **Fail-closed outcome** with user-facing message and human handoff.

```java
package com.acme.support.agent;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.HashMap;
import java.util.Map;

public final class LoopGuard {

    public enum Stop { NONE, MAX_TURNS, DEADLINE, TOKEN_BUDGET, LOOP_DETECTED, TOO_MANY_FAILURES }

    private final int maxTurns;
    private final Instant deadline;
    private final long maxTokens;
    private final Clock clock;
    private final Map<String, Integer> callCounts = new HashMap<>();
    private int turns;
    private long tokens;
    private int consecutiveFailures;

    public LoopGuard(int maxTurns, Duration timeBudget, long maxTokens, Clock clock) {
        this.maxTurns = maxTurns;
        this.deadline = clock.instant().plus(timeBudget);
        this.maxTokens = maxTokens;
        this.clock = clock;
    }

    public Stop beforeTurn() {
        if (turns >= maxTurns) return Stop.MAX_TURNS;
        if (!clock.instant().isBefore(deadline)) return Stop.DEADLINE;
        if (tokens >= maxTokens) return Stop.TOKEN_BUDGET;
        turns++;
        return Stop.NONE;
    }

    public void recordUsage(int inputTokens, int outputTokens) { tokens += inputTokens + outputTokens; }

    public Stop recordToolCall(String tool, String argsHash, boolean failed) {
        int n = callCounts.merge(tool + ":" + argsHash, 1, Integer::sum);
        consecutiveFailures = failed ? consecutiveFailures + 1 : 0;
        if (n >= 3) return Stop.LOOP_DETECTED;
        if (consecutiveFailures >= 3) return Stop.TOO_MANY_FAILURES;
        return Stop.NONE;
    }

    public Duration remaining() { return Duration.between(clock.instant(), deadline); }
}
```

The orchestrator calls `beforeTurn()` at the top of every iteration and `recordToolCall` after every tool; any non-`NONE` result ends the run with an escalation (and a stop-reason attribute on the trace — Unit 37).

#### 4.6 Idempotency and State

**Idempotency.** Agents retry (model retries, worker restarts, at-least-once events). Side-effecting tools must accept idempotency keys derived from stable identifiers (run id + step id, or proposal id), and downstream systems must dedupe. Approval execution uses conditional claims (Unit 35).

**State.** Agent state includes conversation messages, decisions, tool observations, budgets used, pending proposals and checkpoints. Requirements: durable (resume after crash or approval wait), versioned (agent definition version used), bounded (summarize/trim history within context budgets), isolated (per tenant/user), and auditable. Implementations: PostgreSQL JSONB run state + append-only run events; durable execution engines (Temporal) or framework checkpointers (LangGraph-style; LangGraph4j in Java; Spring AI chat memory for conversation history) — but approvals, authorization and audit remain your domain.

**Memory caution.** Long-term memory writes are sensitive: validate, attribute, expire, scope per user, and guard against memory poisoning (OWASP ASI06).

#### 4.7 Tracing Multi-Agent Workflows

**Canonical answer.** One business trace per request; `invoke_agent` spans per agent (supervisor and sub-agents) as parent/child when synchronous, W3C trace context propagated over HTTP/A2A/MCP and Kafka headers; `chat`, `execute_tool` and retrieval spans under each agent with GenAI semantic-convention attributes (Development status — centralize names); handoffs recorded as spans/events with the structured payload's hash; long waits split into linked traces sharing run/conversation ids; per-agent metrics (tokens, cost, latency, outcomes); online eval scores attached; attribution by first anomaly. Content capture off by default.

#### 4.8 Safe Deployment of AI Changes

**What changes.** Prompts, models (including provider-side silent updates behind aliases), tools and their descriptions, retrieval (chunking, embeddings, index, reranker), guardrail thresholds, framework versions.

**Controls.**
1. **Version everything**: prompt templates (in git, hashed), model ids pinned (no floating aliases in production), tool schemas, index versions, eval datasets. Record versions on traces and run records.
2. **Offline eval gate** (Unit 36) in CI for AI-relevant changes.
3. **Shadow mode**: run the candidate on live inputs without effect; compare decisions.
4. **Canary**: small traffic share, automatic rollback on guardrail/eval/latency/cost regressions.
5. **Feature flags** per tenant/agent/tool; **kill switches** to disable a tool or fall back to a workflow or human queue instantly.
6. **Graceful degradation**: model outage → fallback model (only if evaluated), or "we'll follow up" + human queue; retrieval outage → lexical-only or abstain.
7. **Rollback**: previous prompt/model/index versions deployable in minutes.
8. **Post-deployment monitoring**: online evals, approval reject/edit rates, escalation rate, cost per success.

#### 4.9 The FDE Lens

A Forward Deployed Engineer sits between product capabilities and a customer's reality. Interviewers test whether you can:

- **Clarify** what the stakeholder actually wants (outcome, not solution): "handle refunds autonomously" may mean "reduce handle time by 40% without increasing fraud."
- **Find what's ambiguous**: definitions ("resolved"), volumes, edge cases, exceptions, regulatory constraints, integration ownership.
- **Decide what must remain deterministic** (authorization, money, compliance) and **what may be probabilistic** (classification, drafting, triage).
- **Identify authoritative data** (order system vs ticket text; policy repository vs wiki copies).
- **Plan for dependency failure** (CRM outage, model outage, rate limits).
- **Control access** (customer IdP, scopes, data residency).
- **Define success and evidence** (eval set built with their SMEs, agreed thresholds, pilot metrics).
- **Demonstrate** with a scripted, evidence-backed demo, not a lucky live prompt.

For every agent you present, be ready to specify these fourteen elements (they're also the Unit 43 agent specification):

| Element | Support agent (capstone) |
|---|---|
| Goal | Resolve support staff/customer questions about orders and policies; propose actions |
| Instructions | Versioned system prompt: role, scope, citation rules, escalation rules, untrusted-content handling |
| Available tools | `get_order`, `search_policies`, `update_address`, `send_email`, `issue_refund`, `delete_customer_data` (privacy profile only) |
| Tool schemas | JSON Schema per tool generated from argument records; per-run `toolName` enum |
| State | Run record (messages, decisions, observations, budgets, pending proposals) in PostgreSQL; conversation memory trimmed/summarized |
| Decision loop | Typed `AgentDecision` per turn → validation → gateway → observation |
| Stopping condition | FINAL_ANSWER, ASK_CLARIFICATION, ESCALATE, AWAITING_APPROVAL, or guard stop |
| Maximum turns | 8 (staff), 5 (customer) |
| Timeout | 30 s interactive deadline; per-model-call 15 s; per-tool 10 s |
| Validation | Strict Jackson + Bean Validation + semantic checks; output guard |
| Error handling | Classified corrective retries (≤ 2); tool errors as observations; fail closed to escalation |
| Authorization boundary | JWT principal → effective tools → gateway (scope, ownership, policy) → approvals |
| Observability | OTel trace per request; GenAI attributes; tokens/cost/stop-reason metrics |
| Evaluation strategy | Regression suite with expected/forbidden behavior; retrieval metrics; calibrated faithfulness judge; online sampling |

#### Example 2 — Realistic: answering a scenario with the five-part structure

> **Scenario.** "A retailer wants an AI assistant for store managers to adjust inventory counts and reorder stock. Design it."
>
> **1. Clarify.** Who uses it (store managers, ~2,000)? What actions (adjust counts, create purchase orders)? Volumes and value per order? Existing systems (ERP as authoritative inventory)? Approval rules today (PO above $X needs regional approval)? Success metric (time saved, stockouts reduced, error rate)? Constraints (offline stores, data residency)?
>
> **2. Design choice.** Not a free-form agent: a workflow with an LLM for intent and entity extraction ("we sold out of the 2L milk, order 3 cases") into a typed `InventoryAction`; deterministic validation against the ERP (SKU exists, store authorized, quantities within bounds, reorder rules); purchase orders above threshold go to the existing approval chain; adjustments are reversible within a window; read-only Q&A uses RAG over SOPs.
>
> **3. Implementation.** Spring Boot service; OIDC with the retailer's IdP (store id claim); typed decisions with strict validation; ERP adapter with idempotency keys; approval service with argument binding; outbox events; Redis rate limits per store; MCP server exposing read-only ERP queries to other assistants through our gateway.
>
> **4. Evaluation.** 300 cases from real manager messages (with SMEs): extraction accuracy (SKU, quantity, unit), forbidden behavior (orders for other stores, quantities beyond limits), clarification when ambiguous; RAG metrics for SOP answers; gates in CI; pilot with 20 stores; online: correction rate, approval rejects.
>
> **5. Operational controls.** Traces per request; cost per store; kill switch per action type; shadow mode for two weeks (suggestions only), then canary; runbook for ERP outage (queue + notify); audit trail for every change.

#### Example 3 — Production-oriented: the architecture defense session

**Format (45–60 minutes).**
1. **10 minutes — present** the capstone: problem, architecture diagram, request flow, deterministic boundaries, evals, operations, one incident.
2. **25 minutes — challenges**: the interviewer (or a peer using the question bank below) picks components and asks: *Why does this exist? What failure does it address? What simpler alternative did you consider? What would make you change it? Show me the evidence.*
3. **10 minutes — scenario twist**: e.g., "Your model provider has a 2-hour outage" or "Legal requires EU data residency" — adapt the design live.
4. **5 minutes — debrief**: strengths, gaps, follow-ups.

**Challenge question bank (by component).**

| Component | Challenge | Strong-answer elements |
|---|---|---|
| Agent (vs workflow) | Why an agent at all? | Open-ended investigations with unknown steps; read-only tools; bounded loop; measured improvement over workflow baseline in evals; actions still flow through workflow/approvals |
| Tool gateway | Why not checks inside each tool? | Uniformity, single audit/metrics point, impossible-to-forget checks; `@Tool` adapters thin; tested matrix |
| Typed decisions | Why not native tool calling only? | First-class clarify/escalate outcomes, one auditable schema; or "we use native tool calling + virtual tools" — either way strict validation |
| Approvals | Why not let staff confirm in chat? | Binding, authority, SoD, expiry, audit, exactly-once execution |
| pgvector | Why not a dedicated vector DB? | Data size/QPS fit PostgreSQL; transactional ACL metadata; one less system; revisit criteria (latency at N vectors, filter performance) |
| Kafka | Why not direct calls? | Async approvals/resume, decoupled ingestion, replay; outbox for reliability; simpler alternative: Spring Modulith events or a DB queue at small scale |
| Redis | What breaks if Redis is down? | Rate limiting fails open/closed per route; cache misses go to DB with bulkheads; no correctness dependency |
| Evals | How do you know a prompt change is safe? | Regression suite with forbidden behavior, CIs, gates, per-tag thresholds, flipped cases |
| Observability | Show me how you debug a bad answer | Trace walk to first anomaly; retrieval results=0 example; metrics confirm |
| Security | Indirect injection in a policy doc tells the agent to refund | Doc is data; refund tool requires approval; tainted args; output guard; eval case exists |
| Cost | What does a run cost and how do you control it? | Tokens/cost per span; budgets per run/tenant; routing; caching; cost per success metric |
| Degradation | Provider outage | Breaker → fallback model (evaluated) or human queue; RAG lexical-only; banner to users |

### 7. Comparative Analysis

| Comparison | Key difference | When to use each | Trade-offs | Interview trap |
|---|---|---|---|---|
| Workflow vs agent | Code-defined path vs model-chosen path | Workflow when steps known; agent for open-ended exploration | Predictability vs flexibility | "Agent" as default |
| RAG vs tool calling | Retrieve text into context vs call functions for data/actions | RAG for unstructured knowledge; tools for structured/live data and actions | RAG cheaper for docs; tools precise and authorizable | "Just RAG the database" |
| RAG vs fine-tuning | Inject knowledge at runtime vs change model weights | RAG for changing/attributable knowledge; fine-tuning for style/format/narrow skills | Freshness/citations vs latency/consistency | Fine-tuning to add facts |
| Single agent vs multi-agent | One loop vs coordinated specialists | Multi-agent when tasks parallelize or need separated contexts/permissions | Token cost (often several ×), coordination failures | Multi-agent for prestige |
| Spring AI vs direct provider SDK | Portable abstractions (advisors, tools, observability) vs full provider features | Spring AI for Spring integration and portability; SDK for newest provider-specific features | Abstraction lag vs coupling | Assuming portability means identical behavior |
| Native tool calling vs structured decision object | Provider tool blocks vs one decision schema | Native for framework loops/parallel calls; decision object for explicit clarify/escalate and audit | — | Treating them as security boundaries (neither is) |
| MCP vs direct tool integration | Standard protocol for tools/resources vs in-process functions | MCP to share tools across clients/agents and integrate third-party tools; direct for internal, latency-sensitive | Extra hop, auth, supply-chain risk vs reuse | "MCP handles security" |
| Offline vs online eval | Pre-release dataset vs production sampling | Both | Coverage vs representativeness | — |
| Shadow vs canary | No user impact vs small real impact | Shadow first for risky changes; canary to confirm with real outcomes | Shadow can't measure user outcomes | Skipping both |

### 8. Failure Modes and Debugging (scenario drills)

| Incident | First questions | Likely root causes | Controls to cite |
|---|---|---|---|
| Agent refunded the wrong customer | Which order id source? Gateway decision? | BOLA in tool; model-supplied identity; tainted id | Ownership checks from authoritative data; principal via ToolContext; taint → approval |
| Answers cite non-existent policies | Citation validation? Retrieval results? | Retrieval returned 0 → model fabricated; no citation check | cited ⊆ retrieved; abstain; retrieval alerts |
| Costs tripled overnight | Turns per run? Retries? Tenant? | Loop from a tool error; prompt change increasing turns; retry storm | Loop guard; budgets; per-tenant alerts; eval gate on cost |
| Quality dropped with no deploy | Provider model alias changed? Index rebuilt? | Floating model alias; embedding/index change | Pin models; version indexes; online evals; drift alerts |
| Multi-agent answer contradictory | Which sub-agent introduced it? | Supervisor merged unvalidated sub-agent prose | Structured sub-agent outputs; per-agent evals; trace attribution |
| Approval queue overwhelmed | Tier distribution? | Thresholds too conservative; agent proposes unnecessary actions | Evidence-based tiers; agent quality fixes; undo windows |

### 12. Engineering Scenarios

**Scenario 1 — FDE stakeholder clarification (required before implementation).** A COO says: "Build an AI agent that answers all customer emails automatically, starting next month."
*Questions to ask.* Which email types and volumes? What fraction are actionable (refunds, address changes) vs informational? Current SLA and quality metrics? Brand/legal constraints (regulated statements)? Who owns the policies and how current are they? What systems hold authoritative data? Languages? What's the acceptable error rate and what's catastrophic? Is "automatically" negotiable for some categories?
*Expected reasoning.* Propose phased scope: auto-draft for all, auto-send only for low-risk informational categories after evals meet thresholds; actions via workflow + approvals; success criteria agreed with SMEs; dataset from historical emails; pilot plan; weekly evidence reviews. Push back on "all" and "next month" with a concrete alternative timeline and what can ship next month (drafting assistant with human send).

**Scenario 2 — "Why not let the agent query the database directly with SQL?"**
*Expected reasoning.* Excessive agency and injection risk; authorization bypass; unbounded cost; schema leakage. Alternative: narrow read tools with typed parameters, or a semantic layer/text-to-SQL restricted to a read-only, row-level-secured view with query validation, timeouts and evals — only if the use case truly needs ad-hoc analytics.

**Scenario 3 — Multi-agent proposal.** A team proposes planner/researcher/writer/reviewer agents for policy Q&A.
*Expected reasoning.* Measure first: compare against single RAG + citation validation on the eval suite; multi-agent adds tokens, latency and failure surfaces; adopt only if quality gains justify cost; if adopted, structured handoffs, per-agent evals and traces.

**Scenario 4 — Provider outage during a customer demo week.**
*Expected reasoning.* Breakers and fallback model (pre-evaluated), cached demo data, human-queue degradation; demo script includes a recorded fallback; communicate transparently.

**Scenario 5 — Data residency.** EU customer requires all processing in the EU.
*Expected reasoning.* Choose EU-hosted model endpoints (provider regions or cloud-hosted models), EU vector/DB/observability storage, no content capture to non-EU vendors, DPA terms; re-run evals on the regional model; document data flows.

### 13. Interview Preparation

#### The Five Canonical Questions

**Q1: Why an agent instead of a workflow?**
*Strong answer:* "I default to workflows because they're predictable, cheaper, easier to authorize and evaluate. I use an agent only where the steps can't be known in advance — for example, investigating unusual order issues across several read-only systems, where the next query depends on what the previous one found. Even then the agent is bounded: read-only tools by default, max turns, deadlines, budgets, typed decisions, and any action goes through the deterministic refund workflow with approvals. I validated the choice with evals: the workflow baseline resolved 61% of investigation cases, the bounded agent 84%, at 2.3× the cost — acceptable for that slice only."
*Why asked:* Tests whether you add complexity deliberately. *Weak answer:* "Agents are more powerful/flexible." *Trap:* no baseline comparison.

**Q2: When should an LLM not decide?**
*Strong answer:* "When the decision is about authorization, is computable from authoritative data and explicit rules — eligibility, amounts, prices, limits — is high-impact and irreversible without review, or is regulated and needs consistent, explainable rationale. In my capstone the model classifies the complaint and drafts the message; code computes refund eligibility and the amount from the order and policy; approvals gate amounts above the limit. The model proposes; code disposes."
*Trap:* "When it's not confident" — model confidence is poorly calibrated and not a control.

**Q3: How do you prevent unauthorized tools?**
*Strong answer:* "Authenticate and build a server-side principal; compute effective tools as the agent profile intersected with the user's permissions and expose only those; then re-check every call in a single gateway — allow-list, strict typed arguments with Bean Validation, scope, object-level ownership loaded from the authoritative source, business policy, approval for high risk, idempotency key, timeout and audit. Identity comes from ToolContext, never model arguments. MCP tools go through the same gateway. I prove it with a scripted-model test matrix of every tool × role and adversarial evals with injected documents."
*Trap:* "We don't give the model that tool in the prompt."

**Q4: How do you evaluate RAG?**
*Strong answer:* "Separately by stage. Retrieval: labeled queries with relevant chunk ids — recall@5, MRR, nDCG — plus hard checks that ACL filters never return other tenants' chunks. Generation: faithfulness with a judge calibrated against human labels, citation accuracy — cited must be a subset of retrieved and must support the claim — answer correctness against references, and abstention on unanswerable questions. End to end: task success, latency, cost. All compared to a baseline in CI before changing chunking, embeddings, reranker, prompt or model. Retrieval failure and generation failure are fixed in different places, so I never rely on one blended score."

**Q5: How do you trace multi-agent workflows?**
*Strong answer:* "One business trace per request: `invoke_agent` spans for the supervisor and each sub-agent, `chat`, `execute_tool` and retrieval spans beneath them with OpenTelemetry GenAI attributes — model, tokens, finish reasons, tool names and outcomes — centralized because the conventions are still in Development. Context propagates through HTTP, MCP and Kafka headers; long approval waits become linked traces with shared run and conversation ids. Handoffs carry structured payloads I can hash and inspect. Content capture is off by default. To attribute failures I walk to the first anomaly — e.g., a sub-agent's retrieval returning zero results — and confirm with per-agent metrics."

#### Quick Questions

1. **Augmented LLM vs agent?** Augmented LLM has tools/retrieval in a call; an agent loops, choosing actions over multiple steps.
2. **What bounds an agent loop?** Max turns, deadline, token/cost budget, repeated-call and no-progress detection, failure budget, explicit stop conditions.
3. **Why idempotency for agent tools?** Retries and resumes happen; side effects must not duplicate.
4. **What is a kill switch?** A runtime flag that disables a tool/agent/model path instantly, falling back to safe behavior.
5. **Why pin model versions?** Provider-side updates behind aliases change behavior without deploys; pinning enables reproducible evals and rollback.

#### Intermediate Questions

**Q: How do you handle state for an agent that waits for human approval?**
*Strong answer:* Persist run state and the proposal; end the active trace; release compute; resume on an approval event via outbox/Kafka; append the execution outcome as an observation; budgets continue; expiry handling; idempotent execution.

**Q: How do you deploy a new prompt safely?**
*Strong answer:* Version and hash it; run the regression eval with gates; shadow it; canary with automatic rollback on eval/guardrail/latency/cost metrics; feature flag per tenant; keep the previous version deployable; monitor online signals.

**Q: Your RAG answers are wrong for one tenant only. Debug it.**
*Strong answer:* Check traces for that tenant: retrieval result counts and filters; ingestion status of their documents; ACL metadata; index version; compare retrieval metrics on their queries; likely metadata/filter bug or failed ingestion; fix, reindex, add tenant-specific eval cases and an alert on zero-result rates.

#### Advanced Questions

**Q: Design guardrails for an agent that reads emails and can send replies.**
*Strong answer:* Lethal trifecta present (private data, untrusted content, external comms). Options: remove auto-send (drafts only) or restrict recipients to the original sender from authoritative headers; approval for sends; taint tracking (addresses/links from email content can't be used as recipients without approval); output guard (no external links/images); separate summarization (quarantined) from action planning; evals with injected emails; audit; kill switch.

**Q: Multi-agent or single agent for a research-and-report task? Defend with numbers.**
*Strong answer:* Prototype both; measure task success, faithfulness, tokens, latency; multi-agent often uses several times the tokens; adopt only if quality gain matters for the use case (e.g., broad research with parallelizable subtopics); otherwise single agent with better retrieval.

**Q: What's your degradation plan when the LLM provider is down?**
*Strong answer:* Circuit breaker; fallback model evaluated per agent (some agents may not have an acceptable fallback); degrade to deterministic workflows (e.g., status lookups without LLM), templated responses, human queue; user messaging; queue non-interactive work with backoff; monitor and auto-recover.

#### Coding Questions

1. Implement `LoopGuard` with tests (deadline using a fake clock).
2. Implement a gateway check that rejects tool calls whose `orderId` doesn't belong to the principal's customer.
3. Implement a citation validator (cited ⊆ retrieved; quote substring check).
4. Implement a shadow-mode comparator that logs disagreements between production and candidate decisions.

### 14. Explain-It-at-Three-Levels

**Deterministic boundaries in agentic systems**
- *30 seconds:* Security, money and compliance decisions are made by code before and after the model; the model interprets language and proposes; humans approve high-risk actions.
- *2 minutes:* Security spine (authN → authZ → validated scope → gateway → LLM), typed decisions, approvals, idempotent execution, audit; the model's role is classification, extraction, drafting and choosing among authorized options.
- *Deep:* Walk a request through the capstone, show the gateway code, the approval state machine, the eval cases proving forbidden behavior is blocked, and the trace of a denied action.

**Agent vs workflow**
- *30 seconds:* Workflow when steps are known; agent when the next step depends on discoveries; start simple and add agency with evidence.
- *2 minutes:* Criteria table; hybrid designs; bounded agent loops; eval-based justification.
- *Deep:* Pattern catalog (chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer), cost/latency math, failure modes of agents (loops, drift, injection), and how to migrate between them.

**FDE requirement clarification**
- *30 seconds:* Turn the requested solution into the desired outcome, find the ambiguities and risks, agree on success evidence before building.
- *2 minutes:* Question list (users, volumes, actions, authoritative data, constraints, success metrics, failure tolerance), phased scope, demo plan.
- *Deep:* Stakeholder mapping (business owner, security, legal, operations), negotiation of autonomy levels with evidence gates, and running pilots.

### Knowledge Check Answers

1. In a workflow your code defines the path (possibly branching on model outputs); in an agent the model chooses the next action iteratively until a stop condition.
2. Authorization/access; computable rule-based decisions (eligibility, amounts, prices); irreversible high-impact actions without review; regulated decisions requiring consistent explainable rationale (also arithmetic/lookups better done in code).
3. The model can be manipulated or hallucinate, letting it impersonate other users; identity must come from the authenticated server-side principal.
4. They fail for different reasons and are fixed in different components; a blended score can't tell you whether to change chunking/embeddings or prompts/models.
5. Provider updates behind an alias change behavior without your deploy, invalidating eval baselines and complicating rollback.
6. Bounds (max turns, deadline, budgets), validation of decisions, authorization/gateway, error handling, repeated-call detection, stop reasons, observability — it's an unbounded `while`.
7. Model: complaint category (typed) and message drafts. Code: order data, eligibility, amount, approval requirement, execution with idempotency key. It keeps money and policy deterministic and auditable.
8. On the third identical call `recordToolCall` returns `LOOP_DETECTED`, and the orchestrator stops and escalates.
9. Answers are faithful to retrieved context, but the context is wrong/outdated/irrelevant (retrieval failure, stale documents) or the question was misunderstood — check retrieval metrics and document freshness.
10. Trace context isn't propagated across the boundary (HTTP/MCP client not instrumented, async executor without context propagation, Kafka observation disabled).
11. RAG with metadata filter `country = principal.country` applied in the retrieval query (pre-filter), citation validation and abstention; no tools; principal from IdP claims; evals including cross-country negative cases.
12. Clarify the goal (better answers? personalization?); explain risks (memory poisoning, privacy, drift); propose controlled learning: curated feedback → eval cases → prompt/retrieval improvements via the release process; optional per-user memory with consent, scoping, expiry and review — not uncontrolled self-modification.

### 16. Common Interview Traps

| Trap | Correct mental model |
|---|---|
| "An agent is simply an LLM with a prompt." | An agent is a bounded decision loop with tools, state, validation, authorization, observability and evaluation. |
| "Use an agent for flexibility." | Use the simplest architecture that meets requirements; add agency with evidence. |
| "The model checks permissions." | Code enforces authorization before and after the model. |
| "RAG prevents hallucinations." | It reduces them if retrieval works and generation is constrained and verified. |
| "Multi-agent is more capable." | Often more expensive and fragile; justify with evals. |
| "We'll monitor it in production." | Offline eval gates first; monitoring complements. |
| "The prompt says don't do it." | Instructions aren't controls. |
| "MCP is secure by design." | MCP standardizes integration; you still authorize, vet and proxy. |

### 17. Cheat Sheet

- **Taxonomy:** LLM → augmented LLM → RAG / tool calling → workflow → agent → multi-agent.
- **Five-part scenario answer:** clarify → design choice → implementation → evaluation → operational controls.
- **Security spine:** authN → authZ → validated scope → gateway (allow-list, args, scope, ownership, policy, approval, creds, audit) → LLM.
- **LLM should not decide:** access, rule-computable values, irreversible high-impact actions, regulated decisions, arithmetic/lookups.
- **Loop control:** max turns, deadline, token/cost budget, repeated-call & no-progress detection, failure budget, stop reasons.
- **RAG eval:** retrieval (recall@k, MRR, nDCG, ACL checks) ≠ generation (faithfulness, citation accuracy, correctness, abstention); end-to-end; baseline gates.
