## Unit 34 — Structured Agent Output

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** why free-form prose is unsafe as the input to a machine decision, with three concrete failure examples.
2. **Design** a typed decision contract (`AgentDecision`, `ToolRequest`, per-tool argument records) using Java records, sealed types and enums, so the set of possible decisions is closed and every field is bounded.
3. **Generate** a JSON Schema from Java types and **compare** the three ways to get schema-shaped output from a model: prompt-only format instructions, provider-native structured output (constrained decoding), and tool/function-call arguments.
4. **Implement** strict Jackson 3 deserialization: unknown properties, null primitives, trailing tokens, enum handling, numeric coercion and polymorphism, and explain what each setting protects against.
5. **Implement** Bean Validation on records, including nested `@Valid`, container-element constraints, cross-field `@AssertTrue` rules and a custom constraint.
6. **Implement** a malformed-output pipeline that classifies failures (unparseable, schema violation, semantic violation, policy violation), retries only repairable classes with error feedback, enforces a retry budget, and fails closed.
7. **Validate** every software-facing decision before execution, and **prove** this with tests that inject malformed and adversarial model outputs.
8. **Use** Spring AI 2.0's structured-output support (`ChatClient … .entity(...)`, native structured output, `StructuredOutputValidationAdvisor`) and explain what it does and doesn't guarantee.
9. **Measure** schema compliance and retry rates as production metrics and evaluation metrics.

### 2. Prerequisite Knowledge

- **Java records** (Java 16+): canonical constructors, compact constructors for validation/normalization, immutability of fields (shallow; a `List` field must be copied with `List.copyOf`).
- **Sealed interfaces and pattern matching `switch`** (Java 21+): exhaustive handling of a closed set of types.
- **Jackson basics:** `ObjectMapper`/`JsonMapper`, `readValue`, `JsonNode`, annotations `@JsonProperty`, `@JsonTypeInfo`, `@JsonSubTypes`. **[Version-dependent]** Spring Boot 4 uses **Jackson 3**, whose packages moved from `com.fasterxml.jackson.core/databind` to `tools.jackson.core/databind`. Annotations stay in `com.fasterxml.jackson.annotation`. Jackson 3 exceptions are **unchecked** (`tools.jackson.core.JacksonException` extends `RuntimeException`). Jackson 2 remains common in older codebases. [Legacy]
- **Jakarta Bean Validation 3.x** with Hibernate Validator 9: `@NotNull`, `@NotBlank`, `@Size`, `@Pattern`, `@Positive`, `@Digits`, `@Valid`, `Validator.validate`.
- **Unit 33:** the tool policy consumes *typed, validated* requests produced by this unit.

**Refresher: what JSON Schema is.** A JSON document (current draft 2020-12) that describes allowed JSON: types, required properties, `enum`, `pattern`, `minimum/maximum`, `maxLength`, `additionalProperties: false`. Providers that support "structured output" accept a schema (often a restricted subset) and constrain generation to it.

### 3. Mental Model

Treat the model's output as **an untrusted form submitted over the internet**. You already know how to handle form submissions safely: parse strictly, validate every field, reject unknown fields, never trust hidden fields, and check business rules server-side. A model decision is the same, except the "user" filling in the form is non-deterministic and possibly manipulated.

```
Model output (bytes)
   ↓  1. Extract     — is there exactly one JSON object? (no prose, no code fences)
   ↓  2. Parse       — strict Jackson into AgentDecision   ── fail → UNPARSEABLE
   ↓  3. Validate    — Bean Validation constraints          ── fail → SCHEMA_VIOLATION
   ↓  4. Bind args   — ToolRequest.arguments → typed record ── fail → SCHEMA_VIOLATION
   ↓  5. Semantics   — cited docs exist? tool advertised?   ── fail → SEMANTIC_VIOLATION
   ↓  6. Policy      — Unit 33 ToolPolicy                   ── fail → DENIED (no retry)
   ↓
Typed, validated decision → execution / approval / answer
```

Steps 1–5 answer the question "is this a well-formed, meaningful proposal?" Step 6 answers "is it allowed?" Keep them separate. A schema failure may be worth one retry with feedback. A policy denial must **not** become "retry until the model finds a phrasing that passes".

### 4. Comprehensive Theory

#### 4.1 Why Arbitrary Prose Is Unsafe for Machine Decisions

**Definition.** A *machine decision* is any model output that software acts on: which tool to call, with which arguments, whether to escalate, which category a ticket belongs to.

**Why prose fails.**

1. **Ambiguity.** "Refund about $50, maybe the shipping cost too" — is the amount 50, 50 + shipping, or nothing?
2. **Fragile parsing.** Regex over prose (`/refund \$(\d+)/`) breaks on "$1,200.00", "USD 50", "fifty dollars", or two numbers in one sentence. The parser becomes an unbounded set of special cases.
3. **No closed set of actions.** If the model can say anything, your code must handle anything. Typed outputs turn "anything" into an exhaustive `switch`.
4. **Injection through formatting.** Prose parsed with `contains("APPROVED")` can be satisfied by "this is NOT APPROVED".
5. **No measurable compliance.** You can't compute a schema-compliance rate on prose, so you can't detect regressions after a model upgrade.

**Rule.** *Prose is for humans; types are for machines.* An agent's final answer to a human may be prose (wrapped in a typed envelope with citations). Every decision software executes must be typed.

**Interview perspective.** The interviewer is checking that you treat model output as untrusted input and that you can name concrete failure modes, rather than saying "JSON is cleaner".

#### 4.2 Typed Decisions: Designing the Contract

**Design principles.**

- **Closed set of decision types.** An enum: `ANSWER`, `CALL_TOOL`, `ASK_CLARIFICATION`, `ESCALATE`. No "other".
- **Every field bounded.** Lengths, patterns, numeric ranges, list sizes. Unbounded strings are an injection and cost vector.
- **Identifiers are references, not facts.** The model may output `orderId: "8812"`. The *customer* that order belongs to is looked up server-side, never accepted from the model.
- **Cross-field consistency.** `CALL_TOOL` requires `toolRequest` and forbids `answer`. Enforce this in validation, not by convention.
- **Separate envelope from arguments.** The decision envelope is generic. Tool arguments are bound to a **per-tool record** in a second step, so each tool has its own precise schema.
- **Make the model justify, but don't trust the justification.** A `justification` field helps reviewers (Unit 35) and evals, but no logic depends on it.

**Two common shapes.**

*Shape A — flat envelope with optional fields + cross-field rule* (simple, works with every provider's schema subset):

```json
{ "type": "CALL_TOOL",
  "toolRequest": { "toolName": "issue_refund",
                   "arguments": { "orderId": "8812", "amount": 49.00, "reason": "LATE_DELIVERY" },
                   "justification": "Order arrived 9 days late; policy allows shipping refund" },
  "answer": null, "clarificationQuestion": null, "citations": [] }
```

*Shape B — discriminated union* (`oneOf` with a `type` discriminator; maps to a sealed interface in Java):

```json
{ "type": "call_tool", "toolName": "issue_refund", "arguments": {...}, "justification": "..." }
```

Shape B is more precise but some providers' strict modes restrict `oneOf`/`anyOf` at the root. Shape A with a cross-field validator is the portable default. This unit uses Shape A for the envelope and typed records for arguments.

#### 4.3 JSON Schema and How Models Produce Schema-Shaped Output

There are three mechanisms, in increasing order of reliability:

| Mechanism | How it works | Guarantees | Caveats |
|---|---|---|---|
| **Prompt-only format instructions** | Schema text appended to the prompt ("respond with JSON matching …") | None. The model usually complies | Code fences, prose prefaces, missing fields, trailing commas |
| **Tool / function-call arguments** | The model emits a tool call whose arguments are checked against the tool's input schema | Provider-dependent; often valid JSON, not always schema-valid | Arguments may still violate `pattern`/`maximum` |
| **Native structured output (constrained decoding)** | The provider restricts token sampling so output must match the schema (for example OpenAI `response_format: json_schema, strict: true`; Anthropic and Google have equivalents) [Version-dependent] | Output is syntactically valid and matches the supported schema subset | Supported subset varies (often requires `additionalProperties:false`, all fields required, limited `pattern`/`format`); **semantics are not guaranteed**; refusals can come back as a separate field |

**Key insight.** Even with constrained decoding, you still validate. The schema subset providers enforce rarely covers your business constraints (amount ≤ refundable balance, order belongs to customer), and providers, models and settings change. Constrained decoding raises your **schema-compliance rate**; validation guarantees **correctness**.

**Generating schemas from Java.** Spring AI's `BeanOutputConverter` generates a JSON Schema from a Java type (it uses the victools `jsonschema-generator` library) and can feed it either into the prompt or into the provider's native structured-output parameter. You can also generate schemas yourself with victools so the same schema is used for prompts, docs and tests.

#### 4.4 Jackson Deserialization: Strictness Settings

**Definition.** Deserialization maps JSON text to Java objects. For records, Jackson calls the canonical constructor with values matched by component name.

**Why strictness matters.** Defaults are tuned for *tolerant* API consumption, where ignoring unknown fields aids forward compatibility. For model output you want the opposite: anything unexpected is a signal.

| Setting (Jackson 3 `DeserializationFeature` unless noted) | Strict choice | Protects against |
|---|---|---|
| `FAIL_ON_UNKNOWN_PROPERTIES` | **enable** | Model inventing fields (`"approved": true`, `"bypassPolicy": true`) that you silently ignore while the model "thinks" they mattered; also schema drift |
| `FAIL_ON_NULL_FOR_PRIMITIVES` | enable | `null` silently becoming `0` / `false` |
| `FAIL_ON_TRAILING_TOKENS` | enable | `{...} extra text` or two concatenated objects |
| `FAIL_ON_NULL_CREATOR_PROPERTIES` | enable where all creator properties are required | Missing fields becoming `null` without error |
| `ACCEPT_FLOAT_AS_INT` | disable | `2.7` silently truncated to `2` |
| `MapperFeature.ALLOW_COERCION_OF_SCALARS` | disable | `"amount": "49"` (string) accepted as number; "true" as boolean |
| `READ_UNKNOWN_ENUM_VALUES_AS_NULL` | keep **off** | Unknown enum turning into `null` and passing a lax check |
| `USE_BIG_DECIMAL_FOR_FLOATS` (or `BigDecimal` fields) | use `BigDecimal` for money | Binary floating-point rounding |

**[Version-dependent]** Jackson 3 changed several defaults compared with Jackson 2, and Spring Boot applies its own defaults to the auto-configured mapper (historically disabling `FAIL_ON_UNKNOWN_PROPERTIES`). **Never rely on defaults for model output:** build a dedicated, explicitly configured mapper bean (for example `@Qualifier("agentJson")`) and leave the application's HTTP mapper alone.

**Polymorphism warning.** Never enable default typing (`activateDefaultTyping`) on a mapper that reads untrusted input; it has a long history of gadget-chain deserialization vulnerabilities. For sealed hierarchies use `@JsonTypeInfo(use = Id.NAME, property = "type")` with explicit `@JsonSubTypes`. Jackson only instantiates the listed classes.

#### 4.5 Bean Validation on Records

**Definition.** Declarative constraints on fields, evaluated by a `jakarta.validation.Validator`.

**How it works with records.** Annotations on record components propagate to the generated fields and accessors, and Hibernate Validator validates them. `@Valid` on a component cascades into nested objects. Container-element constraints (`List<@Pattern(...) String>`) validate each element. Class-level rules can be expressed as `@AssertTrue` boolean accessor methods (named `isXxx()`) or as a custom class-level constraint.

**Important:** Bean Validation runs when **you call it**. Jackson does not validate. In Spring MVC, `@Valid @RequestBody` triggers it for HTTP input, but model output you parse yourself must be validated explicitly with an injected `Validator`.

**Compact constructor vs Bean Validation.** A compact constructor can normalize (trim, `List.copyOf`) and throw on invariants. However, an exception from a constructor during Jackson binding surfaces as a `ValueInstantiationException` with a less structured message. A good split: **normalize** in the compact constructor, **validate** with Bean Validation (it reports *all* violations at once with paths such as `toolRequest.arguments.amount`, which you can feed back to the model on retry).

#### 4.6 Malformed Output Handling, Controlled Retry and Failure

**Failure classes and responses.**

| Class | Example | Retry? | Feedback to model |
|---|---|---|---|
| `UNPARSEABLE` | Prose, code fences, truncated JSON (hit `max_tokens`) | Yes, ≤ 1–2 | "Output was not a single JSON object. Return only JSON matching the schema." If truncated: raise `max_tokens` or shorten the request instead of blind retry |
| `SCHEMA_VIOLATION` | Missing `toolRequest`, amount negative, unknown field | Yes, ≤ 1–2 | List of violation paths + messages (no stack traces, no internal names you'd rather not reveal) |
| `SEMANTIC_VIOLATION` | Cites doc not retrieved; tool not in advertised set | Yes, ≤ 1 | "Citation D-9 is not among the provided documents." |
| `POLICY_DENIED` | Refund another customer's order | **No** | Model gets a denial observation (Unit 33); count toward denial budget |
| `REFUSAL` | Provider returns a safety refusal | No (or escalate) | Return safe fallback |
| `PROVIDER_ERROR` | 429/5xx/timeout | Transport retry with backoff (separate budget) | n/a |

**Retry design rules.**

1. **Bounded.** Max repair attempts per decision (typically 2) and an overall run budget (steps, tokens, wall clock).
2. **Feedback, not repetition.** Re-sending the same prompt at temperature 0 gives the same wrong answer. Include the specific validation errors.
3. **Never retry policy denials** as format errors. That would turn the retry loop into an automated jailbreak search.
4. **Fail closed.** After the budget, return a typed failure (`ESCALATE` to a human, or an error response). Never fall back to "best-effort parse the prose and act".
5. **Measure.** Schema-compliance rate on first attempt, repair success rate, and failures by class. These are your regression signals after a model change.
6. **Idempotency.** A retried *decision* must not cause a repeated *action*. Actions execute only after a fully validated decision, and they carry an idempotency key (Unit 35).

**Spring AI 2.0 equivalents.** [Version-dependent] `chatClient.prompt()...call().entity(MyRecord.class)` converts output to a type via `BeanOutputConverter`. Native structured output can be enabled so the provider constrains decoding. `StructuredOutputValidationAdvisor` validates the result against the JSON schema and re-prompts with the errors (default 3 retries; configurable with `maxRepeatAttempts`). These give you schema-level repair. You still run **Bean Validation, semantic checks and policy** in your own code, because the advisor validates the JSON schema, not your business rules. Third-party reports also indicate that combining the validation advisor with tool-calling rounds can multiply model calls, so measure the call count in tests.

#### 4.7 Validating Every Software-Facing Decision Before Execution

**The invariant:** no code path executes a tool, writes data or sends anything based on model output unless that output has passed parse → validate → bind → semantic → policy. Enforce this structurally:

- The executor's API only accepts `ValidatedToolCall` (a type that can only be constructed by the validator, using a package-private constructor). This is the *parse, don't validate* idea: once validated, the type carries the proof.
- An ArchUnit test forbids calls to tool implementations from anywhere except the executor.
- Framework auto-execution of tools is disabled for write tools (Unit 33).

### 5. Internal Mechanics

#### 5.1 What Jackson does with a record

```
JSON text
 → JsonParser (streaming tokens: START_OBJECT, FIELD_NAME "type", VALUE_STRING "CALL_TOOL", …)
 → BeanDeserializer for AgentDecision (introspected once, cached per mapper)
     - detects canonical constructor as "properties-based creator"
     - buffers properties by name until all creator params seen or END_OBJECT
     - unknown name? → FAIL_ON_UNKNOWN_PROPERTIES → UnrecognizedPropertyException
     - "type": "CALL_TOOL" → EnumDeserializer → DecisionType.CALL_TOOL (unknown → InvalidFormatException)
     - "toolRequest": {...} → nested BeanDeserializer (ToolRequest), "arguments" → JsonNode (tree)
 → invoke canonical constructor (compact constructor runs: normalization)
 → if FAIL_ON_TRAILING_TOKENS: ensure no more tokens
 → AgentDecision instance
```

Deserializers are built once per type per mapper and cached, so **reuse one mapper instance**. Mappers are thread-safe after configuration, and creating one per call is expensive.

#### 5.2 What Bean Validation does

```
validator.validate(decision)
 → BeanMetaData for AgentDecision (cached): constraints per component + @AssertTrue methods
 → evaluate each constraint → ConstraintViolation(path, message, invalidValue)
 → @Valid toolRequest → recurse
 → returns Set<ConstraintViolation<AgentDecision>> (all failures, not just first)
```

#### 5.3 Two-stage binding of tool arguments

The envelope keeps `arguments` as a `JsonNode`. After the envelope validates, the registry looks up the tool's argument class and calls `mapper.treeToValue(arguments, IssueRefundArgs.class)`, then validates that record. This gives every tool its own strict schema and lets you advertise per-tool schemas to the model (tool definitions) while keeping one generic decision envelope.

#### Example 1 — Minimal: Strict parse + validate

```java
package com.example.supportops.decision;

import com.fasterxml.jackson.annotation.JsonProperty;
import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import tools.jackson.databind.JsonNode;

import java.util.List;

public enum DecisionType { ANSWER, CALL_TOOL, ASK_CLARIFICATION, ESCALATE }

public record ToolRequest(
        @NotBlank @Pattern(regexp = "[a-z][a-z_]{2,39}") String toolName,
        @NotNull JsonNode arguments,
        @NotBlank @Size(max = 500) String justification) {}

public record AgentDecision(
        @NotNull DecisionType type,
        @Size(max = 4000) String answer,
        @Valid ToolRequest toolRequest,
        @Size(max = 500) String clarificationQuestion,
        @NotNull @Size(max = 10) List<@Pattern(regexp = "D-\\d{1,6}") String> citations,
        @DecimalMin("0.0") @DecimalMax("1.0") Double confidence) {

    public AgentDecision {
        citations = citations == null ? List.of() : List.copyOf(citations);  // normalize + defensive copy
        answer = answer == null ? null : answer.strip();
    }

    @AssertTrue(message = "fields must match decision type")
    @JsonProperty(access = JsonProperty.Access.READ_ONLY)   // Not a JSON property; validation only.
    public boolean isConsistent() {
        if (type == null) return true; // @NotNull reports this
        return switch (type) {
            case ANSWER -> answer != null && !answer.isBlank() && toolRequest == null;
            case CALL_TOOL -> toolRequest != null && answer == null;
            case ASK_CLARIFICATION -> clarificationQuestion != null && toolRequest == null;
            case ESCALATE -> toolRequest == null;
        };
    }
}
```

package com.example.supportops.decision;

import jakarta.validation.Validation;
import jakarta.validation.Validator;
import tools.jackson.core.JacksonException;
import tools.jackson.databind.DeserializationFeature;
import tools.jackson.databind.MapperFeature;
import tools.jackson.databind.json.JsonMapper;

public final class MinimalDecisionParser {

    static final JsonMapper STRICT = JsonMapper.builder()
        .enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)
        .enable(DeserializationFeature.FAIL_ON_NULL_FOR_PRIMITIVES)
        .enable(DeserializationFeature.FAIL_ON_TRAILING_TOKENS)
        .disable(DeserializationFeature.ACCEPT_FLOAT_AS_INT)
        .disable(MapperFeature.ALLOW_COERCION_OF_SCALARS)
        .build();

    static final Validator VALIDATOR = Validation.buildDefaultValidatorFactory().getValidator();

    public static void main(String[] args) {
        String fromModel = """
            {"type":"CALL_TOOL","answer":null,"clarificationQuestion":null,"citations":[],
             "confidence":0.8,
             "toolRequest":{"toolName":"issue_refund",
                            "arguments":{"orderId":"8812","amount":49.00,"reason":"LATE_DELIVERY"},
                            "justification":"Late delivery"}}
            """;
        try {
            AgentDecision d = STRICT.readValue(fromModel, AgentDecision.class);
            var violations = VALIDATOR.validate(d);
            System.out.println(violations.isEmpty() ? "VALID " + d.type() : "INVALID " + violations);
        } catch (JacksonException e) {
            System.out.println("UNPARSEABLE: " + e.getOriginalMessage());
        }
    }
}
```

Try mutating the JSON: add `"approved": true` (unknown property → fails), set `"type":"REFUND"` (invalid enum → fails), set `"answer":"ok"` alongside a tool request (`isConsistent` → violation), or append `garbage` after the object (trailing tokens → fails).

#### Example 3 — Production-oriented: Decision validator with classified failures and bounded repair

**Architecture.** `DecisionValidator` turns raw text into a sealed `ValidationResult`. `DecisionLoop` calls the model, validates, and on a repairable failure re-prompts with the error list, up to `maxRepairs`. It records metrics per failure class. A `ValidatedToolCall` can only be created by the validator.

```java
package com.example.supportops.decision;

import com.example.supportops.tools.ToolRegistry;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validator;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.stereotype.Component;
import tools.jackson.core.JacksonException;
import tools.jackson.databind.json.JsonMapper;

import java.util.Comparator;
import java.util.List;
import java.util.Set;

@Component
public class DecisionValidator {

    public enum FailureClass { UNPARSEABLE, SCHEMA_VIOLATION, SEMANTIC_VIOLATION }

    public sealed interface ValidationResult {
        record Valid(AgentDecision decision, ValidatedToolCall toolCall) implements ValidationResult {}
        record Invalid(FailureClass failureClass, List<String> errors) implements ValidationResult {}
    }

    private static final int MAX_RAW_CHARS = 20_000;

    private final JsonMapper mapper;
    private final Validator validator;
    private final ToolRegistry registry;

    public DecisionValidator(@Qualifier("agentJson") JsonMapper mapper, Validator validator, ToolRegistry registry) {
        this.mapper = mapper;
        this.validator = validator;
        this.registry = registry;
    }

    public ValidationResult validate(String raw, Set<String> advertisedTools, Set<String> retrievedDocIds) {
        if (raw == null || raw.length() > MAX_RAW_CHARS) {
            return invalid(FailureClass.UNPARSEABLE, "Output missing or too long");
        }
        String json = stripSingleCodeFence(raw.strip());

        final AgentDecision decision;
        try {
            decision = mapper.readValue(json, AgentDecision.class);
        } catch (JacksonException e) {
            // getOriginalMessage() omits source snippets; don't echo large raw content back.
            return invalid(FailureClass.UNPARSEABLE, "Invalid JSON: " + e.getOriginalMessage());
        }

        List<String> errors = messages(validator.validate(decision));
        if (!errors.isEmpty()) return new ValidationResult.Invalid(FailureClass.SCHEMA_VIOLATION, errors);

        // Semantic checks: things the schema cannot know.
        for (String c : decision.citations()) {
            if (!retrievedDocIds.contains(c)) {
                return invalid(FailureClass.SEMANTIC_VIOLATION, "Citation " + c + " was not provided in context");
            }
        }
        if (decision.type() != DecisionType.CALL_TOOL) {
            return new ValidationResult.Valid(decision, null);
        }

        ToolRequest tr = decision.toolRequest();
        if (!advertisedTools.contains(tr.toolName())) {
            return invalid(FailureClass.SEMANTIC_VIOLATION, "Tool " + tr.toolName() + " is not available");
        }
        var def = registry.require(tr.toolName());
        final Object typedArgs;
        try {
            typedArgs = mapper.treeToValue(tr.arguments(), def.argsType());
        } catch (JacksonException e) {
            return invalid(FailureClass.SCHEMA_VIOLATION,
                "Arguments for " + tr.toolName() + " invalid: " + e.getOriginalMessage());
        }
        List<String> argErrors = messages(validator.validate(typedArgs));
        if (!argErrors.isEmpty()) {
            return new ValidationResult.Invalid(FailureClass.SCHEMA_VIOLATION,
                argErrors.stream().map(m -> "arguments." + m).toList());
        }
        return new ValidationResult.Valid(decision, new ValidatedToolCall(tr.toolName(), typedArgs, tr.justification()));
    }

    /** Accept exactly one ```json fenced block; anything else must be bare JSON. */
    static String stripSingleCodeFence(String s) {
        if (s.startsWith("```")) {
            int firstNl = s.indexOf('\n');
            int last = s.lastIndexOf("```");
            if (firstNl > 0 && last > firstNl) return s.substring(firstNl + 1, last).strip();
        }
        return s;
    }

    private static <T> List<String> messages(Set<ConstraintViolation<T>> violations) {
        return violations.stream()
            .map(v -> v.getPropertyPath() + ": " + v.getMessage())
            .sorted(Comparator.naturalOrder())   // deterministic order → stable prompts and tests
            .toList();
    }

    private static ValidationResult invalid(FailureClass c, String msg) {
        return new ValidationResult.Invalid(c, List.of(msg));
    }
}
```

    public sealed interface Outcome {
        record Decided(DecisionValidator.ValidationResult.Valid valid, int attempts) implements Outcome {}
        record GaveUp(DecisionValidator.FailureClass lastFailure, List<String> errors, int attempts) implements Outcome {}
    }

    private final DecisionValidator validator;
    private final MeterRegistry meters;
    private final int maxRepairs;

    public DecisionLoop(DecisionValidator validator, MeterRegistry meters) {
        this(validator, meters, 2);
    }

    DecisionLoop(DecisionValidator validator, MeterRegistry meters, int maxRepairs) {
        this.validator = validator;
        this.meters = meters;
        this.maxRepairs = maxRepairs;
    }

    public Outcome decide(DecisionModel model, List<String> conversation,
                          Set<String> advertisedTools, Set<String> retrievedDocIds) {
        List<String> convo = new ArrayList<>(conversation);
        DecisionValidator.ValidationResult.Invalid last = null;

        for (int attempt = 1; attempt <= 1 + maxRepairs; attempt++) {
            String raw = model.next(List.copyOf(convo));
            var result = validator.validate(raw, advertisedTools, retrievedDocIds);
            switch (result) {
                case DecisionValidator.ValidationResult.Valid v -> {
                    meters.counter("agent.decision.validation", "result", "valid",
                                   "attempt", String.valueOf(attempt)).increment();
                    return new Outcome.Decided(v, attempt);
                }
                case DecisionValidator.ValidationResult.Invalid inv -> {
                    meters.counter("agent.decision.validation", "result", inv.failureClass().name(),
                                   "attempt", String.valueOf(attempt)).increment();
                    last = inv;
                    convo.add("assistant: " + truncate(raw, 2_000));
                    convo.add("user: Your previous output was rejected (" + inv.failureClass() + "). "
                        + "Fix ONLY these problems and return a single JSON object matching the schema:\n- "
                        + String.join("\n- ", inv.errors()));
                }
            }
        }
        return new Outcome.GaveUp(last.failureClass(), last.errors(), 1 + maxRepairs);
    }

    private static String truncate(String s, int max) {
        return s == null ? "" : (s.length() <= max ? s : s.substring(0, max) + "…");
    }
}
```

**Important design notes.**

- Errors fed back to the model are **Bean Validation paths and messages**, which are useful and safe. Don't feed back stack traces, SQL, or policy rule details.
- Code-fence stripping is deliberately narrow: one fenced block. Anything else is `UNPARSEABLE`. Don't build a "find any JSON in the prose" extractor, because it will happily extract an attacker's JSON from quoted email text.
- `GaveUp` maps to an `ESCALATE` response to the user ("I couldn't complete this; a human will follow up") plus an alert if the rate exceeds a threshold.

### 7. Comparative Analysis

| Comparison | Key difference | When to use | Trap |
|---|---|---|---|
| Prose vs typed decision | Human-readable vs machine-checkable | Prose for final answers to humans; types for anything executed | Regex over prose "works in the demo" |
| Prompt-only JSON vs native structured output | Instruction vs constrained decoding | Native wherever supported; prompt-only as fallback | Believing native output = valid business data |
| Structured output vs tool-call arguments | Response format vs function-call payload | Tool calls when the model chooses among actions; structured output for classification/extraction/final envelope | Both still need validation |
| Jackson strict vs lenient | Fail on surprises vs ignore them | Strict for model output; lenient for evolving public API clients | Reusing the Boot HTTP mapper for model output |
| Bean Validation vs compact-constructor checks | All violations with paths vs first exception | Validation for reporting; constructor for normalization/invariants | Throwing in constructors hides useful error detail |
| Flat envelope vs sealed `oneOf` | Portable vs precise | Flat for multi-provider; sealed when provider supports it | Root-level `oneOf` rejected by strict modes |
| Retry with feedback vs blind retry | Repair vs repeat | Always feedback; bounded | Unbounded retries; retrying policy denials |
| `entity()` vs own validator | Convenience vs control | `entity()` for low-risk extraction; own validator for actions | Assuming framework validation covers business rules |

### 8. Failure Modes and Debugging

**Failure 1 — Schema compliance drops after a model upgrade.**

- SYMPTOM: `agent.decision.validation{result=SCHEMA_VIOLATION, attempt=1}` jumps from 1% to 12%.
- LIKELY CAUSE: New model formats differently (wraps output in prose; uses `"amount": "49.00"` strings), or native structured output got disabled by a config key change during a Spring AI upgrade (for example the removed `.options` segment in property names in 2.0).
- INVESTIGATE: Sample failed raw outputs from the (redacted) debug store; group by error path; diff the effective request (is the schema being sent? which mode?).
- FIX: Re-enable native mode; update the prompt example; don't loosen coercion just to make it pass.
- PREVENT: The Unit 36 regression suite includes schema compliance with a threshold; config-diff checks in CI.

**Failure 2 — Truncated JSON.**

- SYMPTOM: `UNPARSEABLE: Unexpected end-of-input` for long answers.
- LIKELY CAUSE: `max_tokens` reached (the provider's finish reason is `length`/`max_tokens`).
- INVESTIGATE: Check the finish reason in the response metadata/trace.
- FIX: Raise the limit for this call; constrain answer length in the schema (`maxLength`) and prompt; retrying unchanged won't help.
- PREVENT: Alert on finish reason = length.

**Failure 3 — Model invents a field and nobody notices.**

- SYMPTOM: Model emits `"requiresApproval": false`. The team believes the model "decided" no approval was needed, and the code path silently ignored it. A reviewer later asks why approvals were skipped. The real cause was a separate bug, but the investigation was misdirected.
- LIKELY CAUSE: Lenient mapper.
- FIX/PREVENT: Strict mapper; approval is decided by policy only (Unit 35).

**Failure 4 — Repair loop amplifies cost.**

- SYMPTOM: Token spend doubled; p95 latency up 3×.
- LIKELY CAUSE: A new semantic check fails 40% of the time and each failure triggers two repairs; or validation advisor + tool rounds multiply calls.
- INVESTIGATE: Distribution of `attempt` tag; model call count per run in traces.
- FIX: Fix the root cause (prompt/schema mismatch), lower `maxRepairs`, and treat a high repair rate as a defect.

**Failure 5 — `isConsistent` breaks deserialization.**

- SYMPTOM: `UnrecognizedPropertyException: "consistent"` when *serializing then deserializing* audit records.
- CAUSE: The boolean accessor was serialized as a property.
- FIX: `@JsonIgnore` or `READ_ONLY` access, plus a round-trip test.

**Debugging tools.** Store **redacted raw outputs** for failed validations with a short retention period. Use a replay harness that runs `DecisionValidator` over a file of stored outputs. Record trace attributes such as `agent.decision.failure_class` and `agent.decision.attempt` (Unit 37). Jackson's `getOriginalMessage()` and the location info in `JacksonException` point at the offending token.

### 12. Engineering Scenarios

**Scenario 1 — "Can't we just ask for JSON in the prompt?"** A teammate's prototype parses `{...}` from prose and works "99% of the time". *Questions:* What happens in the 1%? What does a wrong parse cost? *Reasoning:* 1% of 50k daily decisions is 500 bad parses per day. With refunds, one wrong parse is an incident. Use native structured output for compliance, a strict validator for correctness, bounded repair for the residual failures, and a metric so "99%" is measured rather than assumed.

**Scenario 2 — Multi-provider portability (FDE).** The customer requires a fallback provider for outages, and the two providers support different schema subsets. *Options:* lowest-common-denominator flat schema; per-provider schema adapters; prompt-only fallback with heavier validation. *Reasoning:* Keep one Java contract (records + Bean Validation) as the source of truth. Generate per-provider schemas from it, and run the eval suite against both providers before enabling failover.

**Scenario 3 — Stakeholder wants "confidence".** Product wants auto-execution when `confidence > 0.9`. *Reasoning:* Model-reported confidence is not calibrated and is attacker-influenceable. Use it as a UX signal or eval feature only. Routing must use deterministic risk rules (Unit 35). If confidence is wanted, calibrate it against eval outcomes first.

**Scenario 4 — Schema evolution.** You need to add `currency` to `IssueRefundArgs`. *Reasoning:* With a strict mapper, old prompts and new code are fine (new required field → model must supply it; update prompt and schema together). Ship schema + prompt + validator in one change, rerun evals, and version the decision contract in the audit records (`decisionSchemaVersion`).

### 13. Interview Preparation

#### Quick Questions

**Q: Why is prose unsafe for machine decisions?**
*Strong answer:* Ambiguity, fragile parsing, no closed set of actions, injection through formatting, and no measurable compliance. Types make the action space closed and checkable.

**Q: Does native structured output remove the need for validation?**
*Strong answer:* No. It guarantees syntax and the supported schema subset, not business semantics (ownership, balances), and providers/models/config change. Validate anyway.

**Q: What does `FAIL_ON_UNKNOWN_PROPERTIES` protect against here?**
*Strong answer:* Silent acceptance of invented fields, which hides schema drift and misleads you about what the model "decided".

#### Intermediate Questions

**Q: Describe your retry strategy for malformed model output.**
*Strong answer:* Classify failures. Retry only repairable classes (unparseable, schema, semantic) with specific error feedback, max ~2 attempts within an overall run budget. Never retry policy denials or refusals. Fail closed to escalation. Measure first-attempt compliance and repair success. Keep transport retries (429/5xx) separate with backoff.
*Trap:* "Retry until it works", or retrying at temperature 0 with the same prompt.

**Q: How do you validate tool arguments for many different tools with one decision type?**
*Strong answer:* Generic envelope with `arguments` as `JsonNode`. After the envelope validates, bind to the tool's argument record with `treeToValue` and validate that. Generate and advertise per-tool schemas from the same records.

**Q: Where does Bean Validation run for model output in Spring?**
*Strong answer:* Only where you call it. `@Valid` on controller parameters covers HTTP input; for model output, inject `Validator` and call it after parsing.

#### Advanced Questions

**Q: Design a decision contract for an agent that can answer, call tools, ask for clarification or escalate. How do you make invalid states unrepresentable?**
*Strong answer:* Either a sealed interface with one record per decision (strongest; exhaustive `switch`) or a flat envelope with an `@AssertTrue` consistency rule (portable across providers' schema subsets). Bounded fields everywhere, IDs as references resolved server-side, a proof-carrying `ValidatedToolCall` type, and an ArchUnit rule that execution only accepts it. Discuss the provider schema-subset trade-off.

**Q: How would you detect that a model upgrade degraded decision quality before customers notice?**
*Strong answer:* Offline regression eval with schema compliance and task metrics vs baseline (Unit 36); canary with live metrics (`validation{attempt=1}` compliance, `GaveUp` rate, repair rate) and automatic rollback thresholds.

**Q: Why not just extract the first JSON object from the output?**
*Strong answer:* Prose can contain quoted user or attacker content with JSON in it. Lenient extraction lets an injected JSON object become the decision. Accept bare JSON or one fenced block, nothing else.

#### Coding Questions

1. Write a `@ValidRefundAmount` class-level constraint that checks `amount.scale() <= 2`.
2. Implement `stripSingleCodeFence` with tests for: no fence, `json` fence, unclosed fence, two fences.
3. Given `Set<ConstraintViolation<?>>`, produce deterministic, model-friendly error lines.

#### Scenario Questions

**Q: A partner team's agent produces CSV-like text that your service parses into refunds. How do you migrate safely?**
*Strong answer:* Define the typed contract and schema. Run both parsers in shadow mode and log disagreements. Move the partner to native structured output. Gate on compliance metrics. Cut over behind a flag with a rollback plan. Meanwhile, put validation and policy in front of the existing parser immediately.

#### Knowledge Check Answers

1. Ambiguous values, brittle parsing across formats, and injection through formatting/negation (also: no closed action set, no compliance metric).
2. Syntactically valid output matching the provider-supported schema subset. Not business validity, not that IDs exist or belong to the user, and not behavior across provider/config changes.
3. To set strict features explicitly without altering the application's HTTP mapper, and to avoid depending on Boot/Jackson defaults that differ across versions.
4. It turns the repair loop into an automated search for a phrasing that passes policy, and the answer from policy is "no", not "malformed".
5. A type that can only be created after validation, so holding an instance proves validation happened. `ValidatedToolCall` has a package-private constructor used only by `DecisionValidator`, and the executor accepts only that type.
6. Records are only shallowly immutable. Copying prevents external mutation and normalizes `null` to an empty list.
7. Deserialization fails (mismatched input) → `SCHEMA_VIOLATION`/`UNPARSEABLE` → repair with feedback.
8. Deterministic error order gives stable repair prompts (and therefore more cache hits and reproducible behavior) and stable test assertions.
9. The provider's finish reason (likely the max-token limit). Retrying unchanged won't fix truncation.
10. Native structured output disabled or schema no longer sent (for example renamed property keys such as the dropped `.options` segment in Spring AI 2.0), so the model falls back to prompt-only formatting.
11. Usually flat envelope with cross-field validation (portable), unless both providers support root `oneOf` in strict mode, with per-provider evals.
12. No. It's uncalibrated and manipulable. Use deterministic risk rules; treat confidence as a signal for UX/evals only.

### 16. Common Interview Traps

- **"We use JSON mode, so output is valid."** Valid JSON ≠ valid decision.
- **"Unknown fields should be ignored for forward compatibility."** True for public APIs, wrong for model output.
- **"Retry until the output parses."** Unbounded cost, and dangerous if denials are retried.
- **"Bean Validation runs automatically."** Only where Spring triggers it, and model output isn't one of those places.
- **"Use `double` for amounts; it's just JSON."** Money is `BigDecimal` with an explicit scale.
- **"The framework's `entity()` handles validation."** It handles conversion and optional schema checks, not your business rules.
- **"Extract the JSON from wherever it appears in the response."** That is an injection vector.

### 17. Cheat Sheet

- **Pipeline:** extract (bare or one fence) → strict parse → Bean Validation → bind args per tool → semantic checks → policy → execute/approve.
- **Records:** `@NotNull`, `@NotBlank`, `@Size(max)`, `@Pattern`, `@Positive`, `@Digits(integer, fraction)`, `@Valid` nested, `List<@Pattern String>`, `@AssertTrue isXxx()` for cross-field rules (`@JsonIgnore` it).
- **Jackson 3 strict:** `FAIL_ON_UNKNOWN_PROPERTIES` on, `FAIL_ON_NULL_FOR_PRIMITIVES` on, `FAIL_ON_TRAILING_TOKENS` on, `ACCEPT_FLOAT_AS_INT` off, `ALLOW_COERCION_OF_SCALARS` off, `BigDecimal` for money, no default typing. Packages: `tools.jackson.*`; annotations `com.fasterxml.jackson.annotation.*`; exceptions unchecked (`JacksonException`).
- **Failure classes:** UNPARSEABLE / SCHEMA / SEMANTIC → repair ≤ 2 with errors; POLICY_DENIED / REFUSAL → no retry; PROVIDER_ERROR → transport backoff.
- **Spring AI 2.0:** `.call().entity(Type.class)`; native structured output; `StructuredOutputValidationAdvisor` (default 3 retries, `maxRepeatAttempts`); `ToolCallingAdvisor` runs the tool loop, so disable it or keep write tools off it.
- **Metrics:** first-attempt compliance, repair success, GaveUp rate, failures by class, model calls per decision.
