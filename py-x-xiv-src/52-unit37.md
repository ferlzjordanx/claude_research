## Unit 37 — Agent State, Memory and Persistence

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Distinguish** conversation state, working state, long-term memory and authoritative business data, and **decide** where each lives and who may change it.
2. **Model** an agent workflow as an explicit state machine with legal transitions, and **enforce** those transitions in code and in the database.
3. **Implement** durable checkpoints in PostgreSQL (state snapshot per step, optimistic concurrency, versioned schema) and **resume** an interrupted workflow after a crash, deploy or approval pause.
4. **Implement** bounded conversation memory (window + summary) that is separate from RAG retrieval, and **explain** why memory is not a knowledge base.
5. **Design** long-term memory with provenance, scoping, expiry and user control, and **apply** privacy and retention rules (minimization, TTLs, deletion, encryption, audit).
6. **Test** state transitions, checkpoint round trips, resume correctness, memory bounds and deletion.

### 2. Prerequisite Knowledge

- Unit 35 `AgentState`, `StopReason`, and the runner loop. Unit 36 `agent_run`/`agent_event` tables and worker claiming.
- Pydantic v2 serialization (`model_dump(mode="json")`, `model_validate`), discriminated unions.
- PostgreSQL transactions, `jsonb`, row locking, optimistic concurrency with version columns.
- Basic privacy concepts: personal data, data minimization, retention, right to erasure.

**Refresher: optimistic concurrency.** Each row has a `version` integer. An update says `UPDATE … SET …, version = version + 1 WHERE id = :id AND version = :expected`. If zero rows changed, someone else updated first, so you reload and retry or fail. No locks are held between read and write.

### 3. Mental Model

Four kinds of "memory", with different owners and lifetimes:

```
┌──────────────────────┬─────────────────────────────┬─────────────────────┬────────────────────────────┐
│ Kind                 │ Example                     │ Lifetime            │ Source of truth / writer   │
├──────────────────────┼─────────────────────────────┼─────────────────────┼────────────────────────────┤
│ Conversation state   │ Messages in this ticket chat│ The conversation    │ App (append-only log)      │
│ Working state        │ Step, tool results, budget, │ One run / workflow  │ Runner (checkpoints)       │
│                      │ pending proposals, status   │                     │                            │
│ Long-term memory     │ "Prefers email over phone"  │ Weeks–months, TTL   │ App with provenance; user  │
│                      │                             │                     │ can view/delete            │
│ Authoritative data   │ Orders, refunds, tickets    │ System of record    │ Domain services ONLY       │
└──────────────────────┴─────────────────────────────┴─────────────────────┴────────────────────────────┘
```

Rules of thumb:

- **Authoritative data is never "remembered".** It's read fresh through tools every time. A memory that says "order 8812 was refunded" is a stale copy that will eventually lie.
- **Working state is checkpointed** so the workflow can resume exactly where it stopped.
- **Conversation memory is bounded.** You can't send an unbounded history to the model.
- **Long-term memory is a product feature with privacy obligations**, not a cache.

### 4. Comprehensive Theory

#### 4.1 Conversation State vs Working State vs Long-Term Memory vs Authoritative Data

**Conversation state** is the sequence of user and assistant messages (and, for tool-using agents, tool calls and results in provider format). It's append-only, it's what users see, and it feeds the model's context, after bounding.

**Working state** is what the runner needs to continue: current status, step count, budgets spent, tool observations so far, signatures for loop detection, pending approvals, the agent's plan (if any) and error counters. It's internal and machine-oriented. It must be **serializable** and **versioned**.

**Long-term memory** is information carried across conversations: stable preferences, prior resolutions, notes. It's derived, so it needs **provenance** (where did this come from, when, which run), **scope** (this customer, this tenant), **confidence**, and **expiry**.

**Authoritative data** belongs to domain services with their own invariants (Unit 34's refund rules, ticket ownership). Agents read it through tools and change it only through authorized tools or approval workflows.

| Question | Conversation | Working | Long-term memory | Authoritative |
|---|---|---|---|---|
| Who writes? | App on each turn | Runner | Memory service (after validation) | Domain services |
| Who reads? | Model (bounded), UI | Runner, operators | Model (retrieved, labeled) | Tools |
| Can the model change it directly? | Its own replies only | No | Propose only | No |
| Survives the run? | Yes | Until retention | Yes, with TTL | Yes |
| Must be fresh? | N/A | N/A | Tolerates staleness, labeled | Always fresh |

#### 4.2 State Machines for Agent Workflows

Implicit state ("whatever variables the loop has") makes resume impossible and bugs invisible. Make the workflow status explicit:

```
           ┌──────────┐ claim  ┌─────────┐ needs approval ┌──────────────────┐
  create ─▶│ pending  │───────▶│ running │───────────────▶│ waiting_approval │
           └──────────┘        └─────────┘                └──────────────────┘
                │                │  │  │ ▲  ask user             │ approved/rejected
                │ cancel         │  │  │ └────────┐ ┌───────────┘
                ▼                │  │  ▼          │ ▼
           ┌──────────┐          │  │ ┌──────────────┐  user reply  ┌─────────┐
           │cancelled │◀─────────┘  │ │ waiting_user │─────────────▶│ pending │ (requeued)
           └──────────┘  cancel     │ └──────────────┘              └─────────┘
                                    ▼
                         ┌───────────────────┐
                         │ finished / stopped│ (terminal; stop_reason recorded)
                         └───────────────────┘
```

**Enforcement.** A transition table in code (`ALLOWED[from] -> set[to]`) checked on every change, plus database protection: updates include `WHERE status = :from` so a concurrent change can't produce an illegal transition. Terminal states are final.

**Waiting states are not "running".** A run waiting for approval holds no worker slot, no connection and no lock. When the approval decision arrives, a new **segment** of the run is enqueued, which loads the checkpoint and continues.

#### 4.3 Durable Checkpoints in PostgreSQL

**What a checkpoint contains.** A versioned, serialized `WorkingState` (Pydantic model): status, step, budgets, observations (bounded and redacted), action signatures, pending proposal IDs, message history references (not copies of large content), and the **schema version**.

**When to checkpoint.** After every completed step (model decision + tool result) and before entering a waiting state. Write the checkpoint in the **same transaction** as any internal side effect of that step where possible (for example, the agent_event rows). External side effects (an API call) are protected by idempotency keys derived from `(run_id, step)`, so replaying a step after a crash doesn't duplicate them.

**Storage design choices.**

| Option | Pros | Cons |
|---|---|---|
| One row per run, overwritten (`state jsonb`, `version`) | Simple, small | No history; debugging harder |
| Append-only checkpoint per step (`run_id, step` PK) | History, time-travel debugging, audit | Storage growth; needs retention |
| Event sourcing (rebuild state from events) | Full audit, no separate snapshot | Complex; slow rebuilds without snapshots |

A common production choice: **append-only per-step checkpoints with retention** (keep all for N days, then keep only the latest), plus the run row holding status and a pointer to the latest checkpoint.

**Schema evolution.** Checkpoints written by version 3 of your code may be loaded by version 4 after a deploy. Include `schema_version` and write **upcasters** (functions that migrate old state dicts to the current shape). Never deploy a state change that can't read in-flight checkpoints.

**Concurrency.** Only one worker may advance a run. Claim with `UPDATE agent_run SET status='running', worker_id=:w, lease_until=now()+interval '2 minutes' WHERE id=:id AND status='pending'`. Renew the lease while working. A sweeper requeues runs whose lease expired (worker crashed). Checkpoint writes include `WHERE version = :expected` to detect a second writer.

#### 4.4 Resuming an Interrupted Workflow

Interruption causes: a worker crash or deploy (SIGTERM), an approval pause, a user-input pause, a provider outage (the run parks with "retry later"), and an explicit pause by operators.

**Resume algorithm.**

1. Load the run row and the latest checkpoint. Upcast to the current schema.
2. Validate that the transition to `running` is legal and claim the lease.
3. Re-validate the world: the user's permissions may have changed, the ticket may be closed, the approval may be expired. Re-derive `ToolContext` from current identity data, never from the checkpoint alone.
4. Rebuild the model context from the conversation log + working state (bounded).
5. Continue the loop with the remaining budgets (budgets are cumulative across segments, not reset).
6. If the last checkpoint recorded a tool call as `started` but not `completed`, its outcome is **unknown**: re-run it only if it's read-only or idempotent with the same key. Otherwise reconcile (query the downstream by idempotency key) before continuing.

**What resume must not do:** restart from step 0 (duplicate side effects, wasted cost), trust stale permissions, or reset budgets.

#### 4.5 Bounded Conversation Memory (Separate from RAG)

**Why bound.** Context windows are large but not free: cost and latency scale with input tokens, quality degrades with irrelevant history, and old tool outputs can carry injection text.

**Strategies.**

| Strategy | How | Trade-off |
|---|---|---|
| Sliding window | Keep last N turns (by tokens, not messages) | Simple; forgets early facts |
| Summary + window | Summarize older turns into a running summary; keep recent turns verbatim | Keeps gist; summary can drift or embed errors |
| Structured facts | Extract key facts (order IDs mentioned, user's stated goal) into working state | Precise; needs schemas |
| Tool-result elision | Replace old tool results with short stubs ("[order 8812 looked up at step 3]") | Big savings; re-fetch if needed |

**Memory is not RAG.** RAG retrieves from a curated, access-controlled knowledge base (policies, documentation). Conversation memory is what happened in this interaction. Mixing them causes real problems: user statements ("your policy gives me 90 days") retrieved later as if they were policy, cross-customer leakage if memory is indexed with the KB, and stale facts presented with KB-level authority. Keep separate stores, separate retrieval paths, and label each in the prompt (`<conversation_summary>` vs `<knowledge_base_results>`).

**Summaries are model output.** Treat them as untrusted-ish: bound their length, keep them out of authorization decisions, and regenerate rather than endlessly append.

#### 4.6 Long-Term Memory Design

**Write path.** Don't let the model write arbitrary memories. Use a proposal: the model (or a post-run extractor) proposes `MemoryCandidate(kind, content, evidence_run_id, confidence)`, and a validator applies rules: allowed kinds only (preferences, prior resolution summaries), no secrets or sensitive categories, no authoritative facts (order status, refund amounts), scope to the customer and tenant, set TTL. Optionally require human confirmation for some kinds.

**Read path.** Retrieve by scope (tenant + customer) first, then relevance. Label memories in the prompt with their age and source. Never use memories for authorization.

**User control.** Users (customers and agents) can view and delete memories. Deletion must cascade to derived data (embeddings, summaries, caches).

#### 4.7 Privacy and Retention

| Principle | Application |
|---|---|
| Minimization | Store references (order IDs) not copies of PII; redact tool observations in checkpoints |
| Purpose limitation | Memory used only for support of the same customer; not for marketing or model training without consent |
| Retention | TTLs per data class: events 30 d, checkpoints 30 d then latest-only, conversation logs per policy, memories 180 d unless refreshed |
| Deletion / erasure | A deletion job removes or anonymizes conversation logs, checkpoints, events, memories and embeddings for a data subject; verified by tests |
| Security | Encryption at rest, tenant isolation (RLS from Unit 32), access logging for operator views |
| Transparency | Users can see what's remembered; UI labels AI-generated summaries |
| Provider data | Know your LLM provider's data retention and training terms; don't send what you can't justify |

Regulatory specifics (GDPR, CCPA, sector rules) are [Version-dependent] and jurisdiction-dependent, so work with your privacy/legal team. The engineering job is to make retention and deletion **possible and tested**.

### 5. Internal Mechanics

#### 5.1 Checkpoint write within a step

```
step k:
  decision = await llm(...)                     # no state change yet
  record "tool_started" (run_id, k, tool, idem_key=f"{run_id}:{k}") ─┐ tx1
  result = await tool(...)  (external call, idempotent)              │
  BEGIN tx2                                                          │
    INSERT agent_checkpoint(run_id, k+1, state_json, schema_version) │
    INSERT agent_event(... tool_result ...)                          │
    UPDATE agent_run SET last_step=k+1, version=version+1            │
      WHERE id=:id AND version=:v   (0 rows → conflict → abort)      │
  COMMIT                                                             ┘
crash between tool and tx2 → on resume: checkpoint says step k started, not completed → reconcile by idem_key
```

#### 5.2 Context rebuild on resume

```
messages = system prompt (versioned)
         + <conversation_summary> (if any, bounded)
         + last N turns verbatim (token-bounded)
         + working-state digest: "Steps so far: 1) get_order 8812 → shipped; 2) get_shipment_status → delayed"
         + pending: "Refund proposal P-77 was approved by J. Kim at 14:02"
→ model continues from a compact, faithful view instead of replaying raw history
```

```python
# app/agent/status.py
from enum import StrEnum


class RunStatus(StrEnum):
    PENDING = "pending"
    RUNNING = "running"
    WAITING_APPROVAL = "waiting_approval"
    WAITING_USER = "waiting_user"
    FINISHED = "finished"
    STOPPED = "stopped"
    CANCELLED = "cancelled"


TERMINAL = {RunStatus.FINISHED, RunStatus.STOPPED, RunStatus.CANCELLED}

ALLOWED: dict[RunStatus, set[RunStatus]] = {
    RunStatus.PENDING: {RunStatus.RUNNING, RunStatus.CANCELLED},
    RunStatus.RUNNING: {RunStatus.WAITING_APPROVAL, RunStatus.WAITING_USER, RunStatus.FINISHED,
                        RunStatus.STOPPED, RunStatus.CANCELLED, RunStatus.PENDING},   # PENDING = requeue
    RunStatus.WAITING_APPROVAL: {RunStatus.PENDING, RunStatus.CANCELLED, RunStatus.STOPPED},
    RunStatus.WAITING_USER: {RunStatus.PENDING, RunStatus.CANCELLED, RunStatus.STOPPED},
    RunStatus.FINISHED: set(), RunStatus.STOPPED: set(), RunStatus.CANCELLED: set(),
}


class IllegalTransition(Exception):
    pass


def check_transition(current: RunStatus, new: RunStatus) -> None:
    if new not in ALLOWED[current]:
        raise IllegalTransition(f"{current} -> {new}")
```

```python
# app/persistence/transitions.py
from sqlalchemy import text

from app.agent.status import RunStatus, check_transition


async def transition(session, run_id, current: RunStatus, new: RunStatus, **fields) -> bool:
    check_transition(current, new)                                  # code-level rule
    sets = ", ".join(f"{k} = :{k}" for k in fields)
    result = await session.execute(text(
        f"UPDATE agent_run SET status = :new{', ' + sets if sets else ''}, updated_at = now() "
        "WHERE id = :id AND status = :current"),                    # DB-level guard against races
        {"new": new.value, "current": current.value, "id": run_id, **fields})
    return result.rowcount == 1
```

(`fields` keys come from code, never from user input, so the f-string column list is safe. Values are bound parameters.)

#### Example 2 — Realistic: Versioned working state, checkpoint store with optimistic concurrency, and upcasting

```python
# app/agent/working_state.py
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field

CURRENT_SCHEMA = 2


class ObservationRecord(BaseModel):
    step: int
    tool: str
    summary: str = Field(max_length=500)      # redacted, user-safe summary
    ok: bool
    ref: str | None = None                    # e.g. "order:8812" — a reference, not a copy


class PendingToolCall(BaseModel):
    step: int
    tool: str
    idempotency_key: str
    effect: Literal["read", "write"]


class WorkingState(BaseModel):
    model_config = ConfigDict(extra="forbid")
    schema_version: int = CURRENT_SCHEMA
    run_id: str
    step: int = 0
    input_tokens: int = 0
    output_tokens: int = 0
    cost_usd: float = 0.0
    observations: list[ObservationRecord] = Field(default_factory=list, max_length=50)
    action_signatures: list[str] = Field(default_factory=list)
    pending_call: PendingToolCall | None = None          # set before a tool runs, cleared after
    pending_proposals: list[str] = Field(default_factory=list)
    conversation_summary: str = Field(default="", max_length=4000)


def upcast(raw: dict[str, Any]) -> dict[str, Any]:
    """Migrate older checkpoint dicts to the current schema, one version at a time."""
    version = raw.get("schema_version", 1)
    if version == 1:
        # v1 stored "tokens" as a single number and had no pending_call.
        raw = {**raw, "input_tokens": raw.pop("tokens", 0), "output_tokens": 0,
               "pending_call": None, "schema_version": 2}
        version = 2
    if version != CURRENT_SCHEMA:
        raise ValueError(f"unsupported checkpoint schema {version}")
    return raw
```

```python
# app/persistence/checkpoints.py
from dataclasses import dataclass

from sqlalchemy import text

from app.agent.working_state import WorkingState, upcast


class CheckpointConflict(Exception):
    pass


@dataclass
class CheckpointStore:
    session_factory: object

    async def save(self, state: WorkingState, expected_version: int) -> int:
        async with self.session_factory() as s, s.begin():
            await s.execute(text(
                "INSERT INTO agent_checkpoint (run_id, step, schema_version, state) "
                "VALUES (:r, :step, :v, CAST(:state AS jsonb))"),
                {"r": state.run_id, "step": state.step, "v": state.schema_version,
                 "state": state.model_dump_json()})
            res = await s.execute(text(
                "UPDATE agent_run SET last_step = :step, version = version + 1, "
                "lease_until = now() + interval '2 minutes' "
                "WHERE id = :r AND version = :expected"),
                {"r": state.run_id, "step": state.step, "expected": expected_version})
            if res.rowcount != 1:
                raise CheckpointConflict(state.run_id)       # rollback: another writer advanced the run
        return expected_version + 1

    async def load_latest(self, run_id: str) -> tuple[WorkingState | None, int]:
        async with self.session_factory() as s:
            row = (await s.execute(text(
                "SELECT c.state, r.version FROM agent_run r "
                "LEFT JOIN agent_checkpoint c ON c.run_id = r.id AND c.step = r.last_step "
                "WHERE r.id = :r"), {"r": run_id})).one()
        if row.state is None:
            return None, row.version
        return WorkingState.model_validate(upcast(dict(row.state))), row.version
```

#### Example 3 — Production-oriented: Resumable runner segment with reconciliation, bounded memory and deletion

```python
# app/agent/resume.py
import logging
from dataclasses import dataclass

from app.agent.memory import ConversationMemory
from app.agent.status import RunStatus
from app.agent.working_state import WorkingState
from app.persistence.checkpoints import CheckpointStore

log = logging.getLogger("agent.resume")


@dataclass
class SegmentRunner:
    checkpoints: CheckpointStore
    runs: "RunRepository"
    contexts: "ContextBuilder"            # rebuilds ToolContext from CURRENT identity data
    reconciler: "ToolReconciler"          # asks downstream systems about unknown outcomes
    agent: "BoundedAgent"
    memory: ConversationMemory

    async def run_segment(self, run_id: str, worker_id: str) -> None:
        run = await self.runs.claim(run_id, worker_id)          # pending → running with lease, or None
        if run is None:
            return                                              # someone else has it, or not pending
        state, version = await self.checkpoints.load_latest(run_id)
        state = state or WorkingState(run_id=run_id)

        ctx = await self.contexts.for_run(run)                  # re-check permissions, ticket still open
        if ctx is None:
            await self.runs.finish(run_id, RunStatus.RUNNING, RunStatus.STOPPED, stop_reason="context_invalid")
            return

        if state.pending_call is not None:                      # crashed mid-tool last time
            outcome = await self.reconciler.resolve(state.pending_call, ctx)
            log.info("reconciled run=%s step=%s outcome=%s", run_id, state.pending_call.step, outcome.kind)
            state = state.model_copy(update={"pending_call": None,
                                             "observations": [*state.observations, outcome.as_observation()]})
            version = await self.checkpoints.save(state, version)

        messages = await self.memory.build_context(run, state)  # bounded: summary + recent turns + state digest
        result = await self.agent.continue_from(state, messages, ctx,
                                                on_checkpoint=lambda s: self._save(s),
                                                remaining=run.limits.remaining(state))
        await self.runs.finish(run_id, RunStatus.RUNNING, result.status, stop_reason=result.stop_reason)

    async def _save(self, state: WorkingState) -> None:
        current = await self.runs.version(state.run_id)
        await self.checkpoints.save(state, current)
```

The reconciler decides per tool: read-only tools are simply re-run; idempotent writes are re-issued with the same key (the downstream deduplicates); non-idempotent or unknown writes are looked up (`GET /notes?idempotency_key=...`) and, if the outcome can't be determined, the run stops with `unknown_outcome` for human review.

**Bounded conversation memory.**

```python
# app/agent/memory.py
from dataclasses import dataclass

from app.llm.tokens import count_tokens


@dataclass
class ConversationMemory:
    log: "ConversationLog"                 # append-only messages per conversation
    summarizer: "Summarizer"               # LLM call with a strict output schema and max length
    recent_token_budget: int = 6000
    summarize_threshold_tokens: int = 12000

    async def build_context(self, run, state) -> list[dict]:
        turns = await self.log.turns(run.conversation_id)
        recent, older = [], []
        used = 0
        for turn in reversed(turns):                         # newest first, fill the recent window
            t = count_tokens(turn.text)
            if used + t > self.recent_token_budget:
                older = turns[: turns.index(turn) + 1]
                break
            recent.insert(0, turn)
            used += t
        summary = state.conversation_summary
        if older and sum(count_tokens(t.text) for t in older) > self.summarize_threshold_tokens:
            summary = await self.summarizer.summarize(older, previous=summary, max_chars=3000)
        digest = "\n".join(f"- step {o.step}: {o.tool} → {o.summary}" for o in state.observations[-10:])
        blocks: list[dict] = []
        if summary:
            blocks.append({"role": "user", "content":
                           f"<conversation_summary generated=\"true\">{summary}</conversation_summary>"})
        if digest:
            blocks.append({"role": "user", "content": f"<work_so_far>\n{digest}\n</work_so_far>"})
        blocks += [{"role": t.role, "content": t.text} for t in recent]
        return blocks
```

(Consecutive same-role messages must be merged before sending to providers that require alternation. That merging happens in the adapter, per Unit 29.)

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| Conversation vs working state | User-visible log vs runner internals | Both always | Mixing them; resume impossible |
| Long-term memory vs authoritative data | Derived, may be stale vs system of record | Memory for preferences; tools for facts | "Remembering" order status |
| Memory vs RAG | Interaction history vs curated KB | Separate stores and labels | User claims treated as policy |
| Overwrite vs append-only checkpoints | Latest only vs history | Append-only with retention for audit/debugging | Unbounded growth |
| Snapshots vs event sourcing | State copy vs rebuild from events | Snapshots for agents; events for audit | Complexity without need |
| Sliding window vs summary | Drop old vs compress old | Summary + window for long conversations | Summary drift treated as fact |
| Pessimistic lock vs optimistic version | Hold lock vs detect conflict | Leases + versions for long work | Holding DB locks across LLM calls |
| Resume vs restart | Continue from checkpoint vs start over | Always resume when side effects exist | Duplicate writes on restart |

### 8. Failure Modes and Debugging

**Failure 1 — Duplicate side effects after a crash.**

- CAUSE: restart from scratch, or no `pending_call` record, or non-deterministic idempotency keys.
- FIX: record pending calls, keys from `(run_id, step)`, reconcile on resume.

**Failure 2 — Old checkpoints fail to load after a deploy.**

- SYMPTOM: `ValidationError` on resume, runs stuck.
- FIX: `schema_version` + upcasters, a CI test that loads stored fixtures of every past version, expand/contract for state changes.

**Failure 3 — Two workers advance the same run.**

- SYMPTOM: interleaved events, double tool calls.
- CAUSE: claim without status guard, expired lease while still working.
- FIX: guarded claims, lease renewal, version check on checkpoint writes, a worker that stops when it loses the lease.

**Failure 4 — Stale memory overrides facts.**

- SYMPTOM: agent says "your refund was processed" based on a memory from last month.
- FIX: memory kinds exclude authoritative facts, memories labeled with age, tools for current facts, eval cases for this.

**Failure 5 — Context grows until cost or latency explode.**

- FIX: token-based windows, tool-result elision, summary thresholds, metrics on input tokens per step.

**Failure 6 — Erasure incomplete.**

- SYMPTOM: deleted customer's data still appears in an agent's summary.

### 11. Testing Strategy

- **Pure tests:** transition table, upcasters, memory window selection with a fake token counter.
- **DB tests (Testcontainers):** guarded transitions, checkpoint conflicts, lease expiry, erasure.
- **Fault injection:** cancel the worker task at each await point in a step (a parametrized test over "crash points"), then resume and check invariants: no duplicate writes, monotonic steps, terminal status reached.
- **Fixture tests:** stored checkpoint JSON for each schema version committed to the repo.
- **Privacy tests:** seed subject data in every store, run erasure, assert none remains. Assert checkpoints and events never contain raw PII fields (scan for patterns).

### 12. Engineering Scenarios

**Scenario 1 — "Make the agent remember customers" (FDE).** The sales team promised a client the agent will "remember every customer". *Clarify:* remember what, for how long, who can see it, and what the client's privacy policy and region require. *Reasoning:* Propose scoped memory kinds (preferences, prior resolution summaries) with TTLs and user visibility, not raw transcript recall. Facts come from systems of record. Document retention in the statement of work. Run an eval comparing resolution rates with and without memory before expanding.

**Scenario 2 — Approval after a week.** A refund approval arrives 7 days later. *Reasoning:* Proposals expire (Unit 34). On resume, re-validate the order state and the approver's authority. If expired, stop with a clear message and let the agent re-propose with fresh data.

**Scenario 3 — Debugging a wrong answer from yesterday.** *Reasoning:* With append-only checkpoints and events, reconstruct exactly what the agent saw at each step, including the summary text. Without them, you can only guess. This is why retention is "keep for N days", not "delete immediately".

**Scenario 4 — Tenant asks for zero retention.** *Reasoning:* Durable workflows need some state. Offer short retention (delete on completion + 24 h), no long-term memory, no conversation summaries persisted beyond the run, and document the trade-off (no debugging, no resumption after completion).

### 13. Interview Preparation

#### Quick Questions

**Q: Name the four kinds of agent state and who owns each.**
*Strong answer:* Conversation (the app, append-only), working state (the runner, checkpointed), long-term memory (a memory service with provenance and TTL), and authoritative data (domain services, read through tools).

**Q: Why shouldn't an agent "remember" an order's status?**
*Strong answer:* It's authoritative data that changes. The memory becomes a stale copy. Read it fresh through a tool.

**Q: What's in a checkpoint?**
*Strong answer:* A versioned working state: step, budgets, redacted observations, signatures, pending call and proposals, summary. Never authorization or raw secrets.

#### Intermediate Questions

**Q: How do you resume after a crash without duplicating side effects?**
*Strong answer:* Record the pending call (with an idempotency key derived from run and step) before executing, checkpoint after. On resume, reconcile any pending call: re-run reads, re-issue idempotent writes with the same key, look up or escalate unknown outcomes.

**Q: How do you keep conversation context bounded?**
*Strong answer:* Token-budgeted recent window, summary of older turns with a size cap, elided old tool results, and a state digest. Labeled blocks, and the summary never used for authorization.

**Q: Why separate memory from RAG?**
*Strong answer:* Different provenance and authority. Mixing them lets user claims masquerade as policy and risks cross-customer leakage.

#### Advanced Questions

**Q: How do you evolve the state schema with in-flight runs?**
*Strong answer:* `schema_version` in every checkpoint, upcasters chained version by version, fixture tests for all past versions in CI, and expand/contract (new code reads old and new before anything writes new-only fields).

**Q: Two workers might process the same run. How do you prevent corruption?**
*Strong answer:* Guarded claims (status precondition), leases with renewal, optimistic version checks on every checkpoint write, and a worker that aborts on conflict or lost lease. Idempotent tool keys as the last line of defense.

#### Coding Questions

1. Implement `check_transition` and a guarded SQL update.
2. Implement an upcaster chain with tests.
3. Implement a token-bounded window selection function.

#### Scenario Questions

**Q: A customer requests deletion of their data. List every place your agent stack might hold it.**
*Strong answer:* Conversation logs, checkpoints, events, long-term memories and their embeddings, summaries, caches, search indexes, logs and traces, analytics exports, backups, and the LLM provider (per contract). Each needs an erasure or expiry path and a test.

### 16. Common Interview Traps

- **"Just save the chat history."** That isn't working state, and resume needs much more.
- **"Memory makes the agent smarter."** Unvalidated memory makes it confidently stale.
- **"Put memories in the vector store with the KB."** That breaks provenance and access control.
- **"Lock the row while the agent runs."** Holding DB locks across LLM calls kills throughput. Use leases and versions.
- **"Restart failed runs from the beginning."** Duplicate side effects.
- **"Store the user's permissions in the checkpoint."** They may change. Re-derive them.
- **"Deletion is just a DELETE on the conversation table."** Derived data lives in many places.

### 17. Cheat Sheet

- **Four kinds:** conversation (log) · working (checkpoint) · long-term memory (scoped, TTL, provenance) · authoritative (tools only).
- **Status:** pending → running → {waiting_approval, waiting_user, finished, stopped, cancelled}. Waiting → pending (requeue). Terminal is final.
- **Checkpoint:** after each step, `schema_version`, redacted observations, `pending_call`, budgets, version check.
- **Concurrency:** guarded claim, lease + renew, sweeper, `WHERE version = :expected`.
- **Resume:** load → upcast → re-derive context → reconcile pending → continue with remaining budgets.
- **Memory:** token window + summary + state digest. Labeled. Separate from RAG.
- **Privacy:** minimize, TTLs, erasure across all stores, audit without PII.
