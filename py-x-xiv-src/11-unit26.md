## Unit 26 — CI/CD and Engineering Automation

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Compare** Git workflows (trunk-based development with short-lived branches, GitHub Flow, GitFlow) and **design** a pull-request process with branch protection, required checks, CODEOWNERS and review rules.
2. **Configure** fast, deterministic quality gates: Ruff (lint + format), static type checking (mypy or Pyright), and pre-commit hooks that match CI.
3. **Implement** a test pipeline: unit tests with coverage thresholds, integration tests against real PostgreSQL/Redis/Kafka via Testcontainers, and contract/smoke tests.
4. **Integrate** security scanning: dependency vulnerabilities (pip-audit / OSV), secret scanning, SAST (Bandit/Semgrep/CodeQL), container image scanning (Trivy/Grype), SBOM generation and provenance.
5. **Build** container images once per commit, tag by commit SHA, push to a registry using short-lived OIDC credentials, and **promote** the same digest through environments.
6. **Explain** and **implement** deployment strategies (rolling, blue/green, canary), database migration safety (expand/contract), deployment verification and automatic rollback.
7. **Distinguish** CI, continuous delivery and continuous deployment, and **defend** quality-gate choices, artifact promotion and reproducible builds in an interview.
8. **Debug** flaky tests, slow pipelines, cache misses, "works locally, fails in CI" and failed deployments.

### 2. Prerequisite Knowledge

- **Git:** commits, branches, merge vs rebase, tags, `git bisect`.
- **pytest:** fixtures, markers, parametrization; async tests with `pytest-anyio`/`pytest-asyncio`.
- **Unit 25:** the multi-stage uv Dockerfile, Compose stack and health checks.
- **YAML basics** and environment variables.

**Refresher: what a "build" means for Python.** Python isn't compiled to a deployable binary, so your **artifact** is the container image (or a wheel) produced from a commit plus a lockfile. Reproducibility comes from pinned inputs: lockfile, base image digest, tool versions.

### 3. Mental Model

A pipeline is **a series of increasingly expensive filters that a change must pass before it reaches users**, ordered so the cheapest, most common failures are caught first.

```
commit/PR
  │  seconds        ┌─ format + lint (ruff) ─┐
  │                 ├─ type check (mypy)      ├─ fail fast, in parallel
  │                 └─ secret scan            ┘
  │  1–3 min        unit tests + coverage gate
  │  3–8 min        integration tests (Testcontainers: Postgres, Redis, Kafka)
  │                 dependency audit, SAST
  │  2–5 min        image build (cache) → image scan → SBOM → push by SHA
  ▼  merge to main
  deploy to staging (same digest) → migrations (expand) → smoke + health checks
  → promote same digest to production (canary/rolling) → verify SLOs → done | rollback
```

Two ideas dominate:

1. **Build once, promote many.** The artifact that passed tests is byte-for-byte the artifact that runs in production. Environments differ only by configuration and secrets.
2. **Every gate must be trustworthy.** A flaky or slow gate gets bypassed. A gate that's green but meaningless (tests that mock everything) is worse than none, because it creates false confidence.

### 4. Comprehensive Theory

#### 4.1 Git Workflows and Pull Requests

| Workflow | Shape | Best for | Risks |
|---|---|---|---|
| **Trunk-based** | Short-lived branches (hours–2 days) merged to `main`; feature flags for incomplete work | Continuous delivery; most SaaS teams | Requires strong CI and flags |
| **GitHub Flow** | Branch → PR → review → merge to `main` → deploy | Small/medium teams | Long-lived branches drift |
| **GitFlow** | `develop`, `release/*`, `hotfix/*`, `main` | Versioned products with scheduled releases | Merge overhead, slow integration [Legacy for web services] |

**PR practices.** Small PRs (< ~400 lines changed) get better reviews. Templates ask for "what/why/how tested/rollback plan". Branch protection on `main` covers required status checks, required reviews, up-to-date branch or merge queue, no force pushes and signed commits if required. **CODEOWNERS** routes reviews (for example `/migrations/ @db-owners`). **Merge queues** test the combined result of queued PRs, preventing "green PRs, red main".

**Interview perspective.** Interviewers look for an understanding of integration frequency, review quality and how to keep `main` deployable.

#### 4.2 Linting, Formatting and Static Type Checks

**Ruff** is a fast Rust-based linter and formatter that replaces flake8, isort, pyupgrade and black-compatible formatting. Configure it in `pyproject.toml`:

```toml
[tool.ruff]
target-version = "py312"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "W", "I", "UP", "B", "SIM", "ASYNC", "S", "RUF", "PT"]
ignore = ["E501"]                   # formatter owns line length
[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101"]               # assert is fine in tests
```

Rule families worth enabling: `B` (bugbear: mutable defaults, etc.), `ASYNC` (blocking calls in async code, which is crucial for FastAPI), `S` (Bandit-style security), `UP` (modern syntax).

**Static typing.** **mypy** (reference implementation, plugin ecosystem including the Pydantic plugin) or **Pyright** (fast, strict, powers Pylance). Newer Rust-based checkers (Astral's `ty`, Meta's `pyrefly`) are emerging but still pre-1.0 [Experimental]. Strategy: start with `strict = true` on new modules, use per-module overrides for legacy code, and treat `# type: ignore[code]` as a reviewable exception.

```toml
[tool.mypy]
python_version = "3.12"
strict = true
plugins = ["pydantic.mypy"]
[[tool.mypy.overrides]]
module = ["aiokafka.*"]
ignore_missing_imports = true
```

**Why types matter in CI.** They catch `None` handling bugs, wrong argument types across module boundaries, and async misuse (forgetting `await` produces a coroutine where a value was expected). Types complement tests rather than replacing them: they prove absence of a class of errors across all paths, while tests check behavior on chosen inputs.

**pre-commit** runs the same tools locally before commit, pinned to the same versions as CI, so developers get feedback in seconds.

#### 4.3 Automated Tests and Coverage

**Test layers.**

| Layer | Scope | Speed | Tools |
|---|---|---|---|
| Unit | Pure functions, domain logic, services with fakes | ms | pytest, Hypothesis |
| API (in-process) | FastAPI routes with dependency overrides | ms–s | `httpx.AsyncClient` + `ASGITransport` |
| Integration | Real PostgreSQL/Redis/Kafka | seconds | Testcontainers, Alembic migrations |
| Contract | API schema/event schemas don't break consumers | s | Schemathesis, JSON Schema snapshots |
| Smoke/E2E | Deployed stack | s–min | pytest against URL |

**Coverage.** `pytest --cov=app --cov-branch --cov-report=xml --cov-fail-under=85`. Branch coverage is more informative than line coverage. Coverage measures *executed* code, not *verified* behavior. Use it to find untested areas, set a floor, and gate on **diff coverage** for new code (for example `diff-cover coverage.xml --fail-under=90`), which avoids blocking teams on legacy debt.

**Speed and determinism.** Run tests in parallel with `pytest-xdist` (`-n auto`) when tests are isolated. Randomize order (`pytest-randomly`) to expose hidden coupling. Freeze time (`time-machine`) and seed randomness. Never call real external APIs from CI tests (LLM providers included). Use recorded fixtures or fakes.

**Flaky tests.** Quarantine with tracking, not deletion. Fix the root cause: shared state, time, ordering, unawaited tasks, real network calls, or port collisions.

#### 4.4 Security and Dependency Scanning

| Check | What it catches | Tools |
|---|---|---|
| Secret scanning | Committed keys/tokens | GitHub secret scanning + push protection, gitleaks |
| Dependency vulnerabilities | Known CVEs in locked packages | `pip-audit` (PyPI advisory/OSV), `uv` + OSV-Scanner, Dependabot/Renovate |
| SAST | Insecure code patterns | Ruff `S` rules / Bandit, Semgrep, CodeQL |
| Container image scan | OS package + language CVEs in the image | Trivy, Grype |
| SBOM | Inventory of what you ship | Syft, `docker buildx --sbom=true` (SPDX/CycloneDX) |
| Provenance/signing | Proof of how/where it was built | SLSA provenance via buildx, Sigstore cosign |
| License compliance | Disallowed licenses | `pip-licenses`, scanners |

**Policy.** Block on critical/high vulnerabilities with a fix available. Track others with an SLA. Allow time-bound exceptions recorded in code (for example a `.trivyignore` entry with expiry and reason). Automate dependency updates (Renovate/Dependabot) so patches arrive as small PRs that run the full pipeline.

**Supply-chain hygiene.** Hash-pinned lockfile (`uv.lock` includes hashes), pinned GitHub Actions **by commit SHA** (tags can be moved), least-privilege `permissions:` in workflows, OIDC instead of long-lived cloud keys, and no `pull_request_target` with untrusted code checkout.

#### 4.5 Container Builds, Environments, Deployment and Rollback

**Image build in CI.** Use `docker/build-push-action` with BuildKit cache (`cache-from/to: type=gha`), tagged with the **commit SHA** (immutable), and optionally a semantic version on release. Record the **digest** output and use it for every deployment.

**Environments.** `dev → staging → production`, each with its own config, secrets, and approval rules (GitHub Environments with required reviewers for production). Configuration lives outside the image (env vars from a parameter store or secrets manager, Unit 27).

**Artifact promotion.** Promotion means re-pointing an environment at the **same digest**. Never rebuild for production. A rebuild could pick up different base-image patches or dependency resolution, so what you tested isn't what you shipped.

**Deployment strategies.**

| Strategy | How | Rollback | Cost/complexity |
|---|---|---|---|
| Rolling | Replace tasks gradually (`minimumHealthyPercent`/`maximumPercent`) | Roll forward/back by redeploying old digest | Low; mixed versions briefly |
| Blue/green | New fleet alongside old; switch traffic at load balancer | Instant switch back | Double capacity during deploy |
| Canary | Small % of traffic to new version, watch metrics, then expand | Shift traffic back | Needs traffic splitting + metrics |
| Feature flags | Deploy dark; enable per user/tenant | Flip flag | Flag debt; needs discipline |

**ECS specifics** [Current]: rolling deployments with the **deployment circuit breaker** (`enable: true, rollback: true`) roll back automatically when tasks fail to reach a steady healthy state. CloudWatch alarm-based rollback can also be attached. Blue/green and canary are available through ECS's native blue/green deployments or CodeDeploy.

**Database migrations: expand/contract.** Application versions N and N+1 run simultaneously during a rolling deploy, so schema changes must be backward compatible:

1. **Expand:** add nullable columns/new tables. Deploy code that writes both old and new shapes.
2. **Migrate data** (backfill in batches).
3. **Switch** reads to the new shape.
4. **Contract:** remove old columns in a *later* release once no running version uses them.

Never rename or drop a column in the same deploy as the code change. Run migrations as a separate pipeline step (one-shot task) before shifting traffic. Set `lock_timeout` on DDL so a migration waiting for a lock doesn't block all queries.

**Deployment verification.** After deploying: wait for service stability, run smoke tests against the new version (health, a key read path, a key write path in a test tenant), and watch SLO metrics (error rate, latency) for a bake period. If any check fails, roll back automatically.

**Rollback vs roll forward.** Roll back the *application* by redeploying the previous digest, which is fast and safe if migrations were expand-only. Data migrations generally aren't rolled back. You roll forward with a fix, which is why expand/contract matters.

#### 4.6 CI vs CD; Quality Gates; Reproducible Builds

- **Continuous Integration:** every change merges to the mainline frequently and is verified automatically.
- **Continuous Delivery:** every change that passes the pipeline is *deployable*; production release may need a manual approval.
- **Continuous Deployment:** every passing change is deployed to production automatically.

**Quality gate:** an automated pass/fail rule a change must satisfy (tests pass, coverage ≥ X, no critical CVEs, type check clean, image scan clean, smoke tests pass, error rate below threshold after canary). Good gates are **fast, deterministic, meaningful and owned**.

**Reproducible builds:** the same inputs produce the same artifact. Pin everything (lockfile with hashes, base image digest, tool versions, Actions by SHA). Avoid network-dependent steps without pins. Record provenance. Bit-for-bit reproducibility of images additionally needs normalized timestamps (`SOURCE_DATE_EPOCH`) and deterministic file ordering. Most teams aim for *functional* reproducibility (same dependency set and behavior) and record digests.

### 5. Internal Mechanics

#### 5.1 What happens when a PR is opened (GitHub Actions)

```
PR event → workflow triggers (on: pull_request) → GitHub schedules jobs on runners (ephemeral VMs)
→ each job: fresh VM, checkout (actions/checkout), set up tools (setup-uv with cache)
→ jobs with `needs:` form a DAG; independent jobs run in parallel
→ caches restored by key (e.g. hash of uv.lock); artifacts uploaded between jobs
→ job conclusions reported as check runs → branch protection evaluates required checks
→ merge allowed only if all required checks pass (merge queue may re-run on the combined commit)
```

#### 5.2 OIDC to AWS without stored keys

```
job with permissions: id-token: write → requests a signed OIDC JWT from GitHub
  (claims: repo, ref, environment, workflow, sha)
→ aws-actions/configure-aws-credentials calls STS AssumeRoleWithWebIdentity
→ IAM role trust policy checks issuer + audience + sub (e.g. repo:org/supportdesk:environment:production)
→ short-lived credentials (≤ 1 h) for ECR push / ECS deploy only
```

The trust policy's `sub` condition is the security boundary. Scope it to the repository **and** environment/branch so a fork or another branch can't assume the production role.

#### 5.3 ECS rolling deployment with circuit breaker

```
register new task definition (image@digest) → UpdateService
→ scheduler starts new tasks (up to maximumPercent) → tasks pass container health checks
→ ALB target group health checks pass → old tasks deregistered (connection draining) → stopped
→ circuit breaker: if new tasks repeatedly fail to become healthy → deployment FAILED → rollback to last COMPLETED
```

#### Example 2 — Realistic: The PR pipeline (lint → types → tests → integration → image build)

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:
  UV_VERSION: "0.11.30"

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<sha>                    # pin actions by full commit SHA
      - uses: astral-sh/setup-uv@<sha>
        with: { version: "${{ env.UV_VERSION }}", enable-cache: true }
      - run: uv sync --locked --all-groups
      - run: uv run ruff check --output-format=github .
      - run: uv run ruff format --check .

  typecheck:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<sha>
      - uses: astral-sh/setup-uv@<sha>
        with: { version: "${{ env.UV_VERSION }}", enable-cache: true }
      - run: uv sync --locked --all-groups
      - run: uv run mypy app worker

  unit:
    runs-on: ubuntu-24.04
    needs: [lint, typecheck]
    steps:
      - uses: actions/checkout@<sha>
      - uses: astral-sh/setup-uv@<sha>
        with: { version: "${{ env.UV_VERSION }}", enable-cache: true }
      - run: uv sync --locked --all-groups
      - run: >
          uv run pytest -m "not integration and not smoke" -n auto
          --cov=app --cov-branch --cov-report=xml --cov-fail-under=85 --junitxml=junit-unit.xml
      - if: github.event_name == 'pull_request'
        run: |
          git fetch origin ${{ github.base_ref }} --depth=1
          uv run diff-cover coverage.xml --compare-branch=origin/${{ github.base_ref }} --fail-under=90
      - uses: actions/upload-artifact@<sha>
        if: always()
        with: { name: unit-reports, path: "junit-unit.xml\ncoverage.xml" }

  integration:
    runs-on: ubuntu-24.04                             # Docker available on hosted Ubuntu runners
    needs: [unit]
    steps:
      - uses: actions/checkout@<sha>
      - uses: astral-sh/setup-uv@<sha>
        with: { version: "${{ env.UV_VERSION }}", enable-cache: true }
      - run: uv sync --locked --all-groups
      - run: uv run pytest -m integration --junitxml=junit-integration.xml

  security:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@<sha>
        with: { fetch-depth: 0 }
      - uses: astral-sh/setup-uv@<sha>
        with: { version: "${{ env.UV_VERSION }}" }
      - run: uv export --locked --no-dev --format requirements-txt > requirements.lock.txt
      - run: uvx pip-audit --strict -r requirements.lock.txt --disable-pip
      - uses: gitleaks/gitleaks-action@<sha>
        env: { GITHUB_TOKEN: "${{ secrets.GITHUB_TOKEN }}" }

  image:
    runs-on: ubuntu-24.04
    needs: [integration, security]
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    permissions:
      contents: read
      id-token: write                                 # OIDC to AWS (push only on main)
    steps:
      - uses: actions/checkout@<sha>
      - uses: docker/setup-buildx-action@<sha>
      - if: github.ref == 'refs/heads/main'
        uses: aws-actions/configure-aws-credentials@<sha>
        with:
          role-to-assume: arn:aws:iam::123456789012:role/supportdesk-ci-ecr-push
          aws-region: eu-west-1
      - if: github.ref == 'refs/heads/main'
        uses: aws-actions/amazon-ecr-login@<sha>
      - id: build
        uses: docker/build-push-action@<sha>
        with:
          context: .
          target: runtime
          push: ${{ github.ref == 'refs/heads/main' }}
          load: ${{ github.ref != 'refs/heads/main' }}
          tags: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/supportdesk:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          sbom: ${{ github.ref == 'refs/heads/main' }}
          provenance: ${{ github.ref == 'refs/heads/main' && 'mode=max' || 'false' }}
      - name: Scan image
        uses: aquasecurity/trivy-action@<sha>
        with:
          image-ref: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/supportdesk:${{ github.sha }}
          severity: CRITICAL,HIGH
          ignore-unfixed: true
          exit-code: "1"
```

**Notes.**

- `<sha>` placeholders: pin every third-party action to a full commit SHA (with a version comment) and let Renovate/Dependabot update them.
- `permissions: contents: read` at the top, with `id-token: write` only for the job that needs AWS.
- `concurrency` cancels superseded runs on the same branch, which saves runner minutes.
- Job ordering: lint/types run in parallel first, and expensive integration tests run only after cheap gates pass.
- Images are built on PRs (to catch Dockerfile breakage) but **pushed only from main**.
- Integration tests use Testcontainers, so they need Docker on the runner. GitHub-hosted Ubuntu runners provide it.

#### Example 3 — Production-oriented: Deploy, migrate, verify, promote, roll back

```yaml
# .github/workflows/deploy.yml
name: deploy
on:
  workflow_run:
    workflows: [ci]
    types: [completed]
    branches: [main]

permissions:
  contents: read
  id-token: write

jobs:
  staging:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-24.04
    environment: staging
    env:
      IMAGE: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/supportdesk:${{ github.event.workflow_run.head_sha }}
    steps:
      - uses: actions/checkout@<sha>
      - uses: aws-actions/configure-aws-credentials@<sha>
        with:
          role-to-assume: arn:aws:iam::123456789012:role/supportdesk-deploy-staging
          aws-region: eu-west-1
      - name: Resolve digest (deploy by digest, not tag)
        id: digest
        run: |
          DIGEST=$(aws ecr describe-images --repository-name supportdesk \
            --image-ids imageTag=${{ github.event.workflow_run.head_sha }} \
            --query 'imageDetails[0].imageDigest' --output text)
          echo "ref=${IMAGE%%:*}@${DIGEST}" >> "$GITHUB_OUTPUT"
      - name: Run migrations (one-shot ECS task, expand-only)
        run: ./deploy/run-migration-task.sh staging "${{ steps.digest.outputs.ref }}"
      - name: Deploy API and worker
        run: ./deploy/ecs-deploy.sh staging "${{ steps.digest.outputs.ref }}"     # waits for services-stable
      - name: Smoke tests
        run: uv run --locked pytest -m smoke --base-url https://staging.supportdesk.example.com

  production:
    needs: [staging]
    runs-on: ubuntu-24.04
    environment: production                        # required reviewers + wait timer configured in repo settings
    steps:
      - uses: actions/checkout@<sha>
      - uses: aws-actions/configure-aws-credentials@<sha>
        with:
          role-to-assume: arn:aws:iam::123456789012:role/supportdesk-deploy-production
          aws-region: eu-west-1
      - name: Promote same digest
        run: |
          REF=$(./deploy/current-digest.sh staging)    # exactly what staging runs
          ./deploy/run-migration-task.sh production "$REF"
          ./deploy/ecs-deploy.sh production "$REF"     # rolling + circuit breaker + alarms
      - name: Verify SLOs during bake period
        run: ./deploy/verify-slo.sh production --minutes 10 --max-5xx-rate 0.01 --max-p95-ms 800
      - name: Roll back on failure
        if: failure()
        run: ./deploy/ecs-rollback.sh production        # redeploy previous task definition revision
```

The deploy script uses the AWS CLI (`aws ecs register-task-definition` with the new image digest, `aws ecs update-service`, `aws ecs wait services-stable`). The service is configured with:

```json
"deploymentConfiguration": {
  "minimumHealthyPercent": 100,
  "maximumPercent": 200,
  "deploymentCircuitBreaker": { "enable": true, "rollback": true },
  "alarms": { "alarmNames": ["supportdesk-prod-5xx", "supportdesk-prod-p95"], "enable": true, "rollback": true }
}
```

A safe Alembic migration skeleton for the expand phase:

```python
# migrations/versions/0007_add_ticket_priority.py
from alembic import op
import sqlalchemy as sa

revision = "0007"
down_revision = "0006"


def upgrade() -> None:
    op.execute("SET lock_timeout = '3s'")                     # fail fast instead of blocking traffic
    op.add_column("ticket", sa.Column("priority", sa.Text(), nullable=True))   # expand: nullable, no default rewrite
    # Index creation on large tables: CONCURRENTLY, outside a transaction
    with op.get_context().autocommit_block():
        op.execute("CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_ticket_priority ON ticket (priority)")


def downgrade() -> None:
    with op.get_context().autocommit_block():
        op.execute("DROP INDEX CONCURRENTLY IF EXISTS ix_ticket_priority")
    op.drop_column("ticket", "priority")
```

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| CI vs continuous delivery vs continuous deployment | Verify every change vs always deployable vs always deployed | Delivery is the common target; deployment when tests + monitoring are mature | "We do CD" while deploying monthly by hand |
| Trunk-based vs GitFlow | Short-lived branches + flags vs long-lived release branches | Trunk for services; GitFlow for versioned products | Long-lived feature branches → merge hell |
| mypy vs Pyright | Plugin ecosystem vs speed/strictness | Either; be consistent; Pydantic plugin favors mypy | "Types replace tests" |
| Line vs branch vs diff coverage | Lines executed vs decision paths vs new code | Gate on branch + diff | Chasing 100% with assertion-free tests |
| Rebuild per env vs promote digest | Different artifacts vs same artifact | Always promote | "Staging passed" for a different image |
| Rolling vs blue/green vs canary | Gradual replace vs switch vs % traffic | Rolling default; canary for risky changes | Canary without metrics to judge it |
| Rollback vs roll forward | Previous artifact vs new fix | Rollback app; roll forward data | Rolling back after a destructive migration |
| Long-lived keys vs OIDC | Static secrets vs short-lived federated creds | OIDC always | Keys in repo secrets that never rotate |
| Tag vs digest | Mutable vs immutable | Deploy by digest | Re-tagged image silently changes production |

### 8. Failure Modes and Debugging

**Failure 1 — "Passes locally, fails in CI."**

- CAUSE: different tool versions (unpinned ruff/mypy), different Python version, missing env var, test order dependency, timezone/locale, or a stale lockfile used locally.
- INVESTIGATE: compare `uv run ruff --version` etc.; rerun with `-p no:randomly` and with the CI seed; print `sys.version`; check `uv sync --locked` output.
- FIX: pin via lockfile + pre-commit; set `TZ=UTC`; fix test isolation.
- PREVENT: `uv sync --locked` locally too; randomized order everywhere.

**Failure 2 — Pipeline takes 35 minutes.**

- INVESTIGATE: job timing breakdown; cache hit rates for uv and buildx; sequential jobs that could be parallel.
- FIX: parallelize gates, cache uv and BuildKit (`type=gha`), `pytest -n auto`, run integration tests only after cheap gates, path filters for docs-only changes, singleton Testcontainers per session.

**Failure 3 — Flaky integration test.**

- SYMPTOM: Kafka consumer test fails 1 in 15 runs.
- CAUSE: the test asserts before the consumer has joined the group; arbitrary `sleep`.
- FIX: poll with timeout for the condition (`wait_for(lambda: received, timeout=10)`), use explicit topic creation, set `auto_offset_reset=earliest`.
- PREVENT: track flaky tests and quarantine with an owner and deadline.

**Failure 4 — Deployment stuck, circuit breaker rolls back.**

- INVESTIGATE: ECS service events (`aws ecs describe-services`), stopped task reasons (`aws ecs describe-tasks --tasks … --query 'tasks[].stoppedReason'`), container logs in CloudWatch, target group health reasons.
- COMMON CAUSES: missing secret/IAM permission for the new code, readiness failing because a migration didn't run, port/health path mismatch, OOM.
- PREVENT: staging with identical config shape; smoke tests; checks that the task definition references existing secrets.

**Failure 5 — Migration locks production table.**

- SYMPTOM: API latency spikes to timeouts during deploy.
- CAUSE: `ALTER TABLE … ADD COLUMN … DEFAULT …` on older PostgreSQL rewrites (modern PostgreSQL handles constant defaults without rewrite, but volatile defaults or type changes still rewrite); `CREATE INDEX` without `CONCURRENTLY`; waiting on a lock behind a long transaction, which then blocks everything else.
- FIX/PREVENT: `lock_timeout`, `CONCURRENTLY`, expand/contract, migration review checklist, test migrations against a production-sized snapshot.

**Failure 6 — Secret leaked in a PR.**

- RESPONSE: rotate immediately (assume compromised), purge from history if needed, enable push protection, add gitleaks to pre-commit and CI.

### 12. Engineering Scenarios

**Scenario 1 — Customer's mandated scanner (FDE).** The customer requires their enterprise scanner and blocks any image with "high" CVEs, including unfixed ones in Debian. *Questions:* which CVEs are reachable? Is there a fixed version? What's their exception process? *Reasoning:* Show the scan report with fix availability, switch to a minimal base (distroless/Chainguard) if it eliminates most findings, document exceptions with expiry, and agree on an SLA. Evidence = before/after scan reports in the pipeline.

**Scenario 2 — Speed vs safety.** Developers complain that integration tests slow every PR. *Options:* run integration tests only when relevant paths change; test impact analysis; parallelize; nightly full runs. *Trade-off:* Path filters can miss cross-cutting changes. Keep a full run on main and merge queue.

**Scenario 3 — A bad migration reached production.** A backfill locked a table for 4 minutes. *Reasoning:* Roll forward with a fix. Add `lock_timeout` and batching, require migration review by DB owners, and add a "migration against production-sized snapshot" job in staging.

**Scenario 4 — Hotfix path.** A critical bug needs a fix in 30 minutes. *Reasoning:* Use the same pipeline with expedited review (never bypass tests); a feature-flag kill switch as the first mitigation; rollback to the previous digest if safe.

### 13. Interview Preparation

#### Quick Questions

**Q: CI vs CD?**
*Strong answer:* CI integrates and verifies every change automatically. Continuous delivery keeps every passing change deployable, often with a manual production approval. Continuous deployment releases every passing change automatically.

**Q: What's artifact promotion?**
*Strong answer:* Building one immutable artifact (image digest) and moving that exact artifact through environments, changing only configuration, so production runs what was tested.

**Q: Why pin GitHub Actions by SHA?**
*Strong answer:* Tags can be moved, so a compromised or changed action could run with your secrets. SHAs are immutable.

#### Intermediate Questions

**Q: Which quality gates would you put on a FastAPI service and in what order?**
*Strong answer:* Format/lint and type check (seconds, parallel), secret scan, unit tests with coverage/diff coverage, integration tests with real dependencies, dependency audit and SAST, image build + scan + SBOM, then deploy-time gates (migrations, smoke, SLO bake). Cheap first, each deterministic and owned.

**Q: How do you roll back a deployment that included a database migration?**
*Strong answer:* Design to make app rollback safe: expand/contract migrations so the previous version still works with the new schema. Then rollback is redeploying the previous digest. Data changes roll forward. Never combine destructive schema changes with the code change that stops using the old shape.

**Q: How do you get AWS credentials into CI securely?**
*Strong answer:* OIDC federation: GitHub issues a signed token, AWS STS exchanges it for short-lived role credentials, and the role's trust policy restricts repo/branch/environment. Separate roles per environment with least privilege.

#### Advanced Questions

**Q: What does "reproducible build" mean for a Python container, and how close can you get?**
*Strong answer:* Same inputs give the same artifact: hash-pinned lockfile, base image digest, pinned tools/actions, no unpinned network fetches, provenance. Bit-for-bit image reproducibility also needs timestamp normalization. Most teams guarantee functional reproducibility and verify via SBOM/provenance.

**Q: Your canary shows a 0.3% error-rate increase. Promote or roll back?**
*Strong answer:* Compare to baseline noise and SLO budget. Check whether errors correlate with the new version (per-version metrics), whether traffic volume is enough for significance, and which endpoints are affected. Predefine the canary analysis thresholds so this isn't a judgment call under pressure.

#### Coding Questions

1. Write a GitHub Actions job that runs Ruff, mypy and pytest with uv caching.
2. Write a pytest fixture that starts PostgreSQL via Testcontainers and applies Alembic migrations.
3. Write an Alembic migration that adds an index without blocking writes.

#### Scenario Questions

**Q: Production broke after a dependency auto-update merged on Friday. How do you prevent a repeat without losing automated updates?**
*Strong answer:* Keep automated updates, but group minor/patch updates, require the full pipeline including integration tests, add a smoke and canary stage, schedule merges in working hours, pin and review majors, and add a test reproducing the break.

### 14. Explain-It-at-Three-Levels

**Concept: Build once, promote many**

- *30 seconds:* CI builds one immutable image per commit, tagged by SHA and deployed by digest. Staging and production run that same digest with different configuration, so what we tested is what we shipped.
- *2 minutes:* Registry, digest vs tag, environment config/secrets, approvals, and why rebuilding per environment breaks traceability.
- *Deep:* SBOM and provenance, signing and admission control, rollback by digest, and how promotion interacts with migrations and feature flags.

**Concept: Quality gates**

- *30 seconds:* Automated pass/fail checks ordered cheapest-first (lint, types, unit, integration, security, image scan, smoke, SLO bake) that every change must pass.
- *2 minutes:* Characteristics of a good gate (fast, deterministic, meaningful, owned), coverage vs diff coverage, and exception processes.
- *Deep:* Flakiness management, merge queues, path filters vs completeness, DORA metrics, and supply-chain controls.

### 15. Knowledge Check

1. What's the difference between continuous delivery and continuous deployment?
2. Why deploy by digest rather than tag?
3. Why is diff coverage often a better gate than total coverage?
4. Why must schema changes be backward compatible during rolling deploys?
5. What does an OIDC trust policy's `sub` condition protect against?
6. *Code reading:* Why does the `image` job push only on `main`?
7. *Code reading:* What does `concurrency: cancel-in-progress` do here?
8. *Code reading:* Why does the migration set `lock_timeout` and use `CONCURRENTLY`?
9. *Debugging:* ECS deployment rolled back by the circuit breaker. Where do you look first?
10. *Debugging:* Tests pass locally and fail in CI with a timezone-related assertion. Fix?
11. *Design:* Rolling or canary for a change to the LLM prompt template?
12. *Design:* Should integration tests run on every PR?

#### Knowledge Check Answers

1. Delivery: every passing change *can* be released (often with manual approval). Deployment: every passing change *is* released automatically.
2. Tags are mutable and can be re-pointed. Digests identify exact content, so deployments are reproducible and auditable.
3. It focuses on new or changed code, preventing regressions without blocking work on legacy debt, and is harder to game across the whole codebase.
4. Old and new app versions run simultaneously, and the old version must still work with the new schema (and vice versa during rollback).
5. Other repositories, forks, branches or environments obtaining the role's credentials. Only the specified workflow context can assume it.
6. PR builds verify the Dockerfile without publishing untrusted or unmerged artifacts. Only reviewed code on main produces deployable images.
7. A new push to the same ref cancels the older run, saving time and runner cost.
8. To avoid blocking production traffic: fail fast if a lock isn't available, and build the index without taking a write-blocking lock.
9. ECS service events and stopped task reasons, then container logs and target group health check reasons.
10. Set `TZ=UTC` consistently, use timezone-aware datetimes, and freeze time in tests.
11. Canary (or a flag per tenant) plus online AI metrics. Prompt changes alter behavior in ways tests and offline evals may not fully capture (Units 28–29 and the evaluation work in Units 31–32).
12. Yes when relevant code changes (possibly path-filtered), and always on main/merge queue. They catch the integration bugs unit tests can't.

### 16. Common Interview Traps

- **"We have CD"** when releases are manual and monthly.
- **"100% coverage means it's tested."** Coverage measures execution, not assertions.
- **"Rebuild the image for production with prod settings."** That breaks promotion; configuration belongs at runtime.
- **"Rollback fixes everything."** Not with destructive migrations or data changes.
- **"Secrets in CI variables are fine forever."** Prefer OIDC and short-lived credentials, and rotate.
- **"Flaky tests are just noise."** They erode trust in gates and hide real failures.
- **"Static types make tests unnecessary."** They're complementary.

### 17. Cheat Sheet

- **Order:** ruff check/format → mypy → secret scan → unit + coverage (branch, diff) → integration (Testcontainers) → pip-audit/SAST → image build (cache) → Trivy → SBOM/provenance → push by SHA (main only) → staging deploy by digest → migration task → smoke → prod approval → same digest → SLO bake → rollback on failure.
- **Commands:** `uv sync --locked`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy app`, `uv run pytest -n auto --cov=app --cov-branch --cov-fail-under=85`, `diff-cover coverage.xml --fail-under=90`, `uvx pip-audit -r requirements.lock.txt`, `trivy image <ref>`.
- **Actions hygiene:** pin by SHA, minimal `permissions`, OIDC `id-token: write` only where needed, no `pull_request_target` with untrusted checkout, `concurrency`.
- **Deploy:** ECS rolling + circuit breaker rollback + alarm rollback; blue/green/canary for risky changes; expand/contract migrations with `lock_timeout` and `CONCURRENTLY`.
- **Definitions:** CI / continuous delivery / continuous deployment; quality gate; artifact promotion; reproducible build.
