## Unit 37 — Agent Observability

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** traces, spans, span kinds, attributes, events, links, context propagation (W3C `traceparent`/`baggage`), metrics and logs, and how they combine to describe one business workflow.
2. **Design** a span hierarchy that traces an agent run as one workflow: HTTP request → agent invocation → each model call → retrieval → each tool execution → guardrail and validation steps → approval → final response, including asynchronous continuation via Kafka.
3. **Apply** the OpenTelemetry GenAI semantic conventions (Development status) for model, agent and tool spans, and **record** model, provider, tokens, finish reason, latency, errors, retries, loop iterations, cost and eval result.
4. **Implement** instrumentation in Spring Boot 4 with Micrometer Observation and the OpenTelemetry bridge/starter (or the OpenTelemetry Java agent), plus Spring AI's built-in observations, plus custom observations for the agent loop, policy and tools.
5. **Implement** safe logging and tracing: no prompts/PII by default, redaction, opt-in content capture to a restricted store, cardinality control and tail-based sampling that keeps error and slow traces.
6. **Correlate** across agents and services (orchestrator → sub-agents, MCP servers, workers) using propagation and span links.
7. **Debug** a failed request by reading its trace and **attribute** the failure to the responsible component (retriever, model, tool, policy, validator, downstream).
8. **Compare** AI observability with AI evaluation, and connect them (trace IDs in eval transcripts; online eval scores keyed by trace ID).

### 2. Prerequisite Knowledge

- **Micrometer** (Spring's instrumentation facade): `MeterRegistry` for metrics, the **Observation API** (`Observation.createNotStarted(name, registry).observe(...)`) which produces *both* a timer metric and a span through registered handlers.
- **Micrometer Tracing** bridges Observations to a tracer (OpenTelemetry or Brave). Spring Boot auto-instruments HTTP server/client, JDBC (with datasource-micrometer), Kafka (when observation is enabled on templates/listeners), `@Scheduled` and more.
- **OpenTelemetry**: API (vendor-neutral interfaces), SDK (processing/export), OTLP (wire protocol, ports 4317 gRPC / 4318 HTTP), Collector (receive → process → export).
- **Three ways to instrument a Spring Boot app** [Current]:
  1. **OpenTelemetry Java agent** (`-javaagent:opentelemetry-javaagent.jar`): bytecode instrumentation of many libraries, with zero code changes. The OpenTelemetry project's default recommendation.
  2. **Spring Boot 4's `spring-boot-starter-opentelemetry`**: Micrometer Observation instrumentation exported via OTLP. Configure with `management.opentelemetry.tracing.export.otlp.endpoint`, `management.otlp.metrics.export.url` and `management.opentelemetry.logging.export.otlp.endpoint`. Logs require installing an OpenTelemetry Logback/Log4j2 appender. The Spring team's preferred option.
  3. **OpenTelemetry's own Spring Boot starter** (`opentelemetry-spring-boot-starter`): OTel-native auto-configuration, for when the agent can't be used (for example, native images).
  Pick one primary approach per service. Mixing an agent with a second tracer bridge causes duplicate or broken spans.
- **Unit 36:** eval transcripts, metrics and the observability-vs-evaluation distinction.

### 3. Mental Model

A trace is **the flight recorder for one business operation**. The operation isn't "an HTTP request". It's "rep asked about ticket 4411 and a refund was proposed, approved and executed". That may span several requests, a Kafka hop, a human pause of two hours and a resumed agent run. Your job is to make that whole story reconstructable, with every component's contribution and cost visible, **without** recording customer data you shouldn't.

```
TRACE A (chat request)                                                    duration
POST /api/agent/chat  [SERVER]                                            4.8 s
└─ invoke_agent support-assistant  [INTERNAL]  run.id=r-91 steps=3        4.7 s
   ├─ guardrail.input              signals=[]                              2 ms
   ├─ chat claude-x  [CLIENT]      in=2,310 out=180 finish=tool_use        1.1 s
   ├─ decision.validate            result=valid attempt=1                  1 ms
   ├─ execute_tool get_order       policy=ALLOW                            35 ms
   │   └─ SELECT orders  [CLIENT db]                                       6 ms
   ├─ retrieval search_kb          k=5 hits=5 top=D-12                     120 ms
   │   ├─ embeddings  [CLIENT]                                             60 ms
   │   └─ SELECT … ORDER BY embedding <=> …  [CLIENT db]                   48 ms
   ├─ chat claude-x                in=3,950 out=210 finish=tool_use        1.6 s
   ├─ execute_tool issue_refund    policy=REQUIRE_APPROVAL proposal=p-7    18 ms
   │   └─ kafka publish approval.proposed  [PRODUCER]                      3 ms
   ├─ chat claude-x                in=4,300 out=140 finish=end_turn        1.2 s
   └─ guardrail.output             findings=[]                             1 ms

TRACE B (approval, 2 h later)  ── link → Trace A
POST /api/approvals/p-7/decision → approval.decide → kafka publish approval.decided

TRACE C (execution)  ── parent: Kafka header from B; link → A
kafka consume approval.decided → approval.execute → refunds-api POST [CLIENT] → agent.resume
```

Two rules:

1. **Within a synchronous flow, parent/child.** Context flows through threads, HTTP headers and Kafka headers.
2. **Across long human pauses, links.** Don't keep a trace open for two hours. Start a new trace and *link* it to the originating one (store the originating `traceparent` on the proposal). A business-level correlation attribute (`agent.run.id`, `proposal.id`) on every span lets you query the whole story.

### 4. Comprehensive Theory

#### 4.1 Observability vs Evaluation

| | Observability | Evaluation |
|---|---|---|
| Question | What happened in this request/system? | Was the behavior good? |
| Unit | Trace/span/metric/log per execution | Score per case, scorecard per dataset |
| Ground truth | None needed | Expectations, rubric, human labels |
| Timing | Real time, always on | Offline (CI/nightly) and sampled online |
| Typical output | "Tool `issue_refund` took 18 ms, policy=REQUIRE_APPROVAL, model used 4.3k tokens" | "Refund slice task success 91%, groundedness 0.96, 0 critical failures" |
| Failure it catches | Latency, errors, loops, cost spikes, dependency outages, policy denials | Wrong answers, wrong tools, hallucination, safety regressions |

**How they connect.** Eval runs emit traces (with `eval.case.id`), so a failing case can be opened in the trace viewer. Online evaluators score sampled production traces, and the scores are stored keyed by `trace_id` (spans are immutable once ended, so the score lives in an eval store or is sent as a separate event/span linked to the trace). Dashboards join both.

#### 4.3 Metrics vs Traces vs Logs

- **Metrics:** aggregated, cheap, long retention, alerting. Low-cardinality tags only: model, tool, decision, agent, outcome. **Never** user IDs, run IDs or prompt text.
- **Traces:** per-request detail, sampled, medium retention, high-cardinality attributes OK (run ID, proposal ID).
- **Logs:** discrete events with detail. Structured JSON with `trace_id`/`span_id` injected (Spring Boot does this via the tracing MDC integration) so you can jump from log to trace.
- **Exemplars:** metrics with a sample trace ID attached, so you can go from a latency spike in a histogram to an example trace.

#### 4.4 Span Attribution

**Definition.** Determining which component caused an outcome (an error, latency or a wrong answer) from the trace.

**Technique.**

1. Find the **first span with ERROR status** in causal order. The deepest error is usually the cause, and the parents just propagate it.
2. For latency, find the **critical path**: the longest chain of sequential child spans. Parallel spans don't add.
3. For wrong answers (no error): inspect the **retrieval span** (were the right IDs returned?), then the **tool spans** (did tools return what the model claims?), then the **model spans** (finish reasons, token counts suggesting truncation), then **validation** (repairs?), then **policy** (denials?).
4. Use span **events** for notable moments (`guardrail.signal`, `retry`, `fallback.activated`) and **status descriptions** with error codes, not stack traces with data.

Attribution only works if each component creates its own span with clear ownership. A single giant span "agent.run" with logs inside is not attributable.

#### 4.5 Cross-Agent Correlation

**Multi-agent in one process:** the orchestrator's `invoke_agent orchestrator` span is the parent of each sub-agent's `invoke_agent researcher` span. Observation context propagates automatically on the same thread. For virtual threads or executors, use context-propagating executors (Micrometer `ContextSnapshot`/`ContextExecutorService`, or Spring's `TaskDecorator` with `ContextPropagatingTaskDecorator`).

**Across processes:**

- HTTP: `traceparent` header is injected by instrumented clients (`RestClient`/`WebClient` built from the auto-configured builder, **not** `new RestTemplate()`).
- Kafka: headers propagate when observation is enabled (`spring.kafka.template.observation-enabled=true`, `spring.kafka.listener.observation-enabled=true`).
- MCP: tool calls to an MCP server over Streamable HTTP propagate HTTP headers if the client's HTTP transport is instrumented. The MCP specification also reserves `_meta` on requests, which some SDKs use to carry trace context. [Version-dependent]
- **Baggage** (`baggage` header) can carry `tenant.id` or `agent.run.id` across hops so downstream services can tag spans. Never put secrets or PII in baggage: it goes to every downstream service, including third parties.

**Correlation IDs vs trace IDs.** Trace IDs are technical and per-trace. Business correlation IDs (`agent.run.id`, `ticket.id`, `proposal.id`) persist across traces and pauses. Use both: add the business IDs as span attributes, and store `traceparent` on durable records (proposal row, outbox event) to create links later.

#### 4.6 Safe Logging and Tracing

**Risks.** Prompts and completions contain PII, secrets pasted by users, and other customers' data in retrieved context. Observability backends often have wide internal access, long retention and third-party vendors.

**Rules.**

1. **Default: no content.** Record sizes, counts, IDs, hashes, decisions and codes, not text. Spring AI's chat observations do not log prompt/completion content unless explicitly enabled (properties such as `spring.ai.chat.observations.log-prompt` / `log-completion`; check names for your version). Keep them off in production. [Version-dependent]
2. **Opt-in content capture** for debugging goes to a **separate restricted store** (short retention, access-logged, redacted with the Unit 33 redactor), keyed by trace ID. The trace holds only a pointer.
3. **Redact at the source and again in the Collector** (defense in depth): attributes/transform processors that drop or hash known-sensitive keys and mask patterns.
4. **Pseudonymous user IDs:** `enduser.id = hmac(userId)` if needed at all.
5. **Cardinality hygiene** in metrics: unbounded tags (user, run, query text) explode cost and can leak data.
6. **Sampling:** head sampling (decide at start, for example 10%) is cheap but drops rare errors. **Tail sampling** in the Collector (decide after the trace completes) keeps 100% of error traces, slow traces and traces with policy denials, plus a percentage of the rest.
7. **Exceptions:** messages can contain data (`"Invalid email: john@x.com"`). Record `error.type` and sanitized messages.

#### 4.7 Cost and Token Observability

Tokens drive cost and latency. Track per model call (input, output, cached input where the provider reports it), aggregate per run on the agent span, and expose counters by model and agent. Compute cost with a versioned price table (same as Unit 36). Alert on: cost per run p95, runs hitting max steps, token budget exhaustion, and sudden input-token growth (often a retrieval or memory bug stuffing the context).

#### 4.8 Alerting and SLOs for Agents

Examples:

- **Availability SLO:** 99.5% of chat requests return non-5xx within 15 s.
- **Latency:** p95 `agent.run.duration` < 8 s.
- **Quality proxies:** GaveUp rate < 1%; max-steps stop rate < 0.5%; policy denial rate per 1k runs within the band (a spike suggests injection campaign or bug); approval rejection rate < 10%.
- **Dependency:** model provider error rate, 429 rate, fallback activation rate.
- **Cost:** daily spend vs budget; cost per run p95.

### 5. Internal Mechanics

#### 5.1 How a Micrometer Observation becomes a span and a metric

```
Observation.createNotStarted("agent.tool", registry)
   .lowCardinalityKeyValue("tool.name", "get_order")     → metric tag AND span attribute
   .highCardinalityKeyValue("agent.run.id", "r-91")       → span attribute ONLY (not a metric tag)
   .observe(supplier)
      → start(): handlers notified
           DefaultMeterObservationHandler → starts Timer.Sample / LongTaskTimer
           TracingObservationHandler (OTel bridge) → tracer.nextSpan(parent = current) → span.start
           context put in scope (ThreadLocal via ContextRegistry)
      → supplier runs (child observations become child spans)
      → error? observation.error(e) → span status ERROR + error tag
      → stop(): timer recorded with low-card tags; span ended → BatchSpanProcessor → OTLP exporter
```

The **low vs high cardinality** distinction is the key API decision. Low-cardinality key-values become metric tags. High-cardinality ones only go to spans.

#### 5.2 Context propagation across threads

`Observation` scope is held in a `ThreadLocal`. When you hop threads (executor, `CompletableFuture`, virtual thread you create, reactive pipeline), the scope is lost unless propagated. Spring Boot auto-configures context propagation for `@Async` and scheduled tasks when observations are enabled (Boot 4.1 added async context propagation for `@Async` methods [Version-dependent]). For your own executors, wrap them with `ContextExecutorService.wrap(executor, ContextSnapshotFactory.builder().build()::captureAll)`. The `SecurityContext` (Unit 33) has the same problem and the same family of solutions.

#### 5.3 Collector pipeline

```
app (OTLP) → [receiver otlp] → [processor memory_limiter] → [processor attributes/transform: redact]
          → [processor tail_sampling: keep errors, slow, policy-denied, 10% rest] → [processor batch]
          → [exporter otlp → Tempo/Jaeger/vendor]   (traces)
          → [exporter prometheusremotewrite/otlp → Mimir/Prometheus]   (metrics)
          → [exporter otlp → Loki/Elastic]   (logs)
```

Tail sampling needs all spans of a trace to reach the same Collector instance. With several Collectors, put a load-balancing exporter (by trace ID) in front.

```java
package com.example.supportops.agent;

import com.example.supportops.observability.AgentAttributes;
import io.micrometer.common.KeyValue;
import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.observation.Observation;
import io.micrometer.observation.ObservationRegistry;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.time.Instant;

@Service
public class AgentService {

    public record RunLimits(int maxSteps, Duration deadline, long maxTokens) {}
    public enum StopReason { ANSWERED, PENDING_APPROVAL, ASK_CLARIFICATION, ESCALATED,
                             MAX_STEPS, DEADLINE, TOKEN_BUDGET, DENIAL_BUDGET, ERROR }

    private final ObservationRegistry observations;
    private final MeterRegistry meters;
    private final AgentLoop loop;
    private final RunLimits limits = new RunLimits(6, Duration.ofSeconds(30), 20_000);

    public AgentService(ObservationRegistry observations, MeterRegistry meters, AgentLoop loop) {
        this.observations = observations;
        this.meters = meters;
        this.loop = loop;
    }

    public AgentResult run(AgentRequest req) {
        Observation obs = Observation.createNotStarted("agent.run", observations)
            .contextualName("invoke_agent " + req.agentId())
            .lowCardinalityKeyValue(AgentAttributes.GEN_AI_OPERATION, "invoke_agent")
            .lowCardinalityKeyValue(AgentAttributes.GEN_AI_AGENT_NAME, req.agentId())
            .highCardinalityKeyValue(AgentAttributes.RUN_ID, req.runId());

        return obs.observe(() -> {
            Instant deadline = Instant.now().plus(limits.deadline());
            AgentResult result = loop.execute(req, limits, deadline);   // child spans per step/tool/model call

            obs.highCardinalityKeyValue(AgentAttributes.STEPS, String.valueOf(result.steps()));
            obs.highCardinalityKeyValue(AgentAttributes.TOKENS_IN, String.valueOf(result.inputTokens()));
            obs.highCardinalityKeyValue(AgentAttributes.TOKENS_OUT, String.valueOf(result.outputTokens()));
            obs.highCardinalityKeyValue(AgentAttributes.COST_USD, String.format("%.5f", result.costUsd()));
            obs.lowCardinalityKeyValue(AgentAttributes.STOP_REASON, result.stopReason().name());

            meters.counter("agent.run.stop", "agent", req.agentId(),
                           "reason", result.stopReason().name()).increment();
            meters.counter("agent.cost.usd", "agent", req.agentId(), "model", result.primaryModel())
                  .increment(result.costUsd());
            meters.summary("agent.run.steps", "agent", req.agentId()).record(result.steps());
            if (result.stopReason() == StopReason.ERROR) {
                obs.error(new AgentRunFailedException(result.errorCode()));   // sanitized, code only
            }
            return result;
        });
    }
}
```

**Important:** `lowCardinalityKeyValue` added *inside* `observe(...)` before stop still applies to the metric, because tags are read at stop time. Keep that set small and bounded (stop reason is an enum).

The loop wraps each step:

```java
// inside AgentLoop.execute(...)
for (int step = 1; step <= limits.maxSteps(); step++) {
    if (Instant.now().isAfter(deadline)) return result.stop(StopReason.DEADLINE);
    if (tokens.total() > limits.maxTokens()) return result.stop(StopReason.TOKEN_BUDGET);

    int s = step;
    var decision = Observation.createNotStarted("agent.step", observations)
        .highCardinalityKeyValue("agent.step.index", String.valueOf(s))
        .observe(() -> decisionLoop.decide(model, conversation, advertised, retrievedIds));
    // ... validated decision → tool execution via GuardedToolExecutor (its own "agent.tool" observation)
}
return result.stop(StopReason.MAX_STEPS);
```

Spring AI 2.0 already emits observations for `ChatClient` calls, model calls (with GenAI-style token attributes), tool calls and vector store operations, so your `agent.step` spans will contain the framework's `chat` spans as children. [Version-dependent] Check the span names and attributes your version produces before building dashboards on them.

#### Example 3 — Production-oriented: Async continuation, links, safe content capture, Collector config, and the failed-request demo

**Store `traceparent` on the proposal and link later.**

```java
package com.example.supportops.observability;

import io.micrometer.tracing.Link;
import io.micrometer.tracing.Span;
import io.micrometer.tracing.TraceContext;
import io.micrometer.tracing.Tracer;
import org.springframework.stereotype.Component;

import java.util.Optional;

@Component
public class TraceLinks {

    private final Tracer tracer;

    public TraceLinks(Tracer tracer) { this.tracer = tracer; }

    /** Capture the current trace context as "traceId:spanId" to persist on durable records. */
    public Optional<String> currentRef() {
        Span span = tracer.currentSpan();
        if (span == null) return Optional.empty();
        TraceContext ctx = span.context();
        return Optional.of(ctx.traceId() + ":" + ctx.spanId());
    }

    /** Start a new root span (e.g. approval execution) that links back to the originating chat trace. */
    public Span startLinked(String name, String storedRef) {
        Span.Builder builder = tracer.spanBuilder().name(name);
        if (storedRef != null && storedRef.contains(":")) {
            String[] parts = storedRef.split(":");
            TraceContext linked = tracer.traceContextBuilder()
                .traceId(parts[0]).spanId(parts[1]).sampled(true).build();
            builder = builder.addLink(new Link(linked));
        }
        return builder.start();
    }
}
```

`ApprovalService.propose()` stores `traceLinks.currentRef()` on `action_proposal.origin_trace`. `ApprovedActionExecutor.execute()` runs inside the Kafka consumer span (parent = the producer in the approval-decision trace) and adds a link to `origin_trace`, so the viewer can jump between the three traces. API names follow Micrometer Tracing 1.x; with the raw OTel API use `SpanBuilder.addLink(SpanContext)`.

**Opt-in content capture with redaction.**

```java
package com.example.supportops.observability;

import com.example.supportops.guard.InputGuard;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.stereotype.Component;

import java.time.Duration;

@ConfigurationProperties("supportops.debug-capture")
record DebugCaptureProperties(boolean enabled, double sampleRate, Duration retention) {}

@Component
public class DebugCapture {

    private final DebugCaptureProperties props;
    private final DebugCaptureRepository repo;     // separate schema, restricted role, TTL job
    private final InputGuard redactor;
    private final TraceLinks traces;

    public DebugCapture(DebugCaptureProperties props, DebugCaptureRepository repo,
                        InputGuard redactor, TraceLinks traces) {
        this.props = props; this.repo = repo; this.redactor = redactor; this.traces = traces;
    }

    public void capture(String kind, String content) {
        if (!props.enabled() || java.util.concurrent.ThreadLocalRandom.current().nextDouble() > props.sampleRate()) {
            return;
        }
        String redacted = redactor.inspect(content).text();
        traces.currentRef().ifPresent(ref ->

        // The span only gets a flag, never the text.
    }
}
```

**Demonstration: one failed request, attributed from its trace.**

*Scenario:* A rep asks "What's our policy for late deliveries?" and the agent answers "I couldn't find a policy" (no error status at HTTP level, 200 OK). The rep files feedback with the response's trace ID (return it in a response header `traceparent` or in the JSON body).

```
POST /api/agent/chat                         200  2.1 s
└─ invoke_agent support-assistant            stop_reason=ANSWERED steps=2
   ├─ chat claude-x                           in=1,900 out=60 finish=tool_use
   ├─ execute_tool search_kb                  policy=Allow
   │   └─ retrieval search_kb                 k=5 hits=0  ← !!
   │       ├─ embeddings                      ok
   │       └─ SELECT … WHERE tenant_id = ? AND acl && ? ORDER BY …   rows=0
   ├─ chat claude-x                           in=2,050 out=45 finish=end_turn
   └─ guardrail.output                        findings=[]
```

*Attribution:* retrieval returned 0 hits, so the model never saw any evidence. This is a **retrieval failure, not a generation failure**. The DB span's attributes show the ACL filter `acl && ?`. The rep's groups (in baggage/attributes, hashed) changed after an IdP group rename yesterday, while the KB chunks still carry the old group name. *Fix:* re-sync ACL metadata on ingestion and map groups by stable IDs, not names. *Prevent:* an alert on `retrieval.hits=0` rate per tenant, and an eval case with the renamed group.

Compare with a **generation failure** trace: retrieval `hits=5 top=D-12`, but the answer contradicts D-12. The fix is in prompt, model or context construction, and the evidence is in the trace.

And a **dependency failure**: `chat claude-x` spans with `error.type=429` ×3 and then `fallback.activated` event → a second `chat` span against the fallback model. The trace shows the retries and the degradation path.

### 7. Comparative Analysis

| Comparison | Key difference | Use when | Trap |
|---|---|---|---|
| Observability vs evaluation | What happened vs was it good | Both, linked by trace ID | Treating dashboards as quality evidence |
| OTel Java agent vs Boot OTel starter vs OTel's Spring starter | Bytecode auto-instrumentation vs Micrometer-native vs OTel-native config | Agent for breadth/no code; Boot starter for Spring-native config; OTel starter when agent impossible | Running two at once → duplicate spans |
| Micrometer Observation vs raw OTel API | Facade producing metrics + spans vs tracing-only API | Observation in Spring code; raw OTel for advanced span features | Creating spans and timers separately for the same operation |
| Parent/child vs links | Synchronous causality vs related traces | Links across human pauses and fan-in | Hours-long traces |
| Head vs tail sampling | Decide at start vs after completion | Tail to keep errors/slow/denials | Head sampling at 1% loses the incidents you need |
| Trace ID vs business correlation ID | Technical per trace vs domain-wide | Both | Only trace IDs → can't follow a run across pauses |
| Content in spans vs pointer to restricted store | Convenience vs privacy | Pointer | Prompts with PII in a vendor backend |
| Low vs high cardinality key-values | Metric tags vs span-only | Low: enums; high: IDs | User IDs as metric tags |

### 8. Failure Modes and Debugging

**Failure 1 — Broken traces (orphan spans).**

- SYMPTOM: Tool spans appear as separate root traces.
- LIKELY CAUSE: Tool executed on a custom executor or virtual thread without context propagation; or an HTTP client created with `new` (uninstrumented).
- INVESTIGATE: Thread names in logs; compare trace IDs in log lines before and after the hop.
- FIX: Context-propagating executor/TaskDecorator; inject `RestClient.Builder`.
- PREVENT: Integration test asserting a single trace ID across the run (use an in-memory span exporter in tests).

**Failure 2 — Metrics backend cost explosion.**

- SYMPTOM: Time-series count jumps from 50k to 4M.
- CAUSE: `agent.run.id` or `user.id` added as a low-cardinality key-value.
- FIX: Move to high cardinality; drop the series. PREVENT: a test or meter filter (`MeterFilter.maximumAllowableTags`) and code review of tag sets.

**Failure 3 — PII in traces.**

- SYMPTOM: Security finds customer emails in the tracing backend.
- CAUSE: Content logging enabled in prod; exception messages with data; custom attribute with raw tool arguments.
- FIX: Disable content capture; sanitize exceptions; Collector masking; purge data per retention tooling.
- PREVENT: Automated scan of a sample of spans for PII patterns in CI/staging; config assertion test (`log-prompt=false` in prod profile).

**Failure 4 — "Missing" error traces.**

- SYMPTOM: Users report failures, but no traces are found.
- CAUSE: 5% head sampling.
- FIX: Tail sampling with error policy; return `traceparent` to the client so support can look it up.

**Failure 5 — Duplicate spans.**

- SYMPTOM: Every HTTP request shows two server spans.
- CAUSE: OTel Java agent plus the Boot OTel starter both instrumenting.
- FIX: Choose one; disable the other's instrumentation for overlapping libraries.

**Failure 6 — Loop invisible.**

- SYMPTOM: Cost spike, but traces look normal.
- CAUSE: Only the run span exists, with no per-step spans and no `stop_reason`.
- FIX: Step and tool spans; `agent.run.stop{reason=MAX_STEPS}` metric with an alert.

### 13. Interview Preparation

#### Quick Questions

**Q: AI observability vs AI evaluation?**
*Strong answer:* Observability records what happened (spans, metrics, logs: latency, tokens, tools, errors). Evaluation judges whether behavior was good against expectations. Link them via trace IDs.

**Q: What would you put on an LLM call span?**
*Strong answer:* Provider, requested and response model, operation, input/output tokens, finish reason, temperature/max tokens, duration, error type, but not prompt text by default.

**Q: Why tail sampling for agents?**
*Strong answer:* Interesting traces (errors, loops, denials, slow runs) are rare. Head sampling drops most of them. Tail sampling decides after seeing the whole trace.

#### Intermediate Questions

**Q: How do you trace a workflow that pauses for human approval?**
*Strong answer:* End the first trace at the pause. Persist the trace context and business IDs on the proposal. Continuation traces (approval, execution via Kafka) propagate context through headers and link back to the original. Business IDs on all spans make the workflow queryable.
*Trap:* Keeping a span open for hours.

**Q: How do you avoid leaking PII through observability?**
*Strong answer:* No content by default, IDs and sizes only; opt-in redacted capture to a restricted, short-retention store; sanitize exceptions; Collector redaction as a backstop; pseudonymous user IDs; no PII in baggage or metric tags; tests that scan spans.

**Q: A user says the agent gave a wrong answer. How do you investigate?**
*Strong answer:* Get the trace ID (returned in response), then check retrieval (hits, IDs) → tool results → model spans (finish reasons, tokens) → validation/repairs → policy → output guard. Classify as retrieval vs generation vs tool vs policy. Turn it into an eval case.

#### Advanced Questions

**Q: Design observability for a multi-agent system with remote agents and MCP tools.**
*Strong answer:* Span hierarchy (`invoke_agent` per agent, `chat`, `execute_tool`), propagation over HTTP/Kafka/MCP transport, baggage only for safe IDs, links for async/fan-in, central attribute constants, GenAI conventions noted as Development, per-agent metrics, tail sampling, cost per agent, dashboards per agent, and an online eval tied by trace ID.

**Q: What's the difference between a low- and high-cardinality key-value in Micrometer, and why does it matter?**
*Strong answer:* Low-cardinality key-values become metric tags *and* span attributes; high-cardinality ones only span attributes. Metrics multiply series per unique tag combination, so unbounded values explode storage and cost.

**Q: How would you detect agent loops in production?**
*Strong answer:* Steps per run histogram, `stop_reason=MAX_STEPS` counter and alert, repeated identical tool-call detection (canonical args hash as a span event), token budget exhaustion metric, and cost per run p95.

#### Coding Questions

1. Wrap a tool invocation in a Micrometer Observation with tool name (low card) and call ID (high card), and record errors.
2. Write a `TaskDecorator` that propagates both observation context and `SecurityContext`.
3. Compute cost from a list of `(model, inputTokens, outputTokens)` with a price table, using `BigDecimal`.

#### Scenario Questions

**Q: You're asked to prove during a customer demo that a failed request was caused by their CRM API, not your agent.**
*Strong answer:* Show the trace: `execute_tool crm_lookup` → HTTP client span with 504 after 10 s, retries recorded as events, fallback path. Correlate with the CRM's own trace if they propagate `traceparent`. Show the metric of CRM error rate at that time. Mention the circuit breaker and timeout settings.

### 14. Explain-It-at-Three-Levels

**Concept: Tracing an agent as one business workflow**

- *30 seconds:* Every agent run is one trace. The agent invocation is a span, and each model call, retrieval, tool execution, validation and guardrail is a child span with model, tokens, cost, decision and error attributes, but no customer content. Long pauses like approvals are separate traces linked back to the original.
- *2 minutes:* Add Micrometer Observation → OTel export, Spring AI's built-in spans, custom spans, GenAI conventions (provisional), metrics vs traces vs logs, tail sampling and safe logging.
- *Deep:* Cover the internals (observation handlers, low vs high cardinality, ThreadLocal context and propagation), Kafka propagation and links, the Collector pipeline (redaction, tail sampling, load-balanced exporters), attribution technique, cost accounting, SLOs, and the link to evaluation.

**Concept: Span attribution**

- *30 seconds:* Find the first error span in causal order, or for wrong answers, walk retrieval → tools → model → validation → policy, and name the component and its evidence.
- *2 minutes:* Critical-path analysis for latency, the retrieval vs generation distinction, and events for retries/fallbacks.
- *Deep:* Instrument so that attribution is possible: per-component spans, standardized attributes, IDs for evidence, and trace ↔ eval linkage.

### 15. Knowledge Check

1. Why is a single "agent.run" span with logs inside insufficient?
2. When should you use span links instead of parent/child?
3. What's the risk of putting `tenant.id` in baggage? When is it acceptable?
4. Why are GenAI attribute names centralized in one class?
5. Why can head sampling hide the failures you most need?
6. *Code reading:* In `AgentService.run`, why is `STOP_REASON` low-cardinality while `STEPS` is high-cardinality?
7. *Code reading:* In `DebugCapture`, what's stored in the span, and why?
8. *Code reading:* In the Collector config, why does `tail_sampling` come after the redaction processors?
9. *Debugging:* Tool spans show up as separate traces. Two likely causes?
10. *Debugging:* Metrics storage cost spiked after a release. What do you check?
11. *Design:* Java agent or Boot starter for a new Spring Boot 4.1 service?
12. *Design:* Where do online eval scores live if spans are immutable?

#### Knowledge Check Answers

1. You can't attribute latency, errors or cost to components, see parallelism, or query by tool/model.
2. Across long pauses (human approval), async fan-in/fan-out, batch processing of many triggering traces, and continuations started from durable records.
3. Baggage propagates to every downstream service, including third parties, and appears in headers. It's acceptable for non-sensitive internal IDs when downstreams are trusted, never for PII or secrets.
4. The conventions are in Development status and change, so centralizing them makes migration a one-file change and documents the version followed.
5. Failures and anomalies are rare. A 5% head sample keeps 5% of them. Tail sampling can keep 100%.
6. Stop reason is a small enum (a safe metric tag). Step count per run is better recorded as a histogram metric; as a tag it would create one series per value.
7. Only that a capture exists (or nothing). The content goes to a restricted, redacted, TTL-bound store keyed by trace reference, keeping PII out of the trace backend.
8. So sensitive attributes are removed before any export decision. Redaction applies to every trace regardless of the sampling outcome.
9. Lost context on thread hops (custom executor, virtual threads created manually), or an uninstrumented client/library on that path.
10. Newly introduced metric tags with unbounded values (IDs, query text). Check meter IDs by name and tag cardinality.
11. Either is valid. The agent gives the broadest library coverage with no code; the Boot starter offers Spring-native config and works with native images. Pick one and document why. Don't use both for the same libraries.
12. In an eval store keyed by trace ID (or as separate linked spans/events). Dashboards join on trace ID.

### Unit Completion Standard

Before moving on, you must be able to:

- **Explain** how traces, metrics and logs describe an agent workflow, the GenAI conventions and their Development status, observability vs evaluation, cross-agent correlation, span attribution and safe logging.
- **Implement** OpenTelemetry instrumentation for the full capstone: agent/step/model/retrieval/tool/validation/guardrail/approval spans, token/cost/loop/retry metrics, Kafka propagation with links, structured logs with trace IDs, safe content capture, Collector redaction and tail sampling.
- **Test** trace structure, propagation, cardinality and the absence of content/PII in telemetry.
- **Debug** a failed request by attributing it to the responsible component from its trace, and distinguish retrieval, generation, tool, policy and dependency failures.
- **Defend** in an interview your span design, what you record and refuse to record, your sampling strategy, and how observability and evaluation work together.
