## Unit 34 — Function and Tool Calling

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** the tool-calling control flow: the model *proposes* a structured call, your code *validates, authorizes and executes* it, and the result goes back as an *observation*. Distinguish tool calling from RAG.
2. **Design** tool schemas (names, descriptions, JSON Schema arguments) generated from Pydantic models, with strictness, bounds and clear semantics that help the model choose correctly.
3. **Implement** a tool registry and dispatcher: lookup, Pydantic argument validation, per-tool timeouts, error mapping into model-readable observations, and parallel tool calls.
4. **Implement** authentication and authorization at the tool boundary: a `ToolContext` built from verified identity, per-tool scopes, resource ownership checks and tenant isolation, never trusting model-supplied identity.
5. **Distinguish** read-only from side-effecting tools, and **implement** idempotency keys, timeouts and safe retries for side effects.
6. **Implement** explicit approval for selected side effects (pending proposals that a human approves before execution).
7. **Implement** representative tools: calculator (safe evaluation), customer lookup, read-only database query, knowledge search, and an external API call (with SSRF protection).
8. **Test** tools and dispatch with unit, negative, authorization and "compromised model" tests.

### 2. Prerequisite Knowledge

- Unit 28: Messages API, stop reasons, structured output, strict Pydantic validation.
- Unit 29: LLM client, error taxonomy, timeouts, budgets.
- Unit 31: knowledge search (becomes a tool).
- FastAPI auth dependencies (JWT → user with tenant, roles, scopes).
- PostgreSQL roles and permissions, `statement_timeout`.

**Refresher: the provider wire format (Anthropic).** You send `tools=[{"name", "description", "input_schema", "strict"?}]`. When the model wants a tool, the response has `stop_reason="tool_use"` and content blocks `{"type": "tool_use", "id": "toolu_…", "name": "get_order", "input": {...}}`. You execute it and send back a user message with `{"type": "tool_result", "tool_use_id": "toolu_…", "content": "...", "is_error": false}`. Multiple `tool_use` blocks may arrive in one response (parallel calls). Return **all** their results in **one** user message. [Version-dependent] On current Claude models (Opus 5.5, Sonnet 5.5), forced `tool_choice` (`any`/`tool`) returns a 400. Use `auto` plus clear instructions, and `strict: true` for schema-valid arguments. Other providers use similar shapes (`tool_calls` with function name and JSON arguments).

### 3. Mental Model

Tool calling is **a remote procedure call where the caller is untrusted and the callee is your code**:

```
user goal ─▶ model ──proposes──▶ {"name": "issue_refund", "input": {"order_id": "8812", "amount": 49}}
                                              │  (untrusted proposal, possibly manipulated)
                     ┌────────────────────────▼───────────────────────────────────┐
                     │ YOUR TOOL BOUNDARY (deterministic)                         │
                     │ 1 lookup tool in registry (unknown → error observation)    │
                     │ 2 validate args with Pydantic (bounds, patterns)          │
                     │ 3 authorize with ToolContext from verified identity        │
                     │   (scope, tenant, ownership, limits)                      │
                     │ 4 side effect? → approval required? → pending proposal    │
                     │ 5 execute with timeout, idempotency key, least-privilege  │
                     │ 6 map result/error → observation (bounded, safe)          │
                     └────────────────────────┬───────────────────────────────────┘
                                              ▼
                       tool_result (observation) ──▶ model ──▶ next proposal or final answer
```

The model chooses *which* function and *what* arguments. **Your code decides whether that's allowed and how it runs.** Authorization never comes from the model.

### 4. Comprehensive Theory

#### 4.1 Tool Schemas and Structured Arguments

**Definition.** A tool definition tells the model a tool's name, purpose and argument schema (JSON Schema).

**Designing good tools.**

- **Narrow and purpose-built:** `get_order(order_id)` rather than `run_sql(query)`. Narrow tools are easier for the model to use correctly and far easier to secure.
- **Names** are verbs plus objects, unambiguous (`search_knowledge_base`, `get_shipment_status`).
- **Descriptions** say when to use the tool, what it returns, its limitations and its side effects. Descriptions are prompt text and strongly affect tool selection.
- **Arguments:** typed, bounded and minimal. Use enums for closed sets, patterns for IDs, ranges for amounts, `additionalProperties: false`. **Never** include identity/authorization fields (`user_id`, `tenant_id`, `is_admin`) as arguments. Those come from the context.
- **Outputs:** concise and structured (JSON or compact text). Large outputs waste tokens and can contain injection payloads, so truncate and summarize.

**Generate schemas from Pydantic** so validation and advertised schema share one source:

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class GetOrderArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^\d{4,12}$", description="Numeric order ID as shown to the customer")


class IssueRefundArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^\d{4,12}$")
    amount: float = Field(gt=0, le=10_000, description="Refund amount in the order currency")
    reason: Literal["late_delivery", "damaged", "wrong_item", "not_received", "goodwill"]
```

`GetOrderArgs.model_json_schema()` produces the `input_schema`. With strict tool use (`strict: true`), the provider guarantees arguments match the schema's supported subset. You **still** validate with Pydantic (bounds, patterns and semantics) because constrained decoding doesn't cover everything and providers differ. For money, accept a decimal string or integer cents in production to avoid float issues, and convert to `Decimal` in the tool.

#### 4.2 Decision → Validation → Execution → Observation

```
1. Model decision: response with stop_reason="tool_use" and one or more tool_use blocks.
2. Validation: name in registry? args parse & validate? (fail → is_error observation describing the problem)
3. Authorization: ToolContext (identity, tenant, scopes) + resource checks (fail → is_error "not permitted")
4. Execution: with timeout and idempotency; read-only vs side-effecting; approval gate for selected effects.
5. Observation: tool_result content (bounded, structured), is_error for failures; all results in one message.
6. Loop: send history + observations back; model either calls more tools or answers (bounded loop, Unit 35).
```

**Error observations teach the model.** "Order 9999 not found for this customer" lets the model ask the user. "Invalid order_id: must be digits" lets it correct itself. Don't leak internals (stack traces, SQL), and don't reveal *why* authorization failed in detail (don't help an attacker probe).

#### 4.3 Tool Registry and Dispatch

**Registry**: a mapping `name → ToolSpec(args_model, handler, description, side_effect, required_scope, approval_policy, timeout_s, idempotent)`. It produces provider tool definitions (only tools allowed for this user/context) and dispatches calls.

**Dispatch responsibilities**: unknown tool handling, argument validation, authorization, approval routing, timeout enforcement, error mapping, result truncation and metrics/tracing per tool.

**Parallel calls.** If the model emits several independent `tool_use` blocks, execute read-only ones concurrently (bounded with a semaphore or task group). Side-effecting ones should run sequentially or be gated. Return all results together.

#### 4.4 Authentication and Authorization at the Tool Boundary

**ToolContext** is created by your API from the verified token (never from model output):

```python
@dataclass(frozen=True)
class ToolContext:
    user_id: str
    tenant_id: str
    scopes: frozenset[str]
    customer_id: str | None        # e.g. the customer this conversation is about (from the ticket record)
    refund_limit: Decimal          # from the user's role in your DB
    run_id: str                    # for idempotency and tracing
```

**Checks per call:**

1. **Scope:** user has the tool's required scope (`orders:read`, `refunds:write`).
2. **Tenant:** every resource is fetched with `tenant_id` in the query.
3. **Ownership/relationship:** the order belongs to `ctx.customer_id` (the ticket's customer), not to whatever the model says.
4. **Limits:** amount ≤ refundable balance and ≤ the user's limit.
5. **Context policy:** for example, no side-effecting tools when the conversation contains untrusted external content without approval (prompt-injection containment).

**Credential model.** Tools call downstream systems with **least-privilege credentials**: a read-only DB role for read tools, and a scoped API token for the refunds service. Where possible, act **on behalf of the user** (delegated tokens) so downstream authorization also applies. Never use an admin service account for everything (the confused-deputy problem).

**Advertise only allowed tools**: build the `tools` list per request from the user's scopes. Still re-check on every call, because the model may hallucinate tool names or reuse old ones from history.

#### 4.5 Idempotency, Timeouts and Errors

**Read-only tools** (lookups, search, calculation) are naturally safe to retry. **Side-effecting tools** (send email, update record, refund, delete) are not.

**Idempotency for side effects.**

- Derive an **idempotency key** from stable identifiers: `f"{run_id}:{tool_use_id}"`, or a proposal ID after approval. The same logical call always maps to the same key.
- Record executions in a table keyed by that key (unique constraint), inside the same transaction as local effects, and pass the key to downstream APIs that support it (payment providers do).
- A retried call with the same key returns the original result instead of acting twice.

**Timeouts.** Per tool (DB 2 s, external API 5 s, search 3 s), plus the agent's overall deadline. On timeout for a side effect, the outcome is **unknown**. Don't blindly retry with a new key. Query the downstream status by key, or report "pending verification".

**Error mapping.**

| Situation | Observation to model | Also |
|---|---|---|
| Unknown tool | `is_error`: "Unknown tool X. Available: …" | Metric (possible injection/hallucination) |
| Validation error | `is_error`: field-level messages | |
| Not authorized | `is_error`: "Not permitted for this user/context." | Audit log with details (not to the model) |
| Not found | `is_error`: "Order 9999 not found." | Don't distinguish "not yours" from "doesn't exist" |
| Timeout | `is_error`: "Service timed out; try later or ask the user." | Breaker/metrics |
| Downstream 5xx | `is_error`: "Temporary error." | Retry policy for read-only |
| Approval required | not an error: "Refund proposal P-17 created; awaiting approval." | Stop the loop (Unit 35/38) |

#### 4.6 Read-Only vs Side-Effecting Tools

| Aspect | Read-only | Side-effecting |
|---|---|---|
| Examples | `get_order`, `search_kb`, `calculate` | `send_email`, `update_address`, `issue_refund`, `delete_data` |
| Retries | Safe | Only with idempotency keys |
| Parallelism | Yes (bounded) | Sequential / gated |
| Approval | No | Risk-based (refunds, deletions, external communication) |
| Credentials | Read-only roles | Narrow write scopes |
| Audit | Optional | Mandatory (who, what, why, evidence, result) |
| Prompt-injection risk | Data exposure | Unauthorized actions; requires stricter containment |

**Explicit approval for selected side effects.** The tool handler for `issue_refund` (above a threshold, or always in v1) doesn't execute. It creates a **pending proposal** (exact args, context, evidence) and returns "awaiting approval". A human approves via an API, and a separate executor runs the action with the proposal's idempotency key. Unit 38 makes this a durable graph with `interrupt()`. Here it's a simple table.

#### 4.7 Tool Calling vs RAG

| | RAG | Tool calling |
|---|---|---|
| Purpose | Bring relevant *unstructured knowledge* into context | Query *systems of record* or perform *actions* |
| Who decides to call | Usually your code (always retrieve) | The model (chooses tool and args) |
| Data | Documents, chunks | Live structured data, APIs |
| Freshness | As fresh as the index | Real-time |
| Risks | Wrong/irrelevant context, leakage via retrieval | Unauthorized actions, injection-driven calls |
| Example | "What is the refund policy?" | "Has order 8812 shipped?" / "Refund order 8812" |

RAG can itself be exposed as a tool (`search_knowledge_base`), letting the model decide when to search: the agentic RAG pattern.

### 5. Internal Mechanics

#### 5.1 One tool-calling round trip

```
request: system + messages + tools (allowed subset) → model
response: content [text?, tool_use{id,name,input}, tool_use{…}], stop_reason=tool_use
dispatcher for each tool_use:
   spec = registry.get(name) → None? error result
   args = spec.args_model.model_validate(input)  → ValidationError? error result
   authorize(spec, args, ctx)                     → Denied? error result (+audit)
   spec.requires_approval(args, ctx)?             → create proposal → result "awaiting approval"
   with timeout(spec.timeout_s): result = await spec.handler(args, ctx, idempotency_key)
   observation = truncate(serialize(result))
next request: messages + assistant(response.content) + user([tool_result…]) → model
```

The assistant message must be appended **exactly as returned** (including `tool_use` blocks), and the next user message must contain `tool_result` blocks whose `tool_use_id`s match.

#### 5.2 Why a safe calculator needs an AST, not `eval`

`eval("__import__('os').system('rm -rf /')")` executes arbitrary code. A safe calculator parses the expression with `ast.parse(expr, mode="eval")` and evaluates only whitelisted node types (numbers, + − × ÷, parentheses, maybe `**` with exponent limits), rejecting names, calls and attributes. Even "safe" arithmetic can be abused for resource exhaustion (`9**9**9`), so bound exponents and result sizes.

#### Example 1 — Minimal: One tool, one round trip (Anthropic SDK)

```python
# examples/one_tool.py
import json

import anthropic
from pydantic import BaseModel, ConfigDict, Field, ValidationError

client = anthropic.Anthropic()


class GetOrderArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^\d{4,12}$")


ORDERS = {"8812": {"status": "shipped", "carrier": "DHL", "eta": "2026-10-12"}}

tools = [{
    "name": "get_order",
    "description": "Look up an order's status, carrier and ETA by order ID. Read-only.",
    "input_schema": GetOrderArgs.model_json_schema(),
    "strict": True,
}]
messages = [{"role": "user", "content": "Where is order 8812?"}]

resp = client.messages.create(model="claude-opus-5-5", max_tokens=1024, tools=tools, messages=messages)
if resp.stop_reason == "tool_use":
    results = []
    for block in resp.content:
        if block.type != "tool_use":
            continue
        try:
            args = GetOrderArgs.model_validate(block.input)
            order = ORDERS.get(args.order_id)
            content, is_error = (json.dumps(order), False) if order else ("Order not found.", True)
        except ValidationError as e:
            content, is_error = f"Invalid arguments: {e.errors()[0]['msg']}", True
        results.append({"type": "tool_result", "tool_use_id": block.id, "content": content, "is_error": is_error})
    messages += [{"role": "assistant", "content": resp.content}, {"role": "user", "content": results}]
    resp = client.messages.create(model="claude-opus-5-5", max_tokens=1024, tools=tools, messages=messages)

print("".join(b.text for b in resp.content if b.type == "text"))
```

(Pydantic's generated schema includes `title` fields and may include keywords outside a provider's strict subset. If strict mode rejects the schema, post-process it into a minimal JSON Schema with `type`, `properties`, `required` and `additionalProperties: false`, and keep full Pydantic validation in code.)

#### Example 2 — Realistic: Registry, dispatcher, context-based authorization and five tools

```python
# app/tools/registry.py
import asyncio
import json
import logging
from collections.abc import Awaitable, Callable
from dataclasses import dataclass
from decimal import Decimal
from enum import StrEnum
from typing import Any

from pydantic import BaseModel, ValidationError

log = logging.getLogger("tools")


@dataclass(frozen=True)
class ToolContext:
    user_id: str
    tenant_id: str
    scopes: frozenset[str]
    customer_id: str | None
    refund_limit: Decimal
    run_id: str
    groups: tuple[str, ...] = ()            # ACL groups for knowledge retrieval
    untrusted_content_in_context: bool = False


class Effect(StrEnum):
    READ = "read"
    WRITE = "write"


class ToolDenied(Exception):
    """Authorization failure: details go to audit logs, not to the model."""


class ToolNotFound(Exception):
    pass


@dataclass(frozen=True)
class ToolResult:
    content: Any
    is_error: bool = False
    pending_approval_id: str | None = None


Handler = Callable[[BaseModel, ToolContext, str], Awaitable[ToolResult]]


@dataclass(frozen=True)
class ToolSpec:
    name: str
    description: str
    args_model: type[BaseModel]
    handler: Handler
    effect: Effect
    required_scope: str
    timeout_s: float = 5.0
    requires_approval: Callable[[BaseModel, ToolContext], bool] = lambda args, ctx: False

    def provider_definition(self) -> dict:
        schema = self.args_model.model_json_schema()
        schema.pop("title", None)
        schema["additionalProperties"] = False
        return {"name": self.name, "description": self.description, "input_schema": schema, "strict": True}


MAX_OBSERVATION_CHARS = 4000


class ToolRegistry:
    def __init__(self, specs: list[ToolSpec]) -> None:
        self._specs = {s.name: s for s in specs}

    def definitions_for(self, ctx: ToolContext) -> list[dict]:
        """Advertise only tools this user may use in this context."""
        allowed = []
        for spec in self._specs.values():
            if spec.required_scope not in ctx.scopes:
                continue
            if spec.effect is Effect.WRITE and ctx.untrusted_content_in_context:
                continue                         # injection containment: hide writes in tainted contexts
            allowed.append(spec.provider_definition())
        return allowed

    async def dispatch(self, name: str, raw_args: dict, ctx: ToolContext, tool_use_id: str) -> ToolResult:
        spec = self._specs.get(name)
        if spec is None:
            log.warning("tool_unknown name=%s run=%s", name, ctx.run_id)
            return ToolResult(f"Unknown tool '{name}'.", is_error=True)
        try:
            args = spec.args_model.model_validate(raw_args)
        except ValidationError as e:
            msgs = "; ".join(f"{'.'.join(map(str, err['loc']))}: {err['msg']}" for err in e.errors())
            return ToolResult(f"Invalid arguments: {msgs}", is_error=True)

        if spec.required_scope not in ctx.scopes:
            log.warning("tool_denied_scope name=%s user=%s run=%s", name, ctx.user_id, ctx.run_id)
            return ToolResult("Not permitted for this user.", is_error=True)
        if spec.effect is Effect.WRITE and ctx.untrusted_content_in_context and not spec.requires_approval(args, ctx):
            return ToolResult("This action requires human approval in this context.", is_error=True)

        idempotency_key = f"{ctx.run_id}:{tool_use_id}"
        try:
            async with asyncio.timeout(spec.timeout_s):
                result = await spec.handler(args, ctx, idempotency_key)
        except ToolDenied as e:
            log.warning("tool_denied name=%s user=%s run=%s detail=%s", name, ctx.user_id, ctx.run_id, e)
            return ToolResult("Not permitted, or the resource was not found.", is_error=True)
        except TimeoutError:
            log.warning("tool_timeout name=%s run=%s", name, ctx.run_id)
            msg = ("The service timed out; the outcome is unknown and will be verified."
                   if spec.effect is Effect.WRITE else "The service timed out; try again later.")
            return ToolResult(msg, is_error=True)
        except Exception:
            log.exception("tool_failed name=%s run=%s", name, ctx.run_id)
            return ToolResult("Temporary error while running the tool.", is_error=True)

        return _bounded(result)


def _bounded(result: ToolResult) -> ToolResult:
    text = result.content if isinstance(result.content, str) else json.dumps(result.content, default=str)
    if len(text) > MAX_OBSERVATION_CHARS:
        text = text[:MAX_OBSERVATION_CHARS] + " …[truncated]"
    return ToolResult(text, result.is_error, result.pending_approval_id)
```

```python
# app/tools/calculator.py
import ast
import operator as op
from decimal import Decimal, InvalidOperation

from pydantic import BaseModel, ConfigDict, Field

from app.tools.registry import Effect, ToolContext, ToolResult, ToolSpec

_OPS = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv, ast.USub: op.neg, ast.UAdd: op.pos}


class CalcArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    expression: str = Field(min_length=1, max_length=200, pattern=r"^[0-9+\-*/(). ]+$")


def safe_eval(expr: str) -> Decimal:
    def ev(node: ast.AST) -> Decimal:
        if isinstance(node, ast.Expression):
            return ev(node.body)
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return Decimal(str(node.value))
        if isinstance(node, ast.BinOp) and type(node.op) in _OPS:
            return _OPS[type(node.op)](ev(node.left), ev(node.right))
        if isinstance(node, ast.UnaryOp) and type(node.op) in _OPS:
            return _OPS[type(node.op)](ev(node.operand))
        raise ValueError("unsupported expression")
    return ev(ast.parse(expr, mode="eval"))


async def calculate(args: CalcArgs, ctx: ToolContext, key: str) -> ToolResult:
    try:
        return ToolResult({"result": str(safe_eval(args.expression))})
    except (ValueError, SyntaxError, ZeroDivisionError, InvalidOperation) as e:
        return ToolResult(f"Cannot evaluate: {e}", is_error=True)


CALCULATOR = ToolSpec("calculate", "Evaluate an arithmetic expression (+ - * / and parentheses). "
                      "Use for exact money arithmetic instead of computing in your head.",
                      CalcArgs, calculate, Effect.READ, required_scope="tools:basic", timeout_s=1.0)
```

```python
# app/tools/customer.py
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import text

from app.tools.registry import Effect, ToolContext, ToolDenied, ToolResult, ToolSpec


class CustomerLookupArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    customer_id: str = Field(pattern=r"^c-\d{1,10}$")


def make_customer_lookup(session_factory) -> ToolSpec:
    async def lookup(args: CustomerLookupArgs, ctx: ToolContext, key: str) -> ToolResult:
        if ctx.customer_id is not None and args.customer_id != ctx.customer_id:
            raise ToolDenied("customer outside conversation scope")
        async with session_factory() as s:
            row = (await s.execute(text(
                "SELECT id, name, email_masked, tier, created_at FROM customer_view "     # masked projection
                "WHERE tenant_id = :t AND id = :c"), {"t": ctx.tenant_id, "c": args.customer_id})).mappings().first()
        if row is None:
            raise ToolDenied("not found")                                                  # same response as denied
        return ToolResult(dict(row))

    return ToolSpec("get_customer", "Get a customer's profile (masked contact details) for the current conversation.",
                    CustomerLookupArgs, lookup, Effect.READ, required_scope="customers:read", timeout_s=2.0)
```

```python
# app/tools/db_query.py
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import text

from app.tools.registry import Effect, ToolContext, ToolResult, ToolSpec

# Allowlisted, parameterized queries: the model picks a query by name and supplies bounded parameters.
QUERIES = {
    "orders_by_customer": "SELECT id, status, total, created_at FROM orders "
                          "WHERE tenant_id = :tenant AND customer_id = :customer ORDER BY created_at DESC LIMIT :limit",
    "open_tickets_by_customer": "SELECT id, subject, status, updated_at FROM ticket "
                                "WHERE tenant_id = :tenant AND customer_id = :customer AND status <> 'closed' "
                                "ORDER BY updated_at DESC LIMIT :limit",
}


class DbQueryArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    query: Literal["orders_by_customer", "open_tickets_by_customer"]
    limit: int = Field(default=10, ge=1, le=50)


def make_db_query(readonly_session_factory) -> ToolSpec:
    async def run(args: DbQueryArgs, ctx: ToolContext, key: str) -> ToolResult:
        if ctx.customer_id is None:
            return ToolResult("No customer in scope for this conversation.", is_error=True)
        async with readonly_session_factory() as s, s.begin():
            await s.execute(text("SET LOCAL statement_timeout = '2s'"))
            await s.execute(text("SET TRANSACTION READ ONLY"))
            rows = (await s.execute(text(QUERIES[args.query]),
                                    {"tenant": ctx.tenant_id, "customer": ctx.customer_id,
                                     "limit": args.limit})).mappings().all()
        return ToolResult([dict(r) for r in rows])

    return ToolSpec("query_customer_data",
                    "Run a predefined read-only query about the current customer: "
                    "'orders_by_customer' or 'open_tickets_by_customer'.",
                    DbQueryArgs, run, Effect.READ, required_scope="orders:read", timeout_s=3.0)
```

The "database tool" is **not** free-form SQL. Free-form SQL from a model is an injection and data-exfiltration channel. If you must support ad-hoc analytics, use a separate read-only replica, a restricted role with row-level security, query allowlisting or parsing (reject DDL/DML), row/time limits, and human review.

```python
    host = urlparse(url).hostname or ""
    for info in socket.getaddrinfo(host, 443):
        ip = ipaddress.ip_address(info[4][0])
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            raise ValueError("blocked destination")          # SSRF guard (defense in depth)


def make_shipment_tool(client: httpx.AsyncClient, token_provider) -> ToolSpec:
    async def track(args: ShipmentArgs, ctx: ToolContext, key: str) -> ToolResult:
        url = f"{CARRIER_BASE}/v1/tracking/{args.tracking_number}"
        _assert_public_host(url)
        r = await client.get(url, headers={"Authorization": f"Bearer {await token_provider()}"},
                             timeout=httpx.Timeout(4.0, connect=2.0), follow_redirects=False)
        if r.status_code == 404:
            return ToolResult("Tracking number not found.", is_error=True)
        r.raise_for_status()
        data = r.json()
        return ToolResult({"status": data.get("status"), "eta": data.get("eta"),
                           "last_event": (data.get("events") or [{}])[-1].get("description", "")[:200]})

    return ToolSpec("get_shipment_status", "Get carrier tracking status and ETA for a tracking number.",
                    ShipmentArgs, track, Effect.READ, required_scope="orders:read", timeout_s=5.0)
```

Notes. The URL is built from a fixed base with a validated path parameter, so the model never supplies hostnames. `follow_redirects=False` prevents redirect-based SSRF. Responses are reduced to the fields the model needs, and free text is truncated (carrier event text is untrusted). The `getaddrinfo` check is synchronous here for brevity: resolve asynchronously in production, or enforce egress controls at the network layer (allowlisted egress proxy).

```python
import json
import uuid
from decimal import Decimal
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import text

from app.tools.registry import Effect, ToolContext, ToolDenied, ToolResult, ToolSpec

AUTO_APPROVE_CEILING = Decimal("0")          # v1: every refund needs a human


class IssueRefundArgs(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^\d{4,12}$")
    amount: Decimal = Field(gt=0, le=Decimal("10000"), max_digits=9, decimal_places=2)
    reason: Literal["late_delivery", "damaged", "wrong_item", "not_received", "goodwill"]


def make_refund_tool(session_factory) -> ToolSpec:
    async def propose_refund(args: IssueRefundArgs, ctx: ToolContext, key: str) -> ToolResult:
        async with session_factory() as s, s.begin():
            order = (await s.execute(text(
                "SELECT customer_id, total - refunded AS refundable FROM orders "
                "WHERE tenant_id = :t AND id = :o FOR SHARE"),
                {"t": ctx.tenant_id, "o": args.order_id})).mappings().first()
            if order is None or order["customer_id"] != ctx.customer_id:
                raise ToolDenied("order not found or not owned by conversation customer")
            if args.amount > order["refundable"]:
                return ToolResult(f"Amount exceeds refundable balance ({order['refundable']}).", is_error=True)
            if args.amount > ctx.refund_limit:
                return ToolResult("Amount exceeds your refund limit; escalate to a team lead.", is_error=True)

            proposal_id = uuid.uuid4()
            # Idempotent proposal creation: the same tool call (same key) maps to the same proposal.
            row = (await s.execute(text(
                "INSERT INTO action_proposal (id, tenant_id, run_id, requested_by, tool_name, args, status, idempotency_key) "
                "VALUES (:id, :t, :run, :u, 'issue_refund', CAST(:args AS jsonb), 'pending', :key) "
                "ON CONFLICT (idempotency_key) DO UPDATE SET idempotency_key = EXCLUDED.idempotency_key "
                "RETURNING id, status"),
                {"id": proposal_id, "t": ctx.tenant_id, "run": ctx.run_id, "u": ctx.user_id,
                 "args": json.dumps(args.model_dump(mode="json")), "key": key})).mappings().one()
        return ToolResult(f"Refund proposal {row['id']} created and awaiting human approval.",
                          pending_approval_id=str(row["id"]))

    return ToolSpec("issue_refund",
                    "Propose a refund for an order belonging to the current customer. "
                    "Creates a proposal that a human must approve; does not move money by itself.",
                    IssueRefundArgs, propose_refund, Effect.WRITE, required_scope="refunds:write",
                    timeout_s=3.0, requires_approval=lambda a, c: a.amount > AUTO_APPROVE_CEILING)
```

```python
import json

from sqlalchemy import text


class RefundExecutor:
    """Runs after a human approves. Exactly-once effect via conditional claim + idempotency key downstream."""

    def __init__(self, session_factory, payments_client) -> None:
        self._sessions, self._payments = session_factory, payments_client

    async def execute(self, proposal_id: str) -> str:
        async with self._sessions() as s, s.begin():
            row = (await s.execute(text(
                "UPDATE action_proposal SET status = 'executed' "
                "WHERE id = :id AND status = 'approved' RETURNING args, idempotency_key, tenant_id"),
                {"id": proposal_id})).mappings().first()
            if row is None:
                return "not executable (already executed, rejected, or not approved)"
            args = row["args"]
            result = await self._payments.refund(order_id=args["order_id"], amount=args["amount"],
                                                 idempotency_key=row["idempotency_key"])   # downstream dedupe
            await s.execute(text(
                "INSERT INTO tool_execution (idempotency_key, tool_name, result) "
                "VALUES (:k, 'issue_refund', CAST(:r AS jsonb)) ON CONFLICT DO NOTHING"),
                {"k": row["idempotency_key"], "r": json.dumps(result)})
        return "executed"
```

```python
# app/tools/loop.py
import asyncio

import anthropic

from app.tools.registry import Effect, ToolContext, ToolRegistry


async def run_tools_round_trip(client: anthropic.AsyncAnthropic, registry: ToolRegistry, ctx: ToolContext,
                               system: str, messages: list[dict], max_rounds: int = 4) -> dict:
    tools = registry.definitions_for(ctx)
    for _ in range(max_rounds):
        resp = await client.messages.create(model="claude-opus-5-5", max_tokens=2048, system=system,
                                            tools=tools, messages=messages)
        if resp.stop_reason != "tool_use":
            return {"status": "answered", "text": "".join(b.text for b in resp.content if b.type == "text")}

        calls = [b for b in resp.content if b.type == "tool_use"]
        reads = [c for c in calls if registry._specs.get(c.name) and registry._specs[c.name].effect is Effect.READ]
        writes = [c for c in calls if c not in reads]

        results: dict[str, dict] = {}
        read_outcomes = await asyncio.gather(*(registry.dispatch(c.name, c.input, ctx, c.id) for c in reads))
        for c, r in zip(reads, read_outcomes, strict=True):
            results[c.id] = {"type": "tool_result", "tool_use_id": c.id, "content": r.content, "is_error": r.is_error}
        pending = []
        for c in writes:                                               # side effects: sequential
            r = await registry.dispatch(c.name, c.input, ctx, c.id)
            results[c.id] = {"type": "tool_result", "tool_use_id": c.id, "content": r.content, "is_error": r.is_error}
            if r.pending_approval_id:
                pending.append(r.pending_approval_id)

        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": [results[c.id] for c in calls]})   # all results, original order
        if pending:
            return {"status": "pending_approval", "proposals": pending}
    return {"status": "max_rounds"}
```

### 7. Comparative Analysis

| Comparison | Key difference | When | Trap |
|---|---|---|---|
| Tool calling vs RAG | Actions/live data vs document knowledge | Tools for systems of record; RAG for docs | RAG over live order status |
| Narrow tools vs generic tools (`run_sql`, `http_get`) | Purpose-built, securable vs flexible, dangerous | Narrow almost always | Generic tools as injection superpowers |
| Strict schemas vs loose | Constrained arguments vs free JSON | Strict + Pydantic validation | Trusting strict mode for business rules |
| Identity in args vs in context | Model-controlled vs verified | Context always | `user_id` argument |
| Read-only vs side-effecting | Safe to retry/parallelize vs needs idempotency/approval | Classify every tool | Retrying refunds |
| Approval vs auto-execute | Human gate vs immediate | Risk-based (Unit 38) | Gating everything → fatigue |
| Parallel vs sequential calls | Throughput vs ordering/safety | Parallel reads; sequential writes | Parallel side effects with dependencies |
| Error observation vs exception | Model can adapt vs loop crashes | Observations for expected failures | Leaking internals in observations |
| Allowlisted queries vs free-form SQL | Safe parameterized vs injection/exfiltration | Allowlisted | "Read-only role is enough" (still exfiltration) |

### 8. Failure Modes and Debugging

**Failure 1 — Model calls the wrong tool or with wrong arguments.**

- CAUSE: vague descriptions, overlapping tools, too many tools, missing examples of IDs.
- INVESTIGATE: tool-selection metrics (calls per tool, validation error rates), eval set with expected tools.
- FIX: clearer names/descriptions, fewer tools per context, stricter schemas, examples in descriptions.

**Failure 2 — Duplicate refund.**

- CAUSE: retried side effect without an idempotency key; the key derived from a timestamp; resume re-ran the tool.
- FIX: deterministic keys (`run_id:tool_use_id`, proposal ID), unique constraints, downstream idempotency keys.

**Failure 3 — Cross-customer data exposure.**

- CAUSE: the tool trusted a model-supplied `customer_id`, no ownership check, tenant filter missing.
- FIX: identity-derived context, ownership checks, tenant in every query, plus "compromised model" tests.

**Failure 4 — 400 "tool_use ids without tool_result".**

- CAUSE: not returning results for all `tool_use` blocks, results split across messages, or the assistant content modified.
- FIX: append the assistant content as returned, and one user message with all results in order.

**Failure 5 — Tool hangs the agent.**

- CAUSE: no timeout on the external API, blocking sync client in async code.
- FIX: per-tool timeouts, async clients, breaker for flaky dependencies.

**Failure 6 — Observation floods context.**

- CAUSE: returning 500 rows or full documents.
- FIX: limits, projections, summaries, truncation markers, pagination tools.

**Failure 7 — SSRF via "fetch URL" tool.**

- CAUSE: the model supplied an internal URL (metadata service `169.254.169.254`).
- FIX: no free-form URLs, allowlisted hosts, IP checks after DNS resolution, no redirects, egress proxy.

### 11. Testing Strategy

- **Per-tool unit tests:** happy path, validation failures, not found, authorization, timeouts (fake slow handler), output bounds.
- **Property tests:** calculator; schema generation round-trip (every `args_model` schema is accepted by your provider-schema sanitizer).
- **HTTP tool tests:** `respx` to mock carrier responses (200/404/500/timeout), and an SSRF test resolving to private IPs.
- **DB tool tests:** Testcontainers; read-only transaction enforced (attempted write fails); statement timeout.
- **Compromised-model tests:** a scripted model emits exactly the attacker's desired tool call, and you assert the controls hold. These are the most important tests for tool safety.
- **Concurrency:** approval execution exactly once with parallel attempts.
- **Evaluation:** tool-selection accuracy and argument correctness on a labelled query set (feeds Unit 35).

### 13. Interview Preparation

#### Quick Questions

**Q: What actually happens in tool calling?**
*Strong answer:* The model returns a structured request (tool name + JSON args). My code validates, authorizes and executes it, then sends the result back as an observation. The model never executes anything itself.

**Q: Tool calling vs RAG?**
*Strong answer:* RAG retrieves unstructured knowledge into context. Tool calling lets the model request queries or actions against systems of record. Different risks, often combined (search as a tool).

**Q: Why not put `user_id` in a tool schema?**
*Strong answer:* The model (and through it, injected content) controls arguments. Identity and permissions must come from the verified request context.

#### Intermediate Questions

**Q: How do you design a good tool schema?**
*Strong answer:* Narrow purpose, clear name and description (when to use, side effects), minimal typed and bounded arguments with enums/patterns, `additionalProperties: false`, no identity fields, concise structured outputs, generated from Pydantic, validated again in code.

**Q: How do you handle tool errors?**
*Strong answer:* Map expected failures to `is_error` observations the model can act on (validation messages, not found, timeout), keep internals out, audit authorization failures without detail to the model, and bound retries for read-only tools only.

**Q: How do you make side-effecting tools safe?**
*Strong answer:* Authorization at the boundary (scope, tenant, ownership, limits), approval gates for high-risk actions, deterministic idempotency keys with unique constraints and downstream keys, timeouts with unknown-outcome handling, sequential execution and audit.

#### Advanced Questions

**Q: A model was prompt-injected into calling `issue_refund` for another customer's order. Walk through why it fails in your design.**
*Strong answer:* `customer_id` comes from the ticket in `ToolContext`. The order lookup is tenant-scoped and its ownership is compared to the context, so the check fails and returns a uniform "not permitted or not found" (audited). Even for the right customer, amount limits and approval apply, and in tainted contexts write tools aren't even advertised.

**Q: How would you support a "database query" tool safely?**
*Strong answer:* Prefer allowlisted parameterized queries chosen by name. If ad hoc queries are required: read-only replica, restricted role + RLS, SQL parsing to reject non-SELECT, statement timeout, row limits, column masking, audit, and human review for sensitive data.

#### Coding Questions

1. Implement a safe arithmetic evaluator with `ast`.
2. Implement `dispatch` with validation, authorization, timeout and error mapping.
3. Implement idempotent proposal creation with `ON CONFLICT` on the idempotency key.

#### Scenario Questions

**Q: The assistant sometimes calls `search_knowledge_base` when it should call `get_order`.**
*Strong answer:* Inspect descriptions and overlap, add disambiguating guidance ("for a specific order's status, use get_order"), evaluate tool selection on labelled queries, and maybe route by intent or reduce the advertised tools.

### 14. Explain-It-at-Three-Levels

**Concept: Tool calling boundary**

- *30 seconds:* The model proposes structured calls, and my code is the gatekeeper: registry lookup, Pydantic validation, authorization from verified identity, approval for risky side effects, idempotent execution with timeouts, and bounded observations back to the model.
- *2 minutes:* The round-trip format, the error-observation table, read vs write, parallel reads and approval proposals.
- *Deep:* Confused-deputy and delegated credentials, unknown outcomes and reconciliation, injection containment via tool advertisement, compromised-model testing, observability and selection evals.

**Concept: Idempotency for tools**

- *30 seconds:* Every side-effecting call gets a deterministic key, the effect is recorded under a unique constraint, and the key goes to downstream APIs, so retries and resumes don't double-act.
- *2 minutes:* Key derivation, unknown outcomes on timeout, and approval-to-execution claims.
- *Deep:* Transaction boundaries vs external calls, sweepers, exactly-once illusions, and interaction with LangGraph resume (Unit 38).

### 15. Knowledge Check

1. What does `stop_reason="tool_use"` require you to do next?
2. Why validate arguments with Pydantic even when using strict tool schemas?
3. Why return uniform "not permitted or not found" responses?
4. Why execute read tools in parallel but write tools sequentially?
5. What's the difference between an approval-pending result and an error?
6. *Code reading:* Why does `definitions_for` hide write tools when `untrusted_content_in_context` is true?
7. *Code reading:* What does `ON CONFLICT (idempotency_key)` achieve in `propose_refund`?
8. *Code reading:* Why does the DB query tool use `SET TRANSACTION READ ONLY` and `statement_timeout`?
9. *Debugging:* The provider returns a 400 about missing tool results. Cause?
10. *Debugging:* Refunds occasionally execute twice after network blips. Where's the bug likely?
11. *Design:* Should the calculator tool exist, or should the model do arithmetic?
12. *Design:* When would you allow automatic execution of a side-effecting tool?

#### Knowledge Check Answers

1. Execute (or deny) every `tool_use` block, append the assistant message as-is, then send one user message containing a `tool_result` for each `tool_use_id`, and call the model again.
2. Strict mode covers a schema subset and guarantees structure, not business validity. Providers differ, and Pydantic enforces bounds, patterns and types consistently in your code.
3. To avoid leaking the existence of other customers' resources and to deny attackers a probing oracle. Details go to audit logs.
4. Reads are safe to run concurrently. Writes may depend on order, need approval, and must not race each other.
5. Pending approval is an expected, successful outcome that pauses the workflow. An error tells the model something failed.
6. Prompt-injection containment: if untrusted content could have manipulated the model, writes shouldn't even be available (or must require approval).
7. A retried or resumed tool call with the same key maps to the same proposal instead of creating duplicates.
8. Defense in depth: even with allowlisted queries, the transaction can't write, and runaway queries are cut off.
9. Not all `tool_use` blocks received results, results were split across messages, or the assistant content wasn't appended as returned.
10. Missing or non-deterministic idempotency keys, the executor not using a conditional claim, or the downstream call not passing the key.
11. Yes for money and exact math: models make arithmetic errors, and a deterministic tool is cheap and verifiable.
12. When the action is low-risk, reversible or bounded (for example drafting, small credits under a ceiling), approval data shows near-100% approval rates, and the risk owner signs off, with monitoring and kill switches.

### 16. Common Interview Traps

- **"The model executes the tool."** Your code does, and your code decides.
- **"Strict mode means args are safe."** Validate and authorize anyway.
- **"Give the agent a SQL tool for flexibility."** That's an injection and exfiltration channel.
- **"Retry on timeout."** Not for side effects without idempotency and status checks.
- **"Approval means safe."** Only if the reviewer sees exact args and provenance, and execution is exactly-once.
- **"Return the full API response to the model."** That costs tokens and adds injection surface. Project and bound the output.
- **"Advertised tools = allowed tools."** Re-authorize every call.

### 17. Cheat Sheet

- **Round trip:** tools[] → `stop_reason=tool_use` → for each `tool_use{id,name,input}`: lookup → validate → authorize → (approve?) → execute (timeout, key) → `tool_result{tool_use_id, content, is_error}` → all results in one user message → repeat (bounded).
- **Schema rules:** narrow, verb_object names, descriptive, Pydantic → JSON Schema, `additionalProperties: false`, bounds/enums/patterns, no identity fields, `strict: true`.
- **ToolContext:** user, tenant, scopes, customer in scope, limits, run_id, taint flag, all from verified identity and records.
- **Errors:** unknown / invalid / not permitted-or-not-found / timeout / temporary, all as observations without internals.
- **Side effects:** idempotency key `run_id:tool_use_id` (or proposal ID), unique constraints, downstream keys, approval proposals, conditional claim on execution, unknown-outcome reconciliation, audit.
- **Security:** no free-form URLs or SQL, SSRF guards, egress allowlist, least-privilege credentials, compromised-model tests.
- **Provider notes:** forced `tool_choice` unsupported on current Claude models (use `auto` + instructions + strict); parallel calls → one results message.
