## Unit 35 — Human-in-the-Loop

### 1. Learning Objectives

By the end of this unit you will be able to:

1. **Explain** where humans belong in agent workflows (approval, escalation, review, exception handling, feedback) and where they do not add value (rubber-stamping low-risk reads).
2. **Design** a deterministic risk-classification function for proposed agent actions using impact, reversibility, external visibility, data sensitivity, amount, provenance (taint) and detector signals.
3. **Compare** automatic execution, execute-with-undo-window, single approval, dual approval (four-eyes) and prohibition, and assign each to concrete actions.
4. **Implement** an approval state machine (`PROPOSED → PENDING_APPROVAL → APPROVED → EXECUTING → EXECUTED/FAILED`, plus `REJECTED`, `EXPIRED`, `CANCELLED`) with persisted transitions, optimistic locking and atomic execution claims.
5. **Implement** argument binding: canonical serialization and hashing so the approved action is exactly the executed action.
6. **Enforce** reviewer authorization, separation of duties (no self-approval, the agent can never approve) and approval expiry.
7. **Implement** re-validation at execution time (state may have changed between approval and execution) and idempotent execution.
8. **Persist** audit evidence — proposal, evidence shown to the reviewer, reviewer decision and rationale, execution outcome, trace id — in an append-only, tamper-evident store.
9. **Integrate** approvals with a pausable/resumable agent run.
10. **Test** approval flows including concurrency (double approval, double execution), expiry, edits and authorization failures with Testcontainers.
11. **Measure** human-in-the-loop health: approval rate, time-to-decision, override/edit rate, queue depth and auto-approval drift.

### 2. Prerequisite Knowledge

- **Units 33–34**: tool gateway, `PolicyDecision.RequireApproval`, typed and validated `ToolRequest`s.
- **JPA and PostgreSQL**: entities, `@Version` optimistic locking, transactions, `SELECT … FOR UPDATE`, conditional `UPDATE … WHERE status = ?`, unique constraints, Flyway migrations.
- **Spring transactions**: `@Transactional` is applied by a proxy; self-invocation bypasses it; default rollback only on unchecked exceptions; `REQUIRES_NEW` for audit writes that must survive rollback.
- **Spring Security method security**: `@PreAuthorize` with SpEL; the principal available as `authentication`.
- **Events/messaging**: transactional outbox and Kafka (or Spring application events) to resume work after a human decision.

**Refresher — optimistic vs pessimistic locking.** Optimistic: each row has a version; an update includes `WHERE version = :expected` and fails (0 rows) if someone else changed it (`OptimisticLockException` in JPA). Pessimistic: `SELECT … FOR UPDATE` locks the row until commit. For approval workflows with rare contention, optimistic locking plus *conditional status updates* is simple and safe.

### 3. Mental Model

Think of an approval as a **signed cheque**, not a conversation. The agent drafts the cheque (payee, amount, memo). A person with signing authority, who is not the drafter, reviews the evidence and signs *that exact cheque*. The bank checks the signature, the amount and that the cheque hasn't expired or already been cashed, then pays it once.

```
agent proposes ToolRequest
   ↓  gateway: validate + authorize + policy
   ↓  RiskClassifier → AUTO | AUTO_WITH_UNDO | APPROVAL(1) | APPROVAL(2) | PROHIBITED
   ├─ AUTO ─────────────────────────────────────────────────────────→ execute → audit
   ├─ AUTO_WITH_UNDO → schedule execution after delay (cancellable) → execute → audit
   ├─ PROHIBITED → deny → audit
   └─ APPROVAL
        ↓ persist ActionProposal(args canonical JSON + SHA-256, evidence, risk reasons, expiry) — status PENDING_APPROVAL
        ↓ agent run PAUSES (state persisted); user told "awaiting approval"
        ↓ reviewer (authorized, ≠ requester) sees proposal + evidence → APPROVE / REJECT / EDIT(→ new version)
        ↓ APPROVED → atomic claim (APPROVED→EXECUTING) → re-validate against current data → execute idempotently
        ↓ EXECUTED / FAILED → audit → event → agent run RESUMES with observation
```

Key invariants:

1. **Execution requires an approval bound to the exact arguments** (hash match).
2. **Only authorized humans approve**; never the requester, never the agent, never a model.
3. **Every transition is persisted and audited**; the state machine, not the chat transcript, is the source of truth.
4. **Execution happens at most once**, and only if the action is still valid at execution time.

### 4. Comprehensive Theory

#### 4.1 Where Humans Belong in Agent Workflows

**Definition.** *Human-in-the-loop (HITL)* means a human must act before the workflow proceeds (approve, choose, provide information). *Human-on-the-loop* means the system acts autonomously while humans monitor and can intervene (dashboards, sampling, kill switches). *Human-out-of-the-loop* is full automation.

**Roles humans play.**

| Role | When | Example |
|---|---|---|
| **Approver** | Before a high-risk action | Approve a $400 refund |
| **Disambiguator** | Request is ambiguous | "Which of your two orders?" (often the end user) |
| **Exception handler** | Agent cannot proceed or fails closed (Unit 34) | Escalation queue |
| **Editor** | Agent drafts, human finalizes | Email draft edited before sending |
| **Auditor/sampler** | After the fact for low-risk automation | Review 2% of auto-approved refunds weekly |
| **Labeler** | Feedback for evaluation | Mark answers correct/incorrect (Unit 36) |

**Why not approve everything?** Approval costs time and money, and humans who approve hundreds of trivial items stop reading them (*approval fatigue*, *automation bias*). A gate that is always approved provides little protection while creating a false sense of safety. Approval should be **risk-proportionate** and **reviewable** (reviewers see what matters).

**FDE lens.** Stakeholders often say "human in the loop" meaning very different things: a compliance requirement (four-eyes for payments), a trust-building phase (approve everything for 30 days, then relax), or a UX preference (let users confirm). Clarify which, because they lead to different designs and metrics.

#### 4.2 Risk Classification

**Definition.** A risk classifier maps a *validated, authorized* proposed action plus context to a handling tier. It must be **deterministic** and **explainable** (reasons listed), and it must run in code, not in the model.

**Risk factors.**

| Factor | Low risk | High risk |
|---|---|---|
| Reversibility | Can undo (draft, reversible status change) | Irreversible (payment, deletion, sent email) |
| External visibility | Internal only | Customer- or public-facing |
| Financial impact | ≤ threshold | > threshold, or cumulative per customer/day above limit |
| Data sensitivity | Non-personal | Personal/special-category data, bulk data |
| Scope | Single record | Bulk (many customers) |
| Provenance | Arguments from trusted context | Arguments derived from untrusted content (taint) |
| Signals | No detector hits | Injection detector hit, anomaly, new payee/recipient |
| Actor context | Experienced staff, normal hours | New account, unusual location/time |
| Regulatory | None | GDPR erasure, financial regulation |

**Tiers.**

| Tier | Handling | Examples |
|---|---|---|
| `AUTO` | Execute immediately; audit | `get_order`, `search_policies` |
| `AUTO_WITH_UNDO` | Delay execution N seconds/minutes; user/staff can cancel; then execute | Low-value status updates; templated shipping notification |
| `APPROVAL_SINGLE` | One authorized reviewer | Refund $50–$500; address change; email to customer |
| `APPROVAL_DUAL` | Two distinct reviewers (four-eyes) | Refund > $500; bulk email |
| `PROHIBITED` | Never via agent | Changing bank details; deleting audit logs |

`delete_customer_data` is typically `APPROVAL_SINGLE` by the privacy office with identity verification evidence, and is executed by a dedicated deletion workflow, never by the chat agent directly.

**Policy as data.** Encode thresholds and rules in configuration or a policy engine (e.g., Open Policy Agent / Cedar) so risk owners can review and change them with change control, and tests can assert the matrix.

**Escalation only increases.** Signals may *raise* a tier (taint → approval) but nothing the model says can lower it.

#### 4.3 Approval Gates and the Approval State Machine

**Definition.** An *approval gate* blocks execution until an approval record exists that satisfies the policy. The *approval state machine* defines legal states and transitions.

```
            create
              │
              ▼
        ┌─────────────────┐   reject     ┌──────────┐
        │PENDING_APPROVAL │─────────────▶│ REJECTED │
        └─────────────────┘              └──────────┘
          │    │   │ expire (timer)      ┌──────────┐
          │    │   └────────────────────▶│ EXPIRED  │◀─── (APPROVED not executed in window)
          │    │ cancel (requester/system)┌──────────┐
          │    └────────────────────────▶│CANCELLED │
          │ approve (count reached)      └──────────┘
          ▼
     ┌──────────┐ claim (atomic) ┌───────────┐ success ┌──────────┐
     │ APPROVED │──────────────▶│ EXECUTING │────────▶│ EXECUTED │
     └──────────┘               └───────────┘         └──────────┘
                                      │ failure / re-validation failed
                                      ▼
                                 ┌──────────┐
                                 │  FAILED  │
                                 └──────────┘
```

**Transition rules.**

- Only `PENDING_APPROVAL` can be approved/rejected/cancelled/expired.
- `APPROVE` by a reviewer adds an approval record; when the required count of *distinct* qualified reviewers is reached, status becomes `APPROVED`.
- `REJECT` by any qualified reviewer is final (reason required).
- **Edit**: reviewers may not mutate a proposal in place. An edit creates a *new* proposal version (new arguments, new hash) linked to the old one, which becomes `CANCELLED` (superseded). This keeps audit honest: what was proposed vs what was approved.
- `APPROVED → EXECUTING` is an atomic claim (conditional update) so only one executor proceeds.
- Expiry: pending approvals expire (e.g., 24 h); approved-but-unexecuted approvals expire (e.g., 15 min) because context goes stale.

**Why a state machine and not booleans.** `approved = true` columns invite illegal combinations (approved and rejected, executed twice) and lose history. Explicit states plus a transition table make illegal transitions impossible and testable.

#### 4.4 Argument Binding

**Problem.** If the approval references "refund for order A-1001" but the executor reads arguments from somewhere else (the agent's latest message, a re-parsed JSON), the reviewer may approve one thing while another executes — through bugs, parser differentials (Unit 34) or an attacker modifying the pending payload.

**Solution.** At proposal time:

1. Validate and parse arguments into the tool's typed record.
2. Serialize to **canonical JSON** (sorted keys, normalized numbers — e.g., `BigDecimal.stripTrailingZeros().toPlainString()` — no insignificant whitespace).
3. Compute `SHA-256(toolName + "\n" + canonicalArgs + "\n" + tenantId + "\n" + targetResourceId)`.
4. Store canonical args and hash; render the review UI *from the stored canonical record*.
5. The approval record stores the hash it approved.
6. At execution: re-hash the stored args; compare with the approved hash; parse from the stored canonical args; execute.

Optionally sign the hash (HMAC with a key held by the approval service) so a database-level modification is detectable.

#### 4.5 Reviewer Authorization and Separation of Duties

- **Qualified reviewer:** has the required role/authority for this action type and tier (e.g., `REFUND_APPROVER_L2` for > $500) and belongs to the same tenant.
- **Separation of duties:** reviewer ≠ requester (the staff user on whose behalf the agent proposed it); for dual approval, two distinct reviewers.
- **The agent is never a reviewer.** No tool exists that approves; the approval API requires a human user token with reviewer scopes; service accounts cannot call it.
- **Step-up authentication** for critical approvals (re-authenticate / MFA via OIDC `acr`/`max_age` checks).
- **Conflict of interest rules** where needed (reviewer isn't the customer).

#### 4.6 Re-validation at Execution Time and Idempotent Execution

Between approval and execution, the world changes: the order may have been refunded by another channel, the customer may have closed their account, the reviewer's role may have been revoked. Therefore execution **re-runs** the gateway's authorization and business policy (Unit 33) against current data, with the approval as an additional input. If re-validation fails → `FAILED` with reason, notify.

Execution must be idempotent: the proposal id (or a derived key) is the idempotency key sent to the downstream service (payments provider idempotency keys, unique constraints). If the executor crashes after the payment succeeded but before marking `EXECUTED`, a retry with the same key returns the original result rather than paying twice. A reaper job handles proposals stuck in `EXECUTING` by querying the downstream system with the idempotency key.

#### 4.7 Low-Risk Automatic Execution vs High-Risk Human Review

The goal is **maximum safe autonomy**: automate what is low-risk and well-evaluated, gate what is not, and move actions between tiers based on *evidence*:

- **Start conservative** in a new deployment (more approvals), collect data: approval rate, edit rate, rejection reasons.
- If a class of actions is approved > 99% without edits over a significant sample and incident-free, consider lowering its tier (with risk-owner sign-off).
- If rejections or edits are frequent, improve the agent (prompts, retrieval, tools) before considering automation.
- **Undo windows** (send email after 60 s, cancellable) give much of the safety of approval with less friction for reversible-in-window actions.
- **Post-hoc sampling** of auto-executed actions catches drift.

#### 4.8 Auditability and Audit Evidence

**What to persist.**

| Record | Contents |
|---|---|
| Proposal | id, version, run id, trace id, tenant, requester (user), agent profile, model id, prompt/template versions, tool name, canonical args, args hash, risk tier and reasons, evidence references (retrieved doc ids, tool observations ids), model rationale (labeled as model-generated), created/expiry timestamps |
| Review snapshot | exactly what the reviewer was shown (rendered fields), so later disputes can be resolved |
| Decision | reviewer id, decision (APPROVE/REJECT), reason/comment, timestamp, authentication context (MFA level), client info |
| Execution | claim time, executor instance, idempotency key, downstream result id/status, re-validation outcome, error |
| Audit chain | append-only event log for every transition with `prev_hash` → hash chain for tamper evidence |

**Properties.** Append-only (DB permissions: no `UPDATE`/`DELETE` for the application role on the audit table); time-ordered; correlated with traces; retention policy aligned with legal requirements; PII minimized (references instead of copies where possible) and access-controlled. For high-assurance needs, ship audit events to WORM storage (e.g., S3 Object Lock).

**Audit vs logs vs traces.** Logs are for debugging and may be sampled/dropped; traces are for performance and flow; audit is a *business record* with integrity and retention guarantees. Don't use logs as your audit trail.

#### 4.9 Pausing and Resuming Agent Runs

When an action requires approval, the run must stop consuming resources and resume later — possibly hours later, on a different instance. That requires **durable run state**: conversation/messages, decisions, observations, pending proposal ids, budgets used. Persist it (PostgreSQL JSONB or a dedicated table) and resume on an event:

```
ApprovalService (tx): status → APPROVED; write outbox(ProposalApproved)
Outbox relay ⇢ Kafka topic approvals.events
ExecutionWorker: claim → execute → status EXECUTED; outbox(ProposalExecuted)
AgentResumeWorker: load run state → append observation "issue_refund executed: R-88" → continue loop (budgets intact)
```

If the user is waiting in a chat UI, notify them via WebSocket/SSE or let the UI poll the run status. Frameworks with built-in interrupts (e.g., LangGraph-style checkpointers; LangGraph4j for Java) implement the same idea; MCP's *elicitation* feature lets a server request input from the user mid-operation — useful for clarification, but approvals with authority checks and audit should remain in your approval service.

### 5. Internal Mechanics

#### 5.1 Concurrency: what happens when two reviewers click "Approve" at the same time

```
Reviewer A tx                                Reviewer B tx
SELECT proposal (version=3, PENDING)         SELECT proposal (version=3, PENDING)
INSERT approval(A)                           INSERT approval(B)
UPDATE proposal SET status=APPROVED,         UPDATE proposal SET status=APPROVED,
   version=4 WHERE id=? AND version=3           version=4 WHERE id=? AND version=3
→ 1 row, COMMIT                              → 0 rows → OptimisticLockException → ROLLBACK
```

Hibernate generates the `version` predicate for `@Version` entities and throws on zero rows. For single-approval tiers the second reviewer gets "already decided". A unique constraint `(proposal_id, reviewer_id)` prevents the same reviewer from counting twice under dual approval.

#### 5.2 The atomic execution claim

```sql
UPDATE action_proposal
   SET status = 'EXECUTING', claimed_by = :instance, claimed_at = now()
 WHERE id = :id AND status = 'APPROVED' AND approved_until > now();
```

PostgreSQL row locking ensures that if two executors run this concurrently, the second blocks on the row lock until the first commits, then re-evaluates the `WHERE` against the *new* row version (under READ COMMITTED) and updates 0 rows. Only the executor that gets `1` proceeds. This is simpler and more robust than distributed locks.

#### 5.3 Transactions and the proxy pitfall

`ApprovalService.approve()` annotated `@Transactional` runs inside a transaction only when called through the Spring proxy. If another method in the same class calls `this.approve()`, no transaction is started (self-invocation). Keep transactional entry points on separate beans or call through the injected proxy. Audit writes that must persist even if the business transaction rolls back (e.g., a *rejected attempt* to approve one's own proposal) go through a `REQUIRES_NEW` method on a different bean.

#### 5.4 Clock and expiry

Use an injected `java.time.Clock` (testable) and store `timestamptz`. Expiry is enforced *both* by a scheduled sweeper (for UX/notifications) *and* in the transition predicates (`approved_until > now()`), so a late sweeper can never allow execution of an expired approval. In a cluster, schedule the sweeper with a lock (ShedLock) or make it idempotent via conditional updates (it is, with the predicate form).

### 6. Implementation Examples

#### Example 1 — Minimal: deterministic risk classifier

```java
package com.acme.support.approval;

import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public final class RiskClassifier {

    public enum Tier { AUTO, AUTO_WITH_UNDO, APPROVAL_SINGLE, APPROVAL_DUAL, PROHIBITED }

    public record ProposedAction(String toolName, BigDecimal amount, boolean externalCommunication,
                                 boolean irreversible, boolean touchesPersonalData,
                                 boolean argumentsTainted, boolean injectionSignal) { }

    public record RiskAssessment(Tier tier, List<String> reasons) { }

    private final BigDecimal singleApprovalThreshold;
    private final BigDecimal dualApprovalThreshold;

    public RiskClassifier(BigDecimal singleApprovalThreshold, BigDecimal dualApprovalThreshold) {
        this.singleApprovalThreshold = singleApprovalThreshold;
        this.dualApprovalThreshold = dualApprovalThreshold;
    }

    public RiskAssessment assess(ProposedAction a) {
        List<String> reasons = new ArrayList<>();
        Tier tier = switch (a.toolName()) {
            case "get_order", "search_policies" -> Tier.AUTO;
            case "update_address" -> { reasons.add("modifies customer data"); yield Tier.APPROVAL_SINGLE; }
            case "send_email" -> { reasons.add("external communication"); yield Tier.APPROVAL_SINGLE; }
            case "delete_customer_data" -> { reasons.add("irreversible deletion of personal data"); yield Tier.APPROVAL_SINGLE; }
            case "issue_refund" -> refundTier(a.amount(), reasons);
            default -> { reasons.add("unknown action"); yield Tier.PROHIBITED; }
        };
        // Signals can only raise the tier, never lower it.
        if (a.argumentsTainted() && tier.compareTo(Tier.APPROVAL_SINGLE) < 0) {
            reasons.add("arguments derived from untrusted content");
            tier = Tier.APPROVAL_SINGLE;
        }
        if (a.injectionSignal() && tier.compareTo(Tier.APPROVAL_SINGLE) < 0 && tier != Tier.AUTO) {
            reasons.add("prompt-injection signal in this run");
            tier = Tier.APPROVAL_SINGLE;
        }
        return new RiskAssessment(tier, List.copyOf(reasons));
    }

    private Tier refundTier(BigDecimal amount, List<String> reasons) {
        if (amount == null) { reasons.add("missing amount"); return Tier.PROHIBITED; }
        if (amount.compareTo(dualApprovalThreshold) > 0) { reasons.add("refund above " + dualApprovalThreshold); return Tier.APPROVAL_DUAL; }
        if (amount.compareTo(singleApprovalThreshold) > 0) { reasons.add("refund above " + singleApprovalThreshold); return Tier.APPROVAL_SINGLE; }
        reasons.add("low-value refund");
        return Tier.AUTO;
    }
}
```

The enum order (`AUTO` < `AUTO_WITH_UNDO` < `APPROVAL_SINGLE` < …) lets `compareTo` express "raise to at least". A parameterized test asserts the whole matrix (Section 11). Read-only tools stay `AUTO` even with injection signals, because reading within the principal's scope is already authorized — the signal affects *write* tools.

package com.acme.support.approval;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;
import org.hibernate.annotations.JdbcTypeCode;
import org.hibernate.type.SqlTypes;

import java.time.Instant;
import java.util.List;
import java.util.UUID;

@Entity
@Table(name = "action_proposal")
public class ActionProposal {

    public enum Status { PENDING_APPROVAL, APPROVED, EXECUTING, EXECUTED, FAILED, REJECTED, EXPIRED, CANCELLED }

    @Id private UUID id;
    @Version private long version;
    private String tenantId;
    private UUID runId;
    private String traceId;
    private String requestedBy;
    private String toolName;
    @JdbcTypeCode(SqlTypes.JSON) @Column(columnDefinition = "jsonb") private String canonicalArgs;
    private String argsHash;
    private String targetRef;
    private String riskTier;
    @JdbcTypeCode(SqlTypes.JSON) @Column(columnDefinition = "jsonb") private List<String> riskReasons;
    @JdbcTypeCode(SqlTypes.JSON) @Column(columnDefinition = "jsonb") private String evidence;
    private short requiredApprovals;
    @Enumerated(EnumType.STRING) private Status status;
    private UUID supersedesId;
    private Instant createdAt;
    private Instant pendingUntil;
    private Instant approvedUntil;
    private Instant executedAt;
    private String resultRef;
    private String failureReason;

    protected ActionProposal() { }   // JPA

    public static ActionProposal create(UUID runId, String traceId, String tenantId, String requestedBy,
                                        String toolName, String canonicalArgs, String argsHash, String targetRef,
                                        String riskTier, List<String> reasons, String evidence,
                                        int requiredApprovals, Instant now, Instant pendingUntil) {
        var p = new ActionProposal();
        p.id = UUID.randomUUID();
        p.runId = runId; p.traceId = traceId; p.tenantId = tenantId; p.requestedBy = requestedBy;
        p.toolName = toolName; p.canonicalArgs = canonicalArgs; p.argsHash = argsHash; p.targetRef = targetRef;
        p.riskTier = riskTier; p.riskReasons = List.copyOf(reasons); p.evidence = evidence;
        p.requiredApprovals = (short) requiredApprovals;
        p.status = Status.PENDING_APPROVAL; p.createdAt = now; p.pendingUntil = pendingUntil;
        return p;
    }

    /** Called after an APPROVE decision row was inserted; approvalsSoFar includes it. */
    void recordApproval(long approvalsSoFar, Instant now, Instant approvedUntil) {
        requirePending(now);
        if (approvalsSoFar >= requiredApprovals) {
            this.status = Status.APPROVED;
            this.approvedUntil = approvedUntil;
        }
    }

    void reject(Instant now) { requirePending(now); this.status = Status.REJECTED; }

    void cancel(Instant now) { requirePending(now); this.status = Status.CANCELLED; }

    void markExecuted(String resultRef, Instant now) {
        requireStatus(Status.EXECUTING);
        this.status = Status.EXECUTED; this.resultRef = resultRef; this.executedAt = now;
    }

    void markFailed(String reason) {
        requireStatus(Status.EXECUTING);
        this.status = Status.FAILED; this.failureReason = reason;
    }

    private void requirePending(Instant now) {
        requireStatus(Status.PENDING_APPROVAL);
        if (!now.isBefore(pendingUntil)) {
            throw new IllegalProposalTransitionException("proposal expired");
        }
    }

    private void requireStatus(Status expected) {
        if (status != expected) {
            throw new IllegalProposalTransitionException("expected " + expected + " but was " + status);
        }
    }

    public UUID id() { return id; }
    public String tenantId() { return tenantId; }
    public UUID runId() { return runId; }
    public String requestedBy() { return requestedBy; }
    public String toolName() { return toolName; }
    public String canonicalArgs() { return canonicalArgs; }
    public String argsHash() { return argsHash; }
    public String targetRef() { return targetRef; }
    public String riskTier() { return riskTier; }
    public Status status() { return status; }
    public String traceId() { return traceId; }
}

**Canonical arguments and hash.**

```java
package com.acme.support.approval;

import org.springframework.stereotype.Component;
import tools.jackson.databind.JsonNode;
import tools.jackson.databind.SerializationFeature;
import tools.jackson.databind.cfg.JsonNodeFeature;
import tools.jackson.databind.json.JsonMapper;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HexFormat;

@Component
public class ArgumentBinder {

    private final JsonMapper canonical = JsonMapper.builder()
            .enable(SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS)
            .enable(JsonNodeFeature.WRITE_PROPERTIES_SORTED)
            .build();

    public record Bound(String canonicalJson, String hash) { }

    /** typedArgs is the tool's validated argument record (Unit 34 stage two). */
    public Bound bind(String toolName, Record typedArgs, String tenantId, String targetRef) {
        JsonNode tree = canonical.valueToTree(typedArgs);      // BigDecimal written as number; record components sorted
        String json = canonical.writeValueAsString(tree);
        return new Bound(json, sha256(toolName + "\n" + json + "\n" + tenantId + "\n" + targetRef));
    }

    public boolean verify(ActionProposal p) {
        return sha256(p.toolName() + "\n" + p.canonicalArgs() + "\n" + p.tenantId() + "\n" + p.targetRef())
                .equals(p.argsHash());
    }

    private static String sha256(String s) {
        try {
            return HexFormat.of().formatHex(MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8)));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
```

> **Caveat on canonical JSON.** Sorting keys is not full canonicalization: number formatting (`10.0` vs `10.00`) and Unicode normalization also matter. Normalize `BigDecimal` values in the argument records (e.g., `setScale(2)` in a compact constructor) before binding, and store the canonical string exactly as hashed — PostgreSQL `jsonb` *reformats* JSON, so verify against the stored text in a `text` column (or re-canonicalize on read) rather than the `jsonb` rendering. RFC 8785 (JSON Canonicalization Scheme) specifies a full scheme if you need cross-language verification.

Given that caveat, store `canonical_args` as `TEXT` for hashing and an optional `JSONB` copy for querying. (The schema above uses JSONB for brevity; change it to `TEXT` in your project — Exercise 4.1 asks you to find this.)

@Service
public class ApprovalService {

    private final ActionProposalRepository proposals;
    private final ApprovalDecisionRepository decisions;
    private final ReviewerPolicy reviewerPolicy;
    private final ArgumentBinder binder;
    private final AuditService audit;
    private final OutboxPublisher outbox;
    private final Clock clock;

    public ApprovalService(ActionProposalRepository proposals, ApprovalDecisionRepository decisions,
                           ReviewerPolicy reviewerPolicy, ArgumentBinder binder, AuditService audit,
                           OutboxPublisher outbox, Clock clock) {
        this.proposals = proposals; this.decisions = decisions; this.reviewerPolicy = reviewerPolicy;
        this.binder = binder; this.audit = audit; this.outbox = outbox; this.clock = clock;
    }

    @Transactional
    @PreAuthorize("hasAuthority('SCOPE_approvals:decide')")
    public ActionProposal.Status approve(UUID proposalId, Reviewer reviewer, String shownHash, String comment) {
        Instant now = clock.instant();
        ActionProposal p = proposals.findByIdAndTenantId(proposalId, reviewer.tenantId())
                .orElseThrow(() -> new ProposalNotFoundException(proposalId));

        reviewerPolicy.requireQualified(reviewer, p);                       // role for tier, not requester, step-up auth
        if (!p.argsHash().equals(shownHash) || !binder.verify(p)) {
            audit.recordRejectedAttempt(p, reviewer, "hash_mismatch");      // REQUIRES_NEW on another bean
            throw new StaleProposalException("The proposal changed since it was displayed. Reload and review again.");
        }
        decisions.save(ApprovalDecision.approve(p.id(), reviewer, shownHash, comment, now));
        long approvals = decisions.countByProposalIdAndDecision(p.id(), ApprovalDecision.Decision.APPROVE);
        p.recordApproval(approvals, now, now.plus(Duration.ofMinutes(15)));
        audit.append(p, "PROPOSAL_APPROVAL_RECORDED", reviewer.userId());
        if (p.status() == ActionProposal.Status.APPROVED) {
            outbox.publish("approvals.events", p.id().toString(), new ProposalApproved(p.id(), p.runId(), p.traceId()));
        }
        return p.status();   // version increment + optimistic-lock check happen at flush/commit
    }

    @Transactional
    @PreAuthorize("hasAuthority('SCOPE_approvals:decide')")
    public void reject(UUID proposalId, Reviewer reviewer, String reason) {
        if (reason == null || reason.isBlank()) throw new IllegalArgumentException("A rejection reason is required.");
        Instant now = clock.instant();
        ActionProposal p = proposals.findByIdAndTenantId(proposalId, reviewer.tenantId())
                .orElseThrow(() -> new ProposalNotFoundException(proposalId));
        reviewerPolicy.requireQualified(reviewer, p);
        decisions.save(ApprovalDecision.reject(p.id(), reviewer, p.argsHash(), reason, now));
        p.reject(now);
        audit.append(p, "PROPOSAL_REJECTED", reviewer.userId());
        outbox.publish("approvals.events", p.id().toString(), new ProposalRejected(p.id(), p.runId(), reason));
    }
}

    private static final Map<String, String> REQUIRED_ROLE_BY_TIER = Map.of(

**Executor** — consumes `ProposalApproved` events (Kafka) or is invoked directly:

```java
package com.acme.support.approval;

import com.acme.support.audit.AuditService;
import com.acme.support.tools.ToolExecutionPort;
import com.acme.support.tools.ToolResult;
import org.springframework.stereotype.Service;
import org.springframework.transaction.support.TransactionTemplate;

import java.time.Clock;
import java.util.UUID;

@Service
public class ProposalExecutor {

    private final ActionProposalRepository proposals;
    private final ArgumentBinder binder;
    private final ToolExecutionPort tools;        // re-runs gateway checks, then executes with idempotency key
    private final AuditService audit;
    private final OutboxPublisher outbox;
    private final TransactionTemplate tx;
    private final Clock clock;

    public ProposalExecutor(ActionProposalRepository proposals, ArgumentBinder binder, ToolExecutionPort tools,
                            AuditService audit, OutboxPublisher outbox, TransactionTemplate tx, Clock clock) {
        this.proposals = proposals; this.binder = binder; this.tools = tools; this.audit = audit;
        this.outbox = outbox; this.tx = tx; this.clock = clock;
    }

    public void execute(UUID proposalId) {
        // 1. Claim atomically in a short transaction. Only one executor wins.
        Boolean claimed = tx.execute(s -> proposals.claimForExecution(proposalId, clock.instant()) == 1);
        if (!Boolean.TRUE.equals(claimed)) {
            return;   // already executing/executed, expired or not approved: duplicate event, safe to ignore
        }
        ActionProposal p = tx.execute(s -> proposals.findById(proposalId).orElseThrow());

        // 2. Verify binding, re-validate against CURRENT data, execute idempotently. No DB tx held during the remote call.
        ToolResult result;
        if (!binder.verify(p)) {
            result = new ToolResult.Failed("Integrity check failed.");
        } else {
            result = tools.executeApproved(p.tenantId(), p.requestedBy(), p.toolName(), p.canonicalArgs(),
                    /* idempotencyKey */ "proposal:" + p.id());
        }

        // 3. Record the outcome.
        tx.executeWithoutResult(s -> {
            ActionProposal fresh = proposals.findById(proposalId).orElseThrow();
            switch (result) {
                case ToolResult.Success ok -> fresh.markExecuted(String.valueOf(ok.value()), clock.instant());
                case ToolResult.Denied d -> fresh.markFailed("revalidation_denied:" + d.code());
                case ToolResult.Invalid i -> fresh.markFailed("invalid_args");
                case ToolResult.Failed f -> fresh.markFailed(f.safeMessage());
                case ToolResult.PendingApproval pa -> fresh.markFailed("unexpected_pending");
            }
            audit.append(fresh, "PROPOSAL_" + fresh.status(), "system:executor");
            outbox.publish("approvals.events", fresh.id().toString(),
                    new ProposalFinished(fresh.id(), fresh.runId(), fresh.status().name()));
        });
    }
}
```

**Why three short transactions.** Holding a database transaction (and connection) open during a remote payment call ties up pool connections and risks long locks. The claim makes the proposal `EXECUTING` durably; if the process crashes during the remote call, a **reaper** finds proposals `EXECUTING` for longer than a threshold and asks the payments system "did idempotency key `proposal:<id>` succeed?" to complete or fail them.

**Tamper-evident audit chain.**

```java
package com.acme.support.audit;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AuditChainWriter {

    private final AuditEventRepository events;
    private final HashFunction hash;     // SHA-256 over prev_hash + canonical event JSON

    public AuditChainWriter(AuditEventRepository events, HashFunction hash) {
        this.events = events; this.hash = hash;
    }

    /** Serialize writers per tenant with an advisory lock so the chain is linear. */
    @Transactional(propagation = Propagation.MANDATORY)
    public void append(AuditEventDraft draft) {
        events.lockChain(draft.tenantId());   // SELECT pg_advisory_xact_lock(hashtext(:tenantId))
        String prev = events.lastHash(draft.tenantId()).orElse("0".repeat(64));
        String h = hash.sha256(prev + draft.canonicalJson());
        events.insert(draft, prev, h);
    }
}
```

A verification job recomputes the chain and alerts on any break. Use `MANDATORY` so audit rows commit atomically with the state change they describe; for *attempt* records that must survive rollback, a separate `REQUIRES_NEW` method on another bean writes them.

### 7. Comparative Analysis

| Option | What it is | Use when | Trade-offs | Trap |
|---|---|---|---|---|
| Auto-execute | No human before action | Read-only, low-value, reversible, well-evaluated | Fast, cheap; relies on evals and monitoring | Automating irreversible actions because "accuracy is 98%" |
| Execute with undo window | Delay + cancel | Actions reversible within a window (scheduled email) | Good UX; needs a scheduler and clear notifications | Window too short to be useful |
| Single approval | One qualified reviewer | Moderate risk | Latency (minutes–hours), reviewer cost | Approval fatigue → rubber-stamping |
| Dual approval (four-eyes) | Two distinct reviewers | High value, regulated | Slower; needs staffing | Same person with two accounts; no distinctness check |
| Prohibited | Agent can't do it | Unacceptable risk | Less capability | Leaving prohibited tools registered "just in case" |
| Chat confirmation | Model asks user "OK?" | UX clarification only | Not a control: unbound, model-mediated | Calling it HITL |
| HITL vs human-on-the-loop | Gate before vs monitoring during/after | HITL for high-risk; on-the-loop for scaled low-risk | On-the-loop needs good observability and kill switches | Thinking dashboards are approvals |
| Approval in agent framework vs approval service | Framework interrupt vs your domain service | Framework interrupts for pausing; domain service for authority, binding, audit | Frameworks rarely model reviewer authorization or audit | Treating `interrupt()` as the approval control |

### 8. Failure Modes and Debugging

**F1 — Double refund after approval.**
SYMPTOM: Two refunds for one approved proposal.
↓ CAUSE: Two consumers processed the duplicate `ProposalApproved` Kafka event (at-least-once delivery); execution used `findById` + check `status == APPROVED` in Java (check-then-act race) and no downstream idempotency key.
↓ INVESTIGATE: Audit chain shows two `EXECUTED` transitions? Payment provider shows two ids? Trace shows two `execute_tool` spans with different consumer instances.
↓ FIX: Conditional-update claim; idempotency key `proposal:<id>`; unique constraint on refunds by proposal id.
↓ PREVENT: Concurrency integration test; consumer idempotency.

**F2 — Reviewer approved a different amount than was executed.**
SYMPTOM: Dispute: reviewer swears they approved $50; payment was $500.
↓ CAUSE: UI rendered from the agent's chat message; executor used stored args. Or args edited in DB.
↓ INVESTIGATE: Compare review snapshot, approved hash, stored canonical args, executed args.
↓ FIX: Render from stored canonical args; hash check on approve and execute; review snapshot persisted.
↓ PREVENT: Hash-mismatch tests; HMAC-signed hashes; DB permissions.

**F3 — Approvals pile up; users abandon chats.**
SYMPTOM: Queue depth grows; median time-to-decision 6 h; 40% of pending approvals expire.
↓ CAUSE: Thresholds too conservative; no routing; no notifications; staffing mismatch.
↓ INVESTIGATE: Approval metrics by tool/tier; approve-without-edit rates.
↓ FIX: Route by skill/tenant, notify (Slack/email), SLAs, undo windows for reversible actions, raise thresholds with risk-owner approval where evidence supports.
↓ PREVENT: Dashboards and alerts on queue depth and age.

**F4 — Rubber-stamping.**
SYMPTOM: Median review time 2 s; 99.9% approval; an injected refund was approved.
↓ FIX: Show risk reasons and evidence prominently; require reason for high tier; randomized "attention checks" or seeded test proposals; reduce volume by automating truly low-risk actions; dual approval for high value.
↓ PREVENT: Monitor time-on-proposal and approval rates per reviewer.

**F5 — Stuck in `EXECUTING`.**
SYMPTOM: Proposals remain `EXECUTING` for hours.
↓ CAUSE: Executor crashed mid-call; no reaper.
↓ FIX: Reaper reconciles with downstream by idempotency key.
↓ PREVENT: Alert on age of `EXECUTING`.

**F6 — Hash mismatch on every approval after deploy.**
SYMPTOM: All approvals fail with `StaleProposalException`.
↓ CAUSE: Canonical args stored as JSONB (reformatted by PostgreSQL) and re-hashed from the JSONB text; or serializer config changed number formatting.
↓ FIX: Store hashed canonical text verbatim; version the canonicalization; migrate.
↓ PREVENT: Round-trip test through the database.

- [ ] Requester and agent/service accounts can never approve (tested).
- [ ] Execution is exactly-once in tests under concurrency and duplicate events.
- [ ] Expired approvals never execute.
- [ ] Every transition has an audit event; tampering is detected.

### 11. Testing Strategy

- **Unit:** classifier matrix (parameterized from CSV owned with the risk owner); state transitions (every legal and illegal transition); binder canonicalization (key order, BigDecimal scale).
- **Integration (Testcontainers PostgreSQL):** optimistic locking, conditional claims, JSON storage, expiry predicates, DB permission on audit table.
- **Concurrency:** latch-synchronized threads for approve/approve, approve/reject, execute/execute, cancel/execute.
- **Security:** SoD, cross-tenant 404, unqualified 403, service account denied, missing MFA for dual tier.
- **Failure injection:** downstream timeout after success; executor crash; duplicate events; clock skew.
- **End-to-end:** agent proposes → reviewer approves via API → execution → run resumes → final answer cites refund id.
- **Evaluation hooks (Unit 36):** track how often the agent proposes actions that reviewers reject or edit — a quality metric for the agent.

### 12. Engineering Scenarios

**Scenario 1 — FDE: "We want humans to approve everything."** A bank pilot's compliance lead requires approval for every agent action, including reads.
*Questions.* What's the underlying requirement? What will happen operationally? What's the alternative?
*Expected reasoning.* Clarify: is it a regulation (which one?), a pilot trust phase, or fear of data exposure? Approving reads adds latency without reducing risk if reads are already authorization-scoped; approval fatigue will degrade review quality for real risks. Propose: approvals for all writes and external communications during the pilot; reads auto-executed but fully audited and sampled; weekly evidence review; criteria to relax tiers. Demonstrate with audit samples and eval data.

**Scenario 2 — Approval latency kills a use case.** Address changes require approval, but orders ship within 2 hours, so approvals often arrive too late.
*Expected reasoning.* Options: auto-approve address changes within same city/postcode with verified customer identity; undo window; priority routing with SLA; allow customer self-service in the authenticated portal (deterministic, no agent). Choose based on fraud data (address-change fraud is a known pattern).

**Scenario 3 — Reviewer edits are frequent.** 30% of email drafts are edited before approval.
*Expected reasoning.* That's an agent quality signal: analyze edit diffs; improve templates/prompts; use edited versions as eval references; don't automate until the edit rate falls.

**Scenario 4 — Regulatory deletion request.** A GDPR erasure request arrives through the chat.
*Expected reasoning.* The agent should collect the request and create a proposal for the privacy workflow (identity verification, legal holds, systems inventory), not delete data itself. The approval is by the privacy officer; execution is a deterministic, audited workflow across systems; the audit trail itself retains minimal necessary evidence.

### 13. Interview Preparation

#### Quick Questions

**Q: Where do humans belong in an agent workflow?**
*Strong answer:* Before high-risk, irreversible, external or regulated actions (approval); when requirements are ambiguous (clarification); when the agent fails closed (exception handling); after the fact for sampled low-risk automation (audit); and as labelers for evaluation. Not as rubber stamps for low-risk reads.

**Q: Why isn't "the agent asks the user to confirm" a real approval gate?**
*Strong answer:* It's mediated by the model, not bound to arguments, not authorization-checked and not persisted; injection can skip or fake it. A real gate is a persisted state transition by an authorized human on the exact hashed arguments.

**Q: What audit evidence do you store?**
*Strong answer:* The proposal with canonical args and hash, risk reasons, evidence references and model/prompt versions; what the reviewer saw; reviewer identity, decision, reason and auth context; execution result and idempotency key; all transitions in an append-only, hash-chained log correlated with trace ids.

#### Intermediate Questions

**Q: Design an approval state machine.**
*Strong answer:* States PENDING_APPROVAL, APPROVED, EXECUTING, EXECUTED, FAILED, REJECTED, EXPIRED, CANCELLED; transitions only from defined states; approvals counted by distinct qualified reviewers; edits create new versions; optimistic locking on the aggregate; atomic conditional claim for execution; expiry enforced in predicates; every transition audited.
*Trap:* Boolean flags; executing in the approval HTTP request.

**Q: How do you ensure the approved action is exactly what executes?**
*Strong answer:* Canonical serialization and hash at proposal time; UI renders from stored canonical args and submits the hash it displayed; approval stores the hash; executor verifies the hash and parses from the stored canonical args; optional HMAC signature.

**Q: How do you classify risk?**
*Strong answer:* Deterministic function over tool type and arguments plus context: reversibility, external visibility, amount and cumulative limits, data sensitivity, scope, provenance/taint and detector signals. Signals only raise tiers. Policy lives in reviewed configuration with matrix tests.

#### Advanced Questions

**Q: Two Kafka consumers receive the same `ProposalApproved` event. Walk through why your system executes once.**
*Strong answer:* The executor's first step is a conditional `UPDATE … SET status='EXECUTING' WHERE id=? AND status='APPROVED' AND approved_until > now()`; PostgreSQL row locking makes the second update see the new state and affect 0 rows, so it exits. The downstream call uses the proposal id as idempotency key, and a unique constraint on refunds by proposal id is a final backstop. A reaper resolves crashes in `EXECUTING`.

**Q: How do you keep human review effective at scale?**
*Strong answer:* Risk-proportionate gating to keep volume meaningful; show reasons, evidence and diffs; require reasons for high-risk approvals; dual control for the highest tier; monitor time-on-proposal, approval rates and edit rates per reviewer; seed attention checks; move actions to lower tiers only on evidence.

**Q: How does approval interact with agent state and long waits?**
*Strong answer:* The run is persisted and paused; no thread or model context is held. Approval events resume it via an outbox/Kafka; the observation (executed/rejected) is appended; budgets continue; if the approval expires the agent is told and can inform the user or re-propose.

#### Coding Questions

1. Implement `ActionProposal` transitions and a parameterized test of the full transition table.
2. Write the conditional-claim repository method and a concurrency test.
3. Implement `ArgumentBinder` with `BigDecimal` normalization and a DB round-trip test.

#### Scenario Questions

**Q: A reviewer approved a refund that turned out to be fraud driven by an injected ticket. What changes?**
*Strong answer:* Investigate what the reviewer saw (snapshot) — were taint/risk reasons shown? Improve evidence display (highlight that the order id came from an external message), raise tier for tainted arguments to dual approval, add reviewer training and attention checks, add the case to the adversarial eval suite, and fix the agent's tendency to propose refunds from ticket text without verifying with the customer record.

### 14. Explain-It-at-Three-Levels

**Approval gates**
- *30 seconds:* High-risk actions become persisted proposals; an authorized human other than the requester approves the exact hashed arguments; execution happens once, only if still valid, and everything is audited.
- *2 minutes:* Risk classifier → tiers (auto, undo window, single, dual, prohibited); state machine with optimistic locking; argument binding with hashes; reviewer qualification and separation of duties; atomic claim and idempotent execution with re-validation; expiry; audit chain; pause/resume of the run.
- *Deep:* Concurrency under at-least-once delivery, transaction boundaries around remote calls, reaper reconciliation, canonicalization pitfalls (JSONB, number formats), tamper evidence, approval-fatigue metrics, evidence-based tier changes, and how approval outcomes feed evaluation.

**Risk classification**
- *30 seconds:* A deterministic, explainable function in code that maps an action and context to a handling tier; signals can only raise risk.
- *2 minutes:* Factors (reversibility, visibility, money, data, scope, provenance, signals); policy as reviewed config; matrix tests; evidence-based recalibration.
- *Deep:* Cumulative limits, fraud patterns, policy engines, per-tenant policies, interaction with injection detection and taint.

### 15. Knowledge Check

**Conceptual**
1. What is approval fatigue and why does it make "approve everything" unsafe?
2. Why must an edit by a reviewer create a new proposal version?
3. Why re-validate at execution time if the action was validated at proposal time?
4. Difference between audit records and application logs?
5. Why may detector signals raise but never lower risk tiers?

**Code reading**
6. What race exists in `if (p.getStatus() == APPROVED) { refund(); p.setStatus(EXECUTED); }`?
7. Why does `ActionProposal` expose transition methods instead of setters?
8. What problem does storing canonical args in a PostgreSQL `jsonb` column cause for hash verification?

**Debugging**
9. Approvals intermittently fail with `OptimisticLockException` when two reviewers act at once. Is this a bug? What should the user see?
10. Proposals stuck in `EXECUTING` after a deployment. Cause and fix?

**Design**
11. Design handling for refunds: $20, $200, $2000, and a refund whose order id came from an inbound email.
12. Where should approval UI evidence come from, and what must it show?

### Knowledge Check Answers

1. When reviewers see many low-risk items, they approve reflexively and stop reading; the gate then fails for the rare high-risk item while creating false confidence.
2. So the audit shows exactly what the agent proposed and what humans approved; in-place edits would destroy evidence and could bypass hash binding.
3. State changes between approval and execution (already refunded, account closed, permissions revoked); executing stale decisions can be wrong or unauthorized.
4. Audit records are business records with integrity, completeness and retention guarantees (append-only, tamper-evident, access-controlled); logs are debugging aids that may be sampled, rotated or lost.
5. Signals are probabilistic and attacker-influenceable; letting them lower risk would let an attacker craft content that reduces scrutiny.
6. Check-then-act: two threads can both see `APPROVED` and both refund. Use an atomic conditional update to claim, plus idempotency keys.
7. To enforce legal transitions and invariants in one place; setters allow arbitrary illegal states.
8. `jsonb` normalizes formatting/key order/whitespace, so the stored text differs from the hashed text; re-hashing it produces a mismatch (or, worse, people "fix" it by hashing the jsonb form and lose binding semantics). Store the hashed canonical text verbatim.
9. Not a bug — it's the concurrency control working. The second reviewer should get a 409 "already decided/updated, reload" and see the current state.
10. The executor was killed mid-call during the rolling deploy. A reaper reconciles via the idempotency key with the downstream system; graceful shutdown should stop consuming new events before termination.
11. $20: auto (audited, sampled). $200: single approval by L1. $2000: dual approval by L2 with MFA. Email-derived order id: at least single approval regardless of amount, with taint highlighted; consider verifying the order belongs to the case's customer.
12. From the stored canonical proposal and stored evidence references — not from the agent's chat text. Show tool, exact arguments (with diffs to current state), target, risk reasons, provenance/taint flags, cited policies, relevant facts from authoritative systems, AI rationale clearly labeled, and expiry.

### 17. Cheat Sheet

- **Tiers:** AUTO · AUTO_WITH_UNDO · APPROVAL_SINGLE · APPROVAL_DUAL · PROHIBITED; signals only raise.
- **Gate these:** send email, modify customer data, refunds above limit, deletion (privacy officer), bulk anything.
- **States:** PENDING_APPROVAL → APPROVED → EXECUTING → EXECUTED/FAILED; REJECTED, EXPIRED, CANCELLED.
- **Binding:** canonical JSON (sorted keys, normalized decimals) → SHA-256(tool, args, tenant, target); store text verbatim; verify on approve and execute.
- **Reviewer rules:** qualified role per tier; ≠ requester; human only; MFA/step-up for high tier; tenant-scoped.
- **Concurrency:** `@Version` for decisions; `UPDATE … WHERE status='APPROVED' AND approved_until > now()` claim; unique `(proposal_id, reviewer_id)`; idempotency key `proposal:<id>`.
- **Transactions:** short tx for claim → remote call outside tx → short tx for outcome; reaper for `EXECUTING`; `REQUIRES_NEW` for attempt audits; beware self-invocation.
- **Audit:** append-only, hash chain, review snapshot, trace id, retention, no UPDATE/DELETE grants.
- **Metrics:** approval rate, edit rate, rejection reasons, time-to-decision, queue depth/age, expired rate, review time per item.
